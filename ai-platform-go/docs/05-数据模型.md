# 05 · 数据模型

> 关联：需求 ID `REQ-DATA-*`；接缝 J8（Redis Key 隔离）见 [01-§7](./01-总体需求与范围.md)；权威归属见 [README §1.2](../README.md)。

## 1. 存储职责与「明确不建」

### 1.1 网关持有的数据

| 存储 | 存什么 |
| --- | --- |
| **MySQL** | 用户、刷新令牌、会话、消息、配额用量、用量明细、幂等记录、审计 |
| **Redis** | token version 缓存、配额计数、限流计数、并发计数、幂等响应缓存、只读短缓存 |

### 1.2 明确不建的（本清单与「不建」同等重要）

| 不建的东西 | 原因 | 谁持有 |
| --- | --- | --- |
| 会话上下文表 / Redis `ctx:` | AI 侧负责上下文组装与裁剪，网关不缓存对话内容（假设 A4） | `ai-platform` |
| 知识库 / 文档 / 切片表 | AI 侧 `kb_id`/`doc_id` 是权威；网关建副本必然不一致 | `ai-platform` |
| 任务表 | 同上（`task_id` 属 AI） | `ai-platform` |
| 长期记忆表 | 同上 | `ai-platform` |
| 对话摘要表 | 同上 | `ai-platform` |
| 向量 / 对象存储客户端 | 基础设施只属 AI（[README §1.2](../README.md) 推论 1） | `ai-platform` |
| Kafka 生产者/消费者 | 同上 | `ai-platform` |
| Redis `ctx:` / `lock:` / `embed:` / `dedupe:` / `rate:` / `task:` / `summary:` / `cancel:` / `retry:zset` 前缀 | 与 AI 侧 Key 空间隔离（接缝 J8） | `ai-platform` |

> **如果需要展示 KB/文档/任务列表**：实时透传调用 AI（见 [04-§7](./04-AI服务编排与网关.md)），或建 **Redis 只读短缓存**（TTL ≤ 30s、允许过期），**MUST NOT 在 MySQL 建副本表**。

## 2. MySQL 表结构（`REQ-DATA-001`）

**库名 `ai_platform`** —— 即 `MYSQL_DSN` 的默认值 `root:pass@tcp(127.0.0.1:3306)/ai_platform?parseTime=true&loc=UTC`。

两个服务（网关 + AI）的表**全部在同一个库里**，合计 15 张：

| 归属 | 表 | 建表脚本 |
| --- | --- | --- |
| **网关独占**（6） | `user` / `refresh_token` / `conversation` / `message` / `quota_usage` / `usage_record` | `ai-platform-go/deploy/mysql/001_gateway_tables.sql` |
| **AI 独占**（7） | `knowledge_base` / `document` / `document_chunk` / `task` / `user_memory` / `conversation_summary` / `user_settings` | `ai-platform/deploy/mysql/001_init_schema.sql` |
| **共享**（2） | `idempotency_record` / `audit_log` | 同上（**只在那里定义**） |

> ⚠️ **共享表 MUST 只有一份定义**。同一个库、同一个表名只能有一张表 —— 两个服务都在用
> `idempotency_record` / `audit_log`，所以 001 脚本把它们建成了**并集**（网关要的
> `method` / `request_hash` / `ip` / `user_agent` 也包含在内），网关侧**不再重复 `CREATE`**。
> 如果两边各写一份：第二个 `CREATE TABLE` 会因「表已存在」而**看起来成功**，
> 实际用的是先建好的那一张 —— 缺列的问题要到写入时才暴露。

全局约定（与 [`ai-platform/docs/09`](../../ai-platform/docs/09-数据存储模型.md) 的 `§2` preamble **逐条对齐**）：

| 约定 | 取值 | 为什么两侧必须相同 |
| --- | --- | --- |
| 引擎 / 字符集 | `ENGINE=InnoDB`、`utf8mb4` / `utf8mb4_0900_ai_ci` | 同一实例下排序规则不同的列做 JOIN / 比较会走不上索引 |
| 时间列 | `DATETIME(3)`，存 **UTC** | 两侧都按 UTC 存、按 `...Z` 序列化；混用本地时间会出现「差 8 小时的排序」 |
| 主键 | `VARCHAR(32)` 的带前缀 ULID | `u_` / `rt_` / `cv_` / `msg_`（已在 `ai-platform/docs/02` §1 的前缀集合内）；AI 侧同规则（`kb_` / `doc_` / `chk_` / `task_` / `mem_`） |
| `user_id` | **`VARCHAR(64)`** | 它是 JWT 的 `sub`，**跟服务传递**；两侧宽度不同时，一旦 id 变长会在某一侧报 `1406 Data too long`（严格模式）或**静默截断**（非严格模式） |
| 业务表 | MUST 带 `user_id` 且建 `(user_id, ...)` 前缀索引 | 租户隔离（两侧同一要求） |
| 物理外键 | **不建** | 见 §4；AI 侧同样不建（即使现在同一个库） |
| 带 `deleted_at` 的表 | 用生成列 `deleted_key`，**MUST NOT** 把可空列直接放进唯一键 | 唯一索引不比较 `NULL`，详见 §2.9 |

> **为什么当初考虑过分库、最后还是单库**：`idempotency_record` / `audit_log` 同名不同列
> 曾是分库的唯一硬理由；现在改成「共享表只定义一份（并集）」后，这个理由消失了，
> 而单库换来的是「一次事务能同时碰两个服务的表」与「一个 `information_schema` 就能核对
> 全部约束」。代价是**共享表的列归两个 owner**：改动 MUST 双方评审（见 §2.7 / §2.8）。

### 2.0 与 `ai-platform` 的跨服务字段约定

两侧唯一共享的是**标量字段**（没有跳库 JOIN，也没有跳库外键），所以只需把字段的类型与语义钉住：

| 字段 | go-services | ai-platform | 约定 |
| --- | --- | --- | --- |
| `user_id` | `VARCHAR(64)` | `VARCHAR(64)` | JWT `sub`；网关签发、AI 只校验。AI 侧**不存** `user.id`，只存 `user_id` |
| `conversation_id` | `VARCHAR(32)`（`cv_*`，**网关生成**） | `VARCHAR(64)`（引用） | AI 侧留宽一档；AI 在 `conversation_id` 为空时自建**仅用于其独立验收**（[README §1.2 推论 4](../README.md)） |
| `message_id` | `VARCHAR(32)`（`msg_*`） | `VARCHAR(64)`（`StoredMessage.message_id`） | ⚠️ **两侧各自生成，是两套 id 空间**，见下方说明 |
| `kb_id` / `doc_id` / `task_id` | 不落库（只透传） | `VARCHAR(32)` | 权威在 AI 侧（[README §1.2](../README.md)） |
| `trace_id` | `VARCHAR(64)` | `VARCHAR(64)`（日志上下文） | 接缝 J3；两侧同名同宽，可直接按它串联一条链路的日志 |
| 时间戳 | `DATETIME(3)` UTC | `DATETIME(3)` UTC / ISO `...Z` | 跳服务一律传 ISO 8601 UTC 字符串 |

> ⚠️ **`message_id` 目前是两套 id（待收敛）**：网关在 `message` 表里给每条消息分配 `msg_*`，
> 而 `ai-platform` 在 `/chat` 里用自己的 `new_id("msg")` 生成**另一个** `msg_*`
> （`ChatResponse.message_id` 返回的是后者）。后果：客户端拿到网关列表里的 `message_id`
> 无法与 AI 侧 `/conversations/{id}/context` 里的 id 对应，排障只能靠 `trace_id` 对齐。
> **待办（P1）**：二选一 —— ① 网关调用 AI 时把 `message_id` 透传下去（AI 优先用它）；
> ② AI 在响应里回显网关的 `message_id`。收敛前 `trace_id` 是唯一可靠的关联键。

### 2.1 `user`

```sql
CREATE TABLE `user` (
  id             VARCHAR(32)   NOT NULL COMMENT 'u_*',
  email          VARCHAR(254)  NOT NULL COMMENT '统一小写存储',
  nickname       VARCHAR(64)   NOT NULL DEFAULT '',
  password_hash  VARCHAR(255)  NOT NULL COMMENT 'argon2id 编码串',
  plan           VARCHAR(32)   NOT NULL DEFAULT 'free',
  status         VARCHAR(16)   NOT NULL DEFAULT 'active' COMMENT 'active|disabled|deleted',
  token_version  INT           NOT NULL DEFAULT 1 COMMENT '改密码/踢下线时 +1，使旧 access 失效',
  last_login_at  DATETIME(3)   NULL,
  created_at     DATETIME(3)   NOT NULL,
  updated_at     DATETIME(3)   NOT NULL,
  deleted_at     DATETIME(3)   NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_email (email),
  KEY idx_user_status_created (status, created_at)
) ENGINE=InnoDB COMMENT='用户';
```

> **何时拆分 `user_credential`**：当需要支持第二种登录方式（手机号/OAuth/Passkey）时，把 `password_hash` 拆到 `user_credential(id, user_id, provider, identifier, secret_hash, ...)`。当前只有邮箱+密码，合并一张表更简单 —— 提前拆只是增加 JOIN 与心智负担。

> `token_version` 是「一键踢下线」的实现基础：校验时比较 JWT 的 `ver` 与库中值，不匹配即拒绝（见 [02-§3.3](./02-接口规范与鉴权.md) 第 ⑦ 步）。

> `uk_user_email` **不含 `deleted_at`**，这是**刻意**的：邮箱是账号身份的锚点，若允许注销后
> 立即复用，攻击者可以用旧邮箱重新注册来摸到历史数据引用。因此**已软删用户的邮箱永久占用**
> （注销流程 MUST 向用户明说这一点）。
>
> 注意这与 `ai-platform` 的 `knowledge_base` **恰好相反** —— 那边同名知识库在软删后
> **允许**重建（用生成列 `deleted_key` 把 `NULL` 映射成哨兵时刻实现，见
> [ai-platform docs/09-§2.1](../../ai-platform/docs/09-数据存储模型.md)）。差别不在技巧而在业务语义：
> 「资源名可复用」与「身份标识不可复用」是两件事，实现时不要照搬。
>
> 另：本表**没有** `user_id` 列（`id` 就是用户 id）；`refresh_token` 等引用它的列用 `VARCHAR(64)`
> —— 见 §2.0 的宽度约定。

### 2.2 `refresh_token`

```sql
CREATE TABLE refresh_token (
  id          VARCHAR(32)  NOT NULL COMMENT 'rt_*',
  user_id     VARCHAR(64)  NOT NULL COMMENT 'JWT sub；宽度与 ai-platform 对齐（§2.0）',
  token_hash  CHAR(64)     NOT NULL COMMENT 'sha256(明文)，明文只在响应中出现一次',
  device_name VARCHAR(64)  NOT NULL DEFAULT '',
  user_agent  VARCHAR(255) NOT NULL DEFAULT '',
  ip          VARCHAR(45)  NOT NULL DEFAULT '',
  expires_at  DATETIME(3)  NOT NULL,
  revoked_at  DATETIME(3)  NULL,
  created_at  DATETIME(3)  NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_rt_hash (token_hash),
  KEY idx_rt_user (user_id, revoked_at, expires_at),
  KEY idx_rt_expire (expires_at)
) ENGINE=InnoDB COMMENT='刷新令牌（只存哈希）';
```

**刷新语义**：在同一事务内 `UPDATE refresh_token SET revoked_at = now() WHERE token_hash = ? AND revoked_at IS NULL AND expires_at > now()`；`RowsAffected == 0` 即该令牌不存在/已作废/已过期 → 返回 `401 INVALID_REFRESH_TOKEN`；否则插入新令牌行后返回。

> 不做刷新链（`family_id`）与重放即整族作废：代价是令牌泄漏后攻击者可续期至 `expires_at`，非改密码/`logout_all` 不能终止。单人作品集项目风险可接受；若上生产，只需给本表加一列 `family_id` + 改一段轮换逻辑。

### 2.3 `conversation`

```sql
CREATE TABLE conversation (
  id              VARCHAR(32)  NOT NULL COMMENT 'cv_*，网关生成；AI 侧以 VARCHAR(64) 引用',
  user_id         VARCHAR(64)  NOT NULL COMMENT 'JWT sub；宽度与 ai-platform 对齐（§2.0）',
  title           VARCHAR(100) NOT NULL DEFAULT '',
  title_source    VARCHAR(16)  NOT NULL DEFAULT 'auto' COMMENT 'auto|manual',
  status          VARCHAR(16)  NOT NULL DEFAULT 'active' COMMENT 'active|archived',
  model           VARCHAR(64)  NULL,
  kb_ids          JSON         NULL COMMENT 'string[]，会话默认检索范围',
  message_count   INT          NOT NULL DEFAULT 0 COMMENT '同时作为 seq 分配器',
  last_message_at DATETIME(3)  NULL,
  pinned          TINYINT(1)   NOT NULL DEFAULT 0,
  metadata        JSON         NULL,
  created_at      DATETIME(3)  NOT NULL,
  updated_at      DATETIME(3)  NOT NULL,
  deleted_at      DATETIME(3)  NULL,
  PRIMARY KEY (id),
  KEY idx_conv_user_list (user_id, deleted_at, status, pinned DESC, last_message_at DESC),
  KEY idx_conv_cleanup (deleted_at)
) ENGINE=InnoDB COMMENT='会话';
```

`seq` 分配用单条语句原子完成（见 [03-§4.2](./03-用户与会话服务.md)）：

```sql
UPDATE conversation
   SET message_count = LAST_INSERT_ID(message_count + 1),
       last_message_at = ?
 WHERE id = ? AND user_id = ? AND deleted_at IS NULL AND status = 'active';
SELECT LAST_INSERT_ID();
```

- `RowsAffected == 0` ⇒ 会话不存在/越权/已删/已归档 → 按情况返回 `404 CONVERSATION_NOT_FOUND` 或 `409 CONVERSATION_ARCHIVED`。
- `LAST_INSERT_ID(expr)` 是**连接级**的，因此 MUST 在同一连接（同一 `*sql.Tx` / `sql.Conn`）上执行这两条语句，否则会读到别的会话的值。使用 GORM 时 MUST 用 `Session(&gorm.Session{...})` 显式绑定连接或直接走 `db.Raw()` 在同一事务内。**这是本设计中最容易踩的坑**，MUST 有并发测试（`AC-CONV-07`）。

### 2.4 `message`

```sql
CREATE TABLE message (
  id              VARCHAR(32)   NOT NULL COMMENT 'msg_*（网关侧 id；AI 侧另有自生成 id，见 §2.0）',
  conversation_id VARCHAR(32)   NOT NULL,
  user_id         VARCHAR(64)   NOT NULL COMMENT '冗余，用于隔离校验与批量清理；宽度与 ai-platform 对齐',
  seq             INT           NOT NULL COMMENT '会话内自增，排序唯一依据',
  role            VARCHAR(16)   NOT NULL COMMENT 'user|assistant',
  content         MEDIUMTEXT    NOT NULL,
  status          VARCHAR(16)   NOT NULL DEFAULT 'completed' COMMENT 'completed|partial|failed',
  finish_reason   VARCHAR(32)   NULL COMMENT 'stop|length|max_steps|canceled',
  refs            JSON          NULL COMMENT 'Reference[]，结构见 ai-platform/docs/06-§6',
  tool_calls      JSON          NULL COMMENT 'ToolCallTrace[]，结构见 ai-platform/docs/03-§3.1',
  usage           JSON          NULL COMMENT '{prompt_tokens,completion_tokens,total_tokens}',
  model           VARCHAR(64)   NULL,
  degraded        TINYINT(1)    NOT NULL DEFAULT 0,
  degraded_reasons JSON         NULL COMMENT 'string[]',
  elapsed_ms      INT           NULL,
  trace_id        VARCHAR(64)   NULL COMMENT '本轮次 trace，排障用（接缝 J3）',
  created_at      DATETIME(3)   NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_msg_conv_seq (conversation_id, seq),
  KEY idx_msg_conv_list (conversation_id, seq),
  KEY idx_msg_user_created (user_id, created_at),
  KEY idx_msg_conv_status (conversation_id, status)
) ENGINE=InnoDB COMMENT='消息台账';
```

> 列名用 `refs` 而非 `references`：后者是 MySQL 8.0 的保留字，虽可用反引号，但显式避开能省掉一类低级错误。

> `content` 用 `MEDIUMTEXT`（16MB）：单条模型回答理论上限远小于此，但留足余量。**不建全文索引**：消息正文的检索需求不在本期范围，若将来需要，应交给 AI 侧做向量化而不是在网关加 `FULLTEXT`。

### 2.5 `quota_usage`

按「用户 + 指标 + 周期」聚合的**权威计数**（Redis 是加速器）。

```sql
CREATE TABLE quota_usage (
  user_id     VARCHAR(64)  NOT NULL COMMENT 'JWT sub；宽度与 ai-platform 对齐（§2.0）',
  metric      VARCHAR(32)  NOT NULL COMMENT 'chat_requests|llm_tokens|kb_count|documents_count|storage_bytes',
  period      VARCHAR(16)  NOT NULL COMMENT '日指标用 YYYY-MM-DD，存量指标固定 current',
  used        BIGINT       NOT NULL DEFAULT 0,
  limit_value BIGINT       NULL COMMENT '签发周期内的限额快照',
  created_at  DATETIME(3)  NOT NULL,
  updated_at  DATETIME(3)  NOT NULL,
  PRIMARY KEY (user_id, metric, period),
  KEY idx_quota_period (period)
) ENGINE=InnoDB COMMENT='配额用量聚合';
```

> **业务键即主键**，与 AI 侧的 `user_settings`（PK `user_id`）/ `conversation_summary`
> （PK `conversation_id`）风格一致。原设计多一个自增 `id` + 一条 `UNIQUE KEY`
> （两者内容完全重复）：多出来的列与索引没有任何查询会用到，而计数器的 `WHERE`
> 条件正好是这三列，直接走聚簇索引更好。
>
> 注意 `created_at` 也要有：与「可变业务表都带 `created_at` / `updated_at`」的约定一致
> （否则对账任务只能看到「最后一次改动」，看不到这个周期是何时开始的）。

### 2.6 `usage_record`

每请求一条明细，用于对账、账单与用户自查。

```sql
CREATE TABLE usage_record (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  user_id         VARCHAR(64)  NOT NULL COMMENT 'JWT sub；宽度与 ai-platform 对齐（§2.0）',
  metric          VARCHAR(32)  NOT NULL,
  amount          BIGINT       NOT NULL,
  conversation_id VARCHAR(32)  NULL,
  message_id      VARCHAR(32)  NULL COMMENT '**网关侧**的 msg_*（不是 AI 返回的那个，见 §2.0）',
  trace_id        VARCHAR(64)  NULL,
  created_at      DATETIME(3)  NOT NULL,
  PRIMARY KEY (id),
  KEY idx_usage_user_time (user_id, created_at),
  KEY idx_usage_time (created_at)
) ENGINE=InnoDB COMMENT='用量明细';
```

> 该表写入量最大（每对话 2 条）。MUST 只保留 `USAGE_RETENTION_DAYS`（默认 90 天），由每日任务清理；聚合值已在 `quota_usage` 中，删除明细不丢总账。

### 2.7 `idempotency_record`（**共享表**）

> 权威定义在 [`ai-platform/deploy/mysql/001_init_schema.sql`](../../ai-platform/deploy/mysql/001_init_schema.sql)
> —— 它是并集版（把网关要的 `method` / `request_hash` 也包含在内），网关侧**不重复 `CREATE`**。

网关写入 / 读取用到的列：

| 列 | 网关用法 |
| --- | --- |
| `id` | `BIGINT` 自增，代理键 |
| `user_id` | 幂等的租户隔离键 |
| `method` | `POST` / `PATCH` 等；**网关必填** |
| `path` | 业务路径（不带 `/api/v1` 以外的查询串） |
| `idem_key` | 客户端 `Idempotency-Key` 头的原值 |
| `request_hash` | `sha256(body)`；**网关必填** |
| `status_code` / `response_body` | 首次响应快照，用于回放 |
| `created_at` / `expires_at` | `expires_at` 到期的行由每日任务清理 |

唯一键 `uk_idem (user_id, method, path, idem_key)`。

同键不同 `request_hash` → 返回 `409 CONFLICT`（`details.reason="idempotency_key_reused_with_different_body"`），这是标准做法，能防「用同一 UUID 发不同请求」。

> ⚠️ **AI 侧不填 `method` / `request_hash`**：它写的两张表的列是 `NOT NULL DEFAULT ''`，
> 只填 `(user_id, path, idem_key)` 也能插入（不报错、不破唯一性）。
> 两侧共用一张表，所以列定义 MUST 双方评审后再改 —— 改窄（例如把 `method` 改成 `NOT NULL` 无默认值）
> 会直接弄挂 AI 侧的写入。

### 2.8 `audit_log`（**共享表**）

> 与 §2.7 同理：权威定义也在
> [`ai-platform/deploy/mysql/001_init_schema.sql`](../../ai-platform/deploy/mysql/001_init_schema.sql)，
> 网关侧**不重复 `CREATE`**。

网关写入 / 读取用到的列：

| 列 | 网关用法 |
| --- | --- |
| `id` | `BIGINT` 自增 |
| `user_id` | 系统操作（如后台清理）为 `NULL` |
| `action` | `login` / `logout` / `register` / `password_change` / `conversation_delete` / … |
| `resource_type` / `resource_id` | 无资源时为空串（**不用 `NULL`**，避三值逻辑） |
| `ip` / `user_agent` | **网关必填**（AI 侧不填） |
| `detail` | 脱敏后的上下文（`JSON`） |
| `created_at` | 索引：`(user_id, created_at)` / `(action, created_at)` / `(created_at)` |

MUST 记录审计的动作：注册、登录成功/失败、登出、改密码、`logout_all`、会话删除、配额超限拦截、管理类操作（P2）。保留 ≥ 180 天。

> ⚠️ **本表是共享表**（与 §2.7 同）。AI 侧不带 `ip` / `user_agent`（它不直接接触
> 客户端），所以这两列对 AI 而言只是「可空且不填」；`resource_type` / `resource_id`
> 两侧已对齐为 `NOT NULL DEFAULT ''`。改动列定义 MUST 双方评审。
>
> 只追加不更新，因此本表**没有** `updated_at`；`detail` MUST 先脱敏再入库（docs/06 §4）。

### 2.9 唯一索引、`NULL` 与软删除

MySQL 的**唯一索引不比较 `NULL`** —— 两行在唯一键的某一列上都是 `NULL` 时，它们**不算冲突**。
这一条决定了「软删 + 唯一键」该怎么写，同一个库里几张表各取了一面：

| 表 | 唯一键 | 软删后同名/同标识 | 语义 |
| --- | --- | --- | --- |
| `user` | `uk_user_email (email)`（**不含** `deleted_at`） | **不可复用**（永久占用） | 邮箱是身份锚点；复用等于给出账号接管的路径 |
| `conversation` / `message` | 无软删相关的唯一键 | — | 会话/消息的标识是 ULID，天然不会撞 |
| `knowledge_base` / `document`（AI 侧） | `uk_kb_user_name (user_id, name, deleted_key)` / `uk_doc_dedupe (kb_id, content_sha256, deleted_key)` | **可复用** | 「资源名 / 同一份文件」可复用符合直觉，且用户看不见已删记录 |

对照很鲜明，也很容易搞反：**「资源名可复用」与「身份标识不可复用」是两件事**，
`user` 表因此**没用**生成列（这正是 `AC-DATA-09` 要断言的点）。

`deleted_key` 是 AI 侧的生成列：
`GENERATED ALWAYS AS (IFNULL(deleted_at, '1970-01-01 00:00:00.000')) STORED`，把 `NULL` 换成哨兵时刻。

> **不要把含 `NULL` 的列直接放进唯一键** —— 那样约束会**一次也不触发**。
> 这不是推导出来的，是真踩过的：AI 侧本想把 `uk_kb_user_name` 写成
> `(user_id, name, deleted_at)`，实测第二条同名记录的 `ROW_COUNT()` 返回 `1`（插入成功了）。
> 详见 [ai-platform docs/12-§10.1](../../ai-platform/docs/12-实现问题记录.md)。

**验证方式（MUST）**：约束的作用就是「拦住」，而它没拦住时**什么都没发生** —— 既无异常也无日志。
所以 MUST 有一条「证明它拦住了」的断言，见 `deploy/mysql/verify_schema.sql`。
写法上不要把「期望报错」当成断言（那样「预期的冲突」与「真正的失败」就同形了）：
用 `INSERT IGNORE` + `ROW_COUNT()` 断言数字。

## 3. Redis Key 规范（`REQ-DATA-005`，接缝 J8）

**网关所有 Key MUST 以 `gw:` 开头**，且 **MUST NOT** 读写 `ai-platform` 的前缀（`ctx:` / `lock:` / `summary:` / `task:` / `cancel:` / `embed:` / `dedupe:` / `rate:` / `retry:zset`）。

| Key 模式 | 类型 | TTL | 内容 | 关联需求 |
| --- | --- | --- | --- | --- |
| `gw:user:ver:{user_id}` | String | 10 min | `token_version` 缓存，用于校验 JWT 的 `ver` | `REQ-AUTH-004` |
| `gw:quota:{user_id}:{metric}:{period}` | String | 到周期结束 + 1h | 用量计数（`INCR`） | `REQ-AUTH-006` |
| `gw:cc:{user_id}` | String | 到请求结束 | 并发对话计数（`INCR`/`DECR`） | `REQ-AUTH-008` |
| `gw:rate:{scope}:{id}` | String/ZSet | 窗口长度 | 限流计数（`scope` = `login`/`msg`/`upload`/`conv`/`ip`） | `REQ-AUTH-008` |
| `gw:idem:{user_id}:{path}:{key}` | String | 24h | 幂等响应快照 | [02-§7](./02-接口规范与鉴权.md) |
| `gw:conv:list:{user_id}` | String | 30s | 会话首页只读缓存（P2） | `REQ-DATA-006` |
| `gw:kbmeta:{user_id}` | String | 30s | AI 侧 KB 元数据只读缓存（用于 `kb_ids` 校验提速，P1） | [03-§2.1](./03-用户与会话服务.md) |
| `gw:cb:ai` | String | 30s | 熔断状态标记 | `REQ-ORCH-009` |

**强制要求**：

1. **所有 Key MUST 有 TTL**（`PERSIST` 禁止）。唯一的例外是 `gw:user:ver:*` 也设为 10 分钟 TTL（不是永久），避免 Redis 成为第二份权威数据。
2. 拼接进 Key 的值（`user_id` / `metric` / `scope` / `key`）MUST 校验满足 `^[A-Za-z0-9_.:-]{1,128}$`，**MUST NOT 直接拼接用户可控的原始字符串**（防 Key 注入与 Key 爆炸）。
3. 缓存类 Key（`list` / `kbmeta`）MUST 接受「读到过期数据」；**MUST NOT** 用于任何写路径的前置校验（配额计数与并发计数除外，它们不是缓存而是计数器）。
4. 单次请求对 Redis 的操作 SHOULD ≤ 6 次（管道化），避免成为延迟瓶颈。

## 4. 外键、级联与事务

### 4.1 不建物理外键的理由与补偿

| 理由 | 说明 |
| --- | --- |
| 写入热点 | `message` 是高频插入表，外键会在父表（`conversation`）上加共享锁，导致并发写入串行化 |
| 清理成本 | 物理清理（删 30 天前数据）时外键会强制逐行检查，删除变慢 |
| 拆分自由度 | 无外键便于将来按 `user_id` 归档到独立实例（两服务现在已合到一个库，见 §2 preamble） |

**补偿措施（MUST）**：

1. 所有跨表引用 MUST 有索引（已在上文 DDL 中给出）。
2. 应用层 MUST 用事务保证「会话存在 → 才写消息」。
3. MUST 有每日一致性检查任务，输出指标 `gw_orphan_rows_total{table}`：`message` 中存在但 `conversation` 不存在的行数。发现孤儿行记 ERROR 并告警（**不自动删除**，先人工确认）。

### 4.2 事务边界

| 操作 | 事务范围 |
| --- | --- |
| 分配 `seq` + 写 `user` 消息 | **同一事务**（`UPDATE conversation` + `INSERT message`） |
| 写 `assistant` 消息 + 更新会话 `last_message_at` | 同一事务 |
| 配额：Redis 计数器与 MySQL 对账 | **不在同一事务**（跨存储）：先 Redis（快路径），5 分钟对账写 MySQL；以 MySQL 周期重建 Redis |
| 刷新令牌轮换 | 同一事务（`UPDATE` 旧 + `INSERT` 新） |
| 软删会话 + 审计日志 | 同一事务 |

### 4.3 级联删除（应用层）

| 删除对象 | 级联动作 | 方式 |
| --- | --- | --- |
| `conversation`（软删） | 消息不可见（查询 JOIN 会话 `deleted_at IS NULL`）；异步通知 AI 清上下文 | 软删同步；AI 通知异步可失败 |
| `user`（注销，P2） | 软删用户 → 作废全部 refresh → 异步清会话/消息/AI 数据 | 异步任务 + 审计 |
| 物理清理（30 天后） | 删消息 → 删会话 → 删过期 refresh → 删过期幂等记录 | 每日任务，**分批删除**（每批 ≤ 1000 行，避免长事务） |
