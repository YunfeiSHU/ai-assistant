# 07 · 验收标准与测试策略

> 关联：需求 ID `REQ-TEST-*`；接缝清单 J1–J9 见 [01-§7](./01-总体需求与范围.md)；各模块验收用例（`AC-*`）分散在 [02](./02-接口规范与鉴权.md)～[06](./06-非功能需求与可观测性.md)，本篇负责汇总口径、测试手段与通过标准。

## 1. 验收总则

| 项 | 规定 |
| --- | --- |
| 验收对象 | `go-services` 服务**及其与 `ai-platform` 的接缝** |
| 验收方式 | 自动化用例为主（`go test`），接缝与 E2E 用真实 `ai-platform` 容器 |
| 通过定义 | 该里程碑对应的全部 P0 用例通过，且无 P0/P1 缺陷未关闭 |
| 依赖环境 | `docker compose` 拉起 MySQL / Redis / Milvus / MinIO / Kafka / `ai-platform` |
| 用例可追溯 | 每条用例 MUST 在测试中以 `t.Run("AC-XXX-NN", ...)` 命名或以注释引用对应需求 ID |
| 证据 | 每次验收产出：`go test` 报告 + 覆盖率 + 接缝测试结果 + 失败用例的 trace 链接 |

## 2. 测试分层（`REQ-TEST-001`）

| 层 | 目录 | 依赖 | 时间 | 覆盖内容 |
| --- | --- | --- | --- | --- |
| **单元测试** | `internal/**/*_test.go` | 无（全替身） | < 30 s | 密码哈希、JWT 签发/校验、配额算法、限流器、自动标题、游标编解码、错误映射、脱敏函数、SSE 解析 |
| **契约测试** | `tests/contract/` | Fake AI（`httptest`）+ testcontainers MySQL/Redis | < 2 min | 路由存在性、请求/响应 Schema、错误信封结构、分页参数、幂等回放、状态码 |
| **接缝测试** | `tests/seam/` | **真实 `ai-platform`** + compose 全栈 | < 5 min | J1–J9 全部接缝点（§3） |
| **集成测试** | `tests/integration/` | MySQL/Redis 真实容器 + Fake AI | < 5 min | `seq` 并发分配、事务边界、级联删除、缓存 TTL、孤儿检查 |
| **端到端测试** | `tests/e2e/` | compose 全栈（含真实 AI 与 Fake LLM） | < 10 min | §4 的 8 个场景 |
| **性能测试** | `tests/perf/`（`-tags=perf`，默认不跑） | compose 全栈 | 按需 | §5 |

### 2.1 隔离要求

- 每个用例 MUST 使用独立 `user_id`（`u_test_{随机}`）与独立 `email`；结束时按 `user_id` 清理 MySQL 与 Redis（`gw:*` 前缀）。
- 用例 MUST NOT 依赖执行顺序；`-shuffle=on` 与默认顺序都 MUST 通过。
- **MUST NOT 复用生产 AI 数据**：E2E 用独立的知识库与文档。

## 3. 契约与接缝测试（`REQ-TEST-002`，本篇核心）

> **这一节是整套需求的验收焦点。** 单个服务内部测得多好，接缝破裂时系统仍然是坏的。以下 10 条 MUST 全部自动化，且在 CI 中作为独立 gate。

| ID | 接缝 | 测试内容 | 通过标准 | 关联 |
| --- | --- | --- | --- | --- |
| `AC-TEST-01` | **J1 JWT 互操作** | 网关生成的 access_token 直接作为 `Authorization` 调用**真实** `ai-platform` 的 `GET /health`（受保护）与 `POST /chat` | 均返回非 401；且 AI 侧日志中的 `user_id` 等于 JWT 的 `sub` | `REQ-AUTH-002`、`REQ-TEST-002` |
| `AC-TEST-02` | **J1 反例** | 分别把 `iss` / `aud` / `sub` / `token_type` 改成错的值重新签发，各调一次 AI | 全部 401，证明这三个字段是硬约束（不是"恰好能过"） | `REQ-AUTH-002` |
| `AC-TEST-03` | **J5 契约快照** | 用 `ai-platform` 的 `openapi.json` 与网关的调用代码生成字段对照表（字段名/类型/必填） | 差异为空；新增差异时 CI 失败并打印具体字段 | `REQ-ORCH-001/002` |
| `AC-TEST-04` | **J2 错误码透传** | 触发 AI 侧 6 种错误（`KB_NOT_FOUND`、`CONTENT_TOO_LONG`、`UPSTREAM_TIMEOUT`、`DOCUMENT_DUPLICATE`、`TASK_NOT_CANCELABLE`、`UNSUPPORTED_FILE_TYPE`） | 经网关后 `code`/`message`/`retryable`/`trace_id`/HTTP 状态码**全部与直连 AI 一致** | [02-§4.2](./02-接口规范与鉴权.md) |
| `AC-TEST-05` | **J3 trace 传递** | 一次经网关的流式对话 | Jaeger 中该 `trace_id` 下同时存在网关 span 与 AI span（服务名分别为 `go-services`/`ai-platform`）；响应头 `X-Trace-Id` 一致 | `REQ-NFR-006` |
| `AC-TEST-06` | **J4 会话 ID 一致** | 网关首轮调用 AI，抓取 AI 收到的 `conversation_id` | 与网关创建的相同；AI 返回的 `meta.conversation_id` 也相同 | `REQ-ORCH-006` |
| `AC-TEST-07` | **J6 SSE 保真** | 同一请求（脚本化 prompt 触发 `reference` + `tool_call` + `token` + `usage`）分别直连 AI 与经网关 | 提取两侧的事件名序列，**完全相等**；把 `data` 按事件类型归一化后逐字段比对，差异为空 | `REQ-ORCH-003` |
| `AC-TEST-08` | **J7 配额不双扣** | 完成一次消耗 876 token 的对话 | 网关侧 `llm_tokens` 累加 = 876；AI 侧无任何配额变更；重复统计不出现 1752 | [02-§5.2](./02-接口规范与鉴权.md) |
| `AC-TEST-09` | **J8 Redis Key 隔离** | 网关与 AI 共享同一 Redis 实例，各跑一遍完整业务流 | 网关只写 `gw:*`；`redis-cli --scan --pattern 'ctx:*|rate:*|lock:*'` 的结果全部来自 AI 侧；网关侧无一行代码触碰这些前缀 | [05-§3](./05-数据模型.md) |
| `AC-TEST-10` | **J9 内部凭据** | 网关用 `INTERNAL_SERVICE_TOKEN` 调用 AI 的上下文清理接口 | 成功（非 401）；且该凭据调不通用户态接口（如 `POST /chat`，应被拒或按服务身份受限） | [04-§3.2](./04-AI服务编排与网关.md) |

> `AC-TEST-10` 暴露了**一个尚未闭合的接缝**：`ai-platform` 当前的 SRS 只定义了用户 JWT 校验与 `auth.enabled` 开关，**没有定义内部服务凭据**。网关的「删会话时清理 AI 上下文」依赖它。**行动项**：在 `ai-platform/docs/02-接口规范与鉴权.md` 补充「内部服务凭据」章节（`INTERNAL_SERVICE_TOKEN`、来源 IP 白名单、可用接口范围），否则该功能无法实现。
>
> 同理 `AC-TEST-03` 依赖 `ai-platform` 提供稳定的 `openapi.json`（其 SRS 已要求 `/openapi.json` 始终可访问，满足）。

## 4. 跨服务端到端场景（`REQ-TEST-003`）

| # | 场景 | 关键步骤 | 期望 | 关联用例 |
| --- | --- | --- | --- | --- |
| E2E-1 | 注册 → 登录 → 流式对话 → 恢复历史 | 完整走一遍 | 首 token 到达；流结束；`GET /messages` 能还原引用与用量 | `AC-CONV-06`、`AC-AUTH-02` |
| E2E-2 | 上传文档 → 轮询任务 → 知识库问答 | 上传 MD → 等 `SUCCEEDED` → 带 `kb_ids` 提问 | 回答含 `[1]`；`references[0].chunk_id` 可在 Milvus 查到 | `AC-ORCH-05`、`AC-ORCH-11` |
| E2E-3 | Agent 工具调用 | 脚本化 prompt 触发 `kb_retrieve` + `calculator` | 流中出现成对 `tool_call`/`tool_result`；落库的 `tool_calls` 有 2 条 | `AC-ORCH-03` |
| E2E-4 | 配额耗尽 | 把日限额改为 2，发 3 次 | 第 3 次 `429 QUOTA_EXCEEDED`；AI 侧只收到 2 次调用 | `AC-AUTH-06` |
| E2E-5 | 流式中断 | 收到 3 个 token 后断开 | AI 侧记录 `canceled`；库中 `partial` 消息内容为那 3 个 token | `AC-CONV-08`、`AC-ORCH-04` |
| E2E-6 | AI 宕机降级 | 停 `ai-platform` 容器 | `POST .../messages` → 503；`GET /conversations`、`GET /me/quota` → 200 | `AC-ORCH-09` |
| E2E-7 | 令牌刷新 | 刷新一次 → 用旧 refresh 再刷 | 第一次成功；第二次 `401 INVALID_REFRESH_TOKEN` | `AC-AUTH-04` |
| E2E-8 | 会话删除级联 | 删会话 → 查两侧 | 网关：会话与消息 404；AI：该 `conversation_id` 的上下文被清理（或等待 TTL） | `AC-CONV-10`、`AC-TEST-10` |

**每个 E2E MUST 在报告中打印关键中间态**：`trace_id`、`conversation_id`、`task_id`、`usage`。这是答辩演示与事故复盘的直接素材。

## 5. 性能测试（`REQ-TEST-004`）

| 用例 | 方法 | 通过标准 |
| --- | --- | --- |
| 网关增量延迟 | 同一请求直连 AI vs 经网关，各 200 次 | 增量 P95 ≤ 30 ms |
| 并发 SSE 连接 | 500 条连接保持 60 s（mock AI 慢速输出） | 全部成功、RSS ≤ 512 MB、无 goroutine 泄漏（`go test` 前后 goroutine 数稳定） |
| 非 AI 接口吞吐 | `GET /conversations` 压测 100 并发 | QPS ≥ 1000、P95 ≤ 80 ms |
| `seq` 竞争 | 单会话并发 50 次写消息 | 无重复 `seq`、无死锁、P95 ≤ 20 ms |
| 大回答 | mock 输出 200k 字符 | 客户端收全；落库截断到 64000；内存无异常增长 |
| 连接池饱和 | 并发 100（池 20） | 排队而非报错；`gw_db_pool_*` 可见；无请求因超时而失败（在 5s 获取超时内） |

**Goroutine 泄漏检查** MUST 出现在所有流式相关测试中（`runtime.NumGoroutine()` 前后对比，允许 ±5）—— 这是 SSE 代理最常见的事故。

## 6. CI 门槛（`REQ-TEST-005`）

分两个 job：

### job `unit`（快，每次 push）

| # | 检查 | 命令 | 门槛 |
| --- | --- | --- | --- |
| 1 | 编译 | `go build ./...` | 无错误 |
| 2 | 静态检查 | `go vet ./...` | 无问题 |
| 3 | Lint | `golangci-lint run` | 0 issue（`errcheck`/`govet`/`staticcheck`/`ineffassign`/`gosec` 至少开启） |
| 4 | 格式 | `gofmt -l .` | 输出为空 |
| 5 | 单元 + 契约 | `go test ./internal/... ./tests/contract/... -race` | 全通过（`-race` MUST 开启） |
| 6 | 覆盖率 | `go test -coverprofile=cover.out ./...` | 整体 ≥ 70%；`internal/auth`、`internal/quota`、`internal/sse` ≥ 85% |
| 7 | 迁移可逆 | 迁移 up → down → up | 全部成功 |

### job `seam`（慢，PR 与主干）

| # | 检查 | 命令 | 门槛 |
| --- | --- | --- | --- |
| 8 | 起全栈 | `docker compose -f deploy/compose.test.yml up -d --wait` | 全部 `healthy` |
| 9 | 接缝测试 | `go test -tags=seam ./tests/seam/...` | `AC-TEST-01..10` 全通过 |
| 10 | 集成测试 | `go test -tags=integration ./tests/integration/...` | 全通过 |
| 11 | 端到端 | `go test -tags=e2e ./tests/e2e/...` | §4 的 8 个场景全通过 |
| 12 | 契约快照 | `go test -tags=contract ./tests/contract/... -run Snapshot` | 与 `tests/contract/testdata/*.json` 一致；变更需显式更新快照 |

不入 CI（手动触发）：性能测试（`-tags=perf`）。

> **`-race` 是硬要求**：网关涉及大量并发（SSE 转发、配额计数、`seq` 分配、熔断状态），数据竞争在低负载下不显现，上线后变成随机故障。

## 7. 缺陷分级与出口标准

| 级别 | 定义 | 处理要求 |
| --- | --- | --- |
| **P0** | 跨用户数据可见、令牌可伪造/绕过、凭据泄漏、消息丢失 | 立即修复，阻塞发布 |
| **P1** | 接缝破裂（JWT 被拒、事件丢失、trace 断裂、配额双扣）、核心链路不可用 | 本迭代必修 |
| **P2** | 非核心功能异常、指标劣化、日志缺字段 | 可排下迭代 |
| **P3** | 文案、注释、文档不一致 | 随手修 |

里程碑出口：**P0 = 0，P1 = 0**，`unit` 与 `seam` 两个 job 全绿。发布后 24 h 观察：5xx 占比 < 1%、`gw_message_persist_failed_total` 无增长、`gw_session_mismatch_total` 与 `gw_trace_mismatch_total` 均为 0。
