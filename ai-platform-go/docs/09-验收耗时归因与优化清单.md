# 09 · 验收耗时归因与后续优化清单

> 本文回答一个问题：**为什么跑一次 curl 实测这么慢，以及后面该动哪里。**
> 需求在 01–07，实现记录在 08；本文只做「耗时归因 + 可执行的优化项」，
> 目的不是评价现状，而是把"感觉慢"变成**可复算的数字 + 可验收的改动**。
>
> 记录原则：每一条结论都要能指向**一次测量**（命令 + 数字），每一条优化项都要写清
> **预期收益 / 风险 / 验收方式**。凡是"大概能快一点"的都不写进来。
>
> **相关文档**：本文只做"耗时"。上传—索引链路的**正确性 / 产品行为 / 业界基线对照**见
> [`10-大文件上传与索引优化清单`](./10-大文件上传与索引优化清单.md)（UP-01~UP-10 与 OpenAI `file_search` 对照）。

## 1. 基线：一次全套验收的耗时分解

数据来源：`tools/run_all_stages.ps1` 的汇总表（2026-09-30 全绿那次）。

| 阶段 | 脚本 | 断言 | 耗时 | 占比 |
| --- | --- | ---: | ---: | ---: |
| M1 鉴权 | `curl_stage1.ps1` | 99 | **43s** | 11% |
| M2 会话台账 | `curl_stage2.ps1` | 198 | **79s** | 21% |
| M3 编排 | `curl_stage3.ps1` | 29 | **8s** | 2% |
| M4 流式 | `curl_stage4.ps1` | 51 | **42s** | 11% |
| M5 配额/降级 | `curl_stage5.ps1` | 40 | **167s** | 44% |
| M6 可观测 | `curl_stage6.ps1` | 57 | **91s** | 24% |
| | **合计** | **474 PASS** | **≈430s（7 分钟）** | |

**套件级"死时间"另计**（不落在任何阶段里）：

| 位置 | 机制 | 上限 |
| --- | --- | ---: |
| `Wait-AIDrain` | 3s 轮询 × "连续 3 次 `checks.ai_platform.latency_ms` < 500ms" | **150s** |
| `Wait-ForRateWindow` | 5s 轮询 × "探测坏登录不再 429" | **75s** |
| `Start-StageGateway` / `Start-Gateway` | 500ms 轮询 × 60 次就绪探测（× 2 实例） | 60s |
| `curl_stage5/6` 内的 `Start-AuxGateway` | 同上（stage5 共 4 个辅助实例） | — |

> ⇒ **最坏情况一次全套 ≈ 430s + 285s 级等待**。这不是估算，是脚本里写死的轮询上限。

## 2. 逐阶段归因

### 2.1 M1（43s / 99 断言）—— 慢在客户端，不在网关

**这是最反直觉的一段：一句模型调用都没有，却要 43 秒。**

| 测量项 | 数字 | 来源 |
| --- | --- | --- |
| HTTP 次数 | `Invoke-Api` × 49 + 探针 3 ≈ **52 次** | 正则统计脚本内调用点 |
| 平摊每请求 | **0.83s** | 43s ÷ 52 |
| 网关自身应有的量级 | 数 ms（Gin + 1~2 条 SQL，本机回环 1~1.7ms） | docs/08-§7.2 |
| `Invoke-WebRequest` vs `curl.exe` 同一 `/health` | **10s 超时 / 412ms** | `run_all_stages.ps1` 头部实测 |
| Argon2id `HashPassword` / `VerifyPassword` | **40.7ms / 40.7ms** | `go test ./pkg/cryptox -run TestReportPasswordCost -v` |
| Argon2id `BurnPasswordHash`（故意让 401 也不快） | **48.3ms** | 同上 |
| Argon2id 内存维度 | m=8/32/64/128 MiB → 5.5/20.7/43.4/83.2 ms，**0.65~0.69 ms/MiB** | 同上 |

**结论**：M1 里 auth 调用约 20 次，Argon2id 合计只占 **≈1s**；剩下 42s 是
`Invoke-WebRequest` 的固定开销（PS 5.1 的 IWR 走系统代理，本机常驻 Clash 一类，
对 `127.0.0.1` 也要几百毫秒）。**"慢"在这里是脚手架问题，不是产品问题。**

> **已改成防御性改动 —— 但本机实测复现不出它要解决的问题**（见
> [`11-§4`](./11-优化项实测记录.md) 的判别实验：把**记录型代理**设为 .NET 默认代理后，
> **非回环请求 2/2 命中代理、回环请求 0/2 命中** ⇒ 回环本来就不走代理；
> 每请求中位：`Invoke-WebRequest` **13.0ms** / `urllib` 12.9ms / `curl.exe` 28.6ms）。
> 所以：① 本节开头那句"IWR 对 127.0.0.1 也要几百毫秒"**在本机不成立**，
> M1 43s 的成因更可能是"整机被后台向量化拖慢"（`11-§4.3`）；
> ② 这一刀**保留但不计入收益** —— 104 次往返全砍掉也只值 ~1.4s，不是"省一半"。
> 改动内容：`curl_stage1..6` 都加了进程级
> `[System.Net.WebRequest]::DefaultWebProxy = $null`，`Invoke-Api` 的参数表里同时带
> `-Proxy $null`（PS 6+ 用 `-NoProxy`）。
> 为什么不能只写 `-Proxy $null`：PS 5.1 的实现是 `if (Proxy != null) { request.Proxy = Proxy }`，
> 传 `$null` 在部分版本上**等价于不传**，代理照旧生效；进程级默认值才是确定生效的那一下。
> 覆盖范围：stage1..6 的全部 `Invoke-WebRequest` 调用（M2 一家就 96 次）、stage4 的
> `HttpWebRequest` SSE、stage5/6 的健康与 `/metrics` 探测；AI 侧 `tools/curl_e2e.ps1`
> 走 `curl.exe --noproxy *`（curl 认 `http_proxy` 环境变量，不读 WinINET 设置）。
> ⚠ 这几个脚本**假定目标全是回环**；把 `-BaseUrl` 指到非回环地址时要删掉那一段。
> 断言数不变是验收口径：改的是客户端固定开销，不是任何一条判据。
> 与 **OPT-01**（换 `HttpClient` 复用连接）的关系：这一刀只是把代理这一层去掉，
> 没有换实现，所以 OPT-01 的收益空间仍在（`Invoke-Api` 的错误体读取语义要逐条对齐）。
> ⚠️ 但按 [`11-§4.2`](./11-优化项实测记录.md) 的每请求实测（IWR 13.0ms ≈ urllib 12.9ms，
> 已经比 `curl.exe` 28.6ms 快），OPT-01 想再挤出东西，得先证明 IWR 在**你这台机器上**
> 真的比 `HttpClient` 慢 —— 否则它是"看着合理、量不出收益"的那一类。

> 附带确认一条产品事实：Argon2id 耗时随 `m` 近似**线性**（0.65~0.69 ms/MiB），
> 说明瓶颈是算力不是内存缺页 —— 这组数字就是判断"慢是参数选的还是机器被压着"的依据，
> 见 `pkg/cryptox/argon2_cost_test.go` 的注释。

### 2.2 M2（79s / 198 断言）—— 真实模型调用 × 23

| 项 | 数字 |
| --- | --- |
| 串行 `POST .../messages` | 18 次（D/E/F/H 段） |
| G 段并发 | 5 次（`Start-Job`，验 `AC-CONV-07` 的 `seq` 唯一性） |
| 单次 `send` 实测区间 | **0.9s ~ 64s**（含 RAG 命中的那一次 64s） |
| 客户端超时 | 30s → **120s**（M3 起，否则 `status=0` 会报成"接口返回 0"） |

**结论**：M2 的耗时 ≈ 模型排队时间之和，脚本本身没有浪费。
`MsgsPerSend = 2` 是 M3 之后的事实（一次 send 落 user + assistant 两条）。

### 2.3 M3（8s / 29 断言）—— 只有 1 次真实模型调用

18 次 `Invoke-Api` 里只有 `/messages` 那一条会打到模型，其余是透传与错误映射
（19 条路由直接用 `-SkipChat` 也不影响结论）。**这一段是"脚本颗粒度"的正面样本**：
断言密度最高的性价比出现在这里。

### 2.4 M4（42s / 51 断言）—— 8 次真流 + 1 条长流 + 200 次采样

| 消耗点 | 数字 |
| --- | --- |
| 增量对比（默认 `-Runs 4`） | **4 组 × 2 = 8 次真实流式**（AI 直连 + 经网关各一次） |
| S6 断连测试 | 1 条"300 字以上"长流，`-AbortAfterFrames 3` 后主动断连；实测 partial 可见 **1705ms / 2862.6ms**，轮询窗 5s |
| `AC-NFR-01` 采样 | **200 次 `GET /conversations`**（原始要求，未减） |
| 该采样的分布 | 最小 6ms / 中位 **20.9ms** / P95 87ms / **最大 368ms** |

**结论**：200 次采样本身只值 ~4s（20.9ms × 200），不构成瓶颈；
真正的时间在 8 次真流上，而这 8 次是"网关增量延迟"这条要求的**唯一干净口径**
（比首帧 `meta`，不含模型 TTFT），不能省。

### 2.5 M5（167s / 40 断言）—— 全套里最重的一段

| 消耗点 | 数字/机制 |
| --- | --- |
| `go build` | 1 次（编译可复用二进制，替代 `go run`，**已经是优化后的形态**） |
| 辅助实例 | **4 个**（小上限 413 实例 / 配额实例 / 降级+熔断实例 / 主网关），每个都要 500ms×N 就绪探测 |
| 8MB 上传 | **实测**（复刻脚本正文 + 走真实解析/切分链路）：正文 3,467,545 字符 / 2,968,583 token → 切出 **16,969** 块 → 被 `MAX_DOC_CHUNKS=10000` **截断**成 10,000 块入库（只打一条 `ingest.chunks_truncated` warning，接口仍回 202）；上传接口返回 ≠ 算完，后台仍在 CPU 向量化。<br>**2026-10-02 更新（UP-03）**：同一份正文现在切出 **6,056** 块（中位块长 490 token），**不再触发截断** ⇒ M5 之后那段后台向量化的工作量按片数线性下降 **≈2.8×** ⚠️ **该结论已被实测证伪：见 [`11-§2.4`](./11-优化项实测记录.md) —— 长块每 token 更贵(+26~28%)、且不再截断要多嵌入 70% 的 token ⇒ 8MB 全量 ≈101min vs 旧形状同内容 ≈81min**（这条同时是"验收耗时随机浮动"的主要来源：遗留的向量化任务会在下一轮 M1/M2 里抢 CPU） |
| 熔断探针 | `CBFailures + 2 = 12` 次，每次都要等上游"必然不可达"的连接失败 |
| 审计查询 | 每个辅助实例各一次 `mysql.exe`，**~1.1s/次**（10 条与 200 条 `SELECT 1` 总耗时都是 ~1090ms，**斜率 ≈ 0** ⇒ 慢的是进程启动 + 回环，不是 MySQL） |

**结论**：M5 的 167s 由"实例数量 × 就绪探测"+"一次会喂爆 AI 的上传"+"12 次必败连接"
三部分构成，没有一处是"测试写错"。

> ⚠️ **勘误（2026-09-30）**：本节原写"切成 ~4 万个 chunk""在**单事件循环**里跑 CPU 向量化"，
> 两处都不对，实测见 §7.1 —— 真实块数是 **16,969（截断后 10,000）**；而且向量化本来就
> 已经在线程池里跑（`asyncio.to_thread`），**真正占事件循环的是它前后的解析 / 切分 / 哈希**。

### 2.6 M6（91s / 57 断言）—— 自拉干净实例的成本

`curl_stage6.ps1` 是**完全自包含**的：自己 `go build` + 拉一个干净实例（18084/9111），
因为它的核心断言是"计数器为 0"（干净实例是它可信度的前提）。
其余是 `/metrics` / `/health` 轮询与审计查询（同上 ~1.1s 的 `mysql.exe`）。

## 3. 原因分类（按"是不是产品缺陷"分层）

| # | 类别 | 典型表现 | 是否产品缺陷 |
| --- | --- | --- | --- |
| ① | **真实模型调用** | M2 单次 send 0.9~64s；M4 8 次真流 | 否（不可压缩，只能减少次数） |
| ② | **上游 AI 被自己搞慢** | 8MB 上传 → 切出 1.7 万块（截断后 1 万块）→ 后台 CPU 向量化吃满核 → 同机 MySQL/Redis/网关一起慢 2~3 倍（**已加 `TORCH_NUM_THREADS` 开关**，见 §7.2） | 否（AI 侧架构），但**验收参数与线程数可以避免触发** |
| ③ | **套件级固定等待** | `Wait-AIDrain` ≤150s、`Wait-ForRateWindow` ≤75s、就绪探测 | 否（是共享状态污染的代价） |
| ④ | **失败时"卡满超时"** | 熔断自死锁 → 每请求卡满 120s 且**零日志**；Kratos `DialInsecure` 默认 2s | **是**（已修，见 docs/08-§8.3 / §6.3） |
| ⑤ | **每请求固定开销** | IWR 走代理（~0.8s/次）；每写 BEGIN+COMMIT；SSE 首帧前 6~8 条 SQL = 120~260ms；`mysql.exe` ~1.1s/次 | **部分是**（SQL/事务那条是） |
| ⑥ | **断言值本身过严** | 曾把 `AC-NFR-01` 的 30ms 套到 SSE 首帧上 → 间歇假红 | 否（已改为按对象选口径） |

**判别规则（写进脚本注释里的那几条）**：

1. **单跑 B 绿、A 之后跑 B 红 ⇒ 是污染不是缺陷。**
2. **一条从不提 429 的脚本里出现 429 ⇒ 一定是污染**（该脚本的期望值不可能因产品改动变成 429）。
3. 429 先看网关日志的 `code=`：`RATE_LIMITED`（限流，按窗/按 IP）vs `QUOTA_EXCEEDED`（按日累计）。
4. **延迟判据用中位数，不用 P95**（本机只剩 ~1.7GB 可用，P95 的方差比它要测的量还大）。
5. **总在同一个"整数秒"附近失败 ⇒ 先怀疑框架默认超时**（Kratos 的 2s），别急着怀疑上游。

## 4. 后续优化清单

收益都是按 §1 的基线估的；**每条都要求"改完重跑一次全套并对上断言数"**才算完成。

| ID | 目标 | 手段 | 预期收益 | 风险 | 验收方式 |
| --- | --- | --- | --- | --- | --- |
| **OPT-01** | M1/M2/M3/M4 的客户端开销 | 把 `Invoke-Api` 的 `Invoke-WebRequest` 换成 `HttpClient`（`UseProxy=$false`）+ 复用连接（`curl_stage4.ps1` 的 `AC-NFR-01` 段已经是这个写法）。**已先做了其中"关掉代理"的那一半，但实测没有可测收益**：IWR 打回环中位 13.0ms、与 urllib 持平、且根本不走代理（[`11-§4`](./11-优化项实测记录.md)） | M1 **43s → 约 15s**；M2/M3/M4 各再省几秒。⚠️ 按现有实测（每请求 13ms），这条的收益**没有被量出来**；M1 的 43s 更可能是整机被后台向量化拖慢，先看 `TORCH_NUM_THREADS` 与 `Wait-AIDrain` | 低。要注意 IWR 的 `-TimeoutSec`/错误体读取语义要逐条对齐（现有 catch 分支依赖 `$_.ErrorDetails.Message`） | 断言数不变（99/198/29/51），断言内容不变；**先量基线再改**：改前改后各跑一次 M1，报同一台机器上的中位数 |
| **OPT-02** | 本地快跑通道 | 固化 `-SkipChat` 组合：M3/M4 传 `-SkipChat`（下限自动降为 16/30），M5 传 `-SkipUpload -SkipQuota -SkipAiDown` | 本地迭代 **7 分钟 → 约 2 分钟** | 低。CI 必须用完整档，否则覆盖率静默下降 | 两套档位都跑一遍，报出两行计数 |
| **OPT-03** | `Wait-ForRateWindow` ≤75s | M5 结束后**显式清掉** `gw:rate:login_ip:*` 桶（本机有 Redis 访问权），而不是等窗口翻过 | 省 **最多 75s**，且把隐式时间依赖变成显式清理 | 中。脚本会直接摸 Redis 键名 ⇒ 把验收绑死在内部实现上；缓解办法是把键前缀集中成一个常量并加一条自检（键不存在时给出明确提示） | 连跑两遍全套，第二遍的 `Wait-ForRateWindow` 应立即返回 `true` |
| **OPT-04** | `Wait-AIDrain` ≤150s | 改成事件驱动：读 AI 侧"待处理 chunk 数 / 向量化队列深度"指标（AI 侧已有 `METRICS_PORT`），队列为 0 才开跑 | 省 **最多 150s**；且不再依赖 500ms 这个手调阈值 | 中高。需要 AI 侧新增一个指标（跨仓库改动），且要定义"排空"的语义 | 上传后立即跑 M4，`Wait-AIDrain` 应在队列归零时立即放行 |
| **OPT-05** | M5 的实例启动成本 | 4 个辅助实例**并行启动**（`Start-Process` 已在用，只需把启动循环改成"先全部 spawn、再统一等就绪"） | 省 **约 10~20s** | 低中。并行启动会放大瞬时内存占用（本机只剩 ~1.7GB），可能需要降到 2 个一组 | 逐个实例的日志都要有 `GET /health/live 200` |
| **OPT-06** | `mysql.exe` 每次 ~1.1s | 审计断言的查询改用长驻连接（.NET `MySqlConnector`）或网关的只读管理端点；退一步：一个进程内把多条 SQL 合并成一次调用 | 每次省 **~1s**，M5+M6 合计省几秒 | 低（引入一个 DLL）到中（新增管理端点 = 新增攻击面，**默认必须关闭**） | 审计断言仍能拿到行数（`Audit-Rows >= 1`） |
| **OPT-07** | 首帧延迟（**真产品优化**） | `SkipDefaultTransaction:false` 让每条写都是 `BEGIN+stmt+COMMIT`，而 SSE 首帧前要同步走 6~8 条 SQL（`GetOwned → 配额预扣 → 落 user 消息 → 自动标题 → 取历史`） | 首帧 **120~260ms → 目标 < 100ms** | 中。要保证 `LAST_INSERT_ID(message_count+1)` 的 `seq` 分配仍在同一事务里（docs/08 已知约束），且配额预扣的失败语义不能变 | `internal/biz` 单测全绿 + `curl_stage4.ps1` 的"经网关首帧中位延迟"INFO 值下降 |
| **OPT-08** | 就绪探测 | 500ms 固定轮询 → 指数退避（50ms 起，上限 500ms） | 每次实例启动省 **约 0.5~1s** | 低 | 实例就绪日志仍打印，且 `20s 内未就绪` 分支仍可达 |
| **OPT-09** | M5 的 12 次熔断探针 | 12 次是 `CBFailures + 2`，语义上必须"连续 10 次失败"⇒ **不可减**。可减的只有"必败连接"的等待时间（用空闲端口而非黑洞地址，已经是这样） | 0 | — | 保持现状即可，记录为"不可优化项" |
| **OPT-10** | M2 的 23 次模型调用 | **不可减**：18 次串行是台账断言（seq/归档/软删/幂等），5 并发是 `AC-CONV-07` 的唯一证法 | 0 | 减了就是降覆盖率 | 保持现状，本地迭代用 OPT-02 的 `-SkipChat` |

> **明确不做的事**（避免"为了跑得快把验收放松"）：
>
> - 不把 `AC-NFR-01` 的 200 次采样降到 50 次（原文要求 200 次）；
> - 不用"等窗口过期"以外的方式绕限流（伪造 `X-Forwarded-For` / 打开 `TRUSTED_PROXY_COUNT`
>   都是为测试放松安全配置）；
> - 不把 `-UploadMB` 调回 19/49MB（做大文件只是把相对判据的分母变大，却真把 AI 喂爆）。

```python
import math
LINE = "# 上传流式转发测试\n\n这是第 {0} 段占位文本，用于把文件撑到指定大小。\n"

def make_text(target_bytes):          # 复刻 curl_stage5.ps1::New-TextBody
    lb = len(LINE.format(0).encode("utf-8"))
    raw = "".join(LINE.format(i) for i in range(math.ceil(target_bytes / lb))).encode("utf-8")
    if len(raw) > target_bytes:        # 按字节裁到目标以内、在最后一个换行处收尾
        cut = min(target_bytes, len(raw) - 1)
        while cut > 0 and raw[cut] != 10:
            cut -= 1
        raw = raw[: cut + 1]
    return raw

from app.rag.chunking import ChunkingService
from app.rag.parsers import parse_document

raw = make_text(8 * 1024 * 1024)
parsed = parse_document("m5.txt", raw, min_chars=1)        # 真实解析器
svc = ChunkingService(chunk_size=512, chunk_overlap=64)   # 与 .env 一致
drafts = svc.split_blocks(parsed.blocks)
print(len(parsed.blocks), len(drafts))   # -> 84846 16969
```

§2.5 与 §3-② 里记着两个"AI 侧"的问题。查证后：一个是**被写错的描述**，

### 7.1 勘误：8MB 上传到底切多少块，以及"谁占着事件循环"

复刻 `curl_stage5.ps1::New-TextBody` 的正文（同一份 `$line` 模板、同样按字节截到最后一个换行），
再走**真实**链路 `parse_document(...)` → `ChunkingService(chunk_size=512, chunk_overlap=64).split_blocks(...)`：

| 量 | 实测值 |
| --- | ---: |
| 正文字节 | **8,388,573**（8.00 MiB） |
| 字符数 | 3,467,547 |
| token（**分块求和**口径） | **2,968,583** |
| token（整篇 `encode` 口径） | 3,053,429 |
| 解析出的 block | 84,846 |
| 切分出的 chunk | **16,969** |
| 单块 token | min **170** / 中位 **175** / max **178** |
| **实际入库** | **10,000**（被 `MAX_DOC_CHUNKS` 截断） |

> **两个 token 口径都对，差的 84,846 恰好等于 block 数。** `parse_document` 把正文切成
> 84,846 个 block 之后，block 之间原有的 `\n\n` 不再计入 ⇒ 分块求和比整篇少"每块约 1 token"。
> 规矩：**报切分/向量化相关数字用分块求和口径**（切分器看到的就是它），
> 报"这个文件多大"用整篇口径。混用会得到差一个块数的两个数，看起来像算错。

**为什么 8MB 会切出 1.7 万片** —— 三层放大，与文件"大不大"无关：

1. **字节 ≠ token。** 切分只认 token（`count_tokens` → tiktoken `cl100k_base`），
   这份中文实测 **1.33 token/汉字**、**2.75 bytes/token** ⇒ 8MB = 229 万汉字 = **305 万 token**。
   按 A4 一页 ~1000 汉字算，**8MB ≈ 2,290 页 ≈ 20 本中文长篇**。
   "8MB 不算大"说的是**传输量**（网关 RSS 也只涨 0.4MB），与 token 量是两件事。
2. **粒度是 512 token。** `CHUNK_SIZE=512` / `CHUNK_OVERLAP=64`（步长 448），
   光这一层就把片数下限定在 `305 万 ÷ 448 ≈ 6,800` —— 不可能只有几十片。
3. **测试文本的形状又把它放大 2.6 倍。** `New-TextBody` 是**逐行重复同一条模板**，
   解析出 **84,846 个平均只有 39 字符（约 36 token）的碎段**；
   而 `_merge_short` 的停止条件是"累加到 `chunk_size × 0.3 = 153.6` 就停"
   （`chunking.py:167-186`）⇒ 片长中位 **175 token**，只填到配额的 **34%**。

**对照实验**（同一份 8MB 正文，只改切法 —— 这条最能说明问题）：

| 切法 | 片数 | 说明 |
| --- | ---: | --- |
| 整篇一次性切（`create_documents([text])`） | **6,527** | 段边界连续、装箱效率高 ⇒ 接近第 2 层的下限 |
| 按 84,846 个 block 切（**真实链路**） | **16,969** | 碎段 + 合并提前停 ⇒ **2.6×** |

⇒ **"8MB → 1.7 万片"是测试文本形状的上界，不是 8MB 中文文档的常态。**
正常散文（段落本身接近 512 token）在同样体积下约 **6,500 片**；
反过来，只要文件里是大量短段落，**任何体积**都会被放大同样的倍数。

**跨体积实测**（同一模板、同一链路）：

| 上传体积 | 汉字数 | token（整篇） | block | 切分片数 | 入库 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 MB | 28.9 万 | 38.4 万 | 10,704 | 2,141 | 2,141 |
| **8 MB** | **229 万** | **305 万** | **84,846** | **16,969** | **10,000**（截断 41%） |
| 19 MB | 541 万 | 721 万 | 200,341 | 40,068 | 10,000（截断 75%） |
| 49 MB | 约 1,340 万 | 1,854 万 | 514,914 | 102,983 | 10,000（截断 90%） |

> 这张表同时解释了 `-UploadMB` 的历史坑：脚本曾"按字符比大小"，于是 `-UploadMB 8`
> 实际发出 **19.19MB**（对应上表第三行，约 4 万片），而**打印的是字节数**，看起来像打印算错。
> 更要紧的是：**8MB 就已经被截断 41%**，所以"把 `-UploadMB` 调大"只会更早触发截断，
> 不会让 `AC-ORCH-05` 的判据更有分辨力（那条判据本身是**相对**的：RSS 增量 < 文件体积）。

三条结论：

1. **不是"~4 万个 chunk"，是 16,969。** 而且因为 `MAX_DOC_CHUNKS=10000`，
   本次上传**约 41% 的正文被静默丢弃**（只打一条 `ingest.chunks_truncated` warning，
   接口照旧回 202）—— 这比"慢"更值得单独立项，见 §6-5 / §7.3-B。
2. **向量化本来就不占事件循环。** `app/rag/embedding/base.py::embed_texts` 是
   `await asyncio.wait_for(asyncio.to_thread(provider.embed, ...), timeout=...)`。
   把这里说成"在**单事件循环**里跑 CPU 向量化"是**反的**。
3. **真正占事件循环的是它前后三段同步 CPU**：`parse_document`、
   `split_blocks`（tiktoken 逐块计数）、`_build_chunks`（逐块 sha256）。
   它们中间没有一次 `await`，8MB 正文要占住事件循环几十秒 —— 这正是
   `run_all_stages.ps1` 预检里那句"AI 进程在监听但所有请求都超时"的成因。

**修法**：三段各包一层 `await asyncio.to_thread(...)`（`app/rag/service.py::_ingest_document`）。

**回归守门**：`tests/unit/test_rag_ingestion_threads.py` 断言这三段**跑在非事件循环线程上**。
刻意用"线程 id 不等"而不是计时：本机只剩 ~1.7GB 可用，时序断言必然间歇假红。
已做过反向验证 —— 把任意一段改回同步，用例立刻红
（`AssertionError: hash 跑在事件循环线程上`，`assert 20200 != 20200`）。

### 7.2 新增开关 `TORCH_NUM_THREADS`（治"整机慢 2~3 倍"）

§3-② 那条"整机慢 2~3 倍"的机制是：`SentenceTransformer.encode` /
`FlagReranker.compute_score` 默认把 torch 线程数设成**逻辑核数**，
8MB 文档的向量化会把整机的核吃满，同机的 MySQL / Redis / 网关 / curl 一起被饿死。

- 新配置 `TORCH_NUM_THREADS`（默认 **0 = 不干预**，保持单机独占时的吞吐最优）。
- 落点 `app/rag/torch_threads.py::apply_torch_num_threads`，由 `BgeEmbeddingProvider` /
  `BgeReranker` 的**懒加载路径**调用（两个 provider 用同一个值 —— 同一进程、同一份核）。
- 用 `torch.set_num_threads` 而**不是** `OMP_NUM_THREADS`：后者必须在 torch 被 import
  之前设置，而本项目 import 期就会经 `langchain_text_splitters → transformers → torch`
  把它拉进来（与 `HF_ENDPOINT` 失效是同一类问题），读 `.env` 时已经晚了。
- 同步更新：`.env.example`、docs/10-§7.3 配置表。
- 单测 `tests/unit/test_torch_threads.py`（0/负数不干预、>0 生效、没装 torch 跳过、
  以及两个 provider 的懒加载接线）。

> ⚠️ 这条**不减少总 CPU 时间**，它是拿"单次向量化变慢"换"整机不被饿死"。
> `Wait-AIDrain` 仍然必要（后台任务照样在跑，只是不再吃满核）。

> **后续修正（默认值从 `0` 改成"核数的一半"）**：把开关做出来但默认关掉，等于
> **默认仍然吃满整机** —— 上面那条 2~3 倍放大只是变成"可以避免"，而不是"不会发生"。
> 现在 `Settings.torch_num_threads` 的默认值由
> `app/core/config.py::default_torch_num_threads()` 给出：`max(1, os.cpu_count() // 2)`
> （本机 20 逻辑核 ⇒ **10**）；显式写 `0` 仍然是合法的"不干预"，
> 但不再是默认。语义没变、接口没变，只有默认值变了：
>
> * 为什么取一半而不是 `2`：一半是"单次向量化略慢"与"整机不被饿死"的折中；
>   取 `2` 会让大文档的**绝对**耗时成倍上涨，而验收与用户感知的正是绝对耗时。
> * `os.cpu_count()` 与 torch 自己用的口径一致（都是逻辑核）；
>   取不到时兜底 `2 // 2 = 1`（宁可设 1，也不退回"不干预"）。
> * `.env` 里**不写这一行**就是默认值；`.env.example` 里给的是注释掉的
>   `# TORCH_NUM_THREADS=10`（**不要写空值**，空串不是合法整数）。
>
> **2026-10-02 端到端实测（真 BGE + 真 Redis/Kafka/MySQL/Milvus，同一份 150KB 文档，
> 只改这一个变量；详见 [`11-§3.4`](./11-优化项实测记录.md)）**：
>
> | `TORCH_NUM_THREADS` | 上传→终态 | `/health` 中位 | P95 | 最大 |
> | ---: | ---: | ---: | ---: | ---: |
> | **10**（一半核，新默认） | **156.8 / 178.5s** | 39.1 / 43.0ms | 62.2 / 105.7ms | 69 / 130ms |
> | 20（逻辑核，旧默认） | 223.9s | 66.2ms | 133.8ms | **3731ms** |
>
> ⇒ 本机是**双赢**：自身快 25~30%、在线请求中位好 30~40%、尾延迟从 3.7s 降到 <0.13s。
> 上面那句"这条不减少总 CPU 时间"在**本机**（可用内存仅 ~1.7GB）不成立：20 线程会把
> 内存带宽打满并抖动。但在内存宽裕的机器上它可能仍成立（未实测）——
> 唯一稳的结论是"**一半核不会更差**"。

### 7.3 顺带发现的两条（一条 **2026-10-02 已改**，一条只修了"静默"）
