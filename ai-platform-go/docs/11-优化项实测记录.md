| # | 预期（09/10 的原始口径） | 实测 | 判定 |
| --- | --- | --- | --- |
| ① | UP-03 ⇒ 片数 16,969 → ~6,500，**向量化时间按片数线性下降 ~2.6×**（70min → 27min） | 片数 **16,969 → 6,056（2.80×）** ✅；但**向量化时间不降反升**：同样正文下新块形状每 token 贵 **26~28%**（1.45→1.85 ms/token @20 线程），8MB 全量嵌入 ≈ **101min**（旧形状同内容 ≈ 81min） | ⚠️ **片数达标，提速预期不成立**：UP-03 是**正确性**项（不再丢 41% 正文），不是提速项 |
| ② | `TORCH_NUM_THREADS` 一半核 ⇒ 消除整机 2~5× 放大 | 同一份文档、同一台机器：**入库 223.9s → 156.8~178.5s（快 25~30%）**；在线 `/health` 中位 **66.2ms → 39.1~43.0ms**、最大 **3731ms → 69~130ms** | ✅ **双赢，且比预期更强**（不是拿自身耗时换整机稳定，而是两边都变好） |
| ③ | 隔离档 ⇒ 大文件不再拖垮在线请求 | 8MB 入库（6,056 片）期间 API `/health`：**中位 27.7ms / P95 39.2ms / 最大 53.6ms**；任务本身 31.0s 由独立 Worker 跑完 | ✅ 成立（**代价**：不启 Worker 就永远没有终态，见 §3.3） |
| ④ | 关掉系统代理 ⇒ "~104 次往返省一半" | 本机 `Invoke-WebRequest` 打回环**本来就是直连**：把一个记录型代理设为 .NET 默认代理后，**非回环请求 2/2 命中代理、回环请求 0/2 命中**；每请求中位 IWR **13.0ms** / urllib 12.9ms / curl.exe 28.6ms | ❌ **无实测收益**（改动无害但**不是** M1 43s 的成因），见 §5 |
| ⑤ | 换 bge-small / 上 GPU ⇒ 数量级 | CPU 实测 **1.45~2.06 ms/token**（bge-m3，1024 维）：8MB ≈ 3.0M token ⇒ **72~101min**。这是唯一真正的数量级杠杆 | ✅ 方向对，但**必须重定标召回 + 重建集合** |
| ⑥ | （新增）**换成云端 embedding API** | 火山方舟 `doubao-embedding-vision-251215`：并发 32 时 **98.9 req/s**；8MB（5,822 片）入库 **81.4s**，平均 **14 ms/片** vs CPU BGE 的 **992 ms/片** ⇒ 该阶段约 **71×**。语义特殊（**一条请求只返回一条向量**）与三个可用参数见 §6.5 | ✅ **已落地**：出厂档切到 `ark`，本机 6.36 GB 的 bge-m3 权重已删除 |

**一句话**：这一轮真正把"用户可感知的慢"按下去的是 **②③**；**①** 换来的是"不再丢 41% 正文"，
而不是更快；**④** 是防御性改动，本机复现不出它要解决的问题；**⑤⑥** 才是分钟级到秒级的那个杠杆 ——
其中 **⑥ 已经落地**（70~100min → 81s），并且顺带修掉了一个会静默丢正文的 Markdown 解析 bug（§6.5-F）。

## 1. 环境与测量纪律

| 项 | 实测值 |
| --- | --- |
| 机器 | 本机（16GB 内存，**可用仅 ~1.7GB**，逻辑核 **20**） |
| 可用基础设施 | MySQL（3306）、Redis（6379）、Milvus（19530）、Kafka（9092）、MinIO（9005）**全部在线** |
| 不可用 | Jaeger/OTLP 4317（无 collector，测试里靠 `OTEL_ENABLED=false` 关掉） |
| embedding 权重 | `BAAI/bge-m3`、`bge-reranker-v2-m3` **已在本机 HF 缓存**，`HF_HUB_OFFLINE=1` 加载 2.5~3.0s |
| torch | `2.14.0+cpu` |

**四条测量纪律**（不遵守就会得到假数字）：

1. **同一次 shell 调用内完成"起服务 + 打请求"**。本机（DSH 沙箱）每次调用是独立的回环命名空间：
   上一次调用里起的监听端口，在下一次调用里**连不上**（表现为 `ConnectionRefused after ~2048ms`）。
   实测同一调用内父进程 GET 子进程端口：首次 54ms、之后 4ms。
2. **不要用 socket 探测判断依赖在不在**。`socket.connect()` 对 6379/19530/9092 报
   "ConnectionRefused after ~2048ms"，但应用连它们是好的（`/health` 里 redis 8ms / milvus 4ms / mysql 9ms）。
   判断依赖一律读**应用自己的 `/health`**。
3. **跑 B/C 组（真 BGE）时不要同时跑别的重活**，否则 1.7GB 可用内存会抖动，数字不可比。
4. 计时用**中位**；用 `min` 会把冷启动那一次抹掉，用 `mean` 会被抖动拖走。

**被测的 8MB 正文**：复刻 `curl_stage5.ps1::New-TextBody`，8,388,573 bytes / 3,467,547 chars /
**2,968,583 token** / **84,846 blocks**（与 `09-§7.1` 逐字节同源）。

## 2. ① UP-03：切分合并的停止条件

### 2.1 片数与块长（真实 `parse_document` + `ChunkingService`）

命令：`python tools/ingest_bench.py --mb 8`

| 量 | 旧（`0.3` 当停止条件） | 新（填到 `chunk_size`） |
| --- | ---: | ---: |
| chunk 数 | **16,969** | **6,056**（2.80×） |
| 中位块长 | **175** token（配额 512 的 34%） | **490** token（**96%**） |
| min / max | 170 / 178 | 350 / 510 |
| 全部块的 token 和 | 2,968,583 | 2,968,583（**一致**：合并不改内容） |
| 超过 `MAX_DOC_CHUNKS=10000`？ | **是**（截断，丢 41%） | **否** |

**分阶段计时**（同一进程、同一份正文）：

| 阶段 | 旧 | 新 | 说明 |
| --- | ---: | ---: | --- |
| `parse_document` | 0.59s | 0.59s | 与切分配方无关 |
| `_split_block` ×84,846 | 3.62s | 3.62s | 同上 |
| `_merge_short` | 3.11s | **5.43s** | 合并次数 +16%，且每次要重算累计文本的 token 数 ⇒ **+2.3s**（见 §2.4 的待优化项） |
| 逐块 sha256（`_build_chunks` 的同步 CPU） | 0.02s | 0.01s | 随片数走，但绝对值可忽略 |
| `embed+upsert`（hash，batch=16，内存 store） | 6.53s（1,061 批） | **4.04s**（378 批） | 片数少 ⇒ 批次数少 ⇒ 持久化/上报次数少 |

### 2.2 真实 HTTP 端到端（`INFRA_BACKEND=memory` + `TASK_RUNNER=inline` + hash）

| 上传体积 | 片数 | `chunks_total` | `truncated` | 上传→`INDEXED` | 接口读回的块长 |
| --- | ---: | ---: | --- | ---: | --- |
| 1 MB | 760 | 760 | false | **2.1s** | — |
| 8 MB | **6,056** | 6,056 | **false** | **13.3s** | min 479 / 中位 **490** / max 510 |

> 对照 `09-§7.1` 的跨体积表：1MB 旧口径 **2,141** 片 ⇒ 现在 **760**（2.82×，与 8MB 的 2.80× 一致）。
> 这说明 UP-03 的效果**与被测体积无关**（都是"碎段形状"的放大被消掉）。

### 2.3 真实持久化下的 A/B（Redis + Kafka + MySQL + Milvus + MinIO + 独立 Worker，hash）

命令：`python tools/worker_e2e_check.py --mb 8 --embedding hash [--old-merge]`

| 口径 | 切分产出 | 实际入库 | 截断 | 上传→终态 | 入库期间 `/health` 中位 |
| --- | ---: | ---: | --- | ---: | ---: |
| **新条件** | 6,056 | **6,056** | **False** | **31.0s** | 27.7ms |
| 旧条件（`--old-merge`） | 21,212 | 10,000 | **True**（丢 53%） | 31.1s | 25.5ms |

> ⚠️ **口径提醒**：`--old-merge` 把填充目标打回 `0.3`，块长中位 **136**（旧实现是 175），
> 所以切分产出是 **21,212** 片而不是 `09-§7.1` 记的 16,969；两者都被 `MAX_DOC_CHUNKS` 截到 10,000，
> **入库工作量相同**，因此这一行比较的是"持久化 + 哈希向量化"那一侧，不是完整旧实现。
> Worker 日志可验：`ingest.chunks_truncated total=21212 limit=10000` → `ingest.completed chunks=10000 truncated=True`。

**⇒ 在 hash（非模型）路径上，两种配方总耗时相同（31.0 vs 31.1s）**：片数少 2.8 倍省下的批次开销，
被"现在要处理 70% 更多正文"抵消掉了。真正的差别是**是否丢内容**。

### 2.4 ⚠️ 与预期不符：**向量化时间不按片数下降**

原因：合并把块变长，而 transformer 的**每 token 成本随序列变长而上升**。真 BGE 实测
（`tools/ingest_bench.py --part b`（子命令已移除），16 块/批，取 3 次中位）：

| torch 线程 | 形状 A（旧，中位 185 token） | 形状 B（新，中位 481 token） | 每 token |
| ---: | ---: | ---: | ---: |
| 10 | 4.84s ⇒ 303 ms/块 | 15.87s ⇒ 992 ms/块 | 1.64 → **2.06** ms/token（**+26%**） |
| 20 | 4.30s ⇒ 269 ms/块 | 14.21s ⇒ 888 ms/块 | 1.45 → **1.85** ms/token（**+28%**） |

**同一份正文（3.0M token）的 BGE 时间估算**：

| 方案 | 嵌入 token | 每 token | 估算 BGE 时间 | 内容完整度 |
| --- | ---: | ---: | ---: | --- |
| 旧形状 + 截断（出厂） | 1.75M（10,000×175） | 1.64ms | **≈48 min** | 59% |
| 旧形状 + 不截断 | 2.97M | 1.64ms | **≈81 min** | 100% |
| **新形状（UP-03）** | 2.97M | 2.06ms | **≈101 min** | 100% |

> 交叉验证：`09` 记的用户观察值是 **70min**。用 20 线程的旧形状成本算
> `2.97M × 1.45ms = 71.8min` —— 与 70min 几乎相等。也就是说那次 70min **嵌入的是全部 2.97M token
> （没有截断）**，量级与本文的每 token 成本一致，误差 ~15%（机器负载差）。

**端到端 A/B（150KB / 63,540 字符 / ~54.9k token，真 BGE + 真持久化，threads=10）**：

| 口径 | 片数 | 块长中位 | 上传→终态 | `/health` 中位 / P95 / 最大 |
| --- | ---: | ---: | ---: | --- |
| 旧条件 | 404 | 136 | **164.1s** | 46.2 / 110.9 / 157.4 ms |
| 新条件 | 111 | 510 | **178.5s**、**156.8s**（两次） | 43.0 / 105.7 / 129.8 ms；39.1 / 62.2 / 69.2 ms |

> **诚实结论**：端到端差异（164.1 vs 156.8~178.5s）**落在本机运行间噪声（±7%）之内**，
> 分辨不出 §2.4 表格里那个 +26% —— 因为 150KB 这一档里"模型 + 持久化 + 池化开销"混在一起。
> **能确定的是**：片数 2.80× 下降是真的，**"因此快 2.6×"是假的**；方向甚至相反（每 token 更贵）。

### 2.5 结论与建议

* **UP-03 保留**：它消灭了"8MB 丢 41% 正文"这件事（`truncated=False`），片数回到配置附近，
  召回粒度不再被"0.3 当停止条件"这个 bug 决定。
* **不要再把 UP-03 当提速项**：想缩短 70min 只能走 §6 的模型/GPU，或显式接受部分索引（UP-05）。
* **顺带发现一个可优化点**：`_merge_short` 每次合并都用 `count_tokens(累计文本)` 重算，
  8MB 要花 5.43s（旧条件 3.11s）。可以在合并期间累加各段 token（近似），
  只在**收尾**时精确重算一次 —— 最终计数仍然精确（`test_char_offsets_track_the_source` 要求
  `token_count == count_tokens(content)`），但合并的判定会用近似值，
  **会轻微移动块边界与片数**。收益 ~4s/8MB（相对 100min 可忽略），因此**本次没改**，只记在这里。

## 3. ② / ③ 隔离与线程数：**这两项是真正有效的**

### 3.1 出厂档（`real` + `kafka`）启动与降级

用**真实 `.env`**（`INFRA_BACKEND=real` + `TASK_RUNNER=kafka`）启动 API：

```text
app.startup  infra_backend=real task_runner=kafka task_store=RedisTaskStore \
             task_event_bus=RedisTaskEventBus embedding_provider=bge
task.compensator_started  interval=30.0 grace=60.0
```

→ **不因外部依赖未就绪而拒绝启动**（与 README 的口径一致）；`/health` 会逐项报
`storage=real / redis ok 8ms / milvus ok 4ms / mysql ok 9ms`。

### 3.2 隔离度（8MB，hash 向量化，Worker 独立进程）

| 观测量 | 实测 |
| --- | --- |
| 上传响应 | `202`，**558ms**（正文 8.39MB，multipart `file` 字段） |
| 任务流转 | `QUEUED → RUNNING/PARSING → CHUNKING → EMBEDDING(…/6056) → SUCCEEDED` |
| 上传→终态 | **31.0s** |
| **入库期间 API `/health`** | **n=74，中位 27.7ms，P95 39.2ms，最大 53.6ms** |
| Worker 日志 | `ingest.completed chunks=6056 chunks_total=6056 vectors=6056 truncated=False` |

⇒ "大文件不再拖垮在线请求"**成立**：Worker 在满负荷嚼 6,056 片时，API 的 `/health` 仍是几十毫秒级。

### 3.3 隔离的代价（必须写清楚）

* **不启动 Worker ⇒ 任务永远停在 `QUEUED`**。实测：只起 API、上传 8MB，任务 10 分钟不结束
  （`task.created` → `task.queued topic=ai.task.document_ingest attempt=1`，之后没有消费者）。
  这条不是 bug（Kafka 语义如此），但**换了出厂档就多了一个必须先起来的进程**。
* 上一次实验遗留的一个 `PENDING` 任务，在 Worker 起来后被**自动消费并完成**（日志里的 `chunks=1` 那条）
  ⇒ 投递/消费与补偿扫描的链路是通的。

### 3.4 `TORCH_NUM_THREADS`：20（旧默认）vs 10（新默认）

同一份 150KB 文档、同一套真 BGE + 真持久化，**只改这一个变量**：

| `TORCH_NUM_THREADS` | 上传→终态 | `/health` 中位 | P95 | **最大** |
| --- | ---: | ---: | ---: | ---: |
| **10**（一半核，新默认） | **178.5s** / **156.8s** | 43.0 / 39.1 ms | 105.7 / 62.2 ms | 129.8 / 69.2 ms |
| **20**（逻辑核，旧默认） | **223.9s** | 66.2 ms | 133.8 ms | **3731.0 ms** |

**两个方向都变好**：
* 自己的入库快 **25~30%**（223.9 → 156.8~178.5s）；
* 在线请求中位好 **30~40%**，**尾延迟从 3.7s 降到 0.07~0.13s**。

机制：本机**可用内存只有 ~1.7GB**，20 个 torch 线程会把内存带宽/缓存打满并触发抖动
（那 3731ms 的尾延迟就是一次抖动）；把线程减半等于同时缓解了核争用与内存压力。

**独立进程视角**（当时的 `--part c`，已于 2026-10-02 移除；另一个进程做 6M 次乘加的固定任务）：

| 场景 | victim 耗时 | 相对空闲 |
| --- | ---: | ---: |
| 空闲 | 530 ms | 1.00× |
| 向量化中，threads=10 | 1362 ms | **2.57×** |
| 向量化中，threads=20 | 1525 ms | **2.88×** |

⇒ 线程减半只拿回 ~11% 的"饿死"，**剩下的瓶颈是内存带宽而不是核数**：
"整机慢 2~3 倍"里有一大半不是"核被占满"能解释的，所以**单靠线程数消不掉**（与 09-§7.2 的
"这条不减少总 CPU 时间"是同一个意思，但比它更悲观一点：它连"整机退化"也只能缓解 ~11%）。
真正能消掉它的是 §6 的模型/GPU —— 或者在内存更宽裕的机器上跑。

## 4. ④ 代理：**本机复现不出它要解决的问题**

### 4.1 判别实验（记录型代理）

把 `.NET` 默认代理显式指向一个**会记录请求的本地代理**（`BypassProxyOnLocal=$false`）：

| 请求目标 | 结果 | 代理是否收到 |
| --- | --- | --- |
| `http://127.0.0.1:8898/`（回环） | HTTP 200（**目标直接应答**） | **0 笔** |
| `http://probe-host.invalid/x`（非回环） | HTTP 200 | **1 笔** |
| `http://another.invalid/y`（非回环） | HTTP 200 | **1 笔** |

⇒ `.NET/PS` **确实**认 `DefaultWebProxy`，但**对回环地址一律绕过**（即使 `BypassProxyOnLocal=false`）。
`docs/09-§2.1` 记的"IWR 会把 127.0.0.1 也送进代理解析"在本机**不成立**。

### 4.2 每请求开销（同一调用内，各 20 次，中位）

| 客户端 | 中位 | 最小 | 最大 |
| --- | ---: | ---: | ---: |
| `Invoke-WebRequest`（默认） | **13.0 ms** | 12.5 | 14.7 |
| `Invoke-WebRequest -Proxy $null` | 13.5 ms | 12.9 | 14.4 |
| `Invoke-WebRequest`（`DefaultWebProxy=$null`） | 13.9 ms | 13.4 | 14.5 |
| `curl.exe --noproxy '*'` | 28.6 ms | 15.1 | 46.7 |
| `urllib`（无代理） | 12.9 ms | 2.0 | 26.5 |

### 4.3 结论

* 改动（进程级 `DefaultWebProxy = $null` + `-Proxy $null`/`-NoProxy`）**无害、可保留**：
  它是"如果哪天有个真会拦回环的代理（TUN 模式 / WPAD 自动探测）就挡一下"的防御。
* **但它不是 M1 43s 的成因**：IWR 打回环 13ms/次，104 次 ≈ **1.4s**，全砍掉也换不回 43s。
  M1 的 0.83s/请求要么来自网关自身（SQL/Argon2id，实测 Argon2id 仅 ~41ms/次），
  要么来自**整机被后台向量化拖慢**（`docs/08-§9.6` 自己写过"跑前先取消遗留任务，
  否则 M5 会从 34s 涨到 200s"）—— 后者的解释与 §3.4 相符。
* `OPT-01`（换 `HttpClient` 复用连接）的收益空间仍在，但**不在代理这一层**：
  IWR 13ms 已经和 urllib 持平、比 `curl.exe` 更快（curl 每次一个进程，~15ms 启动）。

## 5. ⑤ 换模型 / 上 GPU：这才是数量级杠杆

用 §2.4 的实测成本直接算（bge-m3，1024 维，CPU，**每 token 1.45~2.06ms**）：

| 方案 | 3.0M token 的嵌入时间 | 备注 |
| --- | ---: | --- |
| bge-m3 / CPU / 20 线程 / 短块 | ≈72 min | 与 `09` 记的 70min 观察值吻合 |

**换模型的三个硬约束**（本轮已加校验/文档）：
1. `EMBEDDING_DIM` 与 `MILVUS_VECTOR_DIM` 必须同步改 —— 启动期会拦截"已知模型的维度不符"
   （`app/core/config.py::EMBEDDING_MODEL_DIMS`：bge-m3/large-zh **1024**、base-zh **768**、small-zh **512**）；
2. **必须重建 Milvus 集合**：维度是建集合时固化的，旧向量查不出来也不会报错；
3. 换模型 = 改召回配方 ⇒ 要跑检索评测。**本仓库当前没有检索评测集**（`10-§8-2` 已记），
   所以这一步在评测就位前只是"能切"，不是"敢切"。

## 6.5 换云端 embedding API（2026-10-02，本机实测）

**动机**：§2.4 已经证明"切分配方"救不了 70~100min 的 CPU 向量化 —— 那台机器（可用内存 ~1.7GB、
无 GPU）上唯一的数量级杠杆是**换执行位置**。本次把 `EMBEDDING_PROVIDER` 从 `bge` 换成
火山方舟云端多模态向量化（`doubao-embedding-vision-251215`）。

### A. 这个 API 的语义（**与 OpenAI 的 `/embeddings` 不同**，决定了实现形态）

| 事实 | 证据 |
| --- | --- |
| `input` 是"**一个**多模态输入"（text/image/video 片段数组），**一次请求只返回一条向量** | 官方 SDK 类型：`create(input: List[EmbeddingInputParam]) -> MultimodalEmbeddingResponse`，而 `MultimodalEmbeddingResponse.data: MultimodalEmbedding`（**单数**）；对比文本端点的 `data: List[Embedding]` |
| 传 N 条文本会被**聚合成一条** | 实测 1/3/256 条都只回 1 条 2048 维，而 `usage.prompt_tokens` 随条数累加（256 条 → 3493）；`cos(A, A+B)=0.80`、`cos(A,B)=0.08` |
| `input` 写成"数组的数组"→ 400；文本端点 `/embeddings` 不支持该模型 | 实测 400（`could not parse the JSON body` / `does not support this api`） |
| ⇒ **一个 chunk = 一次 HTTP**，批量只能靠并发 | 与 Dify `dify-official-plugins` PR #3593《Fix Volcengine vision embedding batching》、oGMemory `volcengine_embedder.py` 的做法一致（"each text must be embedded in a separate API call"） |

> 官方文档站（`docs.volcengine.com/docs/ark/multimodal-vectorization-api`）是 JS 渲染，
> 直连与文本代理都只拿到 200 空壳 ⇒ 以**官方 SDK 类型** + 活体测探为准。

### B. 并发与吞吐（每条 ~490 token 的真实块）

| 并发 | 吞吐 | 6,056 片（8MB）墙钟 | 失败 |
| ---: | ---: | ---: | ---: |
| 1 | 4.4 req/s | ~23 min | 0/128 |
| 8 | 31.6 req/s | ~3.2 min | 0/128 |
| **32** | **98.9 req/s** | **~1.0 min** | 0/128 |
| 64 | 99.5 req/s | ~1.0 min（无增益） | 0/128 |

### C. 端到端（内存档 + 真 API；跑的时候 Docker 停着，真 Milvus 链路未复测）

| 量 | 结果 |
| --- | --- |
| 8MB 入库总耗时 | **81.4s**（5,822 片、`truncated=False`） |
| 平均每片 | **14 ms**（含切分/向量化/落库）vs CPU BGE 实测 **992 ms/片** ⇒ 该阶段约 **71×** |
| 小文档语义抽查 | **5/5** 命中正确小节（top1 分数 0.66~0.77，与 top2 拉开 0.2+） |

### D. 从 SDK 里挖到、已落地的三个参数

| 参数 | 实测结论 |
| --- | --- |
| `encoding_format=base64` | 响应体 **34,240B → 11,219B（3.05×）**；`data.embedding` 是 base64 的 **float32 小端**（小端与 float 格式的逐元素差 = API 自身抖动，大端差 150 倍）⇒ 默认开启 |
| `dimensions=N` | 支持降维（**1024 可用、512 被拒**），与全维前 N 维余弦 **0.9992** ⇒ Matryoshka 截断式；默认不传（用原生 2048） |
| `instructions` | 接受（检索指令前缀），默认不发 |

### E. 两个必须记住的坑

1. **维度对齐 ≠ 向量空间能混用**：即使 `dimensions=1024` 对齐了 bge-m3 的维度，
   两者向量也不在同一空间 ⇒ 换模型必须**换集合名或 drop 重建**（本次用
   `ai_platform_chunks_v2` / `ai_platform_memories_v2`，旧集合原样保留作回滚）。
   顺带补了一条启动期校验：**已存在集合的实际维度**与配置不符时直接拒绝启动
   （以前只在写入时才会暴露）。
2. **该 API 跨请求不是逐位确定的**：同一文本连续三次，`#1 == #2` 完全相同，
   但 `#3` 与它们的最大逐元素差 **4.883e-03**（中位 4.578e-04）。
   ⇒ 不要写"同一文本两次调用必须得到同一向量"的断言；项目内的 `content_sha256`
   LRU 缓存反而比上游更稳定。

### F. 顺带修掉的一个真 bug（与 embedding 无关，但在验证时撞上）

**Markdown 解析会静默丢正文**：归一化里的「合并中文孤行」把
「`## 年假` + 下一行中文正文」粘成 `## 年假员工入职满一年后……`，
该行**仍以 `## ` 开头** ⇒ 被当成标题 ⇒ 正文被丢弃（标题只用来填 `heading_path`）。
整篇如此写时 `char_count=0`，用户只看到「文档有效文本不足（0 < 50 字符）」。

* 触发条件是「标题以 CJK 结尾 且 下一行以 CJK 开头」——**中文文档的常态写法**；
* 原有 5 条 markdown 单测**全部**在标题后留了空行，所以一直没暴露；
* 修法：`normalize_text(..., join_cjk_lines=False)` 只给 Markdown 用（行结构是它的语义），
  `.txt` 等仍合并孤行；回归用例见 `tests/unit/test_parsers.py`
  （`test_markdown_heading_immediately_followed_by_cjk_body` 等 3 条）；
* 实测：同一份小文档修复前 `0 字符 / 0 块`、修复后 `184 字符 / 5 块`。

### G. 本机配置清理

* `BAAI/bge-m3` 权重已删除：**释放 6.36 GB**（HF 缓存里 43 个文件）；
* `BAAI/bge-reranker-v2-m3`（2.14 GB）**保留** —— 重排仍在用它；
  `RERANKER_ENABLED=false` 时可一并删除，并移除 `torch` / `FlagEmbedding` / `sentence-transformers` 依赖；
* 因此 `TORCH_NUM_THREADS` 当时只影响重排（§3.4 的结论仍适用于重排）。⚠️ **同轮之后 rerank 也换成了云端**，于是它现在**不影响任何东西** —— 见 §6.7-G。

### H. 顺带查清的一个"顺序敏感"测试缺陷（已修）

换 embedding 之后跑全量，冒出 6 条契约用例失败，且**单独跑全过、连着跑必挂**：
就绪探针报 `2048`（应为 `1024`）、`test_memory.py` 报 `ConfigurationError`。
根因不在本次改动：**`import pymilvus` 会在 import 期执行 `load_dotenv()`，把开发机 `.env`
灌进 `os.environ`**；而 `Settings(_env_file=None, ...)` 只关掉 dotenv 文件、关不掉环境变量，
于是"此后整个进程"的配置都被 `.env` 覆盖（日志里出现 `provider=hash` + `dim=2048` 的混血配置）。

修法：应用侧 `_import_pymilvus_guarded` 做「快照 → import → 恢复」；测试侧 `_BASE` 显式钉住
`embedding_model` / `embedding_dim` / `milvus_vector_dim`，并加 autouse 的 `os.environ` 还原。
完整记录（含定位手段）见 `ai-platform/docs/12-实现问题记录.md` §4.4。

## 6.6 重排（rerank）耗时：本轮首次实测

**为什么之前没有数据**：全仓库只有**目标值**——`docs/10-§1`「同上（含 Rerank）600/1500/2500ms」、
`docs/01`「检索 P95 ≤ 300ms（向量召回）；≤ 1.5s（含 CPU Rerank）」——以及 §2 里记的
**模型加载** 2.5~3.0s。`%TEMP%\ai_platform_worker_e2e\api.log` 里那次 E2E 只发了
`POST /knowledge-bases`、`POST …/documents`、`GET /health`，**从未走过 `/search`**，
所以"重排推理耗时"一次都没被测过。

**测法**：走真实路径 `BgeReranker.rerank(query, documents, top_n=5)`（`app/rag/reranker/bge.py`），
候选文本按真实块形状构造（~847 字/条，被 `FlagReranker` 默认 `max_length=512` 截断 ⇒
每对 ≈ 512 passage + ~15 query token，与真实 490-token 块的实际 token 数几乎一致）。
本机 embedding 已改云端，CPU 空闲 ⇒ 这是**不被抢占的干净数值**。
`FlagReranker` 默认值经查源码确认：`max_length=512`、`query_max_length=384`、`batch_size=128`
（20 条候选 = 一次前向）。

| `TORCH_NUM_THREADS` | 候选 5 条 | 候选 **20** 条（生产默认 `top_k=20`） | 模型加载 |
| ---: | ---: | ---: | ---: |
| 10（本机默认） | 首轮 14,993ms / 稳态中位 **14,016ms**（2,803 ms/对） | 首轮 59,474ms / 稳态中位 **83,140ms**（4,157 ms/对） | 17.31s（冷）/ 6.17s（页缓存热） |
| 20 | — | 首轮 74,171ms / 稳态中位 **68,055ms**（3,403 ms/对） | 6.17s |

**结论与含义**：

* **换掉 embedding 之后，重排成了 RAG 在线路径的最大项**：一次 `/search`（`top_k=20 → top_n=5`）
  光重排就 **~70~83s**，而 SRS 目标是「含 CPU Rerank P95 ≤ 1.5~2.5s」⇒ **超目标约 30~50×**。
  也就是说：入库从 70~100min 降到 81s 之后，**用户可感知的慢转移到了每次提问**。
* **非线性放大，与内存强相关**：候选 5 → 20（×4）墙钟 ×5.9，单对成本 2.8s → 4.2s。
  本机可用内存仅 ~1.7GB，且 CPU 上 `use_fp16=False`（没有半精度加速）。
* **线程数**：干净单测下 20 线程比 10 线程快约 18%（68.1s vs 83.1s）——与 §3.4「一半核更好」
  **不矛盾**：那条测的是**整机被入库抢占**时的表现，这条是空载单测。各只有一次 3 采样中位，
  本机内存压力下方差大，**不宜当结论**。
* **方舟没有 rerank 能力**：`volcengine-python-sdk` wheel 里含 "rerank" 的文件数为 **0**，
  所以"像 embedding 一样换成云端重排"在方舟上走不通，要云端重排得另找产品线并单独确认。
* 可用杠杆（按性价比）：`RERANKER_ENABLED=false`（退化为向量分数，会记 `rerank_skipped`）
  → 把 `top_k` 由 20 降到 5~8（5 条只要 14s）→ 换小模型 / ONNX int8（CPU 上唯一"既快又省内存"）
  → 上 GPU。

## 6.7 换成硅基流动云端（embedding + rerank 全换）：本轮实测

紧接 §6.6 的结论 —— 本地重排 70~83s 不可上线 —— 本轮把 **embedding 与 rerank 一起**
换成硅基流动（SiliconFlow）的云端 API，模型都取 Qwen3 系列：

| 用途 | 模型 | 端点 |
| --- | --- | --- |
| 向量化 | `Qwen/Qwen3-Embedding-0.6B`（原生 **1024** 维） | `POST /v1/embeddings` |
| 重排 | `Qwen/Qwen3-Reranker-0.6B` | `POST /v1/rerank` |

### A. 关键语义（文档 + 活体双重确认）

| 事实 | 证据 |
| --- | --- |
| **`/v1/embeddings` 支持真批量（N 进 N 出）** | 官方文档："input: string \| array —— 要在单次请求中处理多个输入，请传递字符串数组"；实测传 8/32/64/128 条都返回同数量 `data`，每条带 `index` |
| 上下文窗口 **32768 token** | 文档明示（对比 bge-m3 的 8194） |
| `dimensions` 降维**仅 Qwen3 系列**，0.6B 可选 `[64,128,256,512,768,1024]` | 文档明示；实测 `dimensions=512` → 512 维 |
| `encoding_format=base64` 可用 | 实测单条 **21,891B → 5,641B（3.9×）**，解出 4096 bytes = 1024 个 float32，**小端** |
| **可复现性优于方舟** | float×3（间隔 0.4s）、base64×2、跨编码 float↔base64 **全部 0.000e+00**；方舟同一文本三次会出现 4.883e-03 |
| `/v1/rerank` 的 `documents` **必须是字符串数组** | 传 `[{"text": ...}]` → 400 `Input should be a valid string`（那是 VL 端点的形状） |
| 响应**没有 `usage`** | 计费在 `meta.tokens.input_tokens` / `meta.billed_units`；20 条 ×490 token ⇒ 11,950 input tokens |
| 错误体形状 | `{"code":20012,"message":"Model does not exist..."}`；401 是 `{"code":30014,"message":"Token is invalid."}` ⇒ 直接把 `message` 带进异常详情 |

### B. 吞吐（490 token 的块，batch × 并发）

| batch | 并发 | 片/s | 备注 |
| ---: | ---: | ---: | --- |
| 16 | 4 | 140.4 | 中位延迟 406ms |
| 32 | 4 | 205.7 | 中位 612ms |
| **32** | **8** | **379.6** | 中位 654ms ⇒ 取此档 |
| 48 | 8 | 288.8 | 中位 **1265ms**，尾延迟变差 |

### C. 端到端：8MB 入库（5,821 片，`truncated=False`）

| 配置 | 墙钟 | 每片 |
| --- | ---: | ---: |
| **串行等待**（原始实现：交一批 → 等返回 → 再交下一批） | **98.2s** | 16.9 ms |
| `INGEST_EMBED_WINDOW=8` | **40.4s** | 6.9 ms |
| 窗口 16 | 40.9s | 7.0 ms（**8 已是拐点**） |

⚠️ **这里暴露了一个真问题（已修）**：provider 内部有并发池，但入库循环是
「交一批 → `await` 返回 → 再交下一批」的严格串行 ⇒ **池子完全是空的**，
只维持一个请求在飞。本地 BGE 时代串行没有代价（算力在本机），换成云端后
每次调用都是一次网络往返，串行等于自断吞吐。修法是
`_embed_and_upsert` 按窗口 `asyncio.gather`（窗口内顺序 upsert + 逐批上报进度，
保住 `docs/06-§4.5` 的进度与取消语义）。参考坐标：CPU BGE **≈ 101 min**、
方舟（每片一次 HTTP）**81.4s**、硅基流动 **40.4s**。

### D. 重排延迟（同条件对比，`top_k → top_n=5`）

| 候选数 | 硅基流动 `Qwen3-Reranker-0.6B` | 本地 `bge-reranker-v2-m3`（§6.6） |
| ---: | ---: | ---: |
| 5 | **292ms** | 14,016ms |
| 8 | **147ms** | — |
| 12 | **191ms** | — |
| 20 | **320ms** | 83,140ms（10 线程）/ 68,055ms（20 线程） |

⇒ 20 条候选 **320ms**，回到 `docs/10-§1`「含 Rerank P95 ≤ 1.5~2.5s」的目标内；
排序正确（问"退款要几个工作日"，退款段得 0.9998，无关段 0.0007）。
实测 50/100/201 条候选都是 200，但 201 条耗时 2903ms ⇒ 实现按
`SILICONFLOW_RERANK_MAX_DOCUMENTS=100` 分片，各取 `top_n` 后全局归并。

### E. 语义抽查（换模型后必须重测；5 个主题的小文档）

**5/5 命中**，且分数比 hash 档高一个量级：年假 0.802 / 报销 0.637 / 加班 0.778 /
保密 0.730 / 培训 0.768（top1 与 top2 普遍拉开 0.25 以上）。

### F. 一个边角事实：批量组成会影响末位精度

同一条文本：**单独编码 vs 放进批 2 ⇒ 0.000e+00**；**单独 vs 放进批 32 ⇒ 1.938e-03**。
即"批量大到一定程度后，同一条文本的向量会有 ~2e-3 的差异"（服务端不同 batch 形状的
归约顺序不同）。对检索无影响（余弦差 ~1e-6），但**不能写"同文本必得同向量"的断言**；
项目内按 `content_sha256` 缓存的向量反而更稳定。

### G. 依赖与配置的连带变化

* `RERANKER_PROVIDER` 显式枚举（`bge` / `siliconflow`）——**删掉了"看模型名里有没有 bge"
  的猜法**：`Qwen/Qwen3-Reranker-0.6B` 名字里没有 `bge`，老实现会在这里**静默退化成不重排**；
* Milvus 集合换到 **v3**（1024 维）。⚠️ v1（bge-m3）也是 1024 维，但**向量空间完全不同**，
  不能因为"维度一样"就复用；
* 本地 `bge-reranker-v2-m3`（2.14GB 权重）现已**无人使用**：`RERANKER_PROVIDER=bge`
  才需要它，日常可以删（`torch` / `FlagEmbedding` / `sentence-transformers` 同理）；
* `TORCH_NUM_THREADS` 在新档位下**不再影响任何东西**（本地推理栈完全退出链路）。
