| `internal/conf/` | 配置加载 | `.env` → 环境变量 → 默认值 → 校验 |
| `internal/data/` | 仓储实现（向下依赖 biz 接口） | user / token / audit / idem / conversation / message / quota |
| `internal/data/model.go` | 8 张表的 PO 与跨表列约定 | `user_id` 一律 `VARCHAR(64)`、时间一律 `DATETIME(3)` |
| `internal/data/ai/` | AI 侧出网客户端 | `grpc.go` / `http.go` / `httpchat.go` / `grpc_stream.go` / `http_stream.go` / `probe.go` |
| `internal/data/{mysql,redis}/` | 引擎层 | 连接、事务、Key 命名空间、配额 Lua，不含业务 |
| `internal/biz/` | 业务 + DO + 仓储接口 | MUST NOT import gin / gorm / redis |
| `internal/service/` | HTTP handler + 响应 DTO | MUST NOT import data |
| `internal/server/` | 路由装配、生命周期、幂等中间件 | `http.go` 是 58 处路由注册的唯一处 |
| `internal/server/middleware/` | trace / 鉴权 / 恢复 / 访问日志 / 安全头 / 限流 | — |
| `deploy/mysql/` | `001_gateway_tables.sql`、`002_test_accounts.sql`、`verify_schema.sql` | 建表 + 自检 + 账号 |
| `tools/` | 分阶段验收 + `run_all_stages.ps1` + `falsify_m4.ps1` + `gen_proto.ps1` | 见 §2.4 |
| `docs/` | 01–07 需求 + 08–11 实现与优化记录 | — |

**分层规则**（违反即返工）：

- 依赖单向向下：`cmd/server → server → service → biz → pkg/*`，`data → biz`；**`biz` 不得 import `data`**。接口归 `biz`、实现归 `data`（`data` 用小写类型实现，只导出 `NewXxxRepo(*Data) biz.XxxRepo`）—— 反过来写会让同一份业务规则在 HTTP 与 gRPC 两个入口各写一遍。
- `service` 不写业务判断，只做「绑定 → 调 biz → 映射错误 → 写响应」与 `biz → DTO`。
- 4xx/5xx 只能经 `httpx.Fail` 写出，否则信封字段会缺（客户端按 `error.code` 分支会落到 default）。
- `data/redis` 不能成为业务判据：它挂了只允许「多查一次 SQL、配额精度下降」，不能让请求失败（MySQL 是权威台账，Redis 只是加速器）。

两处刻意偏离常规布局：`httpx` 放 `pkg/` 是因为它只依赖 `errs`/`logx`/gin，不认识 `biz`/`conf`/`data`（契约适配层，不属于本服务的层）；`data` 按引擎分而不按聚合分，是因为每个聚合只有 1 个文件，而 8 张表的跨表列约定只有放在 `model.go` 一起才看得出「哪张表不一致」。

### 2.1 必跑命令序列（顺序不可反）

```powershell
# 1) 建表 —— 顺序不能反：AI 侧 001 先建共享表 idempotency_record / audit_log
mysql --default-character-set=utf8mb4 -u root -p -e "source ../ai-platform/deploy/mysql/001_init_schema.sql"

# 2) 配置（填 MYSQL_DSN / JWT_SECRET）；3) 编译

# 6) 分阶段接口验收（网关需已在跑；前置条件见 §2.4）

powershell -ExecutionPolicy Bypass -File tools\curl_stage2.ps1
powershell -ExecutionPolicy Bypass -File tools\curl_stage3.ps1      # 需 AI 侧两进程
powershell -ExecutionPolicy Bypass -File tools\curl_stage4.ps1      # -SkipChat / -SkipLatency 可跳过真实模型
powershell -ExecutionPolicy Bypass -File tools\curl_stage5.ps1
powershell -ExecutionPolicy Bypass -File tools\curl_stage6.ps1      # 自包含；-AILogPath 可做两侧 trace 比对
powershell -ExecutionPolicy Bypass -File tools\run_all_stages.ps1   # M1→M6 一次跑完并打汇总表
```

### 2.2 进程与端口

| 进程 / 组件 | 端口 | 说明 |
| --- | --- | --- |
| 网关 HTTP | `18080` | `HTTP_ADDR` 代码默认 `0.0.0.0:8080`；**8080 上坐着 Kafka UI**，见 §2.6 |
| 网关指标 | `9121` / `9122` | 独立端口；`METRICS_PORT` 默认 9100 |
| AI HTTP / 指标 | `8000` / `9100` | `python -m app.main` |
| AI gRPC | `50051` | `GRPC_ENABLED` 默认 **false**；指标端口需与 HTTP 进程分开（9106 / 9107） |
| MySQL / Redis | `3306` / `6379` | 网关用 Redis `db=1`，AI 用 `db=0` |
| Milvus / MinIO | `19530` / **`9005`** | Milvus 自带 etcd、MinIO(9002)、attu(3000)；业务对象存储在 9005（控制台 9011），**不是默认 9000** |

### 2.3 启动

```powershell
$env:ENV_FILE = "<repo>\ai-platform-go\.env"   # 绝对路径
$env:HTTP_ADDR = "0.0.0.0:18080"
.\bin\server.exe
```

- **为什么必须 `ENV_FILE`**：`.env` 默认按进程工作目录查找，从 IDE / 计划任务启动时 cwd 往往不是项目根，于是「`.env` 写了却全走默认值」——这类故障没有任何报错。`.env` 存在但解析失败现在直接退出，不再静默回退。
- **AI 侧要两个进程**（stage3 起缺一不可）：`uv run python -m app.grpc`（50051，需 `GRPC_ENABLED=true`，否则入口以退出码 2 报错）+ `uv run python -m app.main`（8000）。入口是包 `app/grpc/__main__.py`，**没有 `app/grpc.py`**。只起 gRPC → 19 条透传全红（`AI_PLATFORM_BASE_URL` 那个端口上没人）；只起 HTTP → `send` 不走 gRPC。`AI_GRPC_ENABLED` 代码默认 true、`.env.example` 写 false：「默认开」是生产语义，「示例关掉」是为了只跑 stage1/2 时不必起 AI 侧。
- 起服务前先 `Get-NetTCPConnection -LocalPort 18080 -State Listen`：上一轮进程没退干净时脚本会连到旧进程，「用新代码跑出全绿」是假的。

### 2.4 分阶段验收：脚本、前置、断言

| 脚本 | 断言数（文档记录） | 前置 | 实测耗时（2026-09-30） |
| --- | --- | --- | --- |
| `curl_stage1.ps1` | 99 | 网关 | ≈20s |
| `curl_stage2.ps1` | 198 | 网关 + AI（真实模型） | 60~120s（M3 后 35~120s） |
| `curl_stage3.ps1` | 29 | AI gRPC 50051 + AI HTTP 8000 + 网关 | ≈4s |
| `curl_stage4.ps1` | 50（全套记 51 PASS） | 同 stage3 + AI 的 HTTP 通道（增量对比） | ≈30s |
| `curl_stage5.ps1` | 40（全栈轮 43） | 自拉实例 18082/18083；第 5 段「限流按真实 IP」打在 18080 | ≈25s |
| `curl_stage6.ps1` | 57 | 自包含（自编译 + 干净实例 18084/9111） | ≈80s |
| `run_all_stages.ps1` | 474（网关单侧）/ 477（全栈） | 自拉实例 A/B（18085/18086） | 6~8 分钟 |

- 脚本打 `[PASS] / [FAIL]` 与最终计数，任何 FAIL 以非 0 退出码结束 —— 这个退出码**可以**接 CI，但仓库当前**没有 CI**（§11）。
- `run_all_stages.ps1` 里 `Min` 是断言数**下限**（断言只会增加），`SkipMin` 是 `-SkipChat` 时的下限。
- SKIP 要和 FAIL 一样看：`-SkipChat` / `-AILogPath` / RSS 采样拿不到进程都会让整组降级成 SKIP，**「变绿」与「少验了东西」在计数上几乎一样**（§9.4 的 RSS 端口缺陷就这样藏了一轮）。
- 客户端超时已从 30s 提到 **120s**：先超时会让 `status` 变成 0，断言报成「接口返回 0」，方向全错。

### 2.5 工具链基线：`go` 指令钉在 `1.24.0`

`go.mod` 的 `go` 是**下限**。本机 Go 1.24.8；若写 `1.26.0`，`GOTOOLCHAIN=auto`（默认）会在任何一次构建前先联网下载工具链 —— 新克隆的机器在编译第一个文件前就要能上外网。压回 1.24.0 时被卡住的正好 5 个依赖（`x/crypto` v0.57→v0.45、`gin` v1.12→v1.11、`x/net` v0.58→v0.47、`x/sys` v0.48→v0.38、`x/text` v0.42→v0.31，括号内是各自声明的 go 版本），顺手甩掉了 `gin v1.12` 为 HTTP/3 加的 `mongo-driver/v2`。验证就是 §2.1 第 5 步 + `go env GOVERSION` 得 `go1.24.8`。**不要上调那一行**，一上调整批依赖就被拉回高版本。

### 2.6 本机环境坑

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 8080 绑定失败，`Get-NetTCPConnection` / `tasklist` / `netsh` 都查不到占用者 | 占用者是 `kafka-ui` 容器：Docker Desktop 经 WSL2 NAT 转发，宿主侧看不见监听者；打到 8080 会拿到 200 + HTML 首页，`/api/v1/...` 回另一个框架的 404 信封 | `docker ps --format "{{.Names}} {{.Ports}}"` 一眼看到；脚本 `-BaseUrl` 默认值已统一为 18080。**默认值本身是契约**：一个「当时能跑」的默认值，环境变了就变成人人都得记住的例外 |
| 先起 AI 再起网关，网关启动失败报 `LOG_FORMAT="console" 不合法` | 同名不同域：网关只收 `json`/`text`，AI 只收 `json`/`console` | 脚本的启动函数里硬写 `LOG_FORMAT=text` |
| 脚本输出重定向后中文变「楠屾敹」 | PS 5.1 父 shell 按 gb2312 解码子进程的 UTF-8 | `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)` |
| 集成测试用例**失败**而不是跳过 | `AI_TEST_MINIO_ENDPOINT` 默认 `localhost:9000`，`_reachable()` 只做 TCP 探测，VS Code 的 HTML 404 能过门 | `$env:AI_TEST_MINIO_ENDPOINT='127.0.0.1:9005'` |
| compose 覆盖 `ports` 后容器只剩 `expose`，不报错 | compose 2.28 的 `!reset` 会清空序列 | 用 `!override` |

## 4. M1 · 鉴权与用户闭环

**结论**：验收 8 组 **99 项断言全通过**（文档记录，2026-09-29）。接口在根路径与 `/api/v1` 下各注册一份；中间件链 RequestID → Trace（W3C `traceparent`）→ RealIP → AccessLog → SecurityHeaders → CORS → BodyLimit → Auth。

### 4.1 验收项清单与输入 → 期望

| 覆盖组 / 请求 | 期望 | 关键字段 / 说明 |
| --- | --- | --- |
| 健康检查 | 200 | `/health`、`/health/live`、`/health/ready`；ready 检查「MySQL 连通 + 表齐全 + Redis 连通」 |
| `POST /auth/register` | 201 | 只回用户资料，**不回令牌**；重复邮箱 409 `EMAIL_ALREADY_EXISTS`（软删行也占用） |
| `POST /auth/login` | 200 | `access_token` / `refresh_token` / `token_type=Bearer` / `expires_in` / `user` |
| 登录失败 | 401 / 403 | 密码错与账号不存在同码 `INVALID_CREDENTIALS`（防枚举）；禁用账号 `USER_DISABLED` |
| `POST /auth/refresh` | 200 | 旧 refresh 一次性（再用 401 `INVALID_REFRESH_TOKEN`） |
| `POST /auth/logout` | 204 | `token_version` 递增；旧 access 在剩余 TTL 内仍可用（无 `jti`） |
| `POST /auth/password` | 204 | 旧 refresh 失效；旧 access 因 `ver` 不匹配 → 401 `UNAUTHENTICATED` |
| `GET /me` | 200 | 无 `password_hash` / `token_version`；`last_login_at` 为 `null` 或 RFC3339 |
| 过期 access / 弱密码 / 截断 JSON | 401 / 400 / 400 | `TOKEN_EXPIRED`；`INVALID_ARGUMENT` + `details.fields[]`；`details.reason=truncated_json` |

### 4.2 代表性响应（400 错误信封）

```json
{
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "请求参数不合法",
    "details": { "fields": [{ "field": "password", "reason": "too_weak" }] },
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "retryable": false
  }
}
```

### 4.3 关键取舍与坑

| 事项 | 为什么 / 根因 | 留下的防线 |
| --- | --- | --- |
| `ver` 不匹配回 `UNAUTHENTICATED` 而非 `TOKEN_EXPIRED` | 客户端见 `TOKEN_EXPIRED` 会静默刷新，而刷回来的还是同一个已失效版本 → 必然再 401 → 死循环 | 错误码语义写进契约测试 |
| `token_version` 缓存失效曾写成 `Set(key,"0",0)` | `TTL=0` 在 Redis 里是**永不过期**，脏值 `0` 与任何真实版本都不等 → 该用户**永久 401** | 改 `DEL`；递增版本后必须清缓存（否则「改密码踢下线」要等一个 TTL 才生效） |
| `httpx.Fail` 起初用 `slog.Default()` | 下游包拿不到启动时构造的 logger，错误日志脱离主日志流（缺 `service`/`version` 字段） | logger 放进 context（`logx.WithLogger`），`logx.From(ctx,nil)` 优先取 context |
| 截断 JSON 曾被报成 `empty_body` | gin 的 decoder 对 `{"email":` 返回 `io.ErrUnexpectedEOF`，被与 `io.EOF` 一起映射 | 拆成 `empty_body` / `truncated_json` / `malformed_json` 三种 reason |
| 批量改名用 `\bUser\b` | 词边界正则不认识「标识符还是字面量」，产出 `TableUser="userPO"`——**编译、单测全过**，运行时查不存在的表 | 改完反向 grep `"[A-Za-z_]*PO"` |
| `/health/ready` 不检查 AI 可达性；Redis 不可用只告警 | AI 抖 → 就绪探针摘掉全部网关 → 全体不可用，把局部故障放大成全局故障（当前还没编排层，见 §11）；权威数据在 MySQL | ready 只看 MySQL + 表 + Redis 连通；Redis 为多实例配额精度留告警 |
| 不用 `gin.Default()`、关 `RedirectTrailingSlash`、`RealIP` 取 XFF 右起第 N 个 | 默认 Logger 往 stdout 打非结构化文本，与 slog 的 JSON 流混流；自动 301 会让 `POST` 变成 `GET`；取 XFF 首值等于让调用方填个 IP 就绕过按 IP 限流 | 自建 Engine 装配；`TRUSTED_PROXY_COUNT` 显式配置；`http_wiring_test.go` 走真实 `NewEngine` |
| 脚本侧取 4xx 响应体 | PS 5.1 的 `GetResponseStream()` 已被 `Invoke-WebRequest` 消费，再读是空串 → 所有 `error.code` 断言假失败（首轮 19 个 FAIL 全源于此） | 统一用 `$_.ErrorDetails.Message` |
| 错误码名不能凭印象写 | 会造出不存在的 `VALIDATION_ERROR` / `WEAK_PASSWORD` | `pkg/errs/codes_test.go` 把契约表**双向**比对（多一个、漏一个都 FAIL） |
| 不能断言「刷新后 access 字节不同」 | 无 `jti`、`exp` 为秒级，同一秒签发必然相同 —— 设计如此 | 改为断言「旧 access 仍有效」 |

## 5. M2 · 会话与消息闭环

**结论**：`curl_stage2.ps1` **198 项断言全通过**（文档记录，2026-09-29；M3 接入编排后按新语义重跑）。接口 11 条；`Idempotency` 中间件只挂 `POST /conversations` 与 `POST /conversations/{id}/messages`。

### 5.1 输入 → 期望状态码 → 关键字段

### 5.3 关键取舍与坑

| 事项 | 为什么 / 根因 | 留下的防线 |
| --- | --- | --- |
| 先写 user 消息、再调 AI（顺序不可换） | AI 失败时提问仍在台账里；反过来写，失败路径上没有任何记录能证明用户提过问 | 重发由幂等键去重（docs/02-§7） |
| `503` 也要被幂等记录记住 | 否则重试会在台账里多一条重复提问 | 幂等做成「响应缓冲中间件」，而不是各 handler 写一遍 |
| 原生 SQL 里写着 `conversationPO` | M1 的改名修复只覆盖了表名常量，手写 SQL 字符串没被覆盖：**编译、类型、单测全绿**，连上 MySQL 才报 `Table 'xxx.conversationPO' doesn't exist` | 表名一律 `quoteIdent(TableXxx)`；`internal/data/sqlguard_test.go` 用 **AST** 扫字符串字面量（grep 会误报注释与 `toConversationPO`，假阳性多了守卫就没人看），另配「必须判违规 / 不得误报」两条用例防「永远绿」 |
| `engine.Use(IdempotencyKey())` 写在 `engine.Group(...)` 之后 | gin 的 `Group()` 在调用那一刻就拷走中间件链，之后 `Use` 不会补进去 → 幂等读到空键、**静默放行**。本次 15 个失败里 12 个是它（`/api/v1/conversations` 的 handler 数 11→12） | `http_wiring_test.go` 用真实 `NewEngine` 断言可观测效果 —— 手工拼链的测试结构上不可能发现「引擎没接上」 |
| `response_body` 空体写不进 MySQL | 列是 `json NOT NULL`，空串不是合法 JSON 文档 → `ERROR 3140`；失败只发生在 `Remember`，响应早已写回客户端，现象是「接口正常、重试却重新执行」 | 空体编码成 JSON 字面量 `null`；代价（body 恰为 `null` 时不可区分）由测试钉住 |
| 该 JSON 列读写两侧都会规范化文档 | 键按「键长 + 字节序」重排并补空格：写入 `{"seq":3,"a":1}` 读回 `{"a": 1, "seq": 3}`；数值无损 | 回放承诺语义等价：验收脚本改**深度比较**（空容器额外发 `=<obj:N>`/`=<arr:N>` 标记，只比叶子会让 `[]` 与 `{}` 相等），比较器自带 12 条自检随脚本跑 |
| 响应缓冲中间件把 panic 后的 500 一起吞掉 | 还原 writer 的语句紧跟在 `c.Next()` 后，panic 时直接掀到外层 `Recovery`，那行不执行 → 客户端拿到 **200 + 空响应体** | 还原改成 `defer`；panic 的 500 **不进**幂等快照（同键重试会真的再执行一次，已由测试钉住） |
| `Update` 的 `RowsAffected=0` 被当成「不存在」 | MySQL 对「设成同一个值」返回 0 行 → 取消归档已 active 的会话误报 404 | 0 行时再查一次可见性 |
| 游标分页 / `seq` 排序 | MySQL 里 `NULL < 'x'` 恒为 NULL，「还没有消息的会话」会被整段跳过（静默漏记录）；Windows 的 `time.Now()` 粒度约 15.6ms，同毫秒两条消息按时间排序会退化成随机 | 必须写两条 NULL 分支；`MessageRepo.Append` 用 `LAST_INSERT_ID(expr)` 把「分配 seq + 插入」合成一个方法（连接级，必须同事务，`biz` 因此不用拿事务句柄） |
| `PATCH` 不提供 `MarshalJSON` | 补上会把「未出现」与「显式 null」一起写回 `null`；幂等指纹需要原始字节 | 需要原样请求体的地方一律用 `[]byte` |

### 7.1 输入 / 场景 → 期望 → 关键字段与实测

### 7.3 关键取舍与坑

| 事项 | 为什么 / 根因 | 留下的防线 |
| --- | --- | --- |
| 复杂度全收在 `biz`，传输层只会「渲染 + 写」 | `pump` 自己 `select` 六件事（等事件 / 心跳 / 首字节 / 空闲 / 总超时 / 进程退出 / 请求取消），只有第一件与上游有关；放进传输层，「超时」就退化成连接级细节，而它其实是业务策略 | `internal/biz/message_stream.go` 的累积器是纯数据结构（无 logger、无 ctx、只注入时钟） |
| `gatewayStreamError` 曾把「是哪个超时」丢了 | 三个超时同码（`AI_TIMEOUT`），收尾时重新合成裸错误，于是「该调 `AI_FIRST_BYTE_TIMEOUT_SECONDS` 还是 `AI_TOTAL_TIMEOUT_SECONDS`」无从判断 | 码相同时优先返回 `loopErr` 保留 `WithDetail`，三个 `reason` 各钉一条用例。**错误码与细节是一体的** |
| 零事件的失败会落一条空白 assistant 消息 | gRPC server-streaming 里「第一个 `yield` 之前 abort」表现为零事件 + 非 OK 状态（`ChatStream()` 仍返回 nil error，错误在第一次 `Recv` 才到），于是 `finishStream` 照样 `Append` 空正文；非流式与 HTTP 降级路径都不会 | `hasContent()`（正文/引用/工具/用量/`done`/`error` 任一存在）+ 落库前早退，配一对对照用例 |
| 一个「我以为的缺陷」被证伪 | 注释称 `resetTimer` 的 drain 必不可少；实测 Go 1.23 起 `Timer.Reset` 已无陈旧值，且受 `go.mod` 的 `go` 指令门控 | 注释改写为「当前工具链下冗余，只作将来降 `go` 指令的安全网」；补真正可证伪的 `TestStreamSendIdleTimerIsResetByEachEvent`。**证伪脚本对旧测试报 `NOT-FALSIFIED`（源码改坏后它依然绿）比没测试更危险** |
| 测试写法三个坑 | 假 gRPC server 不能在**每一帧之前**都 sleep（首帧早到就观察不到，延迟只能加在帧与帧之间）；`io.EOF` 必须不算错误（否则每次正常答完都判成 `partial`）；客户端断开时 user 消息早已落库、`ctx.Err()` 是 `nil` | 断言价值在**第二条**（assistant）落库的 `ctx.Err()==nil` —— 这是 `WithoutCancel` 真生效的唯一可证伪证据 |
| 每帧重置写超时（`http.NewResponseController` → `SetWriteDeadline`，10s） | `http.Server.WriteTimeout` 会误杀正常长响应；而「客户端不读也不断开」的一个连接能永久钉住一条 goroutine + 一个上游连接 | gin v1.11 的 `responseWriter` 实现了 `Unwrap()`，链能通到真连接 |
| 未知事件透传、非法 JSON 包成 JSON 字符串、不映射 `ping` | 直接透出非法 JSON 会让客户端**整条流**中断，「丢一帧」是可控的；`ping` 是 docs/04-§2.3 映射表里「不映射」那一栏，包成 `unknown` 会让客户端收到两路心跳 | `http_stream_test.go` 覆盖解码（CRLF / 多行 `data:` / 前导空 `data:` / 无空行结尾 / 超长行） |
| 「首 token 增量」怎么量 | 不能直接比首 token 时刻：含模型 TTFT，抖动远大于 30ms（实测两次中位差 **-30.6ms** 与 **-191.4ms**，符号都会翻）。AI 侧 `ChatService.stream_prepared` 是**先 yield meta 再调模型** | `增量 ≈ 首帧(经网关) − 首帧(直连)`；`-Runs 4` 串行交替采样、每轮用**全新会话**（否则历史回灌把 prompt 越拉越长）；同时打中位数与最小值 |
| 与 docs/04-§4.2「字节级一致」的偏差 | `meta` 的 `conversation_id` / `message_id` **必须**换成网关自己的值（转发 AI 的会让下一轮「AI 忽然失忆」，拿 AI 的 `message_id` 去 `GET /messages/{id}` 还会 404）；网关可能**追加** `gw_degraded` / `gw_persist_error` | 采用 01-§8 的 `AC-ORCH-03` 口径（事件名序列与顺序一致、`data` 语义一致），写进 proto 注释，并由三条断言钉住：帧内无 `\r`、帧格式两行、事件顺序单调不回头 |

### 8.3 关键取舍与坑

| 事项 | 为什么 / 根因 | 留下的防线 |
| --- | --- | --- |
| `used` 的权威只在网关，AI 只上报 `usage`（接缝 J7） | 扣减发生在调用**前**：事后回滚在「上游超时但实际执行了」时必然漏扣，而预扣 + 回滚最坏是多扣一次后补回，可对账收敛 | `Reserve` 返回 `Reservation`，`Rollback(res)` 幂等（同一快照回滚两次只生效一次） |
| Lua 脚本返回值形状不同 | `reserveScript` 返回表、`addScript` 返回标量，而 `eval()` 只按表解析 → `Add` 永远报错 → 配额计数器**永久**退到进程内 → 第 2 条消息被放行 | 拆 `evalNumbers` / `evalNumber`；`scripts_guard_test.go` 用 AST 把「脚本 → helper」钉死 |
| 限流把裸邮箱当桶 id | `@` 不在 Redis key 的字符白名单 `^[A-Za-z0-9_.-]{1,128}$` 内 → 每次决策都失败并降级成进程内计数，多实例下等于没有账号维度限流 | `SHA256Hex(NormalizeEmail(email))[:16]`，**刻意不加 `acct:` 前缀**（冒号同样在白名单外）；白名单在 middleware **另存一份**，免得放宽容错时守卫跟着放宽 |
| 熔断首次状态跃迁自死锁 | `logf` 在持 `b.mu` 时调 `Snapshot()`（同一把锁，不可重入）→ 第 10 次失败把熔断卡死：之后每个请求卡到客户端超时，`state` 已是 2 但 `result="rejected"` 恒 0，**一行日志都没有 —— 卡住的正是写日志那一步**（物证：`elapsed_ms=120031,120014` 且 `status=0`） | 各 `xxxLocked()` 返回 `circuitEvent`，`emit` 严格在解锁后；`circuit_test.go` 带 2s 看门狗（死锁变成具名失败而不是十分钟 `test timed out`），把日志调用塞回去立刻报错 |
| 断连后配额可被稳定绕过 | `commit` 用**请求的 ctx** 做 `Counter.Add` 与 `insertUsage`，而结清发生在流结束之后、客户端已断连 → 计数与明细一起失败，只留一条 WARN。同文件的 `rollback` 反而已经用了 `WithoutCancel` | `commit` 里 `WithoutCancel` + 5s 上限（去掉取消信号会连带去掉 deadline）；守卫用「记录调用时 ctx 状态」的替身。**「收尾必须无视取消」要成对检查** |
| `-UploadMB` 默认 8MB 而不是 49MB | `AC-ORCH-05` 真正有分辨力的是**相对**判据（RSS 增量 < 文件体积）：流式实现读 8MB 与 49MB 增量都是 0.4MB 上下，非流式是 +文件体积，8MB 时余量仍有 20 倍。做大只是把分母变大，却会真的把 AI 拖死：49MB → 切出 **40,475 片**（被 `MAX_DOC_CHUNKS=10000` 截断）→ CPU 向量化 → `/health` 十数分钟不应答 | 保留「误差 < 1MB」断言：`-UploadMB` 曾因**按字符而非字节**比大小而失效（传 8 实际发了 19.19MB） |
| 上面那条的口径修正（2026-09-30） | 当时把 `/health` 不应答归因于「跑在事件循环里」，与当前代码不符：解析/切分/哈希都已 `await asyncio.to_thread(...)`，索引在独立 worker 进程 | 再出现「`/health` 不应答」**先查进程/部署状态**（worker 是否在跑、是否同版本）；核对记录见 [`09-优化清单与实测记录`](./09-优化清单与实测记录.md) §3.4（UP-04） |
| 辅助实例用 `-NoNewWindow` 起 | 子进程与调用者共用控制台，终端标签页被回收会变成 `CTRL_CLOSE_EVENT` 送到实例 → 整棵树消失，而 stage5 的 A/B 实例还活着（「谁和终端共用控制台」正好是判据） | 改 `-WindowStyle Hidden`，长验收改「脱钩启动 + 轮询输出文件」 |
| `GET /documents/{id}/download` → 302；`AC-ORCH-12` 实机 `SIGTERM` | AI 侧没有下载路由、`DocumentOut` 也没有 presigned URL 字段 —— **没有可重定向的目标**；Windows 不提供 `SIGTERM` | 前者不做（要做须先扩两侧契约）；后者归容器化部署环节，**当前未做**（§11） |

### 9.4 一次性跑完全套（`run_all_stages.ps1`）

六条脚本**不是顺序无关的**。「A 全绿 / B 全红」里有一部分根本不是产品缺陷，而是脚本之间通过共享全局状态互相污染。汇总脚本用三层手段处理：

| 层 | 手段 | 为什么必须这样 |
| --- | --- | --- |
| ① 按实例隔离 | 阶段实例 A（18085/9121）放宽限流 + 配额；限流实例 B（18086/9122）**全走生产默认** | M1–M4/M6 从不断言限流与配额拦截，却会被它们打死；M5 恰恰**只**断言这两件事 |
| ② 等窗口过期 | M5 开跑前「探一次坏登录，看还 429 吗」判断 `login_ip` 窗口是否翻过（最多 75s） | 限流桶按 IP 存 Redis ⇒**换实例换不出一份新配额** |
| ③ 等 AI 排空 | 读 `/health` 的 `checks.ai_platform.latency_ms`，连续 3 次 < 500ms 才开跑 | 上一轮（尤其 8MB 上传）留下后台向量化，整机慢 2~3 倍，M4 的时序断言会假红 |

两套档案必须**先清空再覆盖**（`Start-Process` 继承本进程环境块，没有 `-Environment`，不清就串味）。跑这套时另修掉 7 处问题（后 3 处来自 2026-10-01 全栈轮，最后一条在 Go 单测里，不是脚本）：

| 问题 | 根因 | 修法 / 判据 |
| --- | --- | --- |
| `curl_stage5.ps1` 反复 OOM（数据对、断言全过，只有内存爆） | `$bytes[0..$cut]` 对 `byte[]` 求范围返回 `Object[]`，每个字节被装箱（约 **77 倍**放大）：`New-TextBody(8MB)` 时 RSS 740MB（+652），再叠 multipart 到 849MB | `[byte[]]::new($len)` + `[System.Array]::Copy`；加 3 条类型/取值断言（`正文是 byte[]`、`元素类型是 Byte`、`造 body 增量 < 预算`） |
| 两个「按用户/按 IP 累计」的桶跨轮次污染，表象都是 429 | `code=RATE_LIMITED`：`MSG_RATE_PER_MINUTE=20` 而 M2 发了 23 条；`code=QUOTA_EXCEEDED`：free 档 `chat_requests=100/日`，固定 `user_id` 的日额度按自然日累计（实测实例 A 日志 16 条） | 两套档案，A 给足、B 留空。判据：**429 出现在一条从不提 429 的脚本里，就是污染** |
| `stage4` 的 30ms 断言套错了对象 | 该数字出自 `AC-NFR-01` 的**纯查询接口** `GET /conversations`，却被套到 SSE 首帧：首帧前必须同步完成 `GetOwned` → 配额预扣 → `Append` → `applyAutoTitle` → `recentHistory`，共 6~8 条 SQL。实测单条 `elapsed_ms` 平均 8.9ms、最长 65.2ms，连 `SELECT LAST_INSERT_ID()` 平均都要 5.1ms（`SkipDefaultTransaction:false`，每条写 = BEGIN+语句+COMMIT 三次往返）；`mysql.exe` 跑 10 条与 200 条 `SELECT 1` 都是 ~1090ms（**斜率 ≈ 0**）⇒ 慢的是本机回环往返（1~1.7ms/次） | delta 降为 INFO；补 `AC-NFR-01` 原文口径（200 次 `GET /conversations` 判中位：实测中位 20.9ms、P95 87ms、最大 368.2ms —— 共享开发机上 P95 的方差比要测的量还大） |
| `S6：断连后 partial ≤1s` 与文档不一致 | 1s 取自 01-S6「网关 1s 内取消上游」，被套到「partial 行可见」上，而 03 的 `REQ-CONV-006` 对落库**没给时限**：docs 记录 23.5/30.2ms，本机对真实模型实测 **1705ms / 2862.6ms**，网关日志显示该请求整体 4420ms 才结束 | 分辨需要「AI 侧出现 canceled 的时刻」，即 AI 侧指标缺口；在此之前脚本按能测准的要求判（partial 必须出现且逐项校验），实际延迟记 INFO |
| `curl_stage5.ps1` 的 RSS 采样把端口写死成 18080 | 单跑正常；被 `run_all_stages.ps1` 以 18086 调用时**拿不到进程**，`AC-ORCH-05` 两条判据降级成 SKIP —— 症状只是「M5 少 2 条 PASS、多 1 条 SKIP」，看着像断言数波动，实际是判据没跑 | 从 `-BaseUrl` 派生 `$MainPort` |
| `Start-RssSampler` 的冷启动竞态 | `Start-Job` 返回时作业还没被调度，而采样窗口只有上传那几秒 ⇒ 偶发在首次探测前就收到停止信号、返回 `-1`，又变成 SKIP：同一份代码上一轮绿、下一轮 SKIP | 加握手：作业探测到端口后写握手文件，主线程等握手再上传 |
| `internal/data/mysql/roundtrip_live_test.go` 预热 `QueryContext` 丢弃 `*sql.Rows` 且未 Close | 同一个 `*sql.Conn` 上写锁被永久占住，用例**挂死 11 分钟被 kill**（日志只有 `busy buffer`），包耗时被记成 36254s | 显式 `Close()`；另加 90s 看门狗，超时即 `sqlDB.Close()` |

修完后的两轮结果（均为文档记录）：

| 轮次 | 结果 | 备注 |
| --- | --- | --- |
| 2026-09-30（只有网关） | **474 PASS / 0 FAIL / 1 SKIP**（M1 99、M2 198、M3 29、M4 51、M5 40、M6 57） | 该轮 AI 侧走 `AI_GRPC_ENABLED=false` 的 HTTP 兜底路径 |
| 2026-10-01（全栈） | **477 PASS / 0 FAIL / 1 SKIP**（M5 40 → 43） | 新增 3 条 UP-01 端到端断言；`AC-ORCH-05` 两条判据第一次真正跑起来 |

- 那条 SKIP 是 M6「干净实例」组里需要 `-AILogPath` 的环境相关项，脚本设计上允许。
- 三层隔离的作用能在结果里对上：M2 由 **187/11 → 198/0**（那 11 条是 `QUOTA_EXCEEDED`，不是台账问题）；M5 **40/0** 跑在全生产默认的实例 B 上 —— 如果只放宽实例 A 而没留默认实例，M5 会变成「什么都拦不住」的假绿。
- 全栈轮 M5 耗时 199s（原 34s）**不是回归**：每个 8MB 用例在 AI 侧留下 1 万片 CPU 向量化任务（`TASK_RUNNER=inline`、`EMBEDDING_DEVICE=cpu`），连跑几次互相抢 CPU；跑前先取消遗留的 `document_ingest` 任务。

## 11. 与设计的偏差、未实现项、已知缺陷

| 项 | 设计口径 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 向量库 | Qdrant | **Milvus**（HNSW/COSINE + 标量倒排） | 生态与 `langchain-milvus` 集成更顺，本机已验证 |
| 内部通信 | gRPC | `Chat` / `ChatStream` 走 **gRPC**，其余 **HTTP 透传**（SSE 不进 gRPC） | 少一层 proto 维护；SSE 天然适合流式透传，取消可用连接断开表达 |

| 微服务拆分 | User / Conversation / Task 三个服务 | Go 侧**单进程多模块** | 三者共享同一 MySQL 事务边界，拆进程会引入分布式事务而无收益 |
| 服务发现 | Nacos | **没有实现**：配置字段在（`NACOS_ADDR` 等），无 SDK、无注册逻辑；`AI_DISCOVERY_ENABLED=false` 直连 `AI_PLATFORM_GRPC_TARGET` | 单实例直连不需要；要负载均衡再补 |
| Agent 编排 | LangGraph 状态图 | **自研 Agent Loop**（`app/agent/loop.py`，`app/main.py` 装配）；LangGraph 状态图是设计初期的备选，最终未落地，仓库内无节点代码 | 护栅、轨迹、降级原因都可机械断言；设计初期考虑、最终未采用 |
| Go 测试依赖 | README 曾列 `testify` + `testcontainers-go` | `go.mod` 里**都没有**；`validator` 只是 gin 的间接依赖、项目代码 0 处引用 | 单测用标准库 + 替身即可；集成用 env-gated 的 `*_live_test.go`（如 `GW_LIVE_REDIS`） |
| CI / K8s | 设计目标 | **都没有**：仓库只有 Docker Compose（本地基础设施 + 可观测栈），没有 `.github/`、没有 Deployment/Service 清单 | 部署形态是设计目标，不是既成事实；`AC-ORCH-12` 的实机 `SIGTERM` 因此也缺席 |
| OTel 跨服务 trace | 两条链路在观测平台拼成一条 | 网关侧的**导出与传播已就位**，但没有 collector 接收（`OTEL_EXPORTER_OTLP_ENDPOINT` 默认 `localhost:4317` 无人监听 ⇒ span 被丢弃且不报错）；`OTEL_ENABLED` 代码默认 true、`.env.example` 里 false | 需要部署侧多一个组件 |
| 审计查询 / 记忆 / 工具 / MCP | — | 审计只落库，**没有** `GET /audit-logs`（docs/02 未定义该端点）；记忆、工具、MCP 网关只做透传 | 保持单一职责 |

**已知长期缺陷**：长驻的 Python gRPC 进程数小时后 `Chat` 全退化为 `503`（Python 直连探测同样失败，可排除网关），**重启即恢复**；根因未定位，运维按定期重启兜底（§6.3）。
