### 1.1 为什么 `httpx` 在 `pkg/` 而不在 `internal/`

判据是「有没有本服务的业务语义」，不是「名字像不像工具」：

- `httpx` 只依赖 `pkg/errs` + `pkg/logx` + gin，**不认识** `biz`/`conf`/`data`。
  它和已经在 `pkg/` 里的 `errs` 是同一层：契约适配层。
- 它当初就是**刻意不 import `middleware`** 的（直接读 gin key `gw.trace_id`/
  `gw.failed` 取 trace id），所以搬进 `pkg/` 不会成环。
- 真正的毛病是原先 `internal/` 里**混放了两种东西**：`conf/data/biz/service/server`
  是本服务的层，`httpx` 不是。

它不是「对 JSON 的包装」：它是**唯一允许写 4xx/5xx 的出口**，因此承载了
信封契约（docs/02-§2.2）、429 的 `Retry-After`、4xx=INFO / 5xx=ERROR 的日志分级。

### 1.2 为什么 `data` 按引擎分而不是按聚合分

按聚合分（`user/`、`conversation/`、`message/` 各一个目录）在这个仓库里是错的：

- 每个聚合**只有 1 个文件**，拆进独立目录只是仪式感，没有减少任何耦合；
- `model.go` 把 8 张表放一起是**故意的** —— `user_id` 一律 `VARCHAR(64)`、
  时间一律 `DATETIME(3)` 存 UTC 这类跨表约定，只有放一起才能一眼核对；
  拆成 8 个目录就再也看不出「哪张表不一致」。

按引擎分则正好切在 docs/04-§9 那条最要紧的边界上：
**MySQL 是权威台账，Redis 只是加速器**。这条边界是「降级行为是否允许」的判据，
值得在目录上体现。两个子包各自自足（各含自己的连接构造），且
`data/redis` → `data/mysql` 是**单向**依赖，不成环。

因此层次是：`internal/data` 放**仓储文件**（每个聚合一个，直接坐在 `data.Data` 上），
`internal/data/{mysql,redis}` 放**引擎**。引擎层只知道连接/事务/驱动细节，
不认识任何表；仓储层知道 SQL，不认识 gin。这样「换驱动」与「换表结构」是两件独立的事。

### 1.3 分层规则

**分层规则**（违反即返工）：

- 依赖方向**单向向下**：`cmd/server → server → service → biz → pkg/*`，
  `data → biz`。**`biz` MUST NOT import `data`**（规范 §四）。
- 仓储**接口归 `biz`、实现归 `data`**（规范 §六）：`biz` 定义 `UserRepo` 等接口，
  `data` 用小写类型实现并只导出 `NewXxxRepo(*Data) biz.XxxRepo` 构造函数。
  倒置这一条不是为了好看 —— 若 `biz` 反向依赖 `data`，同一份业务规则会在 HTTP 入口
  与（M3 起的）gRPC 入口各写一遍，且换存储要改业务代码。
- `biz` MUST NOT import `gin` / `gorm` / `redis`；`service` MUST NOT import `data`
  （连驱动类型都不该出现）。二者合计的效果：`biz` 的依赖只有 `pkg/*`。
- `service` MUST NOT 写业务判断。它只做「绑定参数 → 调 biz → 映射错误 → 写响应」，
  以及 `Biz 结果 → Response DTO`（规范 §三.2）。
- 4xx/5xx **只能**经 `httpx.Fail` 写出。绕过它就会出现信封字段缺失的响应
  （客户端按 `error.code` 分支时落到 default）。
- `data/redis` MUST NOT 成为业务判据。它挂了只能让鉴权多一次 SQL、配额精度下降，
  不能让请求失败（docs/04-§9）。

### 1.4 与 `代码生成规范.md` 的对应（2026-09-29 按规范重构）

规范 §四要求依赖**单向向下**（`service → biz → data`），即 `biz` 不得 import `data`。
M1 第一版恰好是反的：`biz` 为了拿到仓储而 import `data`，`biz` 因此被迫认识
GORM 的实体类型。这次做的是**依赖倒置**，不是搬文件。

| 规范条款 | 落地方式 |
| --- | --- |
| §六 接口归 `biz`、实现归 `data` | `biz` 定义 `UserRepo` / `TokenRepo` / `AuditRepo` / `TokenVersionChecker` / `VersionInvalidator`；`data` 小写类型实现，只导出构造函数 |
| §四 单向依赖 | `go list` 实测：`biz` 只依赖 `pkg/*`；`service` 只依赖 `biz`/`conf`/`server/middleware`；`data` → `biz` 向下 |
| §三.2 DTO 归 service | `UserResponse` / `TokenResponse` 从 `data` 挪到 `service/dto.go`；`PasswordHash` / `TokenVersion` 只存在于 DO，物理上无法泄漏 |
| §三.5 中间件归 server | `internal/middleware` → `internal/server/middleware` |
| §五.3 禁止按类型命名文件 | 删除 `models.go` / `repositories.go` 式命名：`model.go`（PO + 列约定）、`json.go`（列的自定义类型），其余每个聚合一个业务文件 |
| §一.3 / §一.5 不为架构而加层 | PO/DO 拆分只用于**真的跨 biz↔data 的 3 个类型**（`User` / `RefreshToken` / `AuditLog`）；`Conversation` / `Message` / `Quota` / `Idem` 在 M2 有 biz 服务之前保持 PO |

**刻意偏离规范的地方**（有理由，不是遗漏）：

- **`api/` + `*.proto` + 生成代码** —— **2026-09-29 已落地，本条从「偏离」改为「已对齐」**：
  M3 引入 Kratos 后，`proto/aiplatform/v1/chat.proto` 是 `Chat` 的契约真源，
  `tools/gen_proto.ps1` 一次生成 Go 侧 `api/aiplatform/v1/{chat.pb.go,chat_grpc.pb.go}`
  与 Python 侧 `app/grpc/*_pb2*.py`。仍然偏离的**只剩**一点：**不用 kratos 的 HTTP 注解**，
  对外 HTTP 仍走 Gin —— `Chat`/`ChatStream` 之外的接口都按 [04-§2.1](../docs/04-AI服务编排与网关.md)
  以 OpenAPI 为真源透传，给它们再生成一套 kratos HTTP 路由只会多一份要同步的契约。
  所以 `api/` 里**只有 gRPC 生成物，没有 `*_http.pb.go`**。
- **`configs/config.yaml`**：现在是 `.env` + `ENV_FILE`，加载与校验都已可用
  （且「`.env` 存在但解析失败即退出」这条行为有测试意义）。换 YAML 要重写一遍加载器，
  当前收益为零。
- **`third_party/` / `test/` / `wire` / `Makefile` / `Dockerfile`**：分别对应
  「无 protobuf 第三方依赖」「Go 单测按惯例与被测代码同目录」「装配只有 7 步线性代码，
  `wire` 只是多一步生成」「本机没有 `make`，命令直接写在 §2 里」「部署在 M6」。
- **`pkg/`**：规范目录树里没有这一层，但按项目负责人明确要求保留
  （`httpx` 这类契约适配层既不属于某个业务层，也不该混进 `internal/`，理由见 §1.1）。

**证据**：`go build ./...` / `go vet ./...` / `go test ./...` 全绿、`gofmt -l .` 无输出、
`tools/curl_stage1.ps1` 仍 **99/99** —— 纯结构重构，对外行为一个字节都没变。

## 2. 本地运行

### 2.1 准备

```powershell
# 1) 建库建表（顺序不能反：AI 侧 001 含共享表 idempotency_record / audit_log）
mysql --default-character-set=utf8mb4 -u root -p -e "source ../ai-platform/deploy/mysql/001_init_schema.sql"
mysql --default-character-set=utf8mb4 -u root -p -e "source deploy/mysql/001_gateway_tables.sql"
mysql --default-character-set=utf8mb4 -u root -p -e "source deploy/mysql/002_test_accounts.sql"

# 2) 配置
Copy-Item .env.example .env   # 然后填 MYSQL_DSN / JWT_SECRET

# 3) 编译
go build -o bin/server.exe ./cmd/server
```

> **工具链基线：`go.mod` 的 `go` 指令钉在 `1.24.0`**
>
> 原因是「本机安装的是 Go 1.24.8」这个事实，而不是某个需求。之前 `go` 指令是 `1.26.0`
> （`go mod init` 当时用的是自动下载下来的新工具链），后果是：`GOTOOLCHAIN=auto`（默认值）
> 会在**任何一次构建前先联网下载 go1.26.0** —— 一台新克隆的机器在能编译第一个文件之前
> 先要能上外网。
>
> 把 `go` 改回 `1.24.0` 不是只改一行：模块的 `go` 指令是**下限**，只要有一个依赖声明了
> 更高的版本，构建就会失败。实测被卡住的正好 5 个（`go list -m -json <mod>@<ver>` 逐个查出来的）：
>
> | 依赖 | 原版本（声明 go） | 现版本（声明 go） | 为何不能再高 |
> | --- | --- | --- | --- |
> | `golang.org/x/crypto` | v0.57.0（**1.26**）| v0.45.0（1.24）| v0.50/v0.54 → 1.25，v0.56 → 1.26 |
> | `github.com/gin-gonic/gin` | v1.12.0（**1.25**）| v1.11.0（1.23）| v1.12 → 1.25 |
> | `golang.org/x/net` | v0.58.0（1.25）| v0.47.0（1.23）| v0.50/v0.56 → 1.24/1.25 |
> | `golang.org/x/sys` | v0.48.0（**1.26**）| v0.38.0（1.23）| v0.40 → 1.24，v0.46 → 1.25 |
> | `golang.org/x/text` | v0.42.0（**1.26**）| v0.31.0（1.23）| v0.30 → 1.24，v0.35 → 1.25 |
>
> 顺带的好处：`gin v1.11.0` 不再拖入 `go.mongodb.org/mongo-driver/v2`（gin 1.12 为 HTTP/3
> 支持加的），依赖树小了一圈。
>
> **验证「真的不再依赖网络」的方法是关掉代理再构建**（`GOPROXY=off` 同时也会禁掉工具链下载），
> 并且用 `go env GOVERSION` 看默认 `GOTOOLCHAIN=auto` 下解析到哪个工具链：
>
> ```powershell
> go env GOVERSION            # 期望 go1.24.8（改之前是 go1.26.0）
> $env:GOPROXY='off'; $env:GOTOOLCHAIN='local'; $env:GOFLAGS='-mod=readonly'
> go build ./... ; go vet ./...   # 期望 exit 0
> ```
>
> **不要上调 `go` 那一行**：一上调就会把上面整张表重新拉回高版本，`GOTOOLCHAIN=auto`
> 又开始联网下工具链。`go.mod` 里已经写了这段原因。

### 2.2 启动

```powershell
$env:ENV_FILE = "<repo>\ai-platform-go\.env"
.\bin\server.exe
```

> **为什么用 `ENV_FILE`**：`.env` 的默认查找位置是**进程工作目录**。从 IDE、任务、
> 计划任务启动时 cwd 往往不是项目根，于是「`.env` 明明写了却全部走默认值」。
> 这类故障没有任何报错，只会表现为「连的环境不对」。用绝对路径显式指定即可绕开。
>
> 相关：`.env` **存在但解析失败**现在会直接报错退出，不再静默回退默认值 ——
> 静默回退会让「配置写错」表现成「配置没生效」，而默认值通常也能启动，
> 于是带着错配置一路跑下去。

> **本机已知异常：`8080` 无法绑定。** 现象是 `bind: Only one usage of each socket address`，
> 但 `Get-NetTCPConnection -LocalPort 8080 -State Listen`、`tasklist`、
> `netsh http show urlacl` 与 TCP 排除端口段**都查不到任何占用**（实测 8081 / 18080
> 均可正常绑定）。
>
> **2026-09-29 补充：那个「看不见的占用者」确实存在，而且会接客。** 直接把请求打到
> `http://127.0.0.1:8080/` 会拿到一个 **200 + HTML 首页**，打 `/api/v1/auth/register`
> 拿到的是另一个框架的错误信封（`{"code":5000,"message":"404 NOT_FOUND",
> "stackTrace":"org.springframework.web.server.ResponseStatusException..."}`）。
> 也就是说：**在 8080 上有一个监听者，只是本机现有工具都看不见它**。
>
> 后果很阴险：`tools/curl_stage*.ps1` 的 `-BaseUrl` 默认值是 `http://127.0.0.1:8080`，
> 在 8080 上实际跑起来会得到「一屏全红、失败详情指向另一个框架」——看起来像网关
> 被打坏了，实际上是打到了**另一个服务**上。
>
> **2026-09-30 更新（M5）：脚本默认值已改为 18080。** 既然 8080 上确定坐着 Kafka UI，
> 而「默认值踩上去会得到一屏指向另一个框架的假红」，**留着这个默认值只有坏处**。
> `curl_stage1/2.ps1` 的 `-BaseUrl` 默认值已与 stage3/4/5/6 对齐为 `http://127.0.0.1:18080`，
> 于是「不带参数跑」不再需要先读一遍文档。
>
> 保留这条历史记录的原因：它演示了**默认值本身就是一门契约**——一个“当时能跑”的默认值，
> 在环境变化后会变成每个人都得记住的例外。
>
> ```powershell
> $env:HTTP_ADDR = "0.0.0.0:18080"
> .\bin\server.exe
> powershell -ExecutionPolicy Bypass -File tools\curl_stage2.ps1 -BaseUrl http://127.0.0.1:18080
> ```
>
> **不要**因为「换端口能跑」就跳过 §4.5 第 5 条的前置检查：真正常见的失败原因
> 仍然是上一轮的进程没退干净。两者现象一样（都是绑定失败），判定方式不同
> （旧进程能被 `tasklist` 看见，本机这个异常看不见任何东西）。
>
> **2026-09-30 结案：占用者是 `kafka-ui` 容器。** `docker ps` 一眼就能看到
> `kafka-ui  0.0.0.0:8080->8080/tcp`（同一条输出里还有 `ai-platform-redis 6379`、
> `kafka 9092`、`ai-platform-minio 9000/9011`）。所以那个「接客的 200 + HTML 首页」
> 就是 Kafka UI 的页面，`/api/v1/...` 404 信封来自它内嵌的 WebFlux。
>
> **为什么本机工具查不到**：端口是 Docker Desktop 的转发进程（`com.docker.backend` +
> WSL2 NAT）在监听，`Get-NetTCPConnection -LocalPort 8080` 在宿主侧看不到它，
> `netsh` / `tasklist` / TCP 排除端口段自然也都查不到 —— **不是幽灵，是跨了网络命名空间**。
>
> 教训：**「查不到占用者」时先去 `docker ps` 看一眼**。Docker 的端口转发是
> 「宿主看不见监听者、但连接确实被接走」的唯一常见成因，比排除法快得多：
>
> ```powershell
> docker ps --format "{{.Names}} {{.Ports}}"   # 一条命令就能看到谁把 8080/6379/9092 拿走了
> ```

### 2.3 验收

```powershell
# 全量静态检查 + 单测
go build ./... ; go vet ./... ; gofmt -l . ; go test ./...

# 证明不依赖网络（GOPROXY=off 同时禁掉工具链下载）
$env:GOPROXY='off'; $env:GOTOOLCHAIN='local'; $env:GOFLAGS='-mod=readonly'

>
> ```powershell

>   （报 `LOG_FORMAT="console" 不合法`），而现象只是“实例没起来”。
>   `tools/curl_stage5.ps1` / `curl_stage6.ps1` 的启动函数里已经硬写了 `LOG_FORMAT=text`。
> - **AI 侧入库是 CPU 密集的**（`WORKER_CONCURRENCY` / `TaskTimeoutSeconds=1800`）：
>   一次 19MB 上传会切成 10000 片（`MAX_DOC_CHUNKS`）在 CPU 上跑 BGE 向量化，可能持续几十分钟。
>   这段时间内启动 stage5/6 **之前**先确认 AI 还答应（`curl http://127.0.0.1:8000/api/v1/health`）。
>   （2026-09-30 补充：向量化跑在**独立 worker 进程**里，不再与 API 同进程抢事件循环；
>   但**整机 CPU 仍会被占满**，所以「先确认 AI 还答应」这条依然必要。

### 4.2 关键实现决策

| 决策 | 理由 |
| --- | --- |
| **`ver` 不匹配返回 `UNAUTHENTICATED` 而不是 `TOKEN_EXPIRED`** | 客户端看到 `TOKEN_EXPIRED` 会去静默刷新，而刷新回来的新令牌**还是同一个（已失效的）版本** → 必然再次 401 → 死循环。版本不匹配只能重新登录。 |
| **`/health/ready` 不检查 AI 可达性** | AI 挂着时网关仍应接流量（会话、历史、配额都可用）。把 AI 状态算进就绪会造成「AI 抖动 → K8s 摘除全部网关 → 全体不可用」，把局部故障放大成全局故障。 |
| **`/health/ready` 检查「表是否齐全」而不只是「能否连上」** | 「MySQL 连上了」≠「表建对了」。迁移没跑完就接流量，会在第一个业务请求时才暴露，且表现为 500。 |
| **Redis 不可用不阻止启动，只告警** | 权威数据在 MySQL，Redis 只是加速器与计数器。停服带来的可用性损失远大于「缓存不命中」（但配额精度在多实例下会下降，必须显式告警）。 |
| **`ExpiresAt` 秒级、无 `jti`** | 契约（02-§3.2）明确接受。**代价**：同一秒内签发的两个 access token 完全相同；登出后 access 在剩余 TTL 内仍可用，靠 `ver` 解决主要场景。 |
| **不用 `gin.Default()`** | 它的 Logger 往 stdout 打非结构化文本，与 slog 的 JSON 流混在一起，采集侧会解析失败。 |
| **关闭 `RedirectTrailingSlash`** | 自动 301 会让客户端的 `POST` 变成 `GET`（重定向不保留方法），症状极难排查。 |
| **`RealIP` 取 XFF 右起第 N 个** | XFF 是客户端可追加的头。取首值等于让调用方随便填一个 IP 就绕过按 IP 的限流。 |

### 4.3 实现中发现并修掉的缺陷

1. **`token_version` 缓存失效写成了 `Set(key, "0", 0)`**
   - `TTL=0` 在 Redis 里是「**永不过期**」，等于把一个脏值永久写死；
   - 而 `0` 与任何真实版本都不相等 → 该用户被**永久 401**，只能人工清 Key。
   - 改为 `DEL`。同时补上**递增版本后必须清缓存**：缓存里存的是递增**前**的版本，
     而校验规则是「相等才通过」，于是刚被踢下线的旧令牌会因为与缓存值相等而**继续放行**，
     「改密码踢下线」最多要等一个 TTL（10 分钟）才生效。

2. **错误日志脱离了主日志流**
   - `httpx.Fail` 用 `logx.From(ctx, slog.Default())`，输出成
     `2026/09/29 12:56:40 INFO http.rejected ...` —— 那是 stdlib 未配置的 handler：
     没有 `service`/`version` 字段，格式与其它行不一致。
   - 根因是下游包拿不到启动时构造的 logger。修法：把 logger 放进 context
     （`logx.WithLogger`），`logx.From(ctx, nil)` 优先从 context 取。

3. **截断的 JSON 被报成 `empty_body`**
   - gin 的 `json.Decoder` 对 `{"email":` 这类**截断**输入返回 `io.ErrUnexpectedEOF`，
     而代码把它与 `io.EOF` 一起映射成 `empty_body`。
   - 后果：客户端明明发了 9 个字节，服务端回答「没有请求体」，排障方向直接跑偏。
   - 现拆成三种可区分的 `reason`：`empty_body` / `truncated_json` / `malformed_json`。

4. **`RequestID` 命名冲突**：中间件函数与上下文取值函数同名，中间件改名 `WithRequestID`。

### 4.4 验收方法上的三个坑（脚本侧，已修正）

1. **PowerShell 5.1 取 4xx/5xx 响应体的唯一可靠方式**是 `$_.ErrorDetails.Message`。
   `$_.Exception.Response.GetResponseStream()` 已被 `Invoke-WebRequest` 内部消费，
   读到的是空串 → `ConvertFrom-Json` 得 `null` → 所有 `error.code` 断言**假失败**
   （首轮 19 个 FAIL 全部源于此，代码本身没问题）。
2. **错误码名不能凭印象写**。契约是 `INVALID_ARGUMENT`（弱密码/格式错统一用它 +
   `details.fields[]` 指明字段）、`INVALID_CREDENTIALS`（与「用户不存在」同码防枚举）、
   `USER_DISABLED`；**不存在** `VALIDATION_ERROR` / `WEAK_PASSWORD` / `ACCOUNT_DISABLED`。
   为此增加了 `pkg/errs/codes_test.go`：把文档 §4.1 的表逐行抄成期望值并**双向**比对
   （多一个码、漏一个码都 FAIL），避免编码表慢慢漂移出文档。
3. **不能断言「刷新后新 access token 与旧的字节不同」**。契约无 `jti`，`exp`/`iat` 为秒级，
   同一秒内签发必然完全相同 —— 这是**设计如此**（02-§3.1 明确列为有意不做的事）。
   改为断言「旧 access 仍然有效」（`ver` 未变，refresh 不注销 access）。

### 4.5 结构重构（对齐 `代码生成规范.md`）中发现并修掉的缺陷

1. **批量改名用 `\bUser\b` 这种词边界正则，会改到字符串字面量里**。
   于是产出 `TableUser = "userPO"`、`MsgRoleUser = "userPO"` ——
   **编译通过、单测通过**，但运行时会去查 `userPO` 这张不存在的表。
   教训：批量改名必须顺手做一次反向检查（grep `"[A-Za-z_]*PO"` 找字符串常量），
   正则不认识「这里是标识符还是字面量」；这类错误编译器和测试都看不见。
2. **`ErrIdemRace` 被误赋成 `biz.ErrTokenInvalid`**（复制粘贴残留）。幂等键冲突本该映射
   `IDEMPOTENCY_KEY_REUSED`，赋值错误会让它表现成 401。这类「同类型不同语义」的误赋值，
   靠类型检查抓不到，只能靠逐个核对错误码表。
3. **`data` 的驱动错误漏进 `biz`**：倒置后 `biz` 不认识 GORM，`ErrNoRows` 之类必须
   在边界上翻译。现统一为 `biz.ErrNotFound`，由 `data.translate` 单向转换 ——
   好处是 `biz` 里的判断全变成 `errors.Is(err, biz.ErrNotFound)`，与驱动无关。
4. **带中文注释的 `.ps1` 一次性脚本没有 BOM**：PowerShell 5.1 按 GBK 解析，
   报「意外的标记」。这类脚本一律写成纯 ASCII（同一个坑本文档已记录过多次，
   但只在「脚本里有中文」时才复现）。
5. **必须先确认端口空闲再起服务**。上一轮的进程没退干净时，新进程绑定失败，
   而验收脚本会去连**旧进程**，于是「用新代码跑出全绿」是假的。
   起服务前一律 `Get-NetTCPConnection -LocalPort 8080 -State Listen` 确认没有监听。
   本机还存在一个查不到任何占用的 8080 绑定失败异常，处置方式见 §2.2。

### 5.2 关键实现决策

| 决策 | 理由 |
| --- | --- |
| **先写 user 消息、再调 AI**（顺序不可换） | AI 调用失败时用户的提问仍在台账里，不会被「一次失败的调用」顺手丢掉；重发由 `Idempotency-Key` 去重（02-§7）。反过来写的话，失败路径上**没有任何记录**能证明用户提过问。 |
| **M2 的 `Orchestrator` 留 `nil`，落库后返回 `503 AI_UNAVAILABLE`** | 用户消息已落库，此时若返回 200 + 空回答就是**假成功**。如实报 503（`details.reason=orchestrator_not_configured`）让「M2 只做到写台账」这件事在响应里可见，而 M3 只需换上实现、不动接口与协议。**M3 已换上实现（§6）**：同一个接口现在返回 200 + `assistant_message`；503 只剩「AI 真的不可达」这一种成因，而它由 `internal/biz/{ai_proxy,orchestration}_test.go` 覆盖，不再依赖环境。 |
| **`503` 也要被幂等记录记住** | 否则客户端重试会在台账里**多出一条重复提问** —— 正是幂等要防的事。这也解释了为什么幂等必须做成「响应缓冲中间件」而不是在 handler 里各写一遍。 |
| **幂等键用路由模板 `c.FullPath()` 而不是具体路径** | 具体路径会让「同一个键被复用到另一个会话」变成两条互不相关的记录，看不出误用；模板则让正常调用（同键、不同会话）稳定命中 `409 CONFLICT`。 |
| **回放只承诺「状态码 + 响应体」，但显式补 `Content-Type`** | 契约（02-§7）只要求「回放首次响应（含状态码）」。但首次响应头属于**另一个请求**的 header map，不补时 net/http 会嗅探 body 把 `{"id":...}` 判成 `text/plain` —— 客户端的 `res.json()` 只在**重试路径**上失败。`Location` 等其它头不回放（表里没有存响应头的列）。 |
| **归档会话返回 `409 CONVERSATION_ARCHIVED` 而不是 404** | 会话对用户是可见的，说「不存在」会让他以为会话被删了。 |
| **`delete` 不存在的资源返回 404 而不是 204** | 204 会把「这个 id 存在」变成可探测的信息（02-§7），攻击者用一个别人的 id 也能拿到「成功」。 |
| **游标分页必须写两条 NULL 分支** | MySQL 里 `NULL < 'x'` 恒为 NULL，于是「还没有消息的会话」（`last_message_at IS NULL`）会被整段跳过 —— 表现为**翻页时静默漏记录**，不报任何错。 |
| **`Update` 在 0 行受影响时还要再查一次可见性** | MySQL 对「把值设成同一个值」的 UPDATE 返回 `RowsAffected = 0`，把它当成「不存在」会让「取消归档一个已经 active 的会话」误报 404。 |
| **`PATCH` 字段用三态 `PatchValue`，且刻意不提供 `MarshalJSON`** | `model: null` 是**有效**语义（回到全局默认模型），用 `*T` 会把「未出现」和「显式 null」折叠成同一个 nil。反过来补上 `MarshalJSON` 又会把两者一起写回 `null` —— 需要「请求体原样」的地方（幂等指纹）一律用**原始字节**。 |
| **自动标题的条件判断落在 SQL 里**（先读后写不允许） | 并发下「先读后写」会把用户刚手工改过的标题覆盖掉（AC-CONV-04）；SQL 条件（`title = '' AND title_source = 'auto'`）是唯一的原子判据。 |
| **`MessageRepo.Append` 把「分配 seq + 插入」合成一个方法** | `LAST_INSERT_ID(expr)` 是**连接级**的，两条语句必须同连接同事务。拆开就意味着 `biz` 要拿事务句柄 —— 那等于 `biz` 认识了 GORM（规范 §四）。 |
| **`seq` 是排序唯一依据，绝不用 `created_at`** | Windows 上 `time.Now()` 粒度约 15.6ms，同一毫秒内的两条消息按时间排序会退化成**随机**。 |
| **列表 `limit` 越上限报 `INVALID_ARGUMENT` 而不是截断** | 静默截断时客户端以为拿到了全部数据、翻页逻辑因此漏记录，而「请求参数写错」这件事再也没人会发现（REQ-AUTH-010）。 |
| **`List` 先查会话再查消息** | 只靠 JOIN 过滤时，「会话不存在」与「会话没有消息」都返回空列表，而前者按契约必须是 404（软删会话的消息 MUST 一并 404）。 |
| **附件非空即拒绝（400 `not_supported`）** | 静默忽略会让用户以为模型看过那个文件。 |
| **空响应体存成 JSON 字面量 `null`** | `response_body` 是共享表的 `json NOT NULL` 列，空串不是合法 JSON 文档（`ERROR 3140`）—— 写不进去就等于 204 类接口永远记不下幂等，而且失败只发生在 `Remember` 里、对客户端完全不可见。详见 §5.3 第 7 条。 |
| **回放承诺「语义等价」，不承诺「字节相等」** | 同上：`JSON` 列在读写两侧都会规范化文档（键序、空白）。02-§7 要的是「回放首次响应（含状态码）」，JSON 客户端解析后拿到的值完全一致。因此验收脚本对回放体做**深度比较**，而不是字节比较。 |
| **panic 的 500 不进幂等快照** | 那个响应由外层 `Recovery` 生成，此刻缓冲里没有它；把一个「未知错误」当成该键的最终答案钉死 24 小时没有任何好处。代价：同键重试会真的再执行一次（已由 `TestIdempotencyPanicIsNotSwallowedByBuffer` 钉住）。 |

### 5.3 实现中发现并修掉的缺陷

1. **批量改名缺陷的「第二现场」——而且这次编译、单测全都过得去。**

   M1 的 §4.5 已经记录过「词边界正则改到了字符串字面量」，当时的修复是把表名收敛成
   `TableXxx` 常量。但 `conversation.go` / `message.go` 里**手写的原生 SQL 字符串**
   没有被那条修复覆盖，仍然是 PO 类型名：

   - `UPDATE \`conversationPO\` ...`、`SELECT messagePO.* FROM conversationPO`
   - `FROM conversationPO c JOIN ...`、`UPDATE \`messagePO\` SET ...`

   它们**能编译、类型正确、单测通过**，只有连上 MySQL 才报
   `Table 'xxx.conversationPO' doesn't exist` —— 而这恰好是三样里最难在本地复现的那样。
   修法两步：

   - 所有原生 SQL 的表名一律走 `quoteIdent(TableXxx)`（表名只有一处来源）；
   - 新增 `internal/data/sqlguard_test.go`：用 **AST** 扫本包所有**字符串字面量**，
     出现 `xxxPO` 即 FAIL。用 AST 而不是 grep 是因为注释与标识符
     （`toConversationPO`）里出现 PO 名字是合法且常见的，grep 会把它们一起报出来，
     假阳性多了之后这个守卫就没人看了。守卫本身另配两个用例（合成源码必须被判违规、
     合法写法不得误报）——否则它最大的风险是「永远绿」。

2. **`SendMessageInput` 里去找会话 ID**。会话 ID 在 URL 路径上，请求体里没有这个字段。
   若按「从请求体读」实现，会永远读到空串，症状是**每次发送都 404**。
   现 `Send` 的签名把 `conversationID` 显式化（路径参数就是它的唯一来源）。

3. **`conversationPO.Metadata` 的类型是 `JSONRaw`，而服务层要按 map 用**。
   新增 `JSONMap`（并定义清楚 NULL 语义：`Value()` 时 nil 输出 `"{}"`，
   而不是让 `null` 流到契约里 —— 契约规定 `metadata` 是对象）。

4. **`data` 层把「0 行受影响」当成「资源不存在」**。MySQL 对
   「UPDATE 把值设成与原值相同」返回 0，于是归档/取消归档的幂等重放会误报 404。
   修法：0 行时在同一逻辑里再查一次可见性，只有确实查不到才算 404。

5. **`retention.go` 里重复实现了用量明细清理**（与 `QuotaRepo.PurgeRecordsOlderThan`
   是同一句 `DELETE`）。保留期清理只留一处实现 —— 两处各写一遍，
   迟早出现「两处保留期不一致，而两边看起来都对」。

6. **`engine.Use(IdempotencyKey())` 写在 `engine.Group(...)` 之后 → 幂等整体失效。**
   gin 的 `RouterGroup.Group()` 在**调用的那一刻**就把当前中间件链拷贝走了
   （`combineHandlers`），之后 `engine.Use(...)` 不会补到已存在的组上。于是
   两件互相矛盾的事同时成立：路由表里 `/api/v1/...` 确实多了一个 handler，
   而那个 handler 从来没执行过 → `Idempotency` 读到空键，**直接放行**，
   不报错、不打日志、响应完全正常。**这是本次验收里 15 个失败中的 12 个**。

   - 症状形状很特别：所有别的断言组全绿，红的 12 条**全集中在幂等**；
   - 判据：对比启动日志的 handler 数。修复前后 `/api/v1/conversations` 从
     `11 handlers` 变成 `12 handlers`，`/api/v1/health` 从 `9` 变成 `10`
     —— 中间件是否真的进了每一条链，只看**计数**就够了；
   - **教训**：`internal/server/idempotency_test.go` 手工拼中间件链，
     它验证的是「中间件写得对」，结构上**不可能**发现「引擎没接上」。
     因此新增 `internal/server/http_wiring_test.go`：用**真实的 `NewEngine`**
     装配（靠 `Deps.Extra` 注册一条探针路由），断言可观测效果
     （同键第二次请求不重复执行 handler、响应带 `Idempotency-Replayed`）。
     凡「缺失时静默」的中间件，都必须有这样一条引擎级测试。

7. **`response_body` 是 MySQL 原生 `JSON` 列，空响应体写不进去 → 204 类接口永远记不下幂等。**
   该列定义是 `response_body json NOT NULL`（共享表，docs/05-§2.7）。空串
   **不是**合法 JSON 文档，写入直接报
   `ERROR 3140 (22032) Invalid JSON text: "The document is empty."`，已用 mysql 实测。
   失败只发生在 `Remember` 里，而响应**早已写回客户端**，所以现象是
   「接口一切正常、重试却每次都重新执行一遍副作用」，没有任何错误可见
   （幂等表上只会留下自增 ID 的空洞）。

   修法：空体编码成 JSON 字面量 `null`（`data.encodeResponseBody`）。实测 `json NOT NULL`
   列接受 `null`，且 `JSON_TYPE()` 为 NULL、`IS NULL` 为 0 —— 即它是「值为 JSON null」，
   正好与 SQL NULL 区分开。**代价已写进测试**：body 字面量恰好是 `null` 时与空体不可区分
   （`TestEncodeResponseBodyNullLiteralIsIndistinguishableFromEmpty` 把它钉出来，
   而不是留成一条只有读源码才知道的隐式约定）。

   同一个发现牵出第二件事：该列在**读写两侧都会规范化文档**（对象键按「键长 + 字节序」
   重排并递归、`,` `:` 后补空格）。实测同一 body：

   ```
   写入 {"seq":3,"a":1,"b":{"y":2,"x":1}}  →  读回 {"a": 1, "b": {"x": 1, "y": 2}, "seq": 3}
   ```

   所以**回放是语义等价而不是字节相等**（02-§7 要的是「回放首次响应（含状态码）」，
   JSON 客户端解析后拿到的值完全一致）。数值无损（实测 `12345678901234567890` 往返一致）。
   对应的两处修改：

   - 验收脚本 H2b 由「字节相等」改成**深度比较**（`Compare-JsonBody`，递归成
     `path=scalar` 再比集合，且为空容器额外发 `=<obj:N>` / `=<arr:N>` 标记 ——
     只比叶子的话 `kb_ids:[]` 与 `kb_ids:{}` 会被判成相等）；
     该比较器自带 12 条自检断言（`Assert-JsonComparerWorks`）随验收一起跑，
     因为它一旦「恒返回相等」就会把 H2b 变成永久假绿。
   - `internal/server/idempotency_test.go` 里那条「逐字节相等」的断言保留，
     但注释写明它只在**内嵌内存版 store**下成立，真实存储是语义等价。

8. **响应缓冲中间件会把 panic 后的 500 一起吞掉（比不修更危险）。**
   `Idempotency` 把 `c.Writer` 换成缓冲 writer 之后，还原真实 writer 的语句
   紧跟在 `c.Next()` 后面。handler panic 时 `c.Next()` 会把栈**直接掀到最外层的
   `Recovery`**，中间那行一行都不执行 → `Recovery` 的 500 信封被写进缓冲，
   再也不 flush → 客户端拿到 **`200` + 空响应体**。

   已实测确认（临时去掉修复后 `TestIdempotencyPanicIsNotSwallowedByBuffer` 报
   `panic 应变成 500，实际 200`）。修法是把还原改成 `defer`（panic 路径也会执行），
   并在注释里写明这个 defer 是给 panic 路径用的、不是给正常路径用的。

   顺带定的语义：**panic 产生的 500 不进幂等快照**。那个响应由外层 `Recovery` 生成，
   此刻缓冲里没有它；而把一个「未知错误」当成该键的最终答案钉死 24 小时没有任何好处。

### 6.2 验收前置：AI 侧要同时起**两个**进程

### 6.3 关键实现决策

1. **`Chat` 走 gRPC、其余走 HTTP 透传 —— 这是同一条边界，不是两套实现。**
   判据是「有没有流式事件要映射」：`Chat` / `ChatStream` 需要把 AI 的事件映射成显式契约，
   值得一份 proto；KB / 文档 / 任务 / 上下文摘要**没有本土逻辑**，转发即可 ——
   给它们再生成一套 kratos HTTP 路由只会多一份要手工同步的契约（对外契约的真源
   仍然是 docs/02、docs/03 与 Pydantic 模型）。

2. **超时只能有一个来源。** gRPC 客户端的 deadline 由 `biz` 的档位
   （meta 8s / chat 70s / upload 120s）决定，其他地方**一律不许**再叠一层
   （踩过的坑见 §6.4 第 1 条）。规则写成这样是有原因的：两个来源意味着实际生效的是
   `min(两者)`，而**较小那个的来源从错误信息里看不出来**。

3. **错误只翻译一次，出口只有一个。** AI 侧的 `error.code` 原值保留（网关不认识其码表，
   照传），`error.trace_id` 沿用 AI 的值（否则排障时链路在网关这一跳断开），
   HTTP 状态码沿用上游的（只接受 4xx/5xx —— 上游若把一个错误报成 200，照抄会让网关以
   200 + 错误信封回客户端，客户端的解析器会直接崩）。翻译结果一律是 `*errs.AppError`，
   只有 `httpx.Fail` 能把它写成响应。

4. **非信封响应归一化成错误，而不是猜一个领域错误。** AI 返回 5xx + `text/html`
   （网关路由没匹配上、代理超时页等）时，`code` 里**没有**任何可信信息；
   把它映射成某个具体业务错误（比如 `CONTEXT_TOO_LONG`）会让排障从一个错误方向开始。
   现在的做法是保留 `reason`（`non_envelope_status` + 上游状态码）挂到 `details` 上。

5. **trace 上下文只认 W3C `traceparent`；`X-Trace-Id` 是响应头。**
   请求侧塞 `X-Trace-Id` 会被完全忽略（排查时表现为「断言 trace 透传永远看不到自己给的值」）。
   gRPC 侧同理，用 metadata 传 `traceparent`，AI 在 **trailer** 里回 `trace_id`。

6. **透传是字节级的，且路径同名。** 请求体、响应体、`Content-Type`、状态码、
   以及 429 的 `Retry-After` 都原样转发；网关**不解析**上游的业务响应，也不重建错误信封
   （上游的信封已经是契约形状，重建一次就多一次漂移机会）。注册的路径必须与 AI 的
   权威路径一致，否则只会「404」或「转发到另一个接口」，不会静默成功。

7. **服务凭据不足以识别用户。** `Internal.ServiceToken` 只用于后台任务
   （如清上下文，接缝 J9）；透传**必须**带用户令牌，因此「无令牌访问 AI 接口」是 401，
   而不是降级成服务凭据（那会把跨用户越权伪装成正常调用）。

8. **`Chat` 永不重试**（docs/04-§3.4）：重试会重复计费、重复落上下文。
   重试只允许出现在**幂等**的读类透传上，且由 §5 的幂等键机制兜底。

### 6.4 实现中发现并修掉的缺陷

1. **Kratos `DialInsecure` 默认给每次调用套 2 秒超时 —— 本次验收 15 个失败里有 15 个是它。**

   现象极具误导性：`send` 在 ~2.1s 后返回 `504 AI_TIMEOUT`，`details.reason` 是
   `non_envelope_status`，`grpc_code` 是 `DeadlineExceeded`；而**同一时刻**用 Python
   直接调同一个 gRPC 方法，无 RAG 1.0s、带 RAG 1.25s 都能成功。也就是说
   「错误里写着上游超时，但上游根本没超时」。

   根因在 kratos v2.8.4 的 `transport/grpc/client.go`：`dial()` 里
   `clientOptions{timeout: 2000 * time.Millisecond, ...}`，并且**无论是否配置**
   都会装上 `unaryClientInterceptor(options.middleware, options.timeout, options.filters)`，
   那个拦截器里是 `if timeout > 0 { ctx, cancel = context.WithTimeout(ctx, timeout) }`。
   于是「借它的 ClientConn、自己设按档位的 deadline」这个设计实际得到的是
   `min(档位, 2s)`：1.2s 的回答能过，3s 的 RAG 回答必失败。

   修法是 `kratosgrpc.WithTimeout(0)`（源码里那个 `> 0` 守卫使 0 成为「不装超时」），
   并在代码里写明**这条不能删**。

   **真正值得记住的是为什么单测全绿却看不出来**：原有用例通过 `bufconn` +
   `newChatOrchestratorFromConn` 注入连接，**绕过了 kratos 的 `Dial` 选项**，
   结构上不可能观察到这个默认值。所以新增的回归测试
   `internal/data/ai/grpc_test.go :: TestProductionDialHonoursOwnDeadlineNotKratosDefault`
   做了两件反直觉但必要的事：用**真实 TCP 监听**（`net.Listen("tcp","127.0.0.1:0")`）、
   走**生产构造函数** `NewChatOrchestrator`；两个子用例一个证明「档位比 2s 长时不被截断」
   （6s 档位 + 2.5s 服务端延迟必须成功），一个证明「档位比 2s 短时仍然生效」
   （400ms 档位必须 `AI_TIMEOUT` + `gateway_deadline_exceeded`，且耗时 ≤ 2s）。
   该测试已**实测能被证伪**：注释掉 `WithTimeout(0)` 后它报
   `6s 档位下 2.5s 的回答应当成功，实际失败: AI_TIMEOUT ... DeadlineExceeded`。

   > 一般化的教训：**「注入连接」的测试模式会丢失所有连接建立阶段的配置**。
   > 凡是「缺失时静默」的默认值（超时、重试、拦截器），都必须有一条走生产入口的测试
   > —— 与 §5.3 第 6 条（中间件没接上）是同一类问题、同一种解法。

2. **验收脚本自己制造了三个「看起来像网关坏了」的假失败。** 三处都已写进
   `curl_stage3.ps1` 的头部注释，这里只记要点：

   - **注册成功（201）只回用户资料、不回令牌**。脚本写成「201 就取 `access_token`」，
     于是 `$token` 为 `$null`，后面所有带令牌的断言集体 401 —— 看起来像鉴权坏了，
     其实是脚本少了一步。修法是无论如何都补一次 `login`，并把 `register=` / `login=`
     两个状态码一起放进断言详情。
   - **`X-Trace-Id` 是响应头**（网关回写用），塞进请求里会被忽略（见 §6.3 第 5 条）。
   - **PS 5.1 里错误响应的 `GetResponseStream()` 往往已经被读过一遍**，
     再读只得到空串 —— 表现为「4xx 明明带了错误信封，脚本却断言 `404 回包是约定信封` 失败」。
     正确的是 `$_.ErrorDetails.Message`（PowerShell 已按 `Content-Type` 的 charset 解好码）。
     `curl_stage2.ps1` 早就是这么写的，所以它的 404 断言一直是绿的 —— 同一个仓库里两种写法并存，
     正好可以互相印证。

3. **Python 侧 gRPC server 的四处实现陷阱**（都是「能跑但语义不对」的类型）：

   - **`Any.Pack()` 是就地修改并返回 `None`**（与 Go 的 `Any.Pack()` 返回 `*Any` 相反），
     写成 `append(Any().Pack(m))` 会往 details 里塞 `None`；已抽成 `app/grpc/errors.py :: _pack`。
   - **`context.abort(..., trailing_metadata=...)` 是取代语义**，不能先 `set_trailing_metadata`
     再 `abort` —— 后者会把前面设的 trailer 整片换掉；所以 trailer 必须一次拼好交给 `abort`。
   - **`ValidationError` 的捕获范围过宽**：把整个调用体包进 `except ValidationError`
     会把服务内部（比如适配层）抛的 `ValidationError` 也映射成 400 参数错误；
     现在只在「请求体 → 领域对象」那一步捕获。
   - **`agents.run(...)` 漏了 `await`**（Agent 分支），返回的是协程对象而不是结果。

4. **长驻的 Python gRPC 进程会「丢上游」**：跑了约 3 小时后，所有 `Chat` 都变成
   `503 DEPENDENCY_UNAVAILABLE`（python 直连探测同样失败，证明不是网关的问题），
   **重启进程即恢复**。同一次验收里还有一例 RAG 调用耗时 **64s** —— 这也反过来印证了
   §6.3 第 2 条的档位选择（70s chat 档）与脚本的 120s 客户端超时都不是随手写的。
   记录在此是因为它**不报错、不崩溃**，只表现为「网关突然全红」。

### 7.2 关键实现决策

1. **复杂度全部收在 `biz`，传输层只会「渲染 + 写」。** `pump` 自己 `select` 六件事：
   等事件 / 发心跳 / 首字节超时 / 空闲超时 / 总超时 / 进程退出 / 请求取消 —— 其中只有
   第一件与上游有关。把它们放进传输层，「超时」就退化成连接级的实现细节，
   而它其实是业务策略（docs/04-§5 的时延表）。
2. **第一帧才写响应头。** 顺序是刻意的：首字节超时要在那之前还能回 **504 信封**
   （脚本里「不存在的会话 404」「空内容 400」「一帧都没写出」三条正是钉这个）；
   一旦写出 200，失败就只剩 `event: error` 一条路。
3. **流式路由不挂幂等中间件**（docs/02-§7 的适用范围不含流式）：重放一个已经推了一半的流，
   客户端会把正文再拼一遍。脚本用同一个 `Idempotency-Key` 连打两次，断言「user 消息**确实新增**」。
4. **三个超时共用一个错误码，`details.reason` 是唯一的区分手段** —— 这正是缺陷 #1 的成因。
5. **累积器是纯数据结构**（无 logger、无 ctx、只注入时钟）：截断**只停止累积、不停止透传**；
   `reference` 帧是**全量覆盖**（AI 每次重发全集，追加会得到 N 倍引用）；
   `tool_call`/`tool_result` 按 `call_id` 配对，未配对的降级成 `error` 而不是丢。
6. **落 `partial` 用 `context.WithoutCancel`**（docs/03-§5：客户端走了，回答仍要存），
   唯一例外是「一个事件都没收到」—— 见 §7.3 第 2 条。
7. **每帧重置写超时**（`http.NewResponseController` → `SetWriteDeadline`，10s）。
   `http.Server` 上**不能**设 `WriteTimeout`（会误杀正常的长响应），而「客户端不读也不
   断开」的一个连接就能永久钉住一条 goroutine + 一个上游连接。gin v1.11 的
   `responseWriter` 实现了 `Unwrap()`，所以这条链能通到真正的连接。
8. **未知事件字节透传**，且**不合法的 JSON 会被包成一个 JSON 字符串** —— 直接透出会让
   客户端**整条流的解析中断**，而「丢一帧」是可控的。
9. **gRPC 侧不映射 `ping`**：docs/04-§2.3 的映射表里它就是「不映射」那一栏，
   包成 `unknown` 会让客户端收到两路心跳。
10. **两条上游通道共用一套归一化**：`tool_call.arguments` 在 HTTP 侧是**对象**、
    在 gRPC 侧是**字符串**（proto3 没有任意 JSON），归一后对外只有一个形状；
    两侧各有一条单测钉死这个差异，免得将来只改一边。

### 7.3 实现中发现并修掉的缺陷

1. **`gatewayStreamError` 把「是哪个超时」丢了。** `pump` 造的三个超时分别带着
   `details.reason = first_byte_timeout / idle_timeout / total_timeout`，而收尾时重新
   合成的是一个**裸**的 `AI_TIMEOUT` —— 三者在日志与 `error` 帧里长得一模一样，
   于是「该调 `AI_FIRST_BYTE_TIMEOUT_SECONDS` 还是 `AI_TOTAL_TIMEOUT_SECONDS`」无从判断。
   修法是让 `gatewayStreamError(end, loopErr)` 在**码相同**时优先返回 `loopErr`（保留
   `WithDetail`），并补 `assertDetail` 把三个 `reason` 各自钉一条用例。
   > 一般化的教训：**错误码与细节是一体的**。合成错误时必须问一句「原来那层的细节还在不在」，
   > 否则排查时拿到的是「看起来对、信息量为零」的错误。
2. **零事件的失败会落一条空白 assistant 消息。** gRPC 的 server-streaming 里
   「第一个 `yield` 之前 abort」表现为**零事件 + 非 OK 状态**（且 `ChatStream()` 仍返回
   nil error，错误在**第一次 `Recv`** 才到），首字节超时同理。这两条路径下 `finishStream`
   会照样 `Append` 一条空正文的消息 —— 而**非流式**路径（`Chat` 报错不写 assistant）与
   **HTTP 降级**路径（回 4xx 信封，压根没有流）都不会。同一次失败在两种传输下落库结果
   不同，正是生产里会被当成「偶发脏数据」的那类问题。
   修法是 `streamAccumulator.hasContent()`（正文 / 引用 / 工具 / 用量 / `done` / `error`
   任一存在）+ 落库前早退，并配一对**对照用例**：零事件失败 → 无行；带 `error` 帧的内容
   失败 → `failed` 行。
3. **一个「我以为的缺陷」被证伪，注释与测试一起改正。** `resetTimer` 里原写着
   「先 `Stop()` 再 drain 通道，否则 `Reset` 会把陈旧值留给你」，并配了一条声称
   「这段代码必不可少」的测试。用一次性程序实测后：**Go 1.23 起 `Timer.Reset` 已经是
   「无缓冲、不会有陈旧值」的语义**，而且这个行为**受 `go.mod` 的 `go` 指令门控**
   （本项目是 `go 1.24.0`，所以按新语义走）。于是把注释改写成「在当前工具链下这段
   drain 是**冗余**的，只作为将来把 `go` 指令降回去时的安全网」，测试改名
   `TestResetTimerFiresAtTheNewDeadline`（它验证的是「重置后在新 deadline 触发」这条
   **真实**行为），另补一条真正可证伪的 `TestStreamSendIdleTimerIsResetByEachEvent`
   （10 个 token、间隔 30ms，空闲阈值 80ms）。
   > 值得记住的是**证伪脚本对那条旧测试报的是 `NOT-FALSIFIED`**：源码被改坏之后它**依然绿**。
   > 「测不出差异的测试」比没有测试更危险 —— 它看起来在保护一个约束，实际什么都没保护。
4. **三条测试写法的坑（不是产品缺陷，但都制造过假结论）：**
   - **假 gRPC server 不能在每一帧之前都 sleep**：那样「首帧早到」根本观察不到（第一帧
     也被延迟）。延迟只能加在**帧与帧之间**（`TestChatStreamDeliversEachEventAsItArrives`）。
   - **`io.EOF` 必须不算错误**：否则每一次正常答完都会被判成 `partial`（流末尾 `Recv` 返回 EOF）。
   - **客户端断开时 user 消息早就落库了**，所以那条 `Append` 的 `ctx.Err()` 是 `nil`；有断言
     价值的是**第二条**（assistant 落库）的 `ctx.Err() == nil` —— 它是「`WithoutCancel`
     真的生效」的唯一可证伪证据（假 repo 忽略 ctx 的话，两种写法一样绿）。

### 7.4 「首 token 增量」是怎么量的（口径）

退出条件里的量化项只有这一条，而它**不显然**，所以把口径写下来。

**不能直接比「首 token 时刻」。** 那里面含模型 TTFT，两次真实调用的 TTFT 抖动远大于 30ms
—— 本机两次运行量到的**首 token 中位差**分别是 **-30.6ms** 与 **-191.4ms**（符号都会翻）。
用它判阈等于在测模型排队状况。

**能干净量的是「首帧（`meta`）时刻」。** AI 侧 `ChatService.stream_prepared` 是
**先 `yield meta`、再去调模型**（`app/application/chat.py`），所以 `meta` 的到达时刻里
**不含模型耗时**：

```
网关增量 ≈ 首帧(经网关) − 首帧(直连 AI)
```

剩下的正是网关自己的开销：鉴权（JWT + 版本缓存）→ 落 user 消息 → 建流 → 转发。
实测（`-Runs 4`，串行交替采样，每轮用**全新会话**以免历史回灌把 prompt 一轮轮拉长）：

| 运行 | 直连中位 | 经网关中位 | 增量（中位差） | 最小值对 |
| --- | --- | --- | --- | --- |
| 2026-09-30 #1 | 4.7 ms | 16.7 ms | **+12.0 ms** | 4.6 / 8.7 ms |
| 2026-09-30 #2 | 5.2 ms | 15.9 ms | **+10.7 ms** | 4.5 / 12.5 ms |

即 **10.7 ~ 12.0 ms ≤ 30 ms** ✓。口径与 docs/06 的 `AC-NFR-01`（直连 AI vs 经网关）一致，
只是样本从 200 降到 4（真实模型调用有成本）；脚本因此同时打出**中位数与最小值**两组，
并单独**记录不判阈**地打出含模型耗时的首 token 数字，便于人工判断抖动。

### 7.5 与 docs/04-§4.2「字节级一致」的偏差（已记录）

docs/04-§4.2 写的是「同一请求直连 AI 与经网关，SSE 流**字节一致**」。本项目采用
[01-§8](../docs/01-总体需求与范围.md) 的 **`AC-ORCH-03` 口径：事件名序列与顺序完全一致、
`data` 内容语义一致**。两处必然不同，且都不是缺陷：

1. `meta` 的 `conversation_id` / `message_id` **必须**换成网关自己的值
   （REQ-ORCH-006 / AC-ORCH-07）—— 转发 AI 的值会让用户下一轮提问时「AI 忽然失忆」，
   拿 AI 的 `message_id` 去 `GET /messages/{id}` 还会 404（网关台账里没有它）；
2. 网关可能**追加** `gw_degraded` / `gw_persist_error`（docs/04-§4.1 允许，且排在 `done` 之后）。

该口径写进了 `proto` 的注释，并由 `curl_stage4.ps1` 的三条断言钉住：
**帧内不含 `\r`**、**帧格式就是 `event:` + `data:` 两行**、**事件顺序单调不回头（`ping` 忽略）**。

### 8.2 关键实现决策

1. **`used` 的权威只在网关，AI 只上报 `usage`**（接缝 J7）。判决点是「扣减发生在调用**前**」——
   事后回滚在「上游超时但实际执行了」的情况下必然漏扣，而预扣 + 回滚最坏是**多扣一次后补回**，
   后者可以靠对账（`RetentionService` 的每日检查）收敛。
2. **回滚必须发生在「响应已定」之后，且只回滚自己扣的那一次**：编排层用 `Reserve` 返回的
   `Reservation` 携带指标快照，`Rollback(res)` 幂等（同一 `Reservation` 回滚两次只生效一次）。
3. **限流的 scope 是有限枚举，不是自由字符串**：它同时要进指标标签与错误信封。
   把 `user_id` / 路径当 scope 传进来会让时间序列数按用户数增长（docs/06-§5.2 禁止高基数标签）。
4. **熔断的状态机与日志分离**：`Allow` / `OnSuccess` / `OnFailure` 各自只做「加锁 → 算状态 → 解锁」并
   **返回一个值拷贝的 `circuitEvent`**，由 `emit` 在锁外打印 —— 见 §8.3 第 3 条。
5. **降级路径必须"绕开"而不是"穿透"**：`CircuitChatOrchestrator` 包在编排外，熔断打开时**根本不进入**编排，
   于是 `/conversations`、`/me/quota` 这些不经过编排的接口天然不受影响（S7 的实质）。
6. **上传的上限判断在**转发之前**、且只看 `Content-Length`**：读 body 再判等于把「防止内存被吃光」的
   保护自己拆掉。没有 `Content-Length`（分块传输）时按 `UPLOAD_MAX_MB` 边转边限。
7. **`limit = 0` 在契约里是 `null` 而不是 `0`**：内部用 `0` 表示「不限量」，直接输出 `0` 会让客户端
   显示「剩余 0 次」，用户以为自己被禁用了（`QuotaMetricResponse.Limit` 因此是指针）。

### 8.3 实现中发现并修掉的缺陷

M5/M6 一共抓到 7 个缺陷（第 6、7 个是 2026-09-30 跑全套回归时补上的；第 7 个在**验收脚手架**里），
其中 3 个是「**功能明明写了，但静默不生效**」这一类 —— 它们全都靠**实测验收**（而不是 code review）暴露出来。
按发现顺序：

1. **配额被静默绕过（P1）。** `internal/data/redis/counter.go` 的两个 Lua 脚本返回值形状不同
   （`reserveScript` 返回 `{ok, remaining}` 表，`addScript` 返回标量），而 `eval()` **只按表解析**。
   于是 `Add` 永远报「期望返回 Lua 表，实际 int64」→ `DegradedQuotaCounter` **永久**退到进程内计数
   → `Reserve` 看不到自己的写入 → **第 2 条消息被放行**。
   修法：拆出 `evalNumbers` / `evalNumber` 两个 helper，并补 `scripts_guard_test.go` 用 AST 把
   「脚本 → helper」的对应关系**钉死**（漏一个就是 `脚本 addScript 应由 evalNumber 执行，实际用了 evalNumbers`）。

2. **限流静默降级（P1）。** `RateScopeLoginAccount` 直接把裸邮箱当桶 id 传给 Redis key 拼接，
   而 key 片段有字符白名单 `^[A-Za-z0-9_.-]{1,128}$` —— `@` 不合法，于是**每一次决策都失败**
   并降级成进程内计数。多实例部署下等于没有账号维度限流。
   修法：`accountBucketKey(email) = cryptox.SHA256Hex(cryptox.NormalizeEmail(email))[:16]`，
   **刻意不加 `acct:` 前缀**（冒号本身就在白名单之外），并把白名单在 `middleware` 里**另存一份**
   做守卫 —— 不 import 数据层的那份，免得「放宽白名单」时守卫跟着一起放宽。

3. **熔断首次状态跃迁自死锁（P0）。** `AICircuitBreaker.logf` 在**持有 `b.mu`** 时调
   `b.Snapshot()`，而 `Snapshot()` 要加**同一把**锁。`sync.Mutex` 不可重入，于是
   **连续 10 次上游失败 → 熔断打开那一步把自己锁死**：之后每个请求都卡到客户端超时，
   `gw_circuit_breaker_state` 已经是 2 但 `result="rejected"` 恒为 0（拒绝路径根本没走到），
   而且**一行日志都没有 —— 卡住的正是写日志那一步**。
   `gw-stage5-dead.log` 里的物证：日志停在 9 次失败之后，脚本随后记到
   `elapsed_ms=120031,120014,120019` 且 `status=0`、code 为空。
   修法：删掉 `logf`，改为各 `xxxLocked()` 返回 `circuitEvent`，`emit(ev)` **严格在解锁之后**调用；
   配 `circuit_test.go` 的**看门狗**（`watchdogTimeout = 2s`，死锁变成一条具名失败而不是十分钟的
   `test timed out`）。**反向验证**：把日志调用塞回 `openLocked` → 守卫立刻报
   `第 2 次 OnFailure（触发熔断打开）卡住超过 2s`。修后实测拒绝路径 **8~14 ms**。
   > 一般化的教训：**「持锁时不要调用会再取同一把锁的方法」这条规则，在日志这种"边角代码"上最容易被违反**
   > —— 因为写日志看起来不像业务逻辑。而且它的失败是**完全静默**的：日志是它的输出，卡住之后你连
   > 「它卡住了」都收不到。另一条同源的教训：**状态机 + 日志必须分离**，`*Locked` 系列返回事件值，
   > 锁外统一发送。

4. **`/health` 缺 `checks.circuit_breaker`（M6，真缺陷）。** docs/06-§5.4 把这个字段列为**接口的一部分**
   （连响应示例里都有），而实现从 M3 起就没有它。字段缺失比字段为 `disabled` 更糟：
   按字段消费的面板/脚本会拿到 `undefined`，而不是「未启用」这个**确定且可判**的状态。
   修法：`service.CircuitStatus` + `NewHealthHandler(..., circuit func() CircuitStatus)`，
   `circuit == nil` 时输出 `{"state":"disabled","note":"..."}`；**且不影响状态码** ——
   「熔断打开」意味着网关正在正确地自我保护，不是不健康。`RetryAfterSeconds` 下限钳到 1
   （`Retry-After: 0` 会被客户端理解成「立刻重试」）。

5. **`/health` 的 `status` 恒为 `degraded`（M6，真缺陷）。** `checks.ai_platform` 自 M3 起一直是
   `{"ok":false,"configured":false,"note":"AI 探针未接入"}` —— 一个**恒定**的字段，
   于是 `/health` 的 `status` 永远是 `degraded`。运维看到 `degraded` 会去查 AI，而 AI 其实好好的；
   更糟的是它把「真的挂了」淹掉了。
   修法：`internal/data/ai/probe.go`（`NewProbe`，探 `GET /api/v1/health`，独立 2s 超时、独立
   `http.Client` 但**共用 transport**）+ `cmd/server/main.go` 的 `aiHealthProbe`。
   实测两侧都验过：AI 在 → `status=ok` / `ai_platform.ok=true`；
   AI 不在（指向空端口）→ `status=degraded` / `ai_platform.ok=false` + 原始错误，
   而 `/health/ready` **仍然 200**（AI 可达性 MUST NOT 参与就绪判断，否则 AI 抖动会摘掉全部网关）。
   > 一般化的教训：**恒定的健康字段比没有字段更坏**。它看起来有意义、可消费、能上面板，
   > 但它的取值与真实状态无关 —— 于是把「值班时最该看见的那个信号」占了位。

6. **断连后配额可被稳定绕过（M5/M4 交界，真缺陷，2026-09-30 补）。**
   现象：网关日志里反复出现
   `level=WARN msg=quota.usage_insert_failed ... metric=chat_requests error="context canceled"`。
   根因：`QuotaService.commit` 直接用**请求的 `ctx`** 去做两件收尾 —— `Counter.Add`（Redis 累加）
   与 `insertUsage`（明细入库）。而「结清」发生在**流结束之后**，客户端中途断连时 `ctx` 早已被取消
   （`MessageService.finishStream` 正是拿原始 ctx 调 `Commit` 的），于是**计数与明细一起失败**，
   只留一条 WARN。**而计数正是限额依据** ⇒ 凡是断连过的对话，这次调用不计入配额。
   同一个文件里的 `rollback` 反而**已经**用了 `context.WithoutCancel`（注释还写着「客户端的 ctx
   往往已经取消」）—— 方向相反的那条路径漏了。
   修法：`commit` 里 `ctx = context.WithTimeout(context.WithoutCancel(ctx), settleTimeout)`；
   `WithoutCancel` 去掉取消信号但会连带去掉 deadline，所以另加 5s 上限，避免 Redis/DB 卡住时
   把 goroutine 与连接无限占住。
   守卫：`internal/biz/quota_commit_test.go` 用「记录调用时 ctx 状态」的替身断言
   「已取消的 ctx 也不能让累加/明细失败」。**反向验证**：把 `WithoutCancel` 换成 `ctx`，
   `TestCommitSettlesAfterClientDisconnect` 立刻报
   `累加用的是**已取消的** ctx（context.Canceled）`；还原后 ok。
   > 一般化的教训：**"收尾动作必须无视取消"这条规则要成对检查**（`commit` / `rollback`、
   > 成功路径 / 失败路径）。只在一侧写对时，另一侧的表现是**静默丢数据 + 一条没人看的 WARN**，
   > 而它的业务后果（配额可绕过）与被绕过的那个功能离得很远，很难顺着报错找回来。

7. **`curl_stage5.ps1` 用 `-NoNewWindow` 起辅助实例，整棵树跟着终端一起死（脚手架缺陷，2026-09-30 补）。**
   现象：`tools/run_all_stages.ps1` 跑到 M5 第 3 节（配额）时**整个进程树消失** ——
   `allstages5.txt` 停在 `---- M5 : curl_stage5.ps1 -> http://127.0.0.1:18086 ----` 一行，
   没有结果、没有报错，父进程与子进程都查不到；而 suite 自己拉起的两个实例 A/B 却**还活着**。
   物证在辅助实例自己的日志里（`gw-stage5-quota.log`）：
   `19:26:51 /health/live 200` → `19:26:54 app.signal_received signal=shutdown` →
   `19:26:55 http.error route=/api/v1/auth/register cause="context canceled"`，
   即**实例先被关掉，脚本还在等它**。
   根因：`Start-AuxGateway` 用的是 `Start-Process -NoNewWindow`，**子进程与调用者共用控制台**，
   于是终端标签页被回收（或在同一终端按 Ctrl+C）会变成 `CTRL_CLOSE_EVENT` 送到这些实例。
   `run_all_stages.ps1` 与 `curl_stage6.ps1` 一直是 `-WindowStyle Hidden`（独立控制台），
   所以只有 stage5 拉起的实例会被连带杀死 —— **「谁和终端共用控制台」正好是判据**。
   修法：改成 `-WindowStyle Hidden`，并在注释里写明为什么不能用 `-NoNewWindow`。
   另外把「长验收」也改成**脱钩启动 + 轮询输出文件**（`Start-Process -WindowStyle Hidden -PassThru`
   配 `-RedirectStandardOutput`），不再占着交互终端前台跑。
   > 一般化的教训：**后台/长驻进程必须有自己的控制台**。共用控制台时，
   > 「宿主关了窗口」这件事会**冒充成被依赖方的故障**（脚本看到的是 `503 context canceled`），
   > 而真正的死因只在被关掉那个进程的日志里；这类故障在验收脚本里尤其贵，
   > 因为它把「跑一次 8 分钟」变成「跑一次 8 分钟后什么都查不到」。

> M5/M6 的缺陷有一个共同形状：**前三个都是"降级兜底把错误吃掉了"**。
> 降级（进程内计数、跳过限流、返回默认值）本身是对的，错的是**只打一条 WARN 就永久粘住**。
> 补上的守卫因此都长成「**钉住"哪种返回值配哪个 helper" / "哪种 key 合法"**」的形状，
> 而不是「测一遍 happy path」。

### 9.2 关键实现决策

1. **指标名 / 标签名 / 分桶是跨系统契约，因此单独成包**（`pkg/metricsx`）：告警规则、Grafana 面板、
   Runbook 都按这些字符串写。散在各调用点意味着「改一个标签名要全仓搜」，而漏改的那一处**不报错**，
   只是面板上少一条曲线。
2. **`*Vec` 必须在启动时预置**（`initLabels()`）：不预置的族**根本不出现在 `/metrics` 里**，
   于是 docs/06-§5.5 的比率型告警规则**永远不会触发**（分母不存在）。这条由
   `TestAllDocFamiliesVisibleAtStartup` + `TestVecFamilyPreSeededWithZero` 钉死。
3. **所有打点方法接受 nil 接收者**：于是「指标没启用」= 传 `nil`，调用点不需要写 if，
   测试也不需要假实现。**但 `biz.Metrics` 字段必须永远持有非 nil 的 `*metricsx.Metrics`** ——
   `METRICS_ENABLED` 只决定要不要起监听端口（关的是**暴露**而不是**采集**）。
   > 这是两件不同的事：`var m *metricsx.Metrics`（nil 指针）上调用方法安全，
   > 而**空接口**（nil interface）上调用会 panic。装配层因此 `mx := metricsx.New()` 无条件创建。
4. **标签值一律归一化，`route` 用独立的更宽松上限**（`label()` vs `routeLabel()`）：
   同一个 32 字节上限会**静默合并** `/conversations/:conversation_id` 与
   `/conversations/:conversation_id/messages` 两条序列（实测前者 1ms、后者数秒，合并后曲线不可读）。
5. **尾部采样替代「头部采样 + 错误 100%」这条做不到的组合**：头部采样的决策时刻在 span 创建时，
   而「这条链路会不会出错」要到它结束才知道。因此头部一律记录（`AlwaysRecord`），
   结束时按 trace 决定是否导出 —— 见过 `Error` 的全量导出，其余按 `OTEL_TRACES_SAMPLER_ARG` 抽。
   `DEBUG=true` 或请求带 `X-Debug-Trace: 1` 时用 **span 属性**（不是 context 值）强制导出，
   因为采样发生在 span **结束**时，那时原始 context 可能已因客户端断连而取消。
6. **`/health` 的字段必须"要么准确、要么明确 disabled"**：`ai_platform` 与 `circuit_breaker`
   都遵守这条（§8.3 第 4/5 条）。健康端点里的**恒定值是最坏的一种**：它占住了值班时最该看的信号。
7. **就绪（`/health/ready`）只看 MySQL + Redis + schema，不看 AI**（docs/06-§3）：
   把 AI 状态算进就绪会造成「AI 抖动 → 摘掉全部网关 → 全体不可用」的错误放大。
   Redis 也只查**连通**不查功能（挂了只是变慢，权威在 MySQL）。
8. **`retention.go` 的调度是「起一个 goroutine + context 取消」而不是塞进 HTTP 生命周期**：
   它的存在必须能由「配置了几点 / 间隔多久」推出，而不是由「有没有人访问过某个路由」决定。

### 9.3 实现中发现并修掉的缺陷

M6 的两个缺陷就是 §8.3 的第 4、5 条（`/health` 的 `checks.circuit_breaker` 缺失、
`ai_platform` 恒 `false` 导致 `status` 恒 `degraded`）。除此之外还修掉三处**验收环节**的问题
（两处假绿/假红 + 一处脚本互相污染，第 3 条同时也解释了 §8 里「上传体积默认 8MB」的由来）：

1. **直方图族不能按族名计数**：`gw_request_duration_seconds` 在纯直方图下**没有裸族名样本行**，
   按族名匹配会数出 0，看起来像「族不存在」。脚本改为按**前缀 + `_bucket`** 计数。
2. **`gw_login_attempts_total{result="ok"} == 0` 被误判成"脏实例"**：它是 `initLabels()` 预置的
   （比率型告警需要分母一直在）。把「预置且为 0」当成脏会让每次运行都失败。脚本改为只对
   **已发生的请求**做脏检查（同时查登录路由有无请求记录）。
   另有一处高基数检查的假阳性：原本匹配到了参数**名**（`:doc_id`）而不是值，产生 80 条误报；
   改为对**去重后的 route 值**比对裸 ID 正则。

3. **两条验收脚本不能背靠背跑（脚本顺序缺陷，最隐蔽的一个）。** 现象：stage5 **全绿**之后
   紧接着跑 stage6，stage6 报了 **11 条失败** —— 第一条是 `登录 200 :: status=429`，
   后面全是它的级联（拿不到 token → 建会话 401 → 拿不到 refresh → 401 → 没有 `logout` 审计行）。

   根因有两层，**都不是产品缺陷**：
   * **限流桶是全机器共享的。** 限流键是 `rate:login_ip:<IP>` 存在 **Redis** 里，
     与「哪个网关实例」无关。stage5 的最后一段**故意**把登录限流打满（要验 `AC-NFR-07`），
     于是 stage6 用的虽然是 18084 上的另一个干净实例，第一个 login 照样吃 429。
     ——「另一个实例」并不等于「另一份配额」，这是本地多实例验收最容易搞错的一点。
   * **stage5 会把 AI 喂爆。** `-UploadMB` 默认曾是 49MB，AI 侧切出 40,475 片后在
     `EMBEDDING_DEVICE=cpu` 下于事件循环里跑向量化，**`/health` 十数分钟不应答**。
     这时 stage6 里所有真实编排的断言都会失败，而报出来的是「连不上 AI」。

   修法（都在脚本侧，不动产品）：
   * stage6 的临时实例显式放宽登录限流（`LOGIN_RATE_PER_MINUTE=1000`）——
     限流**不在 stage6 的验收范围内**（那是 stage5 的事），抬高它不掩盖任何东西；
     而「等窗口过期」会把脚本顺序 + 时间变成隐式依赖，「打开 `TRUSTED_PROXY_COUNT` 换桶」
     更是为了测试放松安全配置。
   * `-UploadMB` 默认改 **8**（理由见 §8 的补充说明）。
   * 断言数从 34 增到 36（新增「体积低于默认上限」与「体积贴合目标误差 < 1MB」两条，
     后者专门用来防「参数静默失效」，因为 `-UploadMB` 曾真的因**按字符而非字节比大小**而失效：
     传 8 实际发了 19.19MB）。

   > 一般化的教训：**验收脚本之间会通过共享的全局状态互相污染，而且污染方向是"下游怪上游"**。
   > 这台机器上共享的东西至少有三层：Redis 限流桶（按 IP，跨实例）、MySQL 里的账号与审计表、
   > 以及**上游 AI 的健康**。所以「A 全绿 / B 全红」时要先问「B 是不是被 A 弄脏的」，
   > 再去看 B 被测的那个东西。判据是**顺序**：单跑 B 绿、A 之后跑 B 红 ⇒ 是污染不是缺陷。

### 9.5 一次性跑完全套（`tools/run_all_stages.ps1`）与它暴露的问题

六条脚本**不是顺序无关的**。逐条手跑时，「A 全绿 / B 全红」里有一部分根本不是产品缺陷，
而是**脚本之间通过共享全局状态互相污染**；另一部分则是**时序断言在这台机器上定标过低**。
为此新增了 `tools/run_all_stages.ps1`：一次跑完 M1→M6 并打一张汇总表。它把污染显式处理掉，
手段分三层（详见脚本头部注释）：

| 层 | 手段 | 为什么必须这样 |
| --- | --- | --- |
| ① 按实例隔离 | 阶段实例 A（18085/9121）**放宽限流 + 放宽配额**；限流实例 B（18086/9122）**全走生产默认** | M1–M4/M6 从不断言限流与配额拦截，却会被它们打死；M5 恰恰**只**断言这两件事，必须用默认上限 |
| ② 等窗口过期 | M5 开跑前「探一次坏登录，看还 429 吗」判断 `login_ip` 窗口是否翻过（最多 75s） | 限流桶**按客户端 IP 存在 Redis 里 ⇒ 跨实例共享**，「换实例」换不出一份新配额 |
| ③ 等 AI 排空 | 读网关 `/health` 的 `checks.ai_platform.latency_ms`，连续 3 次低于 500ms 才开跑 | 上一轮（尤其 M5 的 8MB 上传）会在 AI 侧留下后台 CPU 向量化，整机慢 2~3 倍，M4 的时序断言会假红 |

跑这套过程中另外发现并处理了 4 个问题：

1. **`curl_stage5.ps1` 反复 OOM（脚本侧，已修）。**
   现象：脚本跑到「造 8MB 请求体」一步就 `OutOfMemoryException`，而**数据是对的、所有断言都过**，
   只有内存爆掉 —— 最难归因的一种。
   根因是 PowerShell 的一个语义坑：`$bytes = $bytes[0..$cut]` 对 `byte[]` 求范围，返回的是
   **`Object[]`，每个字节都被装箱**（约 32 字节/字节，**77 倍放大**）；`return $ms.ToArray()`
   也会经管道再装箱一次。实测：

   | 阶段 | 修前 RSS | 修后 RSS |
   | --- | --- | --- |
   | 起进程 | 88 MB | 88 MB |
   | `New-TextBody(8MB)` | **740 MB**（+652） | **127 MB**（+39） |
   | 再叠 `New-MultipartBody` | **849 MB** | 同量级 |
   | 单次 8MB `byte[]` 的范围切片 | **+618 MB** | — |

   这台机器 16GB 但只剩 ~1.7GB 可用（VS Code + Chrome + Docker），于是必然 OOM。
   修法：改用 `[byte[]]::new($len)` + `[System.Array]::Copy` 一次性分配，并**加了 3 条类型/取值断言**
   （`正文是 byte[]（不是 Object[]）`、`正文元素类型是 Byte（未装箱）`、`造 body 的内存增量 < 预算`）
   把这类回归钉死 —— 光修不守，下次改回来还是静默的。

2. **两个「按用户/按 IP 累计」的桶会跨阶段、跨轮次污染（脚本侧，已修）。** 现象与成因各不相同，
   但**表象一样都是 429**，而排查方向完全不同 —— 看网关日志的 `code=`：

   * `code=RATE_LIMITED`：`MSG_RATE_PER_MINUTE` 默认 **20**，而 M2 用同一个用户发了 **23** 条消息
     （18 条显式 + G 段 5 条并发）⇒ 第 21 条起 429，被报成
     `I6 sending to a deleted conversation -> 404 :: expected=404 actual=429`。
     消息桶是 `RateLimitByUser(..., RateScopeMessage)`，**per user ⇒ 换实例救不了**。
   * `code=QUOTA_EXCEEDED`：`DefaultPlanLimits()` 的 free 档是 `chat_requests = 100/**日**`，
     而验收脚本用**固定 `user_id`**（如 `u_test_stage2`），日额度存在 Redis 里按自然日累计
     ⇒「今天第 N 次跑全套」会从某条断言起**全部**变成 429。实测实例 A 日志里 **16 条**
     `QUOTA_EXCEEDED`，M2 的 G 段 5 并发只成功 1 条。
     顺带把 `concurrency` 也放大：free 档是 5，而 G 段正好 5 并发真实模型调用，机器一忙就退化。

   修法：`Start-StageGateway` 的 `-RateEnv` / `-PlanMap` **两个档案**，**先清空再覆盖**
   （`Start-Process` 继承的是本进程环境块，没有 `-Environment`，不清就会串味）；
   实例 A 给足、实例 B 留空。

   > 判据：**429 出现在一条从不提 429 的脚本里，就是污染而不是缺陷** ——
   > 该脚本的期望值不可能因为产品改动变成 429。

3. **延迟断言的定标问题（口径错配，已纠正）。** 两处都源于「把一个数字套到了不是它的路径上」：

   * `stage4` 的 `网关自身额外延迟（首帧中位差）≤ 30ms` 抄的是 `AC-NFR-01` 的数字，
     但 **`AC-NFR-01` 的原文对象是纯查询接口 `GET /conversations`**，而它量的是 **SSE 首帧**。
     SSE 首帧前网关**必须**同步完成台账：`GetOwned`(SELECT) → 配额预扣 → `Messages.Append`(写事务)
     → `applyAutoTitle`(UPDATE) → `recentHistory`(SELECT JOIN)，共 6~8 条 SQL。
     本机实测（`LOG_LEVEL=debug` 的 `db.query` 日志，113 条）：单条 `elapsed_ms` 平均 **8.9ms**、
     最长 **65.2ms**；连 `SELECT LAST_INSERT_ID()`（服务端零 IO）平均都要 **5.1ms**
     —— 因为 `SkipDefaultTransaction:false`，每条写 = `BEGIN`+语句+`COMMIT` 三次往返。
     而 `mysql.exe` 跑 10 条与 200 条 `SELECT 1` 总耗时都是 ~1090ms（**斜率 ≈ 0**）⇒ 慢的**不是
     MySQL 服务端**，是本机每个回环往返 1~1.7ms（跨 WSL 的 Redis PING 也是 1.11ms，同一地板）。
     ⇒ 同一个 30ms 在此路径上不可达：同一份代码多次运行实测 delta 落在 **120~260ms**，
     且**随机器负载红绿翻转**。修法：delta 降为 INFO；**补上 `AC-NFR-01` 原文口径**
     （打 200 次 `GET /conversations`）；只留一条绝对上限做回归兜底。
   * 该新增断言本身也做了定标：实测 `最小 6ms / 中位 20.9ms / P95 87ms / **最大 368.2ms**`。
     中位只有目标值的 1/4 ⇒ **网关自己不慢**，P95 是被单次 368ms 的尾部拉过线的，
     而这个尾部来自机器本身（16GB 只剩 ~1.7GB 可用）。P95 是对尾部极敏感的分位数，
     **在共享开发机上它的方差比它要测的量还大** ⇒ 判据用**中位**（4 倍余量，仍能抓住真回归），
     P95 与最大值记 INFO 做趋势观测。

4. **`S6：断连后已生成内容落库 ≤1s` 与文档不一致（未决项，需要 AI 侧信号才能定性）。**
   这个 1s 取自 docs/01-S6「网关 **1s 内取消上游调用**」，但脚本套到了「partial 行可见」上，
   而 docs/03 的 `REQ-CONV-006` / `AC-CONV-08` 对落库**只要求「必须有、内容必须对」，没给时限**。
   实测差异很大：

   | 来源 | 实测 |
   | --- | --- |
   | docs/04 `AC-ORCH-04` 记录值 | **23.5ms / 30.2ms** |
   | 本机对**真实模型**实测（两轮） | **1705ms / 2862.6ms** |

   网关日志显示那条流式请求**整体跑了 4420ms** 才结束（`http.request elapsed_ms=4420`，
   `msg=message.stream_aborted end=client_gone`），即延迟在「**察觉断连**」这一侧，
   不在落库这一侧（落库只有一次 `Append`）。但 `pump` 里明明有 `case <-ctx.Done()`
   且立即返回 `streamEndClientGone`，本该是即时的 —— 所以只能有三种解释之一：
   ①docs 那次量的上游是 **mock**（`AC-ORCH-04` 的另一半本来就由 Python 单测的 mock 覆盖）；
   ②真实模型路径上取消确实有延迟；③`-NoKeepAlive` + TCP 发送缓冲让小 token 写入一直"成功"。
   **分辨它们需要「AI 侧出现 canceled 的时刻」**，那需要 AI 侧指标 —— 与 `AC-ORCH-04`
   里已记录的「AI 侧无新增 token」那一半是同一个缺口。
   在此之前，脚本按**能测准的那个要求**判（partial 必须在轮询窗口内出现且在下面 5 条里逐项校验
   `status`/`finish_reason`/正文/`elapsed_ms`/user 消息仍在），实际延迟记 INFO。

5. **全套跑到 M5 时整棵树随终端一起消失（脚手架缺陷，已修，详见 §8.3 第 7 条）。**
   现象极具误导性：`allstages5.txt` 停在 `---- M5 : curl_stage5.ps1 -> http://127.0.0.1:18086 ----`
   一行 —— **没有结果、没有报错、没有退出码**，且再查进程时父与子都已不存在，
   只剩 suite 自己拉起的两个实例 A/B。物证来自 stage5 自己拉的那个辅助实例的日志：

   ```
   19:26:51.597  GET /health/live            200
   19:26:54.704  app.signal_received signal=shutdown      ← 实例先被关掉
   19:26:55.084  http.error route=/api/v1/auth/register 503 cause="context canceled"
   ```

   根因是 `Start-AuxGateway` 用了 `Start-Process -NoNewWindow`：**子进程与调用者共用控制台**，
   于是「终端标签页被回收 / 宿主把终端关掉」会变成 `CTRL_CLOSE_EVENT` 送到这些实例。
   `run_all_stages.ps1` 与 `curl_stage6.ps1` 一直是 `-WindowStyle Hidden`（独立隐藏控制台），
   所以**只有 stage5 拉起的实例会被连带杀死** —— 「谁和终端共用控制台」正好是判据。

   > 一般化的教训分两条：①**后台/长驻进程必须有自己的控制台**，共用控制台时
   > 「宿主关了窗口」会**冒充成被依赖方的故障**（脚本看到的是 `503 context canceled`，
   > 而真死因只写在被关掉那个进程的日志里）；②**跑 8~10 分钟的长验收要「脱钩启动 + 轮询输出文件」**
   > （`Start-Process -WindowStyle Hidden -PassThru -RedirectStandardOutput ...`），
   > 不要占着交互终端前台跑 —— 否则一次终端回收就等于白跑一次。

#### 9.6.2 三个必须记住的环境坑

1. **主机 `127.0.0.1:9000` 被 VS Code 自己占着。**
   `Get-NetTCPConnection -LocalPort 9000` 的 `OwningProcess` 是 `Code` —— VS Code 的端口转发
   在它上面返回自己的 `404 text/html`（无 `Server` 头）。于是 Docker 的 `9000:9000` 发布
   **静默失败**：容器 `docker inspect` 是 `healthy`，`docker port` 却看不到映射，
   而 AI 侧报 `InvalidResponseError: non-XML response ... 404 text/html`，
   看起来像"MinIO 坏了"。⇒ 用 `deploy/infra/compose.local.yml` 把 MinIO 挪到 **9005**。
   > **判定手法**：拿不到服务时先 `Get-NetTCPConnection -LocalPort <p>` 看 `OwningProcess`
   > 是谁，别只看"端口通不通"。9001/9002 也是被 Milvus 那套栈占着的。

2. **compose 覆盖 `ports` 必须用 `!override`，不能用 `!reset`。**
   compose 2.28 里 `!reset` 作用在序列上会把 `ports` **整段清空**（`docker port` 输出空、
   容器只剩 `expose`），而 compose 不报错。`!override` 才是"替换这个序列"。

3. **集成测试读的是 `AI_TEST_MINIO_ENDPOINT`，不是 `.env`。**
   `tests/integration/conftest.py` 用这个环境变量（默认 `localhost:9000`），
   而它的 `_reachable()` **只做 TCP 探测** ⇒ VS Code 那个 HTML 404 能通过探测门，
   于是用例**失败（不是跳过）**。跑集成测试前先
   `$env:AI_TEST_MINIO_ENDPOINT='127.0.0.1:9005'`。

   环境齐备后：AI 侧全量 **1616 tests / 0 failed / 4 skipped**（这 4 条全是"依赖缺失时
   优雅降级"的用例，属设计，不是缺口）。

#### 9.6.4 本轮修掉的三个缺陷（都是「静默」类）

| 缺陷 | 为什么危险 | 修法 |
| --- | --- | --- |
| `curl_stage5.ps1` 的 RSS 采样**把端口写死成 18080** | 单跑正常；被 `run_all_stages.ps1` 以 `18086` 调用时**拿不到进程**，`AC-ORCH-05` 的两条判据降级成 SKIP。症状只是"M5 少 2 条 PASS、多 1 条 SKIP"，**看着像断言数波动，实际是判据没跑** | 从 `-BaseUrl` 派生 `$MainPort` |
| `Start-RssSampler` 的**冷启动竞态** | `Start-Job` 返回时作业还没被调度，而采样窗口只有上传本身那么长（个位数秒）⇒ 偶发在首次探测前就收到停止信号、返回 `-1`，又变成 SKIP。**同一份代码上一轮绿、下一轮 SKIP** | 加握手：作业探测到端口后写握手文件，主线程等握手再上传 |
| `internal/data/mysql/roundtrip_live_test.go` 预热 `QueryContext` 丢弃 `*sql.Rows` 且未 Close | 同一个 `*sql.Conn` 上写锁被永久占住，用例**挂死 11 分钟被 kill**（日志只有 `busy buffer`），包耗时被记成 **36254s** | 显式 `Close()`；另加 90s 看门狗，超时即 `sqlDB.Close()` |

> 变成 11 分钟挂起。⇒ **脚本层的判据也要有"它到底跑了没有"的自证**（SKIP 就该被当成
> 信号去看，而不是当成可接受的结果）。
