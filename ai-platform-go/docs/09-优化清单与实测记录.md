## 2 耗时归因

### 2.1 测量方法（只讲一次）

数据来源：`tools/run_all_stages.ps1` 汇总表（2026-09-30 全绿那次）。本机：Windows + 16GB 内存（**可用仅 ~1.7GB**）、20 逻辑核、回环 1~1.7ms；
Python HTTP 8000 / 指标 9100 / gRPC 50051（`GRPC_ENABLED` 默认 **false**）；Go 网关 `HTTP_ADDR` 默认 **8080**（验收脚本统一用 18080，8080 上常坐着 kafka-ui 容器）。

四条纪律：① 延迟判据用**中位数**不用 P95；② **同一次 shell 调用内**"起服务 + 打请求"（换一次调用就是换一个回环命名空间，`ConnectionRefused after ~2048ms`）；③ 依赖在不在读应用自己的 `/health`（redis 8ms / milvus 4ms / mysql 9ms），不要用 socket 探测；④ 跑真模型时不同时跑别的重活（1.7GB 会抖动，数字不可比）。

### 2.3 逐阶段归因

**M1（43s / 99 断言）—— 慢在客户端，不在网关。** 最反直觉的一段：一句模型调用都没有，却要 43 秒。

| Argon2id `HashPassword` / `VerifyPassword` | **40.7ms / 40.7ms** | `go test ./pkg/cryptox -run TestReportPasswordCost -v` |

| Argon2id 内存维度 | m=8/32/64/128 MiB → 5.5/20.7/43.4/83.2 ms，**0.65~0.69 ms/MiB** | 同上 |

auth 调用约 20 次、Argon2id 合计只占 **≈1s**；剩下的 42s 曾归因为 IWR 的代理开销，**该归因已被实测推翻**（§4.6：104 次往返全砍掉也只值 **~1.4s**），更可能是「整机被后台向量化拖慢」（§4.2）。附带确认：Argon2id 耗时随 `m` 近似**线性**（0.65~0.69 ms/MiB）⇒ 瓶颈是算力不是内存缺页。

**M2（79s / 198 断言）—— 真实模型调用 × 23。** 串行 `POST .../messages` **18 次**（D/E/F/H 段）+ G 段并发 **5 次**（`Start-Job`，验 `AC-CONV-07` 的 `seq` 唯一性）；
单次 `send` 实测区间 **0.9s ~ 64s**（含 RAG 命中的那一次 64s）；客户端超时 30s → **120s**（M3 起，否则 `status=0` 会报成"接口返回 0"）。⇒ 耗时 ≈ 模型排队时间之和，脚本本身没有浪费；
`MsgsPerSend = 2` 是 M3 之后的事实。

**M3（8s / 29 断言）—— 只有 1 次真实模型调用。** 18 次 `Invoke-Api` 里只有 `/messages` 那一条打到模型，其余是透传与错误映射（19 条路由直接用 `-SkipChat` 也不影响结论）。**这一段是"脚本颗粒度"的正面样本**：断言密度最高的性价比出现在这里。

**M4（42s / 51 断言）—— 8 次真流 + 1 条长流 + 200 次采样。** 增量对比默认 `-Runs 4` = **4 组 × 2 = 8 次真实流式**（AI 直连 + 经网关各一次）；S6 断连测试是 1 条"300 字以上"长流，
`-AbortAfterFrames 3` 后主动断连，实测 partial 可见 **1705ms / 2862.6ms**（轮询窗 5s）；`AC-NFR-01` 采样 **200 次 `GET /conversations`**（原始要求，
未减），最小 6ms / 中位 **20.9ms** / P95 87ms / **最大 368ms**。⇒ 200 次采样只值 ~4s（20.9ms × 200），不构成瓶颈；时间在 8 次真流上，而这 8 次是"网关增量延迟"的**唯一干净口径**（比首帧 `meta`，
不含模型 TTFT），不能省。

**M5（167s / 40 断言）—— 全套里最重的一段。**

| 消耗点 | 数字/机制 |
| --- | --- |

### 2.4 8MB 上传到底有多大、切多少块

**网关侧没有问题**（唯一例外是 UP-02 的透传验证与 UP-08 的 P2 通道）：它只做三件事 —— 前置 `Content-Length` 判限 → `io.Copy` 转发字节流 → 透传上游响应（`internal/service/upload.go`）；
不落盘 / 不入内存 / 不写 MinIO（8.00 MB 上传，网关 RSS **139.7 → 140.0 MB，增量 0.4 MB**，是文件体积的 5%，`AC-ORCH-05`）；超限 `413 PAYLOAD_TOO_LARGE`，
**只读 `Content-Length`，不读 body**；默认上限 `UPLOAD_MAX_MB=50`；扩展名 / 魔数 / 入库 / 建任务**全部在 AI 侧**（docs/04 明确不重复实现白名单）。

复刻 `curl_stage5.ps1::New-TextBody` 的正文（同一份 `$line` 模板、同样按字节截到最后一个换行），再走**真实**链路 `parse_document(...)` → `ChunkingService(chunk_size=512, chunk_overlap=64).split_blocks(...)`：

| 量 | 实测值 |
| --- | ---: |
| 正文字节 / 字符数 | **8,388,573**（8.00 MiB）/ 3,467,547 |
| token（**分块求和**口径）/（整篇 `encode` 口径） | **2,968,583** / 3,053,429 |
| 解析出的 block | **84,846** |
| 切分出的 chunk（改前） | **16,969** |
| 单块 token（改前） | min **170** / 中位 **175** / max **178** |
| **实际入库** | **10,000**（被 `MAX_DOC_CHUNKS` 截断，**丢 41%**） |

> **两个 token 口径都对，差的 84,846 恰好等于 block 数**：`parse_document` 切开 block 之后，block 之间原有的 `\n\n` 不再计入。规矩：切分 / 向量化数字用**分块求和口径**，"文件多大"用整篇口径；混用会得到差一个块数的两个数，看起来像算错。

**为什么 8MB 会切出 1.7 万片** —— 三层放大，与文件"大不大"无关：① **字节 ≠ token**：切分只认 token（tiktoken `cl100k_base`），这份中文实测 **1.33 token/汉字**、
**2.75 bytes/token** ⇒ 8MB = 229 万汉字 = **305 万 token**，按 A4 一页 ~1000 汉字算 **≈2,290 页 ≈ 20 本中文长篇**（"8MB 不算大"说的是**传输量**，网关 RSS 只涨 0.4MB）；
② **粒度是 512 token**（步长 448），光这一层就把片数下限定在 `305 万 ÷ 448 ≈ 6,800`；③ **测试文本的形状又放大 2.6 倍**：`New-TextBody` 逐行重复同一条模板，
解析出 **84,846 个平均 39 字符（约 36 token）的碎段**，而 `_merge_short` 的停止条件是"累加到 `chunk_size × 0.3 = 153.6` 就停"（`chunking.py:167-186`）⇒ 片长中位 **175 token**，
只填到配额的 **34%**。

| 切法（同一份 8MB 正文，只改切法） | 片数 | 说明 |
| --- | ---: | --- |
| 整篇一次性切（`create_documents([text])`） | **6,527** | 段边界连续、装箱效率高 ⇒ 接近第 2 层的下限 |
| 按 84,846 个 block 切（**真实链路**） | **16,969** | 碎段 + 合并提前停 ⇒ **2.6×** |
| UP-03 之后（填到 `chunk_size`） | **6,056**（中位 490 token，填充率 96%） | 合并跨 block 贪心装箱且不产生重叠 ⇒ 比整篇一次切还少 |

⇒ **"8MB → 1.7 万片"是测试文本形状的上界，不是 8MB 中文文档的常态**：正常散文同体积约 **6,500 片**；反过来，只要文件里是大量短段落，**任何体积**都会被放大同样的倍数。**跨体积实测**（同一模板、同一链路）：

| 上传体积 | 汉字数 | token（整篇） | block | 切分片数（改前） | 入库 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 MB | 28.9 万 | 38.4 万 | 10,704 | 2,141 | 2,141 |
| **8 MB** | **229 万** | **305 万** | **84,846** | **16,969** | **10,000**（截断 41%） |
| 19 MB | 541 万 | 721 万 | 200,341 | 40,068 | 10,000（截断 75%） |
| 49 MB | 约 1,340 万 | 1,854 万 | 514,914 | 102,983 | 10,000（截断 90%） |

> 这张表同时解释了 `-UploadMB` 的历史坑：脚本曾"按字符比大小"，于是 `-UploadMB 8` 实际发出 **19.19MB**（对应第三行），**打印的是字节数**，看起来像打印算错；更要紧的是 **8MB 就已经被截断 41%**，把 `-UploadMB` 调大只会更早触发截断，不会让 `AC-ORCH-05` 更有分辨力（那条判据是**相对**的：RSS 增量 < 文件体积）。
> **真正占事件循环的是解析 / 切分 / 哈希三段同步 CPU**（`parse_document`、`split_blocks` 的逐块 token 计数、`_build_chunks` 的逐块 sha256）：
> 中间没有一次 `await`，8MB 正文要占住事件循环几十秒 —— 这正是"AI 进程在监听但所有请求都超时"的成因。向量化本身**不占**事件循环（`app/rag/embedding/base.py::embed_texts`
> 是 `await asyncio.to_thread(provider.embed, ...)`）。

### 2.5 原因分类与判别规则

| # | 类别 | 典型表现 | 是否产品缺陷 |
| --- | --- | --- | --- |
| ① | **真实模型调用** | M2 单次 send 0.9~64s；M4 8 次真流 | 否（不可压缩，只能减少次数） |
| ② | **上游 AI 被自己搞慢** | 8MB → 1.7 万块（截断后 1 万块）→ 后台 CPU 向量化吃满核 → 同机 MySQL/Redis/网关一起慢 2~3 倍 | 否（AI 侧架构），但**验收参数与线程数可以避免触发**（§4.2） |
| ③ | **套件级固定等待** | `Wait-AIDrain` ≤150s、`Wait-ForRateWindow` ≤75s、就绪探测 | 否（共享状态污染的代价） |
| ④ | **失败时"卡满超时"** | 熔断自死锁 → 每请求卡满 120s 且**零日志**；Kratos `DialInsecure` 默认 2s | **是**（已修，docs/08） |
| ⑤ | **每请求固定开销** | 每写 `BEGIN+COMMIT`；SSE 首帧前 6~8 条 SQL = 120~260ms；`mysql.exe` ~1.1s/次 | **部分是**（SQL/事务那条是） |
| ⑥ | **断言值本身过严** | 曾把 `AC-NFR-01` 的 30ms 套到 SSE 首帧上 → 间歇假红 | 否（已改为按对象选口径） |

判别规则（写进脚本注释的那几条）：① **单跑 B 绿、A 之后跑 B 红 ⇒ 是污染不是缺陷**；② **一条从不提 429 的脚本里出现 429 ⇒ 一定是污染**；③ 429 先看网关日志的 `code=`（`RATE_LIMITED` 按窗/按 IP vs `QUOTA_EXCEEDED` 按日累计）；④ 延迟判据用中位数；⑤ **总在同一个"整数秒"附近失败 ⇒ 先怀疑框架默认超时**（Kratos 的 2s），别急着怀疑上游。

## 3 优化清单

### 3.1 外部基线：OpenAI 的 `file_search` / vector store

口径：官方文档站 2026-09-30 直连返回 **403**，数字取自 **Microsoft Learn《How to use Azure OpenAI Assistants file search (classic)》**（`ms.date: 2026-08-21`）—— `file_search` 规范的镜像（同一套 `vector_stores` / `file_batches` 对象），
**按"业界公开口径"对待，不当作精确契约**。
机制：上传 / 索引 / 对话解耦 —— `POST /v1/files` 只拿 file_id，建 vector store 立即返回 `in_progress`，后台异步 pipeline，客户端**轮询 `status` / `file_counts`**；
run 前若仍有文件在处理，最多等 **60 秒**（只对 thread vector store 生效）；thread vector store **默认 7 天过期**。

| 项 | 业界值 | 我方现状 | 差在哪 |
| --- | --- | --- | --- |
| chunk size / overlap | 默认 **800 token** / **400 token**（= chunk/2） | `CHUNK_SIZE=512` / `CHUNK_OVERLAP=64` | size 合理，overlap 偏小 |
| **有效块长** | 由配置直接决定 | 中位 **175**（配置的 34%）⇒ UP-03 后 **490** | ❌ 配方放大片数（已修） |
| 入上下文块数 | 最多 **20** 块（并 rerank） | `RAG_CONTEXT_TOKEN_BUDGET` | 口径不同，需单独对齐 |
| 单文件上限 | **512 MB / 5,000,000 token** | 网关 `UPLOAD_MAX_MB=50` | 我方更保守（合理） |
| 每 vector store | **10,000 _files_** | `MAX_DOC_CHUNKS=10000` **_chunks_** | ⚠️ 见勘误 |
| 超限行为 | **报错**（`last_error`） | **静默截断 + 仍回 202** | ❌ 假成功 ⇒ UP-01 补可见性，UP-05 待 SRS |
| 批次大小 | 单批最多 500 files | 单请求单文件 | 无差距 |

> ⚠️ **勘误（2026-09-30）**：此前把业界上限说成"向量库最多 10,000 chunks"——**是错的**，官方口径是 **10,000 _files_ / vector store**。
> ① **不要拿"业界也是 1 万"来保留 `MAX_DOC_CHUNKS=10000`**，那把尺子量的是**文件数**；② 业界的块数由 chunk 参数 + "最多 20 块入上下文" + rerank 控制，不靠总块数硬上限。
> 我们的 `MAX_DOC_CHUNKS` 是自己的护栏，保留没问题，**但它不该是静默的**。

差距分析（G1~G8，逐条已收进 §3.3~§3.6 的 UP 行，这里只留性质）：G1 上传语义 **无差距**；G2 索引进度、G3 上限行为是**产品缺陷 → 已修 / 半修**（UP-01/UP-02，仅剩契约回写 04/07 与"是否拒收"待 SRS）；
G4 有效块长、G5 片数**已改，待召回重定标**（UP-03）；G6 重活位置**无差距**（降级为守门项，UP-04/UP-06）；G7 主机资源**已修**（UP-07）；G8 超大文件通道属 **P2**（UP-08）。

| `_merge_short` / `embed+upsert`（hash，batch=16） | 3.11s / 6.53s（1,061 批） | **5.43s** / **4.04s**（378 批） |

> 同一进程、同一份正文的分阶段计时：`parse_document` 0.59s / 0.59s（与切分配方无关）、`_split_block` ×84,846 3.62s / 3.62s（同上）、逐块 sha256 0.02s / 0.01s。`_merge_short` 慢出 +2.3s 是因为合并次数 +16%、且每次都要重算累计文本的 token 数；`embed+upsert` 变快是因为片数少 ⇒ 批次次数少 ⇒ 持久化/上报次数少。

**真实 HTTP 端到端**（`INFRA_BACKEND=memory` + `TASK_RUNNER=inline` + hash）：1MB → **760** 片（`chunks_total`=760、`truncated=false`、
上传→`INDEXED` **2.1s**）；8MB → **6,056** 片（`chunks_total`=6,056、`truncated=false`、**13.3s**、接口读回块长 min 479 / 中位 **490** / max 510）。
对照 §2.4 的跨体积表：1MB 旧口径 **2,141** 片 ⇒ 现在 **760**（2.82×，与 8MB 的 2.80× 一致）⇒ UP-03 的效果**与被测体积无关**（都是"碎段形状"的放大被消掉）。

**真实持久化下的 A/B**（Redis + Kafka + MySQL + Milvus + MinIO + 独立 Worker，hash）：命令 `python tools/worker_e2e_check.py --mb 8 --embedding hash [--old-merge]`。
新条件：切分 **6,056** / 入库 **6,056** / `truncated=False` / 上传→终态 **31.0s** / 入库期间 `/health` 中位 **27.7ms**；旧条件（`--old-merge`）：
切分 **21,212** / 入库 10,000 / `truncated=True`（丢 53%）/ **31.1s** / 25.5ms。

> ⚠️ **口径提醒**：`--old-merge` 把填充目标打回 `0.3`，块长中位 **136**（旧实现是 175），所以切分产出是 **21,212** 片而不是 16,969；两者都被截到 10,000，
> **入库工作量相同**，因此这一行比较的是"持久化 + 哈希向量化"那一侧，不是完整旧实现。Worker 日志可验：`ingest.chunks_truncated total=21212 limit=10000`
> → `ingest.completed chunks=10000 truncated=True`。⇒ **在 hash（非模型）路径上两种配方总耗时相同（31.0 vs 31.1s）**：片数少 2.8 倍省下的批次开销，被"现在要处理 70% 更多正文"抵消掉了；
> 真正的差别是**是否丢内容**。

**⚠️ 与预期不符：向量化时间不按片数下降。** 原因：合并把块变长，而 transformer 的**每 token 成本随序列变长而上升**。真 BGE 实测（16 块/批，取 3 次中位）：threads=10 时形状 A（旧，
中位 185 token）**4.84s ⇒ 303 ms/块**、形状 B（新，中位 481 token）**15.87s ⇒ 992 ms/块** ⇒ 每 token **1.64 → 2.06 ms/token（+26%）**；
threads=20 时 A **4.30s ⇒ 269 ms/块**、B **14.21s ⇒ 888 ms/块** ⇒ **1.45 → 1.85 ms/token（+28%）**。

同一份正文（3.0M token）的 BGE 时间估算：旧形状+截断 1.75M（10,000×175）×1.64ms ≈ **48 min**（内容完整度 59%）；旧形状+不截断 2.97M ×1.64ms ≈ **81 min**（100%）；
**新形状（UP-03）2.97M ×2.06ms ≈ 101 min**（100%）。交叉验证：原记的用户观察值是 **70min**，用 20 线程的旧形状成本算 `2.97M × 1.45ms = 71.8min` —— 几乎相等，
也就是说那次 70min **嵌入的是全部 2.97M token（没有截断）**，误差 ~15%（机器负载差）。

**端到端 A/B**（150KB / 63,540 字符 / ~54.9k token，真 BGE + 真持久化，threads=10）：旧条件 404 片 / 块长中位 136 / 上传→终态 **164.1s** / `/health` 46.2·110.9·157.4ms；
新条件 111 片 / 510 / **178.5s、156.8s**（两次）/ 43.0·105.7·129.8ms 与 39.1·62.2·69.2ms。**诚实结论**：端到端差异落在本机运行间噪声（±7%）之内，
分辨不出那个 +26% —— 150KB 这一档里"模型 + 持久化 + 池化开销"混在一起。**能确定的是**：片数 2.80× 下降是真的，**"因此快 2.6×"是假的**，方向甚至相反。

**顺带发现的可优化点（本次没改）**：`_merge_short` 每次合并都用 `count_tokens(累计文本)` 重算，8MB 要花 5.43s（旧条件 3.11s）。可以累加各段 token（近似）、
只在**收尾**精确重算一次 —— 最终计数仍精确（`test_char_offsets_track_the_source` 要求 `token_count == count_tokens(content)`），但合并判定会用近似值、**会轻微移动块边界与片数**。
收益 ~4s/8MB（相对 100min 可忽略）。

### 4.2 UP-07 / `TORCH_NUM_THREADS`：20（旧默认）vs 10（新默认）

同一份 150KB 文档、同一套真 BGE + 真持久化，**只改这一个变量**：

| `TORCH_NUM_THREADS` | 上传→终态 | `/health` 中位 | P95 | **最大** |
| --- | ---: | ---: | ---: | ---: |
| **10**（一半核，新默认） | **178.5s** / **156.8s** | 43.0 / 39.1 ms | 105.7 / 62.2 ms | 129.8 / 69.2 ms |
| **20**（逻辑核，旧默认） | **223.9s** | 66.2 ms | 133.8 ms | **3731.0 ms** |

**两个方向都变好**：自己的入库快 **25~30%**；在线请求中位好 **30~40%**，**尾延迟从 3.7s 降到 0.07~0.13s**。机制：本机**可用内存只有 ~1.7GB**，20 个 torch 线程会把内存带宽/缓存打满并触发抖动（那 3731ms 的尾延迟就是一次抖动）；线程减半同时缓解了核争用与内存压力。

**独立进程视角**（另一个进程做 6M 次乘加的固定任务）：空闲 530ms（1.00×）→ 向量化中 threads=10 **1362ms（2.57×）** → threads=20 **1525ms（2.88×）**。⇒ 线程减半只拿回 **~11%** 的"饿死"，**剩下的瓶颈是内存带宽而不是核数**，单靠线程数消不掉；真正能消掉它的是换执行位置（§4.5）或在内存更宽裕的机器上跑。

**默认值语义**：`Settings.torch_num_threads` 由 `app/core/config.py::default_torch_num_threads()` 给出 `max(1, os.cpu_count() // 2)`（本机 20 逻辑核 ⇒ 10）；
显式写 `0` 仍是合法的"不干预"，但不再是默认。`.env` 里不写这一行就是默认值；`.env.example` 给的是注释掉的 `# TORCH_NUM_THREADS=10`（**不要写空值**）。取一半而不是 `2`：
一半是"单次向量化略慢"与"整机不被饿死"的折中，取 `2` 会让大文档的**绝对**耗时成倍上涨，而验收与用户感知的正是绝对耗时。

### 4.3 UP-06：隔离档（`real` + `kafka`）的收益与代价

启动日志（用真实 `.env`）：`app.startup infra_backend=real task_runner=kafka task_store=RedisTaskStore task_event_bus=RedisTaskEventBus embedding_provider=bge`
 + `task.compensator_started interval=30.0 grace=60.0` → **不因外部依赖未就绪而拒绝启动**；`/health` 逐项报 `storage=real / redis ok 8ms / milvus ok 4ms / mysql ok 9ms`。


8MB、hash 向量化、Worker 独立进程：上传响应 `202`、**558ms**（正文 8.39MB，multipart `file` 字段）；任务流转 `QUEUED → RUNNING/PARSING → CHUNKING → EMBEDDING(…/6056) → SUCCEEDED`；
上传→终态 **31.0s**；**入库期间 API `/health`：n=74，中位 27.7ms，P95 39.2ms，最大 53.6ms**；Worker 日志 `ingest.completed chunks=6056 chunks_total=6056 vectors=6056 truncated=False`。
⇒ "大文件不再拖垮在线请求"**成立**：Worker 满负荷嚼 6,056 片时，API 的 `/health` 仍是几十毫秒级。

**代价（必须写清楚）**：不启动 Worker ⇒ 任务永远停在 `QUEUED`（实测只起 API、上传 8MB，任务 10 分钟不结束；`task.queued topic=ai.task.document_ingest attempt=1` 之后没有消费者）。
这不是 bug（Kafka 语义如此），但换了出厂档就多了一个必须先起来的进程。另一侧：上一次实验遗留的 `PENDING` 任务在 Worker 起来后被自动消费并完成（日志里的 `chunks=1` 那条）⇒ 投递/消费与补偿扫描是通的。

### 4.4 重排（rerank）耗时：本地 BGE 的首次实测

**为什么之前没有数据**：全仓库只有**目标值**（"含 Rerank 600/1500/2500ms"、"检索 P95 ≤ 300ms（向量召回）；≤ 1.5s（含 CPU Rerank）"）与**模型加载 2.5~3.0s**；此前的 E2E 只发过 `POST /knowledge-bases`、`POST …/documents`、`GET /health`，**从未走过 `/search`**。

测法：真实路径 `BgeReranker.rerank(query, documents, top_n=5)`（`app/rag/reranker/bge.py`），候选按真实块形状构造（~847 字/条，被
`FlagReranker` 默认 `max_length=512` 截断 ⇒ 每对 ≈ 512 passage + ~15 query token）；`FlagReranker` 默认值经查源码：`max_length=512`、
`query_max_length=384`、`batch_size=128`（20 条候选 = 一次前向）。threads=10（本机默认）：候选 5 条 **首轮 14,993ms / 稳态中位 14,016ms**（2,803 ms/对），
候选 **20** 条（生产默认 `top_k=20`）**首轮 59,474ms / 稳态中位 83,140ms**（4,157 ms/对）；模型加载 17.31s（冷）/ 6.17s（页缓存热）。threads=20：
20 条候选 **首轮 74,171ms / 中位 68,055ms**（3,403 ms/对）。

- **换掉 embedding 之后，重排成了 RAG 在线路径的最大项**：一次 `/search`（`top_k=20 → top_n=5`）光重排就 **~70~83s**，而目标是「含 CPU Rerank P95 ≤ 1.5~2.5s」⇒ **超目标约 30~50×**；入库从 70~100min 降到 81s 之后，**用户可感知的慢转移到了每次提问**。
- **非线性放大，与内存强相关**：候选 5 → 20（×4）墙钟 ×5.9，单对成本 2.8s → 4.2s。**线程数**：干净单测下 20 线程比 10 线程快约 18% —— 与 §4.2「一半核更好」**不矛盾**（那条测的是整机被入库抢占时，这条是空载）；各只有一次 3 采样中位，**不宜当结论**。
- **方舟没有 rerank 能力**（`volcengine-python-sdk` wheel 里含 "rerank" 的文件数为 **0**）。可用杠杆（按性价比）：`RERANKER_ENABLED=false`（退化为向量分数，会记 `rerank_skipped`）→ 把 `top_k` 由 20 降到 5~8（5 条只要 14s）→ 换小模型 / ONNX int8 → 上 GPU。

### 4.5 换云端 embedding / rerank：分钟级 → 秒级

动机：§4.1 已证明"切分配方"救不了 70~100min 的 CPU 向量化 —— 这台机器（可用内存 ~1.7GB、无 GPU）上唯一的数量级杠杆是**换执行位置**。先试火山方舟，最终档位是硅基流动。

**方舟 `doubao-embedding-vision-251215`（中间实验）**：`input` 是"一个"多模态输入、**一次请求只返回一条向量**（SDK 类型 `MultimodalEmbeddingResponse.data: MultimodalEmbedding`
 是单数，对比文本端点的 `List[Embedding]`）；传 N 条文本会被**聚合成一条**（1/3/256 条都只回 1 条 2048 维，`usage.prompt_tokens` 随条数累加，256 条 → 3493；
`cos(A,A+B)=0.80`、`cos(A,B)=0.08`）；`input` 写成"数组的数组"→ 400（`could not parse the JSON body`），文本端点 `does not support this api`
 ⇒ **一个 chunk = 一次 HTTP，批量只能靠并发**（与 Dify 插件 PR #3593、oGMemory `volcengine_embedder.py` 的做法一致）。

并发吞吐（每条 ~490 token 的真实块）：并发 1 → 4.4 req/s、6,056 片约 23 min；并发 8 → 31.6 req/s、~3.2 min；**并发 32 → 98.9 req/s、~1.0 min**；
并发 64 → 99.5 req/s（无增益）；四档失败均 0/128。端到端 8MB 入库 **81.4s**（5,822 片、`truncated=False`），平均 **14 ms/片** vs CPU BGE 实测 **992 ms/片** ⇒ 该阶段约 **71×**；
小文档语义抽查 **5/5** 命中（top1 0.66~0.77）。已落地的三个参数：`encoding_format=base64`（响应体 **34,240B → 11,219B，3.05×**，`data.embedding` 是 base64 的 float32 **小端**）、
`dimensions=N`（**1024 可用、512 被拒**，与全维前 N 维余弦 **0.9992**）、`instructions`（接受，默认不发）。两个坑：① **维度对齐 ≠ 向量空间能混用** ⇒ 必须换集合名或 drop 重建；
② 该 API **跨请求不是逐位确定的**（同一文本三次，`#1 == #2`，`#3` 最大逐元素差 **4.883e-03**，中位 4.578e-04）⇒ 不要写"同文本必得同向量"的断言，项目内的 `content_sha256` LRU 缓存反而更稳定。

**硅基流动（最终档位，embedding + rerank 全换）**：向量化 `Qwen/Qwen3-Embedding-0.6B`（原生 **1024** 维，`POST /v1/embeddings`）、
重排 `Qwen/Qwen3-Reranker-0.6B`（`POST /v1/rerank`）。关键语义：`/v1/embeddings` **支持真批量（N 进 N 出）**（实测 8/32/64/128 条都返回同数量并带 `index`）；
上下文 **32768 token**（bge-m3 是 8194）；`dimensions` 仅 Qwen3 系列、0.6B 可选 `[64,128,256,512,768,1024]`；`encoding_format=base64`
 把单条 **21,891B → 5,641B（3.9×）**；**可复现性优于方舟**（float×3、base64×2、跨编码 float↔base64 全部 **0.000e+00**）；`/v1/rerank`
 的 `documents` **必须是字符串数组**（传 `[{"text": …}]` → 400）；响应**没有 `usage`**（计费在 `meta.tokens.input_tokens`，20 条 ×490 token ⇒ 11,950）；
错误体 `{"code":20012,…}` / 401 `{"code":30014,…}` ⇒ 直接把 `message` 带进异常详情。

吞吐（490 token 的块）：batch 16 × 并发 4 → **140.4 片/s**（中位 406ms）；32 × 4 → **205.7**（612ms）；**32 × 8 → 379.6**（654ms，取此档）；
48 × 8 → 288.8（中位 **1265ms**，尾延迟变差）。端到端 8MB 入库（5,821 片、`truncated=False`）：**串行等待**（交一批 → 等返回 → 再交下一批）**98.2s**（16.9 ms/片）；
`INGEST_EMBED_WINDOW=8` → **40.4s**（6.9 ms/片）；窗口 16 → 40.9s（7.0 ms/片，**8 已是拐点**）。

> ⚠️ **这里暴露了一个真问题（已修）**：provider 内部有并发池，但入库循环是严格串行 ⇒ **池子完全是空的**，只维持一个请求在飞。本地 BGE 时代串行没有代价（算力在本机），换云端后每次调用都是一次网络往返，串行等于自断吞吐。
> 修法是 `_embed_and_upsert` 按窗口 `asyncio.gather`（窗口内顺序 upsert + 逐批上报，保住进度与取消语义）。参考坐标：CPU BGE **≈101 min**、方舟（每片一次 HTTP）**81.4s**、硅基流动 **40.4s**。

云端 rerank 与本地对比（`top_k → top_n=5`）：候选 5 → **292ms**（本地 14,016ms）；8 → **147ms**；12 → **191ms**；
20 → **320ms**（本地 83,140ms @10 线程 / 68,055ms @20 线程）。⇒ 20 条候选 **320ms** 回到目标内，排序正确（问"退款要几个工作日"，退款段 0.9998、无关段 0.0007）；
实测 50/100/201 条候选都是 200，但 201 条耗时 2903ms ⇒ 按 `SILICONFLOW_RERANK_MAX_DOCUMENTS=100` 分片、各取 `top_n` 后全局归并。
语义抽查 **5/5 命中**（年假 0.802 / 报销 0.637 / 加班 0.778 / 保密 0.730 / 培训 0.768，top1 与 top2 普遍拉开 0.25 以上）。边角事实：同一文本**单独编码 vs 放进批 2 ⇒ 0.000e+00**，
**单独 vs 放进批 32 ⇒ 1.938e-03** ⇒ 仍不能写"同文本必得同向量"的断言。

连带变化：`RERANKER_PROVIDER` 显式枚举（`bge` / `siliconflow`），**删掉了"看模型名里有没有 bge"的猜法**（`Qwen/Qwen3-Reranker-0.6B` 名字里没有 `bge`，老实现会**静默退化成不重排**）；
Milvus 集合换到 **v3**（1024 维，v1 也是 1024 但**向量空间完全不同**）；本地 `bge-reranker-v2-m3`（2.14GB）已无人使用；`BAAI/bge-m3` 权重删除释放 **6.36 GB**（HF 缓存 43 个文件）；
**`TORCH_NUM_THREADS` 在新档位下不再影响任何东西**（本地推理栈退出链路，§4.2 的结论只对 `bge` 档成立）。

**顺带修掉的两个真 bug（验证时撞上，与 embedding 无关）**

1. **Markdown 解析会静默丢正文**：归一化里的「合并中文孤行」把「`## 年假` + 下一行中文正文」粘成 `## 年假员工入职满一年后……`，该行**仍以 `## ` 开头** ⇒ 被当成标题 ⇒ 正文被丢弃（标题只用来填 `heading_path`）。
整篇如此写时 `char_count=0`，用户只看到「文档有效文本不足（0 < 50 字符）」。触发条件是「标题以 CJK 结尾 且 下一行以 CJK 开头」——**中文文档的常态写法**；原有 5 条 markdown 单测**全部**在标题后留了空行，所以一直没暴露。
修法：`normalize_text(..., join_cjk_lines=False)` 只给 Markdown 用；回归用例见 `tests/unit/test_parsers.py`。实测同一份小文档修复前 `0 字符 / 0 块`、修复后 `184 字符 / 5 块`。
2. **顺序敏感的契约用例**（换 embedding 后冒 6 条失败，单独跑全过、连着跑必挂；就绪探针报 `2048` 应为 `1024`）：根因是 **`import pymilvus` 会在 import 期执行 `load_dotenv()`**，
把开发机 `.env` 灌进 `os.environ`，而 `Settings(_env_file=None)` 只关得掉 dotenv 文件、关不掉环境变量。修法：应用侧 `_import_pymilvus_guarded` 做「快照 → import → 恢复」；
测试侧 `_BASE` 显式钉住 `embedding_model` / `embedding_dim` / `milvus_vector_dim` 并加 autouse 的 `os.environ` 还原。

### 4.6 OPT-01 与"关掉系统代理"：本机复现不出它要解决的问题

把 .NET 默认代理显式指向一个**会记录请求的本地代理**（`BypassProxyOnLocal=$false`）：回环 `http://127.0.0.1:8898/` → HTTP 200（**目标直接应答**），代理收到 **0 笔**；
非回环 `http://probe-host.invalid/x` 与 `http://another.invalid/y` → 各 200，代理各收到 **1 笔**。⇒ .NET/PS **确实**认 `DefaultWebProxy`，
但**对回环地址一律绕过**（即使 `BypassProxyOnLocal=false`）。

每请求开销（同一调用内，各 20 次，中位）：`Invoke-WebRequest`（默认）**13.0 ms**（12.5~14.7）；`-Proxy $null` 13.5 ms（12.9~14.4）；`DefaultWebProxy=$null` 13.9 ms（13.4~14.5）；`curl.exe --noproxy '*'` 28.6 ms（15.1~46.7）；`urllib`（无代理）12.9 ms（2.0~26.5）。

结论：改动（进程级 `DefaultWebProxy = $null` + `-Proxy $null` / `-NoProxy`，覆盖 stage1..6 全部 IWR、stage4 的 `HttpWebRequest` SSE、stage5/6 的健康与 `/metrics` 探测；
AI 侧 `tools/curl_e2e.ps1` 走 `curl.exe --noproxy *`）**无害、可保留** —— 它是"如果哪天有个真会拦回环的代理（TUN 模式 / WPAD）就挡一下"的防御。
**但它不是 M1 43s 的成因**：13ms × 104 次 ≈ **1.4s**，全砍掉也换不回 43s。`OPT-01`（换 `HttpClient` 复用连接）的收益空间仍在，但**不在代理这一层**：
IWR 13.0ms 已和 urllib 持平、比 `curl.exe` 快（curl 每次一个进程，~15ms 启动）。⚠️ 这几个脚本**假定目标全是回环**；把 `-BaseUrl` 指到非回环地址时要删掉那一段。

```python
import math
LINE = "# 上传流式转发测试\n\n这是第 {0} 段占位文本，用于把文件撑到指定大小。\n"

def make_text(target_bytes):          # 复刻 curl_stage5.ps1::New-TextBody
    lb = len(LINE.format(0).encode("utf-8"))
    raw = "".join(LINE.format(i) for i in range(math.ceil(target_bytes / lb))).encode("utf-8")
    if len(raw) > target_bytes:        # 按字节裁到目标以内、在最后一个换行处收尾
        cut = min(target_bytes, len(raw) - 1)
        while cut > 0 and raw[cut] != 10:
            cut -= 1
        raw = raw[: cut + 1]
    return raw

from app.rag.chunking import ChunkingService
from app.rag.parsers import parse_document

raw = make_text(8 * 1024 * 1024)
parsed = parse_document("m5.txt", raw, min_chars=1)        # 真实解析器
svc = ChunkingService(chunk_size=512, chunk_overlap=64)   # 与 .env 一致
drafts = svc.split_blocks(parsed.blocks)
print(len(parsed.blocks), len(drafts))   # 改前 -> 84846 16969；UP-03 之后 -> 84846 6056
```
