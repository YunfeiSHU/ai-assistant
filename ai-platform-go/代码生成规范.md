
1. 使用 Go-Kratos 官方推荐的项目结构：
   api/
   cmd/
   configs/
   internal/
   └── conf/
   └── server/
   └── service/
   └── biz/
   └── data/

2. 不要自行引入 controller、handler、repository、model、dao、manager、
   component、common、utils 等大而泛的目录，除非业务规模确实需要且有明确职责。

3. 优先保持简单、清晰、可维护，不为了体现“架构感”增加无意义的层级。

4. 一个功能应尽量沿着：
   API → Service → Biz → Data
   的方向组织代码。

5. 不允许为了目录数量而拆分代码。
   只有当某个模块具有独立职责、独立依赖或明显复杂度时才拆分文件/目录。

三、各层职责

1. api

只负责 API 契约。

包括：
- protobuf
- HTTP API 定义
- gRPC API 定义
- Request / Response
- API 错误码定义

禁止：
- 数据库操作
- Redis 操作
- 业务逻辑
- 第三方服务调用

不要在 api 层编写业务逻辑。


2. service

负责 API 层与业务层之间的适配。

主要职责：
- 接收 HTTP/gRPC 请求
- 参数基础校验
- Request DTO → Biz Command
- 调用 biz
- Biz Result → Response DTO
- API 层错误转换

Service 不负责：
- MySQL 查询
- Redis 操作
- 复杂业务判断
- Agent 核心逻辑
- 第三方 API 调用

Service 应尽量保持薄。


3. biz

这是核心业务层。

负责：
- 业务规则
- 用例编排
- 领域对象
- 业务状态转换
- 事务边界设计
- Repository / Client 接口定义

Biz 不应该直接依赖：
- GORM
- Redis SDK
- HTTP Client
- MySQL Driver
- Milvus SDK
- Kafka SDK 等具体基础设施实现

如果需要访问外部资源，在 biz 中定义接口，
由 data 层提供具体实现。

例如：

type UserRepo interface {
    Get(ctx context.Context, id int64) (*User, error)
    Save(ctx context.Context, user *User) error
}

具体 MySQL 实现在 data 层。


4. data

负责具体基础设施实现。

包括：
- MySQL
- Redis
- Milvus
- HTTP Client
- gRPC Client
- Kafka
- MinIO
- 第三方 API Client
- Repository 实现

data 层实现 biz 中定义的接口。

依赖方向：

service → biz
data → biz

而不是：

biz → data


5. server

负责服务器基础设施。

包括：
- HTTP Server
- gRPC Server
- Middleware
- Service 注册
- Server 配置
- Server 生命周期

不要在 server 中实现业务逻辑。


6. cmd

只负责应用启动和依赖注入。

包括：
- 加载配置
- 初始化依赖
- Wire Provider
- 创建 Server
- 启动/关闭应用

不要在 main.go 中实现业务逻辑。


四、依赖方向必须遵守

严格遵守：

api
 ↓
service
 ↓
biz
 ↑
data

server → service
cmd → server / biz / data

推荐理解为：

          api
           ↓
        service
           ↓
          biz
           ↑
          data

data 实现 biz 定义的接口。

禁止出现：

biz → data
biz → GORM
biz → Redis
service → GORM
service → Redis
service → MySQL
api → data


五、文件拆分规则

1. 不要把所有业务写进 service.go。

2. 不要创建一个 1000+ 行的巨大文件。

3. 按业务职责拆分，而不是按代码类型机械拆分。

例如：

internal/biz/
├── agent.go
├── conversation.go
├── memory.go
├── rag.go
└── tool.go

而不是：

internal/biz/
├── models.go
├── repositories.go
├── services.go
├── managers.go
└── utils.go

4. 如果两个功能共享大量业务规则，可以放在同一个 biz 文件；
   不要为了形式强行拆分。

5. 如果一个文件超过约 300~500 行，应检查是否存在明显的职责混杂，
   但不要为了达到行数限制而机械拆文件。


六、Repository / Client 规则

1. Repository 接口定义在 biz。

例如：

internal/biz/user.go

type UserRepo interface {
    Get(ctx context.Context, id int64) (*User, error)
}

2. Repository 实现在 data。

例如：

internal/data/user.go

type userRepo struct {
    data *Data
}

func (r *userRepo) Get(...) {...}

3. 外部服务 Client 同样遵循这个原则。

Biz：

type LLMClient interface {
    Chat(ctx context.Context, req *ChatRequest) (*ChatResponse, error)
}

Data：

type llmClient struct {
    client *http.Client
}


七、AI Agent 项目特殊规则

如果项目包含 Agent、RAG、Memory、Tool Calling 等 AI 能力：

不要直接把所有内容放到：

internal/agent/

而应根据业务职责放入 biz：

internal/biz/
├── agent.go
├── conversation.go
├── memory.go
├── rag.go
└── tool.go

如果 AI 能力调用外部基础设施：

LLM API
Milvus
Redis
MCP Server
Object Storage

则：

业务规则 → biz
具体 SDK / HTTP / RPC 实现 → data

例如：

biz:
type VectorStore interface {
    Search(ctx context.Context, query []float32) ([]Document, error)
}

data:
type milvusStore struct {
    client *milvus.Client
}


八、Go 与 Python 服务边界

如果 Go 是 API / 平台服务，Python 是 AI Service：

对外：

Client
 ↓
HTTP / SSE
 ↓
Go-Kratos

内部：

Go-Kratos
 ↓
gRPC
 ↓
Python AI Service

不要为了统一协议，把所有 HTTP API 都改成 gRPC。

Go 负责：
- 用户
- 会话
- API
- 权限
- 任务
- 服务治理

Python 负责：
- LLM
- Agent
- LangGraph
- RAG
- Embedding
- Rerank
- Tool Calling

具体边界根据业务需求决定，不要重复实现。


九、HTTP / gRPC 规则

1. API 契约优先使用 protobuf。

2. HTTP 和 gRPC 如果属于同一业务接口，
   优先通过 Kratos protobuf / gateway 生成对应代码。

3. 不要手写大量重复的 HTTP Handler。

4. ChatStream / SSE 属于流式 HTTP 场景，
   不要为了“全部 gRPC 化”而强行改成普通 gRPC。


十、数据库规则

禁止：

service 直接操作 GORM。

禁止：

biz 直接操作 GORM。

正确：

service
  ↓
biz
  ↓
Repository Interface
  ↓
data
  ↓
GORM
  ↓
MySQL


十一、Redis 规则

Redis 属于基础设施。

禁止在 service 中直接调用 Redis Client。

推荐：

biz 定义：

type SessionRepo interface {
    Get(ctx context.Context, id string) (*Session, error)
    Save(ctx context.Context, session *Session) error
}

data 实现 Redis 访问。


十二、禁止过度抽象

不要为了“设计模式”而增加：

- Manager
- Factory
- Facade
- Adapter
- Helper
- Util
- Common
- BaseService
- BaseRepository

如果只有一个实现，不要为了形式创建多层抽象。

只有当：
- 存在多个实现
- 需要依赖倒置
- 需要测试 Mock
- 存在明显变化点

时才增加接口。


十三、代码生成流程

生成代码之前，必须先：

1. 明确业务需求
2. 明确 API
3. 明确业务用例
4. 明确数据依赖
5. 明确模块边界
6. 确定文件归属
7. 再生成代码

不要直接从需求描述一次性生成整个项目。

如果修改已有项目：

先分析现有目录结构和依赖关系，
然后只修改必要文件。

不要为了实现一个小功能重构整个项目。


十四、输出代码前先给出结构

每次生成较大功能时，先输出：

1. 修改/新增哪些文件
2. 每个文件的职责
3. 文件之间的调用关系
4. 依赖方向

确认结构合理后再生成代码。

例如：

新增：

api/agent/v1/agent.proto
internal/service/agent.go
internal/biz/agent.go
internal/data/agent.go

职责：

proto     → API 契约
service   → 请求适配
biz       → Agent 业务编排
data      → Repository 实现

调用链：

HTTP/gRPC
    ↓
Service
    ↓
AgentUseCase
    ↓
AgentRepo
    ↓
Data
    ↓
MySQL/Redis/External Service


十五、最终原则

代码结构优先级：

业务职责清晰
>
依赖方向正确
>
容易测试
>
容易扩展
>
目录数量

不要为了看起来“高级”而增加架构层。

保持：

API 清晰
Service 薄
Biz 核心
Data 隔离基础设施
Server 负责启动
Cmd 负责组装

任何新代码都必须首先判断：
“它属于 API、Service、Biz、Data、Server 还是 Cmd？”

如果无法明确归属，先分析职责，不要随意创建新目录。
