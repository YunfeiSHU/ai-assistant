# 代码生成规范

本文管四件事：**契约真源在哪、怎么生成、生成物与手写物的边界、跨语言（Go ↔ Python）怎么对齐**。
不管的事：缩进/空行/注释风格由 `gofmt` + `ruff` 管；接口字段明细见 [docs/02](./docs/02-接口规范与鉴权.md) 与
[docs/04](./docs/04-AI服务编排与网关.md)；表结构与 Redis Key 见 [docs/05](./docs/05-数据模型.md)。重复的表格这里一律只给指针。

> **§一~§六 的编号是冻结的**：`internal/{biz,service,data,server}` 的包注释、`cmd/server/main.go`、
> [docs/08-§1.4](./docs/08-实现进度与运行手册.md) 共 30+ 处引用「规范 §四/§六/§三.2/§五.3」。
> 重写内容可以，改编号会让这些引用全部指空 —— 所以下面的章节序与条目号沿用旧版。

## 一、总则

1. **每个接口方向只有一份可编辑契约**：gRPC 方向是 `proto/aiplatform/v1/chat.proto`，HTTP 方向是
   SRS（[docs/02](./docs/02-接口规范与鉴权.md)/[docs/03](./docs/03-用户与会话服务.md)）+ Pydantic（OpenAPI）。
2. **生成物不手改**（详见 §九）。改契约 → 重新生成 → 编译，是唯一合法路径。
3. **不为「架构感」加层**。PO/DO 拆分只用于真的跨越 `biz ↔ data` 的类型，实测只有 3 个：
   `User` / `RefreshToken` / `AuditLog`；`Conversation` / `Message` / `Quota` / `Idem` 保持单一类型。
4. **先定落位再写码**：先回答「它属于 api / service / biz / data / server / cmd」，答不出来说明职责没想清。
5. **不为目录数量拆文件**：拆分判据是职责、依赖、复杂度，不是行数。

`api/` 里**只有 gRPC 生成物**：`chat.pb.go`（`protoc-gen-go`）、`chat_grpc.pb.go`（`protoc-gen-go-grpc`），
**没有** `*_http.pb.go` —— 对外 HTTP 是 Gin，不用 kratos 的 HTTP 注解（理由见 §七）。

## 二、目录与文件落位

| 路径 | 性质 | 放什么 |
| --- | --- | --- |
| `proto/aiplatform/v1/chat.proto` | **真源** | 唯一可编辑的 gRPC 契约（当前 323 行） |
| `api/aiplatform/v1/` | 生成物 | Go 桩，不手改 |
| `internal/conf` | Go | 配置加载 + 启动期校验，fail-fast（`.env` 存在但解析失败即退出） |
| `internal/server` | Go | 路由装配与中间件链：`recovery → trace → logging → metrics → cors → 幂等 → 鉴权 → 限流`（中间件实现在 `server/middleware`） |
| `internal/service` | Go | 用例层：请求绑定、DTO 映射、SSE 逐帧渲染 |
| `internal/biz` | Go | 领域逻辑与**仓储接口**（不 import `data`） |
| `internal/data` | Go | 仓储实现；`mysql/` `redis/` 是引擎层，`ai/` 是 ai-platform 客户端（HTTP 透传 + gRPC 拨号） |
| `pkg/` | Go | 11 个可复用包：`errs httpx ids clockx cryptox jwtx logx cursor ssex metricsx otelx` |
| `cmd/server`、`cmd/hashpw` | Go | 对外入口 / argon2id 离线哈希工具 |
| `app/grpc/aiplatform/v1/` | 生成物 | `chat_pb2.py`、`chat_pb2.pyi`、`chat_pb2_grpc.py` + 两层 `__init__.py` |
| `app/core/sse.py` | Python | SSE 帧格式的唯一出口 |
| `app/schemas/` | Python | Pydantic 模型，逐条对齐 SRS，**不**从 proto 派生 |

禁止引入的大而泛目录：`controller`、`handler`、`repository`、`model`、`dao`、`manager`、`component`、
`common`、`utils`。同一个概念在两侧只有一个名字：`internal/data/redis/keys.go:14` 定义 `gw:` 前缀，MUST NOT 触碰
Python 的 `ctx:` / `lock:` / `summary:` / `task:` / `cancel:` / `embed:` / `dedupe:` / `rate:` / `retry:zset`。

## 三、各层职责

**1. api** —— 只放契约：protobuf、Request/Response、错误码定义。禁止数据库、Redis、业务逻辑、第三方调用。
本项目的 `api/` 是生成物，人不写。

**2. service** —— API 与业务之间的适配：绑定参数 → 调 `biz` → 映射错误 → 写响应，外加
`Biz Result → Response DTO`。`UserResponse` / `TokenResponse` 在这里，`PasswordHash` / `TokenVersion`
只存在于 DO，物理上无法泄漏。不碰 MySQL/Redis、不写业务判断、不 import `data`。

**3. biz** —— 核心：业务规则、用例编排、领域对象、状态转换、事务边界、**仓储与外部 Client 的接口定义**。
MUST NOT import `gin` / `gorm` / `redis` / Milvus / Kafka 等具体实现；依赖只有 `pkg/*`。领域哨兵错误也定义在这里
（`internal/biz/errors.go:7`）：依赖方向是 `data → biz`，业务语义由 biz 命名、`data` 在仓储实现里翻译（唯一翻译点
`data.translate` / `IsDuplicate`）。留在 `data` 的话，`biz` 单测就得拉起真实仓储。

**4. data** —— 基础设施实现：MySQL、Redis、HTTP/gRPC Client、Repository 实现。`data/mysql`、`data/redis` 是引擎层
（只认连接/事务/驱动），仓储文件直接坐在 `data.Data` 上（知道 SQL，不认 gin）——「换驱动」与「换表结构」是两件独立的事。

**5. server** —— HTTP Server、中间件、Service 注册、生命周期。中间件归 `internal/server/middleware`，不写业务逻辑。

**6. cmd** —— 只做启动与依赖注入：加载配置、初始化依赖、创建 Server、启动/关闭。装配是 7 步线性代码，
**不用 `wire`**（`wire` 只是多一步生成）；不写业务逻辑。

## 四、依赖方向（硬约束）

```text
cmd/server → server → service → biz → pkg/*
                        data  → biz
```

禁止：`biz → data`、`biz → gin/gorm/redis`、`service → data`、`service → MySQL`、`api → data`。
验证方式（不是靠肉眼）：

```powershell
go list -f '{{join .Imports "\n"}}' ./internal/biz   # 只应出现 pkg/* 与标准库
go list -deps ./internal/service | Select-String 'internal/data'   # 应无输出
```

4xx/5xx **只能**经 `httpx.Fail` 写出：绕过它就会出现字段缺失的信封，客户端按 `error.code` 分支时落到 default。

## 五、文件拆分与命名

1. 不把业务写进 `service.go`，不造 1000+ 行的大文件；超 300~500 行先查职责是否混杂，不为行数机械拆。
2. 共享大量业务规则的两个功能可以同文件；拆分的理由是独立职责/独立依赖/明显复杂度。
3. **按业务职责命名，不按代码类型命名**。实测文件集就是正面例子：
   `internal/biz/{user,auth,conversation,message,message_stream,chat,chat_stream,idempotency,quota,retention,circuit,metrics}.go`；
   反例 `models.go` / `repositories.go` / `services.go` / `managers.go` / `utils.go`。`internal/data` 只有两个例外：
   `model.go`（PO + 列约定）、`json.go`（列的自定义类型），其余每个聚合一个文件。

## 六、接口归 biz、实现归 data

仓储与外部 Client 的接口定义在 `biz`，实现类型在 `data` 且**不导出**，只导出构造函数
`NewXxxRepo(*Data) biz.XxxRepo`。这条不是为了好看：倒置它，同一份业务规则会在 HTTP 入口与 gRPC 入口各写一遍，
换存储要改业务代码。

```go
// biz：interface
type UserRepo interface{ Get(ctx context.Context, id int64) (*User, error) }
// data：实现 + 唯一导出
type userRepo struct{ data *Data }
func NewUserRepo(d *Data) biz.UserRepo { return &userRepo{data: d} }
```

外部服务同理：`LLMClient` / `VectorStore` 的接口在 `biz`，HTTP/SDK 实现在 `data/ai`。只有一个实现时也建接口，
判据是「需要 Mock / 需要依赖倒置 / 存在明显变化点」，不是「设计模式要求」。

## 七、proto 契约真源

真源只有一份：**`ai-platform-go/proto/aiplatform/v1/chat.proto`**。Python 侧不保留第二份可编辑副本，
`ai-platform/tools/gen_grpc_stubs.ps1:34` 用绝对路径指向它。

为什么放在网关模块而不是父仓库根：网关是这份契约的**所有者**（[docs/04](./docs/04-AI服务编排与网关.md) 是网关的 SRS，
AI 侧按其实现），放在模块内让「改契约 → 重新生成 → 编译」在同一个模块里完成，不依赖模块外的相对路径。

为什么只定义 gRPC、**不写** `option (google.api.http)`：网关对外是 Gin HTTP/SSE，带上该注解要多依赖
`google/api/annotations.proto`（得额外维护 `third_party/`），而对外 HTTP 契约的真源是 docs/02、docs/03 与 Pydantic。

proto 内的命名约定：

| 项 | 约定 | 现状 |
| --- | --- | --- |
| package | `<产品>.v1` | `aiplatform.v1` |
| go_package | `<module>/api/<dir>;<pkgname>`，**必须含 `;` 别名** | `.../ai-platform-go/api/aiplatform/v1;aiplatformv1` |
| service | 一个服务端一段 RPC，注释必须写「等价于哪个 HTTP 接口」 | `AiPlatform` / `Chat` / `ChatStream` |
| 流式事件 | 一个 `ChatEvent` oneof + 每个事件一个 `Stream*` message | `StreamMeta`…`StreamUnknown` |
| 错误信封 | `AiError`，字段 `code/message/http_status/retryable/trace_id/details_json` | `chat.proto:45` |
| 任意 JSON | proto3 无「任意 JSON」类型，统一用 `*_json` 的 **string** 承载 | `details_json`、`arguments_json` |

字段名不许「顺手改」：回答正文在契约里叫 `answer`（落库时才映射到消息台账的 `content`），改成 `content` 两侧
字段快照测试立刻红。`ChatRequest` 也**刻意不含** `stream`（gRPC 方法本身非流式）与 `user_id`（身份来自
`authorization` metadata，网关 MUST NOT 自报身份）。数量约束写进注释并被测试守着：`query` 去空白后 1..8000 字符、
`history` 最多 200 条、`kb_ids` 最多 10 个、`metadata` 键值各 ≤ 64 字符。

`AiError` 为什么不靠 gRPC 规范码：多个业务码共用同一规范码（`UPSTREAM_LLM_ERROR` 与 `OVERLOADED` 都是
`UNAVAILABLE`；`CONTEXT_TOO_LONG` 与 `QUERY_EMPTY` 都是 `INVALID_ARGUMENT`），只靠规范码会让「上下文超限」
与「提问为空」在客户端看起来一样。

## 八、生成命令

两条命令，各自在自己的模块根下执行：

```powershell
# 工作目录：ai-platform-go\
powershell -ExecutionPolicy Bypass -File tools\gen_proto.ps1

# 工作目录：ai-platform\
powershell -ExecutionPolicy Bypass -File tools\gen_grpc_stubs.ps1
```

| 脚本 | 输入 | 输出 | 生成后自检 |
| --- | --- | --- | --- |
| `tools/gen_proto.ps1` | `proto/aiplatform/v1/chat.proto` | `api/aiplatform/v1/{chat.pb.go, chat_grpc.pb.go}` | 从 proto 读回 `go_package` 并校验模块前缀；输出目录非空，否则 FAIL |
| `tools/gen_grpc_stubs.ps1` | `../ai-platform-go/proto/aiplatform/v1/chat.proto` | `app/grpc/aiplatform/v1/{chat_pb2.py, chat_pb2.pyi, chat_pb2_grpc.py}` + 两层 `__init__.py` | ≥2 个 `.py`；`chat_pb2_grpc.py` 必含 `app.grpc.aiplatform.v1`，否则 FAIL |

前置工具（本机已在 PATH）：`protoc` v27.3、`protoc-gen-go` v1.36.10、`protoc-gen-go-grpc` v1.5.1；
Python 侧用 `.venv\Scripts\python.exe -m grpc_tools.protoc`。

**为什么是脚本而不是「文档里写一条 protoc 命令」**——下面五个坑都真踩过，其中前三个是**静默失败**
（生成的代码能编译、但没有任何一处 import 它），后两个的报错信息会把人指向错误的方向：

1. **`--go_opt=module=<module>` 必须与 `go_package` 完全一致**（`gen_proto.ps1:11-14`）。不一致时桩会被写进嵌套的
   `github.com/...` 目录，编译得过、但全项目没有任何一处 import 它。脚本从 proto 反读 `go_package`、不硬编码两次，
   并在生成后做非空自检（`gen_proto.ps1:69-75`）。
2. **仓库路径含非 ASCII（`作品集`）**。PS 5.1 用 ANSI 代码页给原生 exe 传参，绝对路径的 `--proto_path` 到 protoc
   那里就是乱码，报 `directory does not exist`——一个明明存在的目录。对策：`Set-Location` 到模块根、只传相对路径
   （`gen_proto.ps1:51-58`）。
3. **`go_package` 是 `import/path;pkgname`，必须先按 `;` 切**（`gen_proto.ps1:39-42`）。按 `/;` 切会把别名粘在最后一段
   路径上，`mkdir` 会真的造出一个叫 `v1;aiplatformv1` 的目录。
4. **Python 桩的 import 路径由 proto 相对 `--proto_path` 的路径决定**（`gen_grpc_stubs.ps1:11-25`）。原地生成得到
   `import aiplatform.v1.chat_pb2`，运行时得把 `app/grpc` 塞进 `sys.path`；而本项目 100% 代码在 `app` 包内。对策：
   先把 proto stage 到 `$env:TEMP` 的 `app/grpc/aiplatform/v1/` 再生成，得到 `app.grpc.aiplatform.v1`，不污染 `sys.path`。
5. **写文件必须 UTF-8 无 BOM**（`gen_grpc_stubs.ps1:52-59`）。PS 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM，Python
   导入能容忍，但仓库里用 `ast.parse` 读源码的结构性测试会报 `SyntaxError: invalid non-printable character U+FEFF`。

## 九、生成物不手改

| 文件 | 生成标记 |
| --- | --- |
| `api/aiplatform/v1/chat.pb.go` | `// Code generated by protoc-gen-go. DO NOT EDIT.`（`:25`） |
| `api/aiplatform/v1/chat_grpc.pb.go` | `// Code generated by protoc-gen-go-grpc. DO NOT EDIT.`（`:25`） |
| `app/grpc/aiplatform/v1/chat_pb2.py` | `# Generated by the protocol buffer compiler.  DO NOT EDIT!`（`:2`） |
| `chat_pb2.pyi`、`chat_pb2_grpc.py` | 同上 |
| `app/grpc/{aiplatform,aiplatform/v1}/__init__.py` | 模块 docstring `Generated package -- see tools/gen_grpc_stubs.ps1 (do not edit).` |

三条理由：改了下次生成被覆盖；两侧字段快照测试会红；`ruff` 已把 `**/*_pb2*.py` 排除（`pyproject.toml:72-77`）——
那是产物不是源码。

**改契约的标准动作**（顺序不能换）：

1. 只改 `proto/aiplatform/v1/chat.proto`；
2. 跑 §八 两条脚本；
3. `go build ./...`，`go test ./internal/data/ai/ -run TestContractFieldParity`；
4. `uv run pytest tests/unit/test_grpc_server.py`（错误码映射）与 `tests/unit/test_sse_frames.py`（帧格式）；
5. 若动了字段语义，同步 [docs/04-§2.3](./docs/04-AI服务编排与网关.md) 的事件映射表。

## 十、错误码跨语言对齐

三层结构，每一层的真源只有一个：

| 层 | 真源 | 作用 |
| --- | --- | --- |
| 业务码（字符串，对外稳定） | Python `app/core/exceptions.py::ErrorCode` + `ERROR_SPECS`（`:97`）<br>Go `pkg/errs/codes.go`（`specs`，`:73`） | 客户端按它分支 |
| gRPC 规范码 | `app/grpc/errors.py::GRPC_CODE_BY_ERROR`（`:34`） | 传输层的粗分类 |
| HTTP 状态码 | 同上两张 `specs` 表，与 [docs/02-§4](./docs/02-接口规范与鉴权.md) 逐行一致 | 对外响应 |

映射按「调用方该怎么办」分组，不按数字分组：参数/语义 → `INVALID_ARGUMENT`(400)；不存在 → `NOT_FOUND`(404)；
状态冲突 → `ALREADY_EXISTS`/`FAILED_PRECONDITION`(409)；依赖挂了 → `UNAVAILABLE`(502/503)；超时 → `DEADLINE_EXCEEDED`(504)；
过载/限流 → `RESOURCE_EXHAUSTED`(429 或 503)。**可重试性不是分组的副产物**：`QUOTA_EXCEEDED`(429) 不可重试，`RATE_LIMITED`(429) 可重试。

六条硬约束：

1. **`status.message` 必须是机器可读的业务码字符串**（`str(exc.code)`，`app/grpc/errors.py:103-109`）。
   这样非 Go 客户端不必解 detail 就能辨错。
2. **信封挂在 `google.rpc.Status.details` 的 `AiError` 上**，随 `grpc-status-details-bin` trailer 传输；
   同时补一条标准 `google.rpc.ErrorInfo`（`reason` = 业务码，`domain = ai-platform`）。
3. **`details` 是 JSON 字符串而不是 `map<string,string>`**：契约里的 `details` 允许嵌套（`fields` 是数组、
   `hint` 是对象），压平成 map 会改形状，而 [docs/02-§4.2](./docs/02-接口规范与鉴权.md) 要求它对客户端逐字可见。
4. **网关复用的 AI 码 MUST 原样透传**，状态码取上游响应、MUST NOT 改写成网关自己的码
   （`pkg/errs/codes.go:99-132` 的 `aiErrorStatus` 只用于「按码复原状态码」，例如从幂等快照还原）。
   `trace_id` 走 trailer `x-trace-id`，MUST 原样保留，否则排障链路断开。
5. **未登记的码退化成 `INTERNAL` 而不是 `UNKNOWN`**（`app/grpc/errors.py:96-100`）：`UNKNOWN` 会被解读成
   「服务实现有问题」，掩盖「只是忘了登记」。
6. **流中的 `StreamError` 与响应前的 `AiError` 字段刻意同构**（`code/message/retryable`，`chat.proto:296-306`）：
   前者用于「流已开始推」的失败，后者用于「响应头都没发出」的失败，客户端用同一段分支处理。

防回归：`tests/unit/test_grpc_server.py:660` 遍历全部 `ErrorCode` 比对 `GRPC_CODE_BY_ERROR`（漏登记即红），
并断言不可重试的码没有落到可重试的规范码上；`pkg/errs/codes_test.go::TestSpecsMatchContract` 守着 Go 侧表与
docs/02-§4 一致。

## 十一、SSE 帧跨语言对齐

帧格式的唯一出口：Python `app/core/sse.py::format_frame`（`:54`）、Go `pkg/ssex/ssex.go::Frame`（`:67`）。
两侧 MUST 逐字节一致：

```text
event: <事件名>\ndata: <单行紧凑 JSON>\n\n
```

三条细节：JSON 用紧凑分隔符（`separators=(",",":")`）；中文不转义（`ensure_ascii=False`，否则「语义相同、
字节不同」）；负载里禁止裸换行（`\n`/`\r` 会把一帧截成两帧，两侧都早失败）。

事件名与顺序（两侧各有常量，`internal/biz/chat_stream.go:18-39` / `app/core/sse.py:20-29`）：

| 事件 | 位置/语义 |
| --- | --- |
| `meta` | 首帧，必发。`conversation_id` / `message_id` 以网关为准；`degraded_reasons` 比 HTTP 文档多一个字段，因为落库需要原因 |
| `reference` | 可多次；语义是「当前引用集合」，消费方 MUST 整体替换、MUST NOT 追加 |
| `token` | 正文增量；空串也必须原样透传（丢帧会让客户端与服务端帧数不一致） |
| `tool_call` / `tool_result` | 按 `call_id` 配对；只有开始没有结果的，落库时 `status` 取 `error` |
| `usage` | token 用量，收尾前给出 |
| `done` | 正常收尾，客户端判定「回答完整」的唯一依据；带 `partial` |
| `error` | 流中途失败；收到后**不再有** `usage`/`done` |
| `ping` | 心跳，15s 静默发一帧；不在文档事件序列里，客户端可忽略 |
| `gw_persist_error` | 网关追加，SHOULD 在 `done` 之后（插在 `token` 之间会打断正文拼接） |
| `unknown` | gRPC 逃逸口：AI 侧新增事件时老网关原样透传原始 `data_json`，MUST NOT 丢弃 |

正常序：`meta → reference* → (tool_call/tool_result)* → token* → usage → done`。

响应头：`Content-Type: text/event-stream; charset=utf-8`、`Cache-Control: no-cache, no-transform`、
`X-Accel-Buffering: no`。Go 侧**刻意不发** `Connection: keep-alive`（HTTP/1.1 已是默认，HTTP/2 明确禁止，
RFC 9113 §8.2.2）；整条链路 MUST NOT 挂 GZip（`AC-CHAT-04` 断言响应里没有 `Content-Encoding: gzip`）。

gRPC 侧的等价物是 `ChatEvent` 的 oneof（`chat.proto:216`），AI 侧 `app/grpc/server.py:443` 的 `_StreamCursor.map`
负责逐事件映射，`ping` 映射成 `None`（gRPC 有自己的 keepalive）。
**逐字节一致只在 HTTP/SSE 默认传输下成立**：走 gRPC 时事件名与顺序完全一致，但 `data` 由网关重新序列化，
字节不同——口径降为「事件名与顺序一致、`data` 语义一致」（`chat.proto:205-208`）。

防回归的四道防线：

1. `pkg/ssex/ssex_test.go:16` 的 `TestFrameMatchesAISideByteForByte` 把期望字节写死（含中文用例），Go 侧一改就红；
   反方向由 `tools/curl_stage4.ps1` 真调一次 Python 覆盖——只做单侧会漏掉一半；
2. `internal/service/stream.go:208` 的 `renderStreamEvent` switch 因事件接口带未导出标记方法而**编译期穷尽**，
   新增事件类型必定编译不过，不会静默少一帧；
3. `stream.go:113-122` 第一帧才写响应头：首字节超时之前还能回 504（写出 200 后再也改不了状态码）；
4. `stream.go:124-130` 每帧 `SetWriteDeadline` + `Flush`：不 Flush 帧会攒在 4KB bufio 里，「流式」退化成「一次性返回」。

## 十二、哪些东西不要生成

| 不要生成 | 为什么 |
| --- | --- |
| `option (google.api.http)`、`*_http.pb.go`、kratos HTTP 路由 | 对外是 Gin；给这些接口再生成一套 kratos 路由只是多一份要同步的契约。路由是手写的 58 处注册 |
| 第二份 DTO（proto 与 Pydantic 互转的中间模型） | 两份契约必然漂移，字段级测试只是在给漂移兜底。proto 服务 gRPC 面，Pydantic 服务 HTTP 面，各管一边 |
| `api/` 里的 service/biz/仓储骨架 | 生成的空实现会掩盖「还没接线」这件事 |
| 每个 proto 消息的 HTTP 参数校验 | 校验在 Pydantic 与 `httpx.BindJSON`，不在契约文件里 |
| 表结构 / 迁移 / GORM model | schema 归 [docs/05](./docs/05-数据模型.md) 与 `deploy/mysql/*.sql`，由人写 |
| SRS 表格、接口文档 | 生成物没人读，且会与 proto 注释重复。proto 注释写「为什么」，SRS 写「是什么」 |
| 空测试骨架 | 空 `Test*` 让断言数与覆盖率虚高，比没测试更贵 |
| LangGraph 节点与状态图 | 设计初期考虑过 LangGraph 状态图，最终未采用，仓库内没有这类代码；真正在跑的是 `app/agent/loop.py` |
| K8s 清单、CI 配置 | 仓库里没有这两样东西，只有 Docker Compose 起的本地基础设施 |
| 微服务脚手架（User / Conversation / Task 三服务） | 实现是 Go 单进程多模块：建会话 + 写首条消息必须同一事务，拆进程就得上 Saga |
| 指标与看板定义 | 指标名是契约（Go `gw_*`、Python `ai_*` 19 个），手工登记 |
