# RAG 检索效果评测（`docs/11`-§5 落地）

## 1. 为什么有它

`docs/11-§5`（`REQ-TEST-004`）早就规定了 RAG 效果评估的数据集口径、指标与门槛，
但 `tests/eval/` 一直不存在，也没有任何用例挂 `pytest.mark.eval` ——
于是「**没有检索评测集**」成了文档自己承认的最大流程缺口：切片参数、阈值、重排开关
这类改动能改，却没人敢改，因为改完没有可比基线。

本目录把 §5 的口径真正落地：**数据集 + 可复现脚本 + 实测基线数字 + 四个可执行的发现**。

## 2. 数据集

| 项 | 值 |
| --- | --- |
| 语料 | **12 篇 / 55 个切片 / 4611 token**（`corpus/`，Markdown / TXT / HTML 三种格式） |
| 查询 | **61 条**（`dataset.jsonl`）：**57 条有标注** + **4 条负例** |
| 类型分布 | `fact` 37 · `paraphrase` 13 · `disambiguation` 7 · `negative` 4 |
| 覆盖文档 | 12/12 |

语料主题是「AI 平台产品与运维手册」，刻意包含**跨文档可混淆的数字**作为干扰项，
用来检验排序而不只是召回：

- `429` 同时出现在「鉴权与限流」与「故障排查手册」；`402` 与 `429` 是易混的一对
- 相似度阈值 `0.2`（检索）vs 去重阈值 `0.85 / 0.92`（记忆）
- 重试 `3 次`（任务）vs 熔断 `5 次`（故障手册）
- `20` 出现在三处：召回 20 条 / 短期上下文 20 轮 / 企业版 20 路并发

### 与 §5.1 的一处有意偏差

§5.1 要求标注 `gold_chunk_ids`；本数据集标的是 **`gold_spans`**（gold 片段里的原文字串）
加 `gold_doc_ids`。原因：`chunk_id` 由切片参数派生，`CHUNK_SIZE` 一改全部失效，指标就
不可比了 —— 而 §5.2 又明令「禁止为了指标好看而把 `gold_chunk_ids` 改成实现了的切片」。
用「原文字串是否出现在命中片段里」判定，切片参数怎么变都成立，且天然规避了那条禁令。
判定前把两侧空白全部去掉，避免相邻切片合并引入的换行造成漏判。

## 3. 怎么跑

```powershell
cd ai-platform

# 真实链路：.env 里的硅基流动 embedding + 重排（会消耗少量额度）
python tests/eval/run_eval.py --json tests/eval/results-cloud.json

# 离线确定性基线：hash 向量化 + 关重排，不联网、不花钱、可进回归
python tests/eval/run_eval.py --mode hash --json tests/eval/results-hash.json

# pytest 入口（docs/11-§6 规定 eval 不入默认运行，故必须显式 -m eval）
pytest tests/eval -m eval

# 冒烟
python tests/eval/run_eval.py --limit 5 -v
```

脚本强制把基础设施压到内存档（`INFRA_BACKEND=memory`）：Milvus / MySQL 不是被测对象，
连不上不该让评测变成「测环境」。手段是**显式 kwargs**而不是改 `os.environ` ——
后者会污染 pytest 会话（实测曾让 `tests/contract/test_observability.py` 的 6 个用例集体失败）。
链路每一段都走生产代码（`parse_document` → `ChunkingService.split_blocks` → `embed_texts`
→ `VectorStore.upsert` → `Retriever.retrieve_detailed`），只有向量库换成了内存实现。

## 4. 实测结果

> 环境：Windows / Python 3.12 / 本机，2026-10-07。云端档
> `Qwen/Qwen3-Embedding-0.6B`（1024 维）+ `Qwen3-Reranker-0.6B`，`chunk_size=512`、
> `chunk_overlap=64`、`top_k=20`、`rerank_top_n=5`、`score_threshold=0.0`。

### 4.1 入库链路

| 档 | parse | split+merge | sha256 | **embed** | upsert | 合计 | 单块均摊 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 云端 | 0.006s | 0.015s | 0.001s | **0.810s** | 0.005s | **0.837s** | 15.2 ms/块 |
| 离线 | 0.005s | 0.014s | 0.001s | **0.045s** | 0.006s | **0.071s** | 1.3 ms/块 |

云端档**向量化占入库总耗时的 96.8%**（离线档 63.4%），解析与切分合计约 2.5%。
结论很直接：要优化入库，只能动 embedding —— 批大小、并发、供应商，别去抠解析。

### 4.2 检索质量与耗时

| 指标 | 云端 · 仅向量 | 云端 · 向量+重排 | 离线 · 仅向量 |
| --- | --- | --- | --- |
| hit@1 | 91.2%（52/57） | **98.2%（56/57）** | 66.7% |
| hit@3 | 98.2%（56/57） | **100.0%（57/57）** | 75.4% |
| hit@5 | 98.2%（56/57） | **100.0%（57/57）** | 82.5% |
| hit@10 | 100.0% | 100.0% | 87.7% |
| hit@20 | 100.0% | 100.0% | 91.2% |
| **MRR** | 0.9464 | **0.9912** | 0.7357 |
| doc 级命中 | 57/57 | 57/57 | 56/57 |
| 耗时 p50 | 90.0 ms | 395.0 ms | 4.0 ms |
| 耗时 p90 | 102.0 ms | 422.0 ms | 7.0 ms |
| 耗时 p99 | 118.4 ms | 715.4 ms | 8.0 ms |
| 耗时 mean | 92.0 ms | 410.1 ms | 4.9 ms |

**重排段近似增量 ≈ 305 ms（p50）**：召回 90ms + 重排 305ms ≈ 395ms。
重排是延迟的主要来源，换来 hit@1 从 91.2% → 98.2%（**+7.0pp**）、MRR +0.0448。

**语义 vs 词法（同为仅向量臂）**：hit@1 **+24.5pp**、hit@5 **+15.7pp**、hit@20 **+8.8pp**、
MRR **+0.2107**。离线档的未命中集中在 `paraphrase` 与 `disambiguation`
（如「熔断之后多久会尝试恢复？」「摘要什么时候会重新生成？」）——
正是字面不重合、必须靠语义才能命中的那类问题。

### 4.3 `docs/11`-§5.2 门槛核对（云端档）

| 指标 | 实测 | 门槛 | 结果 |
| --- | --- | --- | --- |
| `recall@5` | 1.000 | ≥ 0.85 | **PASS** |
| `recall@20`（仅向量召回） | 1.000 | ≥ 0.92 | **PASS** |
| `MRR` | 0.9912 | ≥ 0.70 | **PASS** |
| `rerank_gain`（recall@5 提升） | +0.0175 | ≥ +0.05 | **FAIL** |

## 5. 四个发现

**① `rerank_gain` 门槛存在天花板问题（最重要的一个）。**
§5.2 把 rerank 的价值定义成「`recall@5` 提升 ≥ 0.05」，但向量臂 `recall@5` 已经
达到 98.2%，**理论上限只有 +1.8pp** —— 这个门槛在当前语料上数学上不可能通过，
它会把一个明显有效的重排判成「无价值」。重排的真实收益在有 headroom 的指标上：
`hit@1 +7.0pp`、`MRR +0.0448`。
**建议**：把该门槛改到 `hit@1` 或 `MRR` 上，或改用相对提升，或使用更难的语料
（更多文档级干扰）把向量臂 `recall@5` 压下来再比。`test_rag_eval.py` 已把这条
标成 `xfail` 并在原因里写清了口径问题。

**② `score_threshold=0.0` 明显偏低，且存在一个干净的分离窗口。**
4 条负例（语料中确实没有答案）重排后的最高分分别是 `0.0002 / 0.0047 / 0.0007 / 0.0036`
（最大 **0.0047**）；而 57 条正例里**最低的** top-1 分数是 **0.0153**。
即所有正例都高于所有负例，中间是一段空档 ——
**阈值取 `0.005`~`0.015` 之间即可过滤掉全部负例且不损失任何召回**。
这是目前最省事、收益最直接的一处改动。离线档的分离度差得多（负例 0.0667~0.0977），
说明这个窗口是**语义模型带来的**，换模型后需要重新标定。

**③ 入库成本的 96.8% 在向量化。** 见 §4.1 —— 优化入库只需盯 embedding。

**④ 词法档恰好卡在门槛之下（`recall@20` 91.2% vs 门槛 92%，差 0.8pp）。**
这说明 §5.2 的 `recall@20 ≥ 0.92` 对词法档是一条有效的判别线，而离线档可以当作
**零成本回归基线**：不联网、不花钱，`hit@1 / hit@5 / MRR` 的变化足以发现切片或
检索逻辑的回归。CI 里适合跑它，云端档按 §6 留作手动。

### 一个测量上的注意点

云端档**不是完全确定性的**：两次完整运行里，重排臂的 hit/MRR 完全一致
（0.9912），但向量臂的 MRR 从 0.9493 漂到 0.9464（Δ0.003），各 hit@k 不变。
推测来自云端 embedding 服务内部的分批/数值细节。因此**结论应看 hit@k 与 MRR 的量级**，
不要把 0.001 级的差异当成回归。离线 `hash` 档是构造性确定的，适合做逐位比较的回归基线。

## 6. 局限（不要把这些数字当成全貌）

- **规模小**：12 篇 / 55 切片，远小于真实知识库，对「文档级干扰」的强度有限；
  §5.1 建议的下限是「≥30 问、≥10 文档」，本集满足但仅略高于下限。
- **未覆盖中英混合与表格**：§5.1 要求「中英混合，含表格与多级标题」，
  当前语料是**纯中文、无表格**（多级标题已覆盖）。
- **未走 Milvus**：向量检索用的是 `InMemoryVectorStore` 的暴力精确余弦，
  因此 recall 是**精确检索的上界**；真实 Milvus（HNSW 近似）下会略低，
  且 Milvus 自身的检索延迟未被度量。§4.2 的 90ms 召回延迟**不含** Milvus 的网络与 ANN 开销。
- **未走 MySQL / MinIO / Kafka**：上传、对象存储、异步任务链路不在本次范围内，
  §4.1 的入库耗时只覆盖「解析 → 切分 → 向量化 → upsert」，不含上传与任务调度。
- **`引用准确率` 与 `反例集`（§5.2 / §5.3）未测**：需要 LLM 参与（生成回答再抽检
  `[n]` 指向是否正确、是否会被 Prompt 注入诱导），不在检索层能力范围内。
