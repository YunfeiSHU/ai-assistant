# 13 · 技术设计说明

> 本文只回答「**为什么这么分层、这么排序、这么降级**」。需求见 [01–11](./README.md)，坑与根因见 [12-实现问题记录](./12-实现问题记录.md)（本文多数设计是那些坑的回写），实测见 [14-接口 curl 示例](./14-接口%20curl%20示例.md)；规模、现状、未完成项见 [README §4](./README.md)，能力清单见根 README。文中路径与默认值以 `ai-platform/app` 为准，关键处标 `file:line`。

## 1. 设计约束与目标

| 目标 | 落点 |
| --- | --- |
| 依赖可替换 | 每个外部依赖（LLM / 向量库 / 存储 / MQ / MCP）在 Protocol 后面，`INFRA_BACKEND`（`memory` / `real`）切换实现，上层不动 |
| 本地零依赖可跑 | `memory` 下全链路可跑（对话 / RAG / Agent / 任务），不需要 Docker |
| 契约可机械校验 | 响应字段与错误码对齐 SRS，用契约测试断言，不靠 review |
| 失败可定位 | 统一错误信封 + `trace_id` + 结构化日志；降级必须写 `degraded_reasons` |
| 降级不失败 | 检索 / 记忆 / MCP 故障只降级；只有「请求本身不合法」才 4xx |
| 测试不依赖外网 | 替身与实现**同协议同形**（Fake LLM / Hash Embedding / 内存存储） |

四条硬约束（SRS 原文）：① 流式响应 MUST NOT 被中间件缓冲（不挂 GZip，不用 `BaseHTTPMiddleware`）；② 错误响应 MUST NOT 含堆栈（`FastAPI(debug=False)` 恒为 False）；③ 生产 MUST `INFRA_BACKEND=real` 且忽略 `AUTH_ENABLED`（`config.py::is_prod`）；④ 启动期**配置**错误 MUST 拒绝启动，**依赖**故障 MUST NOT 阻断启动（§3.4）。

## 2. 分层与依赖方向

| 层 | 目录 | 职责 | 不该出现的东西 |
| --- | --- | --- | --- |
| 接口 | `app/api/v1/*`、`deps.py`、`exception_handlers.py` | 参数绑定、HTTP 语义、把 `AppError` 交给统一处理器（`@router.*` 共 **41** 条） | 业务判断（唯一例外：`stream=true` 打 `/chat` 返 400，属协议层） |
| 编排 | `app/application/`（`chat` / `agent` / `context` / `memory`） | 一次请求的用例流程：装配、降级、引用、收尾 | SDK 调用、SQL |
| 领域 | `app/agent/loop.py`、`app/tools/`、`app/rag/`、`app/tasks/`、`app/memory/` | 与实现无关的规则：护栏、切片、状态机、去重 | `openai` / `pymilvus` / `sqlalchemy` 类型 |
| 适配 | `app/infrastructure/`、`app/llm/`、`app/rag/{embedding,reranker,vectorstore}`、`app/mcp/` | SDK → 领域对象，实现协议 | 业务分支 |
| 基础 | `app/core/`（config / exceptions / logging / context / ids / tokens / pagination / sse / security / health / middleware） | 叶子能力 | 任何对上层模块的 import |

依赖只向下，三条规则：① **`app/core` 不 import 上层** —— 所以 `pagination.py` 能被 `tasks/` 与 `infrastructure/storage/` 共用而不成环；② **协议定义在使用方，实现放适配层**（`rag/base.py::Retriever`、`rag/embedding/base.py::EmbeddingProvider`、`tasks/store.py::TaskStore`），加实现不改协议文件；③ **`app/api` 不写业务判断** —— 绑定参数 → 调服务 → 把 `AppError` 交给处理器。

### 2.1 两个入口，一套服务层

| 入口 | 传输 | 调用方 | 约束 |
| --- | --- | --- | --- |
| `/api/v1/chat`、`/chat/stream` | HTTP + SSE，`PORT=8000` | 外部客户端（经 Gin 透传） | 状态码只有响应头发出前能改 ⇒ 先 `prepare()` 再 `StreamingResponse` |
| `AiPlatform.Chat` / `ChatStream` | gRPC，默认 `127.0.0.1:50051` | Go 网关 | `GRPC_ENABLED` 默认 **false**；`maximum_concurrent_rpcs=64`；`add_insecure_port` |

gRPC 入口是 `python -m app.grpc`（`app/grpc/server.py`），**与 HTTP 共用** `ChatService` / `AgentService`、同一个 `authenticate`（`core/security.py`）、同一张错误码表（`app/grpc/errors.py`）；行为差异只允许出现在 `_StreamCursor`（编排事件 → `ChatEvent`）一处，`trace_id` 经 trailing metadata 回传。**为什么明文端口可接受**：只绑回环，且 `validate_for_startup()` 强制「非回环 `GRPC_HOST` ⇒ `AUTH_ENABLED=true`」（`config.py:468`）——把暴露面做成启动期就拒绝的配置错误。

## 3. 装配：`create_app(settings)` 与注入

### 3.1 为什么不用全局单例

```python
settings = get_settings()          # ❌ 进程级 lru_cache：第二个用例拿到第一个用例的配置

def create_app(settings: Settings | None = None) -> FastAPI:   # app/main.py:370  ✅ 构造期注入
def get_app_settings(request: Request) -> Settings:            # app/api/deps.py:35    ✅ 运行期读实例
    return cast(Settings, request.app.state.settings)
```

测试常态是**一个进程里创建多个应用实例**（每个用例一套配置）；`lru_cache` 单例的表现是「单独跑过、一起跑就挂」。

`app.state` 上是**装配产物**（`main.py:622-661`）：`settings`、`llm`、`chat_service`、`agent_service`、`conversation_store`、`memory_service`/`memory_repo`/`memory_index`、`kb_service`、`document_service`、`search_service`、`ingestion`、`retriever`、`vector_store`、`repositories`、`task_service`/`task_store`/`task_runner`/`task_dispatcher`/`task_event_bus`、`tool_registry`/`tool_service`、`mcp_manager`、`metrics`、`tracing`、`circuit_registry`、`health_registry`。路由层一律经 `deps.py` 取，不在模块级缓存实例。

### 3.2 装配顺序即依赖顺序

```
repositories → object store；task service、vector store、embedding → ingestion → task runner
vector store + embedding + reranker → retriever → chat service / agent service
task service + tool registry → agent service
```

**关键不变量**：`retriever` 依赖的 `vector_store` 必须与 `ingestion` 写入的**是同一个实例**（`main.py:198`、`main.py:645`）。违反它的症状是「入库成功、检索永远 0 条」，且没有任何异常（[12-§3.7](./12-实现问题记录.md)）。因此 `build_retriever(settings, *, embedding=..., vector_store=..., reranker=...)` 的关键字参数**可选但调用方必须传**（`build_rag_services` 里显式传），只有「独立构造一个只读检索器」时才允许缺省。

### 3.3 装配期决定形状，运行期不做分支

三个任务执行器（`none` / `inline` / `kafka`）的差异——谁跑、消息从哪来、状态存哪——决定了整套依赖的形状，所以 `build_task_store` / `build_task_event_bus` / `build_task_producer` / `build_task_runner` 都在 `create_app` 里选型，而不是运行期写 `if`：混在一处会让「为什么这个测试里任务不执行」变成玄学。`task_event_bus` 也必须在 `build_rag_services` **之前**建好并传进去（`main.py:426`），后挂只会变成「部分服务拿到总线、部分拿到另一条」。

### 3.4 启动期与运行期的职责边界

| 阶段 | 做什么 | 失败时 |
| --- | --- | --- |
| import 期 | 只定义，`create_app` 被调用才装配 | 不适用 |
| `create_app` | 构造服务、注册中间件 / 路由 / 异常处理器 | 抛异常（编程错误） |
| lifespan startup | `validate_for_startup()`（配置）、`ensure_ready()`（依赖自检） | **配置错误拒绝启动**；依赖故障只 warning |
| 运行期 | 依赖故障 → `503 DEPENDENCY_UNAVAILABLE`（`/health/ready` 与错误信封表达） | 局部降级 |
| lifespan shutdown | 等进程内后台任务收尾 | 记日志 |

**为什么依赖故障不阻断启动**：容器编排下「启动失败」= 重启循环，会把局部故障（Milvus 挂了）放大成全局不可用（连健康检查与对话都起不来）。代价是必须留一个运行期降级出口——§4.3 那张表。

## 4. 错误处理与降级

### 4.1 错误码规格表 → HTTP 状态码

```python
@dataclass(eq=False)                 # 为什么不是 slots=True，见 §4.4
class AppError(Exception):
    code: ErrorCode
    message: str = ""
    details: dict = field(default_factory=dict)
```

`ErrorCode` 与 **`ERROR_SPECS`**（`app/core/exceptions.py:97`）集中定义「错误码 → HTTP 状态码 → 是否可重试」，`exception_handlers.py` 只查表、不写 `if code == ...`；新增错误码只加两处，状态码不会散落。

| 错误码 | HTTP | retryable | 典型触发 |
| --- | --- | --- | --- |
| `DEPENDENCY_UNAVAILABLE` | 503 | true | `real` 下依赖初始化失败留下的占位仓储 |
| `RETRIEVAL_FAILED` | 503 | true | 显式 `/search` 时检索不可用 |
| `MQ_UNAVAILABLE` | 503 | true | 投递失败，任务停在 `PENDING` |
| `UNSUPPORTED_FILE_TYPE` | 415 | false | 扩展名或魔数不符 |

### 4.2 三层兜底

| 层 | 职责 | 例 |
| --- | --- | --- |
| 适配层 | 把 SDK 异常翻译成领域错误码 | `map_llm_exception`（`app/llm/base.py:145`）：`openai.RateLimitError` → `RATE_LIMITED` |
| 服务层 | 再兜一次 | `ChatService._call_llm`：`except Exception → map_llm_exception` |
| 接口层 | 未预期异常 → `500 INTERNAL_ERROR` + `trace_id` | `app/api/exception_handlers.py` |

**为什么适配层映射了还要兜一次**：适配层是**实现细节**，不是上层可依赖的保证。任何 `LLMClient` 实现（含替身、未来新供应商）都可能抛未识别异常，兜底保证它变成明确错误码而不是 500 —— 否则监控把上游故障算成我们的 bug。

### 4.3 降级矩阵：谁能失败、失败成什么样

| 故障点 | 对外表现 | 兜底位置 |
| --- | --- | --- |
| LLM 超时 / 限流 / 5xx | 明确的 5xx / 429，不降级 | `map_llm_exception` + `_call_llm` |
| 检索（Milvus / embedding / rerank） | 200 + `degraded_reasons: ["rag_unavailable"]` | `ChatService._load_rag`（`chat.py:232`） |
| 短期上下文 / 摘要 / 长期记忆 | 200 + `"memory_unavailable"` | `_load_memory`（`chat.py:199`） |
| 单个 MCP Server | 该 Server 的工具 unavailable，其余工具与对话照常 | client 状态机 + `mcp:{server}` 熔断 |
| `real` 下 MySQL / Milvus / Redis 初始化失败或不曾就绪 | 对应仓储返回 `503 DEPENDENCY_UNAVAILABLE`（`/health/ready` 同码），进程照常起；`/chat` 不因此直接 503 | `storage/unavailable.py`、`memory/unavailable.py`；`core/health.py` 注册表（`memory` 下依赖项返回 skipped） |

两处刻意的「不降级」：**请求本身不合法**（400/404/409）与**上游明确失败**（429/504）。降级只用于「本次没带资料 / 没带记忆」，不能用来掩盖调用方写错参数。

### 4.4 两个容易写错的细节

* **`AppError` 不能用 `@dataclass(slots=True)`**：`slots=True` 会重建类，`__post_init__` 里的零参 `super()` 指向旧类，抛 `TypeError: obj must be an instance or subtype of type`；
* **schema validator 只能抛 `ValueError`**：pydantic 包成 `ValidationError` → 统一变 `INVALID_ARGUMENT`。所以领域错误码必须由**服务层**抛（如 `CHUNK_STRATEGY_INVALID`）——schema 的能力边界是「语法」。

## 5. 配置设计

单一事实来源 `app/core/config.py::Settings`（`config.py:103`，pydantic-settings）。

| 设计点 | 原因 |
| --- | --- |
| `.env` 用 `env_file_encoding="utf-8"`；`_split_csv` validator | 避免中文项目在 Windows 上按 GBK 解码；允许 `A,B,C` 代替 JSON 数组，贴合 `.env` 习惯 |
| `validate_for_startup()` 在 lifespan 调用 | 配置错误表现为明确启动失败，而不是 import 崩溃（`--reload` 友好） |
| 派生属性而非重复字段 | `upload_max_bytes`、`auth_required`、`milvus_connection_args`、`debug_tools_enabled`，避免「字段填了但没人用」 |
| `is_prod` 强制 `real` + 忽略 `AUTH_ENABLED`；跨字段校验成对存在 | 本地便利绝不能变线上后门；`TASK_RUNNER=kafka` ⇒ 必须 `KAFKA_BOOTSTRAP_SERVERS` 且共享任务存储 |

**测试纪律**：一律 `Settings(_env_file=None, **values)` 构造，**不读开发机 `.env`**（否则本机能过、CI 挂）。

## 6. 对话链路（M2）

| 步 | 入口 | 做什么 | 失败时 |
| --- | --- | --- | --- |
| 1 | `ChatService.prepare`（`chat.py:147`） | 空 query → `QUERY_EMPTY`；模型白名单；会话归属 | 400 / 404 / 429，**响应头尚未发出** |
| 2 | `_load_memory` | `recent()` + `summary()`，再 `memory.search()` | 200 + `memory_unavailable` |
| 3 | `_load_rag` | `retriever.retrieve()`（`use_rag=true`） | 200 + `rag_unavailable` |
| 4 | `ContextAssembler.build`（`context.py:139`） | 固定顺序装配 + 确定性裁剪 | `CONTEXT_TOO_LONG`（400） |
| 5 | `complete()` / `stream_prepared()` | 调上游，落库 | 映射后的明确错误码 |
| 6 | `_after_turn`（`chat.py:508`） | 投 `memory_extract` / `summary_build` | 降级 `summary_failed` |

三个刻意的设计：① **准备阶段与推送阶段分离** —— `prepare()` 可能抛 400/404/429，而 HTTP 状态码只有响应头发出前能改，所以路由先 `await prepare()` **再**构造 `StreamingResponse`（`api/v1/chat.py:94`）；② **降级而不是失败** —— 「检索挂了就整个不能聊天」比「这次没带资料回答」严重得多；③ **裁剪顺序是契约** —— 装配顺序固定 `system → memory → summary → history → rag → query`，超预算按 `历史 → RAG → 记忆 → 摘要` 丢；不允许随机，随机裁剪会让「同一请求两次结果不同」无法复现。

### 6.1 SSE 帧序

| 事件 | 负载 | 出现位置 |
| --- | --- | --- |
| `meta` | 模型、`conversation_id`、`degraded` | 首帧 |
| `reference` | `references[]` | 非流式在响应体一次给全；流式**可多次**，语义是「本轮引用集合」 |
| `token` | `delta` | 生成期间 |
| `tool_call` / `tool_result` | 工具名、参数、结果摘要 | 仅 Agent 流 |
| `usage` / `done` | 计量；`finish_reason` / `steps` / `references` | 收尾 |
| `error` / `ping` | 统一错误信封；15s 心跳（`core/sse.py:34`） | 出错时代替 `done`；心跳随时 |

```
/chat/stream        meta → reference* → token* → usage → done
/agent/run/stream    meta → (tool_call → tool_result → reference*)* → token* → usage → done
```

`reference` 在 Agent 流里**紧跟产生它的那次 `tool_result`**，不早于它——否则客户端会渲染出一条还看不见的引用（[12-§7.4](./12-实现问题记录.md)）；每次重发**全量**引用集合（`application/agent.py:339`）。

### 6.2 心跳、中间件与断连

**坑**：心跳不能写成 `asyncio.wait_for(agen.__anext__(), timeout=15)` —— 超时会**取消**那个 `__anext__`，取消信号抛进异步生成器内部 → 生成器终结 → 后续 token 全丢；症状是「心跳正常，但回答只有第一段」。**解法**：独立 pump 任务把事件推进 `asyncio.Queue`，消费端只等队列（超时发 ping），pump 的 `finally` 里 `await events.aclose()`（`core/sse.py:72`）。中间件只允许纯 ASGI：`X-Accel-Buffering: no` 与 `Cache-Control: no-transform` 是硬要求，自己拼帧换来响应头完全可控 + 每帧可单测。**断连语义**（`REQ-CHAT-006`）：消费端被取消 → `finally` 取消 pump → 事件生成器收到 `CancelledError` → 上游 LLM 生成器被 `aclosing` 关闭，**1 秒内**完成。

### 6.3 引用编号

`references[].index` 从 1 开始，与正文 `[n]` 一一对应；非流式路径**裁剪越界标注**（`[9]` 而只有 2 条引用 → 删标注并记 warning，`chat.py:340`），流式路径只**审计**不裁剪 —— SSE 没有「撤回已推送内容」的表达方式。`content_sha256` 哈希的是**返回给用户的文本**（合并会改文本，`chat.py:720`），不是入库原文。

## 7. Agent 与工具链路（M4）

### 7.1 为什么工具层与 Loop 分开

`app/tools/` 管「有哪些工具、怎么安全地调用」（与 LLM 无关），`app/agent/loop.py` 管「按什么顺序推理与调用」（只依赖 tools 的抽象），`app/application/agent.py` 管「装配上下文、落库、产出契约响应」。收益是可测性：Schema 校验、超时、并发、截断、SSRF 防护都能在**不启动 LLM** 时单测；护栏、重复检测、回注格式用**假工具**（`sleep 1s`）单测，不需要真实检索。**主链路就是这两个模块**：设计初期考虑过 LangGraph 状态图，最终未采用（原因见 §14），仓库内没有状态图代码。

### 7.2 工具模型

| `ToolSpec` | 约束 |
| --- | --- |
| `name` / `description` / `parameters` | 名称 `^[a-z][a-z0-9_]{1,63}$`；描述 ≤512 且写清「何时用 / 何时不用」；参数是 JSON Schema，由 pydantic 输入模型的 `model_json_schema()` 生成并去掉 `title` |
| `side_effect` / `source` | `read` / `write`（决定执行器并发策略与审计）；`builtin` / `mcp` |
| `mcp_server` / `timeout_seconds` / `enabled` / `example_arguments` | 可选 |

**单一事实来源是 pydantic 输入模型**：校验用的 schema 与发给上游的 schema 不可能不一致。`ToolOutcome` = `status`（`ok`/`error`/`timeout`/`forbidden`）+ 结构化 `payload` + 面向用户的 `summary`（不含内部路径 / 连接串）+ `elapsed_ms` + 可选 `citations`。

**为什么 `payload` 是结构化 dict 而不是渲染好的字符串**：引用编号需要**全局**分配（同一次运行里第 1 个片段永远是 `[1]`），而工具看不到全局状态。工具产出数据，**由 Loop 渲染成模型可见文本并编号**。

### 7.3 注册表与命名空间

| 场景 | 规则 | 实现 |
| --- | --- | --- |
| 内置工具重名 / 内置 vs MCP | 重名**启动失败**（fail-fast，报出两个冲突来源）；内置优先（先注册内置再 MCP） | `register()` 抛异常 / 装配顺序 |
| 同一 MCP 内 | `mcp__{server}__{tool}`；`-` / `.` → `_` | `namespace()` |

**为什么用双下划线而不是 `:`**：上游 OpenAI 兼容接口的 function name 通常限 `^[a-zA-Z0-9_-]{1,64}$`，用 `:` 会在**运行时**才被拒绝。

### 7.4 执行器与调试接口

调用列表进来后逐项判断：JSON 合法？工具存在且在允许集合内？参数符合 JSON Schema？全通过才执行；任一步失败都变成 `ToolOutcome(status=error)` 回注，`invalid_arguments` 带 detail 好让模型改参数重试。**执行器从不抛异常给上层**：只有调试接口 `POST /tools/{name}/invoke` 会把失败原因变成 HTTP 错误码（`local` / `dev` 才开放，`prod` 返回 `404 TOOL_NOT_FOUND` 而**不是 403** —— 403 等于告诉外界「这个工具存在」；`write` 类工具在该接口下强制 `dry_run=true`）。错误码按**原因**映射：`TOOL_NOT_FOUND` 404 / `TOOL_FORBIDDEN` 403 / `INVALID_ARGUMENT` 400 / `TOOL_TIMEOUT` 504 / `TOOL_EXECUTION_FAILED` 502 —— `status` 只有四种，而 `error` 同时覆盖「参数错」（调用方的锅）与「依赖挂」（服务端的锅）；`_ERROR_TO_CODE` 由 `test_error_to_code_covers_every_reason` 做**穷举断言**，漏配直接失败。

**并发规则**：全部 `read` → `asyncio.gather`；只要含一个 `write` → **整体串行**（`tools/executor.py:135`）。刻意不做「读先并发、写再串行」的精细调度：两次调用之间的可见性会有微妙差异，收益只有几十毫秒。结果统一截断到 `tool_result_max_chars`。

### 7.5 Agent Loop 与三重护栏

```
装配好的 messages → LLM（带 tools schema） → 有 tool_calls？
  ├─ 否 → answer = content，finish_reason = stop
  └─ 是 → 重复调用检测 → 执行器（读并发 / 写串行）→ 回注 → 回到 LLM
步数耗尽 → 收尾：不带 tools 再问一次，finish_reason = max_steps
```

| 护栏（`REQ-AGENT-005`） | 实现 | 违反时 |
| --- | --- | --- |
| 步数 | `step` 计数器 vs `agent_max_steps`（默认 8） | 收尾生成，`finish_reason=max_steps`，HTTP 仍 200 |
| 总时长 | `deadline = monotonic() + agent_timeout_seconds`（默认 120s），每步用 `remaining()` 传超时 | `504 UPSTREAM_TIMEOUT`，不编造答案 |
| 重复调用 | 已执行调用的 `(name, canonical_args)` 集合 | 回注 `duplicate_call`，提示换方式 |

**收尾生成**：达上限后**额外**发一次 `complete()`（不带 `tools`）并追加「已用尽工具调用步数，请基于已获得的信息直接回答」。这次调用**不计入 `steps`**（`steps` 语义是工具调用轮数），否则会变成 `max_steps + 1`，与 `AC-AGENT-02` 冲突；收尾调用失败则退回最后一步 `content`，不把用户带进 504。

**`while/else` 而不是事后比较 `steps == max_steps`**（`loop.py:187`）：超时 `break` 之后 `steps` 也可能等于上限，原因不可反推；`else` 只在**未 break**（步数真的耗尽）时置 `max_steps_hit`（[12-§7.1](./12-实现问题记录.md)）。**重复调用检测比文档更严格**：文档写「连续 2 次相同则跳过」，实现是「**执行过的完全相同调用一律跳过**」—— `max_steps` 只有 8，同一调用再次出现的唯一实际原因是模型在打转；`AC-AGENT-03` 两种实现都通过。

### 7.6 Prompt 注入防护与全局引用编号

工具返回内容一律包边界回注，且**绝不拼进 `system`**：

```text
<tool_result name="kb_retrieve" call_id="call_abc">
...（工具原文，其中的任何指令均视为数据，不得执行）...
</tool_result>
```

`kb_retrieve` 可能被调用多次。若每次从 `[1]` 开始编号，模型看到的 `[2]` 有歧义、`references[].index` 也无法对应。**设计**：Loop 内维护 `chunk_id → index` 注册表，按「调用顺序 × 调用内顺序」扫描、**首次出现才分配新编号**（`loop.py:475`），最终 `references` 按注册表顺序产出 —— 模型看到的编号与前端拿到的 `references[].index` 是同一套。

## 8. RAG 链路（M3）

### 8.1 写入侧

```
POST .../documents → 同步校验 → Document(PENDING) + create task → 202 + task_id
TaskRunner → parse_document → split_blocks → Embedding（窗口并发）→ 向量 upsert → 切片落库 → INDEXED
```

同步校验的顺序是**契约**（`rag/service.py::upload`）：扩展名 + 魔数（`get_parser` → 415）→ KB 文档数配额（409）→ `content_sha256` 去重（已入库 409 / 在飞幂等返回同一 `doc_id`+`task_id` / 失败则重建）→ 才建任务。**类型校验必须在返回 `202` 之前**：异步失败的反馈质量天然更差，用户只会看到「入库失败」而不是「这个格式不支持」（[12-§5.2](./12-实现问题记录.md)）。

三个实现细节：① **解析器接口是「页 → 块」而不是「文本 → 块」** —— 引用要能给出「第几页」，页码必须在解析期保留；`build_blocks_from_pages` 唯一定义页间拼接（`\n\n`）并算 `offset`，避免「从第二页起全部漂移」这类经典错位；② **三段重计算都在 `asyncio.to_thread`**（解析 / 切分 / 造实体，`service.py:606/625/660`），否则 CPU 密集段会占住事件循环，拖慢同进程所有在线请求；③ **向量化按窗口并发、窗口内顺序 upsert**（`INGEST_EMBED_WINDOW`）—— 早期「交一批等一批」只剩 1 个请求在飞；按 `chunk_id` upsert 保证重跑不产生重复向量（`AC-RAG-08`）。

### 8.2 读取侧：两个顺序不可换

```
query → embed → 向量召回 top_k → 重排 top_n → 阈值 → 相邻切片合并 → 预算裁剪 → RetrievedChunk[]
```

（`app/rag/retriever.py:108-125`）

| 步骤 | 为什么必须在这个位置 |
| --- | --- |
| 重排在阈值**前** | `score_threshold` 定义在 `rerank_score` 上；向量分与重排分同量级但**不同分布**，先在向量分上过滤等于用错尺子 |
| 阈值在合并**前** | 合并会改写文本并继承其中较高的分数；先合并再过滤，低分片会**搭着高分邻居的分数**混进上下文，而阈值本来就是为了逐片淘汰 |
| 合并在预算**前** | 合并减少条目与重复文本，先合并再算预算，预算才对应真实注入量 |
| 预算**最后** | 前面的步骤都不该知道上下文总量（预算属于装配层，见 §9.4） |

`_merge_adjacent` 输入已按分数降序，合并结果继承更高分与更靠前的 `chunk_index`，所以「取较小 `chunk_id`」不依赖输入顺序（`retriever.py:222`）。**重排失败不降级成 0 分**：保留向量分数并记 `rerank_skipped` —— 统一成 0 会让阈值把结果全丢掉，等于「重排坏了就检索不到东西」。**`vector_score` 的填充责任在检索层**，不在存储层（`retriever.py:165`）：让每个存储实现各自记得填，就是留一个必被漏掉的坑 —— 漏了的表现是 `/search` 的 `vector_score` 恒为 0 而 `score` 是 0.4，看起来像「重排把分数改了」（[12-§3.6](./12-实现问题记录.md)）。引用侧：`[n]` ↔ `references[].index` 从 1 开始；非流式裁剪越界标注、流式只审计（理由同 §6.3）；`/search` 同时返回 `vector_score` / `rerank_score` / `merged` —— 调参与排障时最常问的就是「这是召回分还是重排分」。

## 9. Memory 链路（M5）

### 9.1 三层与职责边界

| 层 | 组件 | 存储（`memory` / `real`） | 只依赖 |
| --- | --- | --- | --- |
| 短期上下文 | `ConversationStore` | 进程内 / Redis | 存储 |
| 摘要 | `SummaryBuilder` + `ConversationSummary` | 同一个 `ConversationStore` | LLM + 存储 |
| 长期记忆 | `MemoryRepo`（正文与元数据）+ `MemoryVectorIndex`（只管向量） | 进程内 / MySQL、Milvus | 存储 |

四条刻意的边界：① **`summary` / `extractor` 是纯逻辑**（只依赖 LLM + Settings），可脱开存储测；`context_store` / `long_term` 只依赖存储，可脱开 LLM 测；② **向量索引不复用 RAG 的 `VectorStore`** —— 那边过滤条件是 `(user_id, kb_ids, doc_ids)`，硬塞记忆得传一组恒为空的 `kb_ids`，读代码的人会以为「记忆挂在知识库下」；两边靠 `mem_id` 对齐，删除必须**成对**（`REQ-MEM-007` 双删）；③ **`MemoryService` 是唯一写入口** —— `memory_save` 工具、轮末抽取、`POST /memories` 三条路径都走 `remember()`，去重与审计只有一份；④ **工具层只是薄适配器** —— `memory_save` 把 pydantic 参数转成关键字参数，`memory_search` 把结果转成四元组 `{mem_id, content, kind, score}`（`04-§3` 的对外契约）；依赖故障（`AppError`）在这里转成 `ToolExecutionError`，工具失败要变成**可回复的结果**（`REQ-AGENT-006`），不能让整轮对话失败。短期上下文的 `clear` 与长期记忆**分离**：`DELETE /conversations/{id}/context` 只删短期、不删长期，删记忆也不影响已有上下文（「忘了会话」≠「忘了人」）。

### 9.2 读路径：降级粒度 = 依赖粒度

`_load_memory`（`chat.py:199`）把「短期历史 + 摘要」与「长期检索」放在**两个独立 try** 里，任一失败只追加 `memory_unavailable`：

```python
try:
    stored = await store.recent(...);  summary = await store.summary(...)
except Exception:
    return [], None, []      # 短期读不出来：只丢上下文，对话继续
try:
    memories = await memory.search(query, user_id)
except Exception:
    degraded.append(REASON_MEMORY_UNAVAILABLE)
```

**为什么不合并成一个 try**：摘要读不出来不该让长期记忆一起消失。三层是三个独立依赖，降级粒度必须与依赖粒度一致。

### 9.3 写路径：四步去重 + 双写

`MemoryService.remember()` 的判定顺序固定：

| 步 | 判据 | 结果 |
| --- | --- | --- |
| 1 | 归一化后 `content_sha256` 命中 | 不新建，`hit_count += 1`，刷新 `updated_at` |
| 2 | 与已有记忆的余弦 ≥ `memory_dedupe_threshold`（0.92） | 合并为一条，正文取较新，**重算哈希** |
| 3 | 余弦 ∈ [`CONFLICT_LOW`=0.85, 0.92) | **两条并存**（宁可冗余也不丢信息） |
| 4 | 其余 | 新建 |

写入是**双写**：`repo.add(record)` + `index.upsert(mem_id, user_id, vector)`。向量是 `record.id` 的附属物，所以关系库之后调用；删除必须两边都做，漏一边的表现是「列表里没有了，但检索还能命中」。`search` 会把「索引里有、关系库没有」的命中**跳过**而不是报错（幽灵向量）。**归一化只有一个实现**（`normalise_content`，`memory/long_term.py:89`）：哈希去重与语义去重必须基于同一份正文定义，否则「同一句话」在两条路径上得出不同结论。

### 9.4 上下文装配：记忆是**独立**的 system 消息

```text
用户长期偏好与已知事实
- 用户偏好简洁回答，不要使用列表
（以上为用户历史信息，如与当前问题冲突，以当前对话为准）
```

**为什么不拼进主 system 提示词**：记忆是**可能过时**的信息，主提示词是不可协商的规则。拼在一起，模型无法区分「用户以前说过什么」与「系统要求你做什么」，冲突时按最后一条指令执行——正好是反的。独立成段 + 显式声明优先级，把判断写进提示词而不是让模型去猜。

预算（`context.py`）：先按各片段的独立配额裁剪 —— 记忆整条丢弃（`memory_token_budget=600`、`memory_top_n=3`）、摘要超 `summary_token_budget=1200` 降级为前 `SUMMARY_FLOOR_TOKENS=400`、历史从最旧丢（`history_token_budget=2400`）、RAG 按分数从低丢（`rag_context_token_budget=2500`，至少留 1 条）；再按 `历史 → RAG → 记忆 → 摘要` 全局兜底到 `context_token_budget=8192`。`system` 与 `query` 永不被裁。裁剪明细写进 `AssembledContext.trimmed` 并落日志，`GET /conversations/{id}/context` 把它暴露出来 —— 这是「模型为什么没看到某条信息」的唯一答案。

### 9.5 轮末动作：两条路径都接，投递或同步兜底

1. **非流式与流式走同一条收尾路径**（`_after_turn`）：只接在流式上，默认路径就永远不抽记忆（12-§8.1）；
2. **幂等键必须带「本轮」标识**：`make_idem_key(type_, user_id, resource_id, turn_marker)`，产出 64 位 hex（`docs/09` 的 `idem_key` 是 `CHAR(64)`）；用会话 id 当键，第 2 轮起全部被当成重复投递；
3. **没配 `TaskService` / `Runner` 时同步做掉**（`_run_inline`）：这不是测试专用分支 —— 单进程部署下什么都不做，摘要与记忆永远不生成，而表面一切正常，那才是最难排查的形态；同步路径也是唯一能把摘要失败写回 `degraded_reasons` 的路径（异步任务的失败只体现在 `GET /tasks`）。

**改绑处理器**：`MemoryTaskHandlers.bind()` 只能注册一次，所以「重建记忆层」走 `build_memory_services(..., register_handlers=False)` + `bind(新服务)`，而不是再注册一遍。这与路由层「每请求从 `app.state` 取服务」同一口径：**注入点是 `app.state`**。

### 9.6 对外错误码语义

| 场景 | 码 | 为什么不复用别的 |
| --- | --- | --- |
| 记忆能力已关闭时读写 | `409 CONFLICT` | 不是权限问题（403），而是**当前状态**不允许，改设置即可重试；返回空列表会让「关闭了」与「确实没有」同形 |
| `DELETE /memories` 未带 `all=true` | `400 INVALID_ARGUMENT` | 清空全部不接受无参形式，防一次误点抹掉用户数据 |
| 会话不属于当前用户 | `404 CONVERSATION_NOT_FOUND` | 与「不存在」同码，不泄露资源是否存在 |
| 摘要尚未生成 / 手动重建 | 未生成 → `404 SUMMARY_UNAVAILABLE`；重建 → `202` + `task_id` | 「空字符串的 200」会让前端分不清「没摘要」与「摘要是空的」；生成是异步的，响应只能承诺「已受理」 |

## 10. 异步任务（M3 状态机 → M7 Worker）

### 10.1 状态机集中定义

```python
ALLOWED_TRANSITIONS = {                        # app/tasks/models.py:68
    PENDING:   {QUEUED, CANCELED, FAILED},     # → FAILED 仅「补偿放弃」这条边（§10.8）
    QUEUED: {RUNNING, CANCELED},  RUNNING: {SUCCEEDED, FAILED, CANCELED},
    FAILED: {QUEUED, CANCELED},                # 可重试
    SUCCEEDED: frozenset(),  CANCELED: frozenset(),   # 终态
}
```

**为什么用显式白名单而不是「判断是否终态」**：后者表达不了「`FAILED` 只能回 `QUEUED`」。`FAILED` 在状态机里**不是**终态（能重试），必须与 `TERMINAL_STATUSES`（`SUCCEEDED` / `CANCELED`）分开定义 —— 混用会让「重试」把已成功的任务改回 `QUEUED`。

### 10.2 乐观锁 + 变更函数

```python
await store.update(task_id, mutate)   # 内部做版本比对与重试
```

**为什么不是一堆 `update_status()`**：`docs/08` §2 要求状态变更带 `WHERE status = :expected AND version = :v`；写成通用原语，业务动作只描述「改什么」，各自实现并发控制就一定会漏。**约束**：变更函数**不许改 `version`**（store 统一推进），否则「乐观锁」退化成各调用点说了算的形式主义；store 显式检查并抛 `TaskConflict`。Redis 实现用一段 CAS Lua 完成「读 → 比对版本 → 写」（`tasks/redis_store.py:321`）。

### 10.3 取消语义

| 当前状态 | 行为 |
| --- | --- |
| `PENDING` / `QUEUED` | 立即 `CANCELED` |
| `RUNNING` | 只置取消标记（`task:cancel:{id}`），由 Worker 在检查点退出，**不立刻改状态** |
| 终态 / 重复调用 | 终态 `409 TASK_NOT_CANCELABLE`；重复调用幂等返回当前状态（连点两次不该看到 409） |

**为什么 `RUNNING` 不立刻改**：单批 Embedding 不可中断，立刻改状态会让前端显示「已取消」，而这一批还在写向量库。

### 10.4 三个执行器：「配置决定装配」

| `TASK_RUNNER` | 执行者 | 任务存储要求 | 用途 |
| --- | --- | --- | --- |
| `none` | 只建任务不执行 | 任意 | 契约测试（要停在 `PENDING`）、演示「排队」 |
| `inline` | **API 进程**自己跑（`InlineTaskRunner`），库内默认档 | 任意 | 单进程开发档：`curl` 一下就能看全流程。⚠️ 大文档的解析/切分/向量化会占住 API 的事件循环与 CPU，同机所有请求一起变慢（实测 49MB 把 `/health` 拖到十几分钟不应答）⇒ 它是**明确的降级选择**，不是推荐档 |
| `kafka` | **独立 Worker 进程**（`python -m app.worker`） | 必须共享（`INFRA_BACKEND=real`） | 生产形态：任务不抢 API 的 CPU、可水平扩 Worker；`.env.example` 的出厂档 |

「**大文件不许拖垮在线请求**」是 `docs/10` 的 **UP-06** 守门项：实现早就在位（独立进程 + 三段 `to_thread` + Worker 内限并发的 embedding），要守的是**别把 ingest 搬回 API 进程**、别把 `to_thread` 改回同步；单测守门 `tests/unit/test_rag_ingestion_threads.py`。

### 10.5 Worker 自己拒绝在错误配置下启动

`python -m app.worker` 第一件事是自检（`worker/__main__.py`）：① 任务存储不共享（`INFRA_BACKEND=memory`）→ **退出码 2**（`worker.misconfigured`）—— 内存任务存储是**进程私有**的，Worker 拿到消息后查不到那行任务，表现是「消息被消费了但任务永远停在 `QUEUED`」，一个不报错、只静默转圈的故障；② `TASK_RUNNER != kafka` → 只告警（`worker.runner_not_kafka`）：技术上能跑，但「API 内联跑 + Worker 也消费」会让同一任务被两个进程各跑一遍（幂等能兜住，白跑几分钟）。

**推广**：**配置错了一定会坏、且坏得很难查的组合，应该在启动期直接拒绝**，并给出可执行提示（`hint=用 INFRA_BACKEND=real（Redis）`），而不是留一个「看起来在工作」的进程。

### 10.6 投递与消费：谁保证不重、谁保证不丢

| 风险 | 手段 |
| --- | --- |
| 重复投递 / 消费；消息丢失 | 幂等键 `task:idem:{key}`（`SET NX`，与任务同寿命）+ Worker 领取后按状态跳过终态任务；「状态先落库、后 commit offset」+ 补偿扫描兜 `PENDING` |
| 同资源并发 | 分区键：一般任务用 `resource_id`，`memory_extract` 用 `user_id`（避免并发 merge 同一行记忆） |
| 乱序完成跳消息 | **按分区的连续水位线**提交（`app/worker/offsets.py`），不是「谁先完成谁先提交」（12-§12.1） |
| 单条任务卡死 | `asyncio.wait(timeout=task_timeout_seconds)` → `FAILED(TASK_TIMEOUT)` + 调度重试 |

Topic 是 `ai.task.<type>`（`document_ingest` / `document_delete` / `summary_build` / `memory_extract`），死信 `ai.task.dlq`；Redis 侧另有 `task:{id}`（整条 JSON）+ `task:open`（在飞 ZSET）、`task:user:{uid}` 索引（**不用 `SCAN`** —— key 上万后会拖慢整个实例）、`task:events:{task_id}` 频道。

### 10.7 退避重试不占 Worker 并发额度

```python
delay = base * 4 ** (attempt - 1) * (1 ± jitter)    # app/tasks/retry.py:108，jitter 默认 0.2
ZADD retry:zset <到期时间戳> <task_id>:<attempt>     # retry.py:212
```

关键在**谁在什么时候捞**：Worker 主循环在「两条消息之间」顺手 `claim_due()`（间隔 `TASK_RETRY_POLL_SECONDS=1.0`，`worker/loop.py:411`），而不是 `await asyncio.sleep(16)` 占住一个并发槽 —— 后者在 `worker_concurrency=2` 时意味着**卡一个任务就少一半吞吐**。认领必须**原子**：「查到期的」与「从 ZSET 删除」之间若被另一个 Worker 插入，同一任务会被重投两次；因此用一段 Lua 把两步合一（`retry.py:77`，集成测试 `test_claim_is_atomic_across_claimers` 就是它的存在性证明），且用 `ZRANGEBYSCORE` 而不是 `ZPOPMIN`（后者会把**未到期**的也弹出来）。

### 10.8 补偿扫描：兜住「任务建好了但没投出去」

`TaskCompensator`（仅 `TASK_RUNNER=kafka` 启动）每 `task_compensation_interval_seconds=30` 扫一次「仍是 `PENDING` 且创建超过 `task_compensation_grace_seconds=60`」的任务并重投；重投 `task_compensation_max_attempts=3` 次仍失败，或滞留超过 `task_pending_max_age_seconds=600` → `FAILED(MQ_UNAVAILABLE)`。

**为什么必须有它**：`docs/08` §2 的不变式是「`QUEUED` 蕴含已投递」，但**投递之前进程崩了**（Kafka 抖动 / OOM / 部署重启）会留下一条「永远 `PENDING`」的任务 —— 它是唯一能把这类任务救回来的人；前提是扫描必须对**单条脏数据免疫**（12-§12.7）。

### 10.9 进度流与分页

`GET /tasks/{task_id}/events`（`app/tasks/stream.py`）三条容易写错的约定：① **先订阅、后读快照** —— 反过来会丢事件（订阅是异步生成器，函数体要到第一次 `__anext__` 才执行，所以还要**预热**一次，12-§12.2）；② **快照是权威、增量是尽力而为** —— 总线（Redis pub/sub）会丢帧、不重放，首帧一定来自任务表，断线重连等价于「重读一次快照」；③ **超时不能取消上游订阅** —— `asyncio.wait_for(anext(...))` 会把取消信号抛进生成器内部并终结它（M2 踩过同一个坑），所以「竞速但不取消生产者」，只在整个流结束时取消。

`FAILED` 之后**不关流**：`FAILED → QUEUED` 是合法迁移，自动重试可能随后发生；`error.retryable` 的判据是「错误码值得重试**且**预算没用完」（`error_retryable`）。

**列表分页共用一套原语**：`core/pagination.py::cursor_position(created_at, id)` + `is_after_cursor`，知识库 / 文档 / 切片 / 任务 / 工具全部复用；工具没有创建时间，用「固定纪元 + 名字」当位置键，而不是另写一套 name 游标 —— 多一套实现就多一套分叉。

## 11. MCP 与可观测性（M6）

| 关注点 | 设计 | 理由 |
| --- | --- | --- |
| SDK 接触面 | 只有 `app/mcp/session.py` import `mcp`，把两种 transport 归一成 `list_tools()` / `call_tool()` | `mcp` 2.2.0 的 `streamable_http_client` 与 stdio 上下文管理器签名不同；换 SDK 只动一个文件 |
| 状态与熔断 | `connected` / `connecting` / `unavailable` / `disabled` 互斥，变更即同步 `ai_mcp_server_state`；目标名 `mcp:{server}`，家族规则 3 次失败 / 30s 恢复 | 指标只在状态变更的唯一发生地写；单 Server 挂掉不该拖垮所有 MCP 调用 |
| 工具命名 / 重载 / 埋点 | `mcp__{server}__{tool}`，非法字符换 `_`，清洗后变化或超 64 字符则截断 + 6 位摘要；重载先 `unregister_source` 再注册；`ai_tool_calls_total` 只在执行器记一次 | 避免两个工具被洗成同一名字、僵尸工具、埋点翻倍（12-§11.3） |

**指标只走独立端口**（`METRICS_HOST:METRICS_PORT`，默认 `9100`）：主应用不提供 `/metrics`（返回 404），另有极简 HTTP 服务只处理 `GET /metrics`。挂主应用要么暴露运维端点、要么让 Prometheus 持有业务 token；独立端口的代价只是多一个监听。绑定失败只记 `metrics.server_failed`、**不阻断启动**。共 **19** 个 `ai_*` 指标。**`trace_id` 必须等于 OTel 的 trace id**（S10 要求「拿用户给的 id 直接查到链路」）：`Tracing.request_span()` 用上下文里的 id 手工拼**远程父上下文**再挂 span，于是 OTel 产出的 id 就是我们的值；非法 / 全零 id 退化为「新建 trace」而不是崩溃。`endpoint` 标签取路由模板（`effective_route_context.path` → `scope["route"].path` → `unmatched` 三级降级）。

采集栈在 `deploy/observability/`：`docker compose -f deploy/observability/compose.yml up -d`（Prometheus + Grafana + Jaeger，Grafana 18 个面板）。两个实测坑：主机端口可能被占，用覆盖文件时 Compose 的端口列表默认**追加**，必须 `!override`（Compose v2.24+）；`targets` 端口必须与 `METRICS_PORT` 一致 —— 不一致且该端口有别的服务应答时，Prometheus 显示 `up`、样本数不为 0，但**一个 `ai_*` 都没有**；判断依据是哨兵指标 `ai_build_info`，不是 `up`。

## 14. 已知取舍与未实现

| 项 | 现状 | 理由 / 代价 |
| --- | --- | --- |
| 依赖故障不阻断启动 | `real` 下初始化失败退化为 503 占位仓储 | 换来「Milvus 挂了仍能对话与体检」；代价是多一条运行期降级出口（§4.3） |
| 相邻合并在阈值之后 | 见 §8.2 | 先合并会让低分片搭高分邻居的分数混进上下文 |
| 重复调用「一律跳过」 | 比文档的「连续 2 次」更严 | `max_steps=8`，再次出现只说明模型在打转 |
| `dry_run` 不体现在响应体 | `04-§4.2` 响应只有 `name/status/result/elapsed_ms/error`，服务端 `summary` 被响应模型丢掉 | 调用方只能靠 `result == {}` 反推；加字段要改 SRS，`test_memory_save_invoke_is_forced_dry_run` 钉住「库里确实没写」 |
| 摘要防抖只在单进程内有效 | 内存 `_Debouncer`，5 分钟窗口 | 多副本各防各的；当前靠幂等键与任务终态去重夹住扇出 |
| LangGraph 未被采用 | 设计初期考虑过状态图，最终未落地；仓库内没有 LangGraph 节点/状态图代码 | 三重护栅需要精确控制回注与截断，自研 Loop 更直接 |
| MySQL / Milvus 已在 `real` 下实现 | KB / 文档 / 切片 / 任务 / 长期记忆都有实现；仅当初始化失败（缺 extra、DSN 不可解析、Milvus 不可达）才退化为 503 占位 | 旧文档「MySQL 仓储未实现」已过时；占位是为「部署忘了装 extra」留的降级，不是常态 |
| 检索效果无量化验收 | 没有评测集与真实 recall@5 | 改切分 / 换 embedding 缺量化手段，是当前最大的流程缺口 |
| 长驻 gRPC 进程退化 | 跑约 3 小时后所有 `Chat` 退化为 `503 DEPENDENCY_UNAVAILABLE`（Python 直连同样失败，可排除网关），重启即恢复 | 根因未定位；运维按定期重启兜底（`ai-platform-go/docs/08` §6.4） |
| 没有 CI、没有 K8s 清单 | 仓库只有 Docker Compose 本地基础设施与可观测栈 | 部署形态是设计目标，不是既成事实 |

平台级取舍（自研 Loop vs LangGraph、Milvus vs Qdrant、Go 单进程多模块、Gin 承担对外 HTTP/SSE）见根 README 的「关键取舍」与「设计文档与实现的有意偏差」，本文不复述。

## 15. 测试与防线

测试分层（单元 → 契约 → 集成 → 端到端 / 效果）与各层职责见 [11-验收标准与测试策略](./11-验收标准与测试策略.md)，此处只记两条设计约束与实测口径。**替身必须与协议同形**：`FakeEmbedding.embed` 是**同步**的（协议如此，调用方会 `asyncio.to_thread`）；写成 `async def` 会让 `to_thread` 拿到 coroutine。

**结构守卫**（比单点用例更值钱的一类）：`test_route_auth_coverage.py`（非公开路由都声明鉴权依赖）、`test_logging_extras.py`（`extra` 键名与 `LogRecord` 无交集）、`test_tools_*`（重名内置工具必须启动失败、`parameters` 必须是合法 JSON Schema）、`test_error_to_code_covers_every_reason`（失败原因 → 错误码穷举）。**判断标准**：成因是「**任意一处**写错都会犯」→ 结构守卫（扫描全仓）；是「某个具体逻辑算错了」→ 单点用例。实测：`pytest` **1698 collected / 1688 passed / 10 skipped**、覆盖率 **89%**（未起基础设施，集成用例跳过）；口径与复现命令见 [README §4](./README.md)。
