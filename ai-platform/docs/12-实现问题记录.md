## 1. 为什么需要这份文档

这批问题的共同特征：**代码能跑、测试能过、接口有响应，但结果是错的**。

| 类型 | 表现 | 为什么难发现 |
| --- | --- | --- |
| 静默丢数据 | 分页第二页为空 | 不报错、不告警，只有用户发现少一条 |
| 静默不生效 | 中文页眉删不掉 | 结果「看起来正常」，只是检索命中率低 |
| 环境相关 | 测试全绿、生产建任务 500 | 只在日志级别允许输出时才触发 |
| 语义错位 | `vector_score` 恒为 0 | 字段在、类型对、值恒 0 |
| 装配错位 | 入库成功但检索 0 条 | 两个向量库实例，各自都对 |
| 护栏失效（M4） | 步数上限没生效、SSRF 被绕过 | **测试全绿**——护栏在不在正是靠测试证明 |
| 旁路失效（M5） | 记忆不更新、摘要不生成 | 无异常无告警，只是少做一件事 |
| 约束失效（M6 前置） | 唯一键从不触发、同名记录无限插入 | 约束没拦住时什么都没发生 |

每条都要求留下**机器可执行的防线**（测试/结构守卫）。「下次注意」在 6 个人月后等于没写。

## 2. 静默丢数据类

### 2.1 时间戳与字符串比较 → 游标分页漏项

**症状**：`GET /tasks` 第一页 2 条，用返回的 `next_cursor` 取第二页得到**空数组**，不报错。  
**根因**：`now_iso()` 的 `2026-09-28T09:15:45.604Z` 与 `datetime.isoformat()` 的 `...604000+00:00` 做**字符串**比较，第 20 字符 `'.'(0x2E) > '+'(0x2B)`，同一毫秒的任务全被判「已翻过」；Windows 同批创建几乎必落同一毫秒 ⇒ 第二页 100% 空（`app/tasks/store.py`）。  
**修法**：收敛到 `app/core/pagination.py`：`cursor_position(created_at, id)` 同时做排序键与比较键，`is_after_cursor()` 负责比较，`parse_stamp()` 归一 str/datetime。**防线**：`tests/unit/test_pagination.py::test_is_after_cursor_keeps_same_millisecond_items`；另断言 `MILLIS != SAME_MOMENT` 而 `parse_stamp` 相等，把「字符串不等、时刻相等」钉成用例。  
### 2.2 排序键与游标键不一致 → 顺序错乱

**症状**：列表顺序偶发不对，同毫秒记录顺序不稳。  
**根因**：排序用 `(task.created_at, task.id)`（字符串），比较用 `(datetime, str)`——两把尺子量同一件事。  
**修法**：`InMemoryKnowledgeBaseRepo` / `InMemoryDocumentRepo` / `InMemoryTaskStore` 统一 `key=lambda x: cursor_position(x.created_at, x.id)`。**防线**：`test_cursor_position_is_datetime_keyed_not_string_keyed` 断言位置键第一段是 `datetime` 而非 `str`。  
### 2.3 同一位置产生两条不同游标

**症状**：日志里同一位置出现两条不同 `cursor` 串，排查时误判「位置变了」。  
**根因**：`encode_cursor` 对 `datetime` 做 `astimezone(UTC).isoformat()` 归一，对 `str` **原样透传**，两种入参两条编码。  
**修法**：两种入参都先过 `parse_stamp`。**防线**：`test_encode_cursor_accepts_datetime_and_str` 断言两者产出同一串。  
### 2.4 参数被同名局部变量覆盖

**症状**：按 `resource_id` 过滤任务结果不对，但传了值、看起来「生效了」。  
**根因**：`list()` 里 `moment, resource_id = decode_cursor(cursor)` 覆盖了入参 `resource_id`；Python 不报错，过滤条件永远用游标里的 id。  
**修法**：局部变量改 `cursor_id`，并把解码收进 `is_after_cursor` 内部，消除手写解包。**防线**：解码只发生在 `is_after_cursor` 内，调用方拿不到裸元组去解包。

## 3. 静默不生效类

### 3.1 清洗顺序错误 → 中文页眉页脚永远删不掉

**症状**：PDF 清洗后中文页眉「产品手册」仍在正文里，`detect_repeated_lines` 返回空集。  
**根因**：`clean_pages` 先做 `normalize_text`，其中的 CJK 孤行合并（`([CJK])[ \t]*\n[ \t]*([CJK])` → `\1\2`）把页眉与下一行正文粘成一行，此后每页该行都不同，重复计数到不了阈值——一个「让 PDF 更易读」的优化静默废掉了「去页眉」。  
**修法**：归一化拆两步并固定顺序：`_normalize_preserving_lines`（不动行结构：零宽、换行符、NFC、断词、行尾空白）→ `strip_page_numbers` → `detect_repeated_lines` → `normalize_text`（CJK 合并放最后）。**防线**：`test_clean_pages_removes_cjk_only_header` + `..._keeps_cjk_body_lines_merged` + `..._is_idempotent`（清洗两次 == 一次，否则重新入库会产出不同切片）。  
### 3.2 `.strip()` 吃掉首行缩进 → 代码块语义丢失

**症状**：`"    if x:"` 入库后变成 `"if x:"`。  
**根因**：`normalize_text` 末尾用 `.strip()`，而同函数注释写明「只在行尾去空白：行首缩进对代码/列表有意义」——注释与实现自相矛盾。  
**修法**：改成 `.strip("\n")`，只裁剪首尾空行。**防线**：`test_normalize_strips_trailing_space_but_keeps_indent`。  
### 3.3 编码探测顺序导致 encoding 字段总是错的

**症状**：所有 UTF-8 文件元信息里的 `encoding` 都是 `utf-8-sig`。  
**根因**：`for encoding in ("utf-8-sig", "utf-8")`——`utf-8-sig` 对**没有 BOM** 的文件同样能解码成功，第一个分支永远命中。  
**修法**：先判 `codecs.BOM_UTF8` 前缀，再试 `utf-8`，最后 `gb18030`。**防线**：`test_decode_bytes_plain_utf8_reports_utf8` / `..._bom_is_stripped_and_reported`。教训：「能解码」与「该报什么编码名」是两件事，探测类函数的返回值要单独测。  
### 3.4 HTML 解析：块级标签里的文字全丢

**症状**：真实网页解析出来是**空字符串**，表格内容重复出现两次。  
**根因**：`for element in soup.descendants` 里 `if not isinstance(element, Tag): continue` 跳过了真正的文字（`NavigableString`）；`<p>/<div>/<li>` 又在 `_BLOCK_TAGS` 分支 `flush(); continue`，从不进子树。文字落在 `<p>` 的文本子节点上，两条分支各拦一次 ⇒ 整页解析不出来；表格既作原子块收一次、又作 descendants 收一次 ⇒ 重复。  
**修法**：递归 `walk(node)`：`NavigableString` 收进段落；heading `flush` 后入栈；`table`/`pre` 原子收取不递归；其余块级 `flush` 后递归进子树。**防线**：`test_html_drops_script_style_nav_footer`、`test_html_builds_heading_path_and_title`、`test_html_table_is_atomic`（断言 `len(blocks) == 1`）。  
### 3.5 解析顺序错误 → `html_title` 永远为空

**症状**：HTML 的 `metadata["html_title"]` 恒为 `""`。  
**根因**：`_DROP_TAGS` 包含 `head`，而 `page_title = soup.title...` 写在 `for tag in soup.find_all(_DROP_TAGS): tag.decompose()` **之后**，`<title>` 已被删。  
**修法**：先读 `soup.title`，再 `decompose`。**防线**：`test_html_builds_heading_path_and_title` 断言 `html_title == "售后政策"`。  
### 3.6 `vector_score` 恒为 0

**症状**：`/search` 返回的 `vector_score` 永远是 0，而 `score` 正常。  
**根因**：`vector_score` 由**存储层**负责填，两个存储实现都忘了填：字段有、类型对、值恒为 0。  
**修法**：责任上移到检索层——`_recall` 拿到召回结果后统一 `replace(chunk, vector_score=chunk.score)`，存储只保证 `score` 正确。**防线**：`tests/unit/test_rag_retrieval.py`（重排保留 `vector_score`、未重排时 `score == vector_score`）+ 契约测试 `with_rerank=false` 分支。原则：**谁定义语义，谁负责填字段**。  
### 3.7 两个向量库实例 → 入库成功、检索永远 0 条

**症状**：上传返回 202、任务 `SUCCEEDED`、`/documents/{id}/chunks` 有切片，但 `/search` 与 `/chat` 的 `references` 恒空，**没有任何异常或日志**。  
**根因**：`create_app` 里 `build_rag_services()` 与 `build_chat_service()` 各自 `build_vector_store()`：写入写 A 的内存字典，读取查 B 的空字典。真实 Milvus 下连的是同一个服务反而「对」——这类 bug 专挑本地/测试环境骗人。  
**修法**：`build_retriever(settings, *, embedding, vector_store, reranker)` 允许注入，`build_rag_services` **必须**注入同一批实例，并把 `app.state.retriever` 暴露出去。**防线**：`build_retriever` 的 docstring 写明「写入侧与查询侧必须是同一个向量库」；`tests/contract/test_chat_rag.py` 的 `rag_chat_client` 夹具显式复用 `application.state.retriever` 并注明原因。  
### 3.8 重试静默不执行

**症状**：`POST /tasks/{id}/retry` 返回 200、状态变 `QUEUED`，然后**永远停在 QUEUED**。  
**根因**：`docs/08` §4.4 要求「置 `QUEUED` **并**投递」，但 `InlineTaskRunner.submit` 只接受 `PENDING`：`if task.status is not TaskStatus.PENDING: return`——静默返回，连日志都没有。  
**修法**：接受 `PENDING | QUEUED`，加 `_inflight` 集合去重；`retry()` 同时清 `started_at`（否则耗时按 `finished - started` 跨轮次算）。**防线**：`tests/unit/test_task_state_machine.py::test_retry_resets_progress_and_started_at`；契约断言 `retry_count+1` 且最终再次 `FAILED`。静默 `return` 是这类问题的共同形状。

## 4. 环境相关类

> 端口：HTTP `8000`、指标独立 `9100`、gRPC `50051`（`GRPC_ENABLED` 默认 `false`，只监听回环）。
> 已知长期缺陷：长驻 Python gRPC 进程约 3 小时后 `Chat` 全部退化为 `503 DEPENDENCY_UNAVAILABLE`，Python 直连探测同样失败（排除网关），重启即恢复；根因未定位、无自动告警，靠 503 比例监控 + 定期重启兜底，现场见 `ai-platform-go/docs/08` §6.4。

### 4.1 `extra={"created": ...}` 撞 `LogRecord.created`

**症状**：`KeyError: "Attempt to overwrite 'created' in LogRecord"`，**只出现在生产**，建任务接口直接 500，测试全绿。  
**根因**：`Logger.makeRecord` 检查 `extra` 键是否与 `LogRecord.__dict__` 重名，而记录时间戳就叫 `created`。三重巧合躲过测试：只有 `isEnabledFor(level)` 为真才走到 `makeRecord`；`tests/conftest.py` 基线 `log_level="WARNING"` 而这条是 `INFO`；生产默认 `INFO`。  
**修法**：键名改 `is_new`；conftest 的 `log_level` 对齐生产 `INFO`（输出仍被 pytest 捕获）；新增 `tests/unit/test_logging_extras.py`，用 `ast` 扫全仓 `extra={...}` 键名并与 `logging.makeLogRecord({}).__dict__` 求交集，非空即失败。**防线**：`test_extra_keys_do_not_shadow_logrecord` + `test_make_record_actually_rejects_reserved_keys`（反向证明这些键确实会被标准库拒绝）。单点用例防不住，结构化检查能防一整类。  
### 4.2 `INFRA_BACKEND=real` 时整个应用起不来

**症状**：`app_env=prod` 下 `create_app` 直接抛 `NotImplementedError`，连健康检查、鉴权、对话都不可用。  
**根因**：`build_repositories` 在 `real` 分支直接 raise，而 `docs/10` 的依赖矩阵只要求**依赖 MySQL 的接口**返回 503。  
**修法**：新增 `app/infrastructure/storage/unavailable.py`——三个仓储的每个方法都抛 `503 DEPENDENCY_UNAVAILABLE`，`build_repositories` 在 `real` 下返回它们并记一条 warning。**防线**：`tests/contract/test_auth.py` 的 `real` 后端用例。原则：启动期只判「能不能工作」，不判「依赖是否齐全」，后者会把局部故障放大成全局不可用。  
### 4.3 启动期探测失败导致容器重启循环

**症状**：Milvus 没起来时容器反复重启，服务始终起不来。  
**根因**：lifespan 里的 `ensure_ready()` / `verify_model()` 异常直接上抛，把局部依赖故障放大成启动失败。  
**修法**：两处一律 try/except + warning，不阻断启动；依赖健康交给 `/health/ready` 的 503 表达。**防线**：`app/main.py` 里的注释 + `docs/10` 依赖矩阵。  
### 4.4 `import pymilvus` 把开发机 `.env` 灌进 `os.environ`

**症状**：契约测试**单独跑全过、连着跑必挂**：`test_health.py` 报 `assert 2048 == 1024`，`test_memory.py` 5 条配置校验失败；启动日志里 `embedding_provider=hash`（基线显式传的）却带 `.env` 的 `EMBEDDING_DIM=2048`——provider 来自调用方、维度来自开发机 `.env` 的「混血配置」。  
**根因**：三层叠加：① `pymilvus/settings.py` 第 6 行直接调 `load_dotenv()`（**不是本仓库代码**），import 即从 CWD 往上找 `.env` 写进 `os.environ`；② 任何先跑过的 RAG 用例都会 import pymilvus，此后**整个进程**被污染，单跑某文件不 import 所以是绿的；③ `Settings(_env_file=None, **values)` 的 `_env_file=None` 只关 dotenv 文件，关不掉已存在的环境变量（env 优先级更高）。  
**修法**：应用侧 `app/rag/vectorstore/milvus.py::_import_pymilvus_guarded` 做「快照 → import → 恢复」，只回滚它新增/改动的键（不 `clear()`）；`MILVUS_*` 由 `Settings.milvus_connection_args` 显式传入。测试侧 `tests/conftest.py::_BASE` 钉住 `embedding_model`/`embedding_dim`/`milvus_vector_dim`，`autouse` 的 `_isolate_process_env` 每例前后还原 `os.environ`。**防线**：复现 `pytest tests/contract/test_agent.py tests/contract/test_health.py`（修前 1 failed）；定位手法是劫持 `type(os.environ).__setitem__` 打栈（`os.environ` 启动时已把 `putenv` 绑成实例属性，改 `os.putenv` 抓不到写入）。新增第三方依赖先查它在 import 期是否动 `os.environ`。  
### 4.5 云端 provider 接上了，但入库循环在串行等待

**症状**：embedding 换云端后，8MB 入库仍要 **98.2s**（16.9 ms/片），而同一 provider 裸测（batch=32、并发 8）是 **379.6 片/s**，按此应 ~15s；慢 6 倍且没有任何报错与告警。  
**根因**：`_embed_and_upsert` 是「取一批 → `await embed_texts()` → upsert → 再取下一批」的严格串行；provider 内部确有并发池（`ThreadPoolExecutor(max_workers=concurrency)`），但**每次只提交一个批次**（`len(batches) == 1`），池里永远只有一个任务，链路上只有一个 HTTP 请求在飞。本地 BGE 时代算力在本机，串行等待没有额外代价；换云端后每次都是网络往返，空转变纯损耗。  
**修法**：按窗口并发（`INGEST_EMBED_WINDOW`，默认 4、模板 8），窗口内 `asyncio.gather` 提交 N 个批次，然后**仍按顺序** upsert 并逐批上报进度，`docs/06-§4.5` 的「逐批进度 + 逐批取消检查」语义不丢。**防线**：实测 8MB / 5,821 片：98.2s → 窗口 8 的 40.4s → 窗口 16 的 40.9s（8 是拐点）；`tests/unit/test_ingest_facts.py` 补「批次数与调用次数」的事实断言。

## 5. 契约与分层类

### 5.1 Schema 层抛不出领域错误码 → 校验放错层

**症状**：`chunk_overlap >= chunk_size` 返回 `400 INVALID_ARGUMENT`，而 `docs/02` 要求 `400 CHUNK_STRATEGY_INVALID`。  
**根因**：pydantic 的 `field_validator` / `model_validator` **只能抛 `ValueError`**，框架统一转成 `INVALID_ARGUMENT`；自定义 `AppError` 在 validator 里会被包成 `ValidationError`，抛不出去。  
**修法**：切片参数校验整体下移到 `resolve_chunk_params()`（服务层唯一实现），schema 只留结构性校验。**防线**：契约测试断言错误码是 `CHUNK_STRATEGY_INVALID`。规则：领域错误码必须在服务层抛，schema 的能力边界是「语法」。  
### 5.2 不支持的文件类型被伪装成「任务失败」

**症状**：上传 `.xyz` 返回 202，任务 3 秒后 `FAILED`，错误消息是解析器底层异常——用户看到「系统出错」而不是「这个格式不支持」。  
**根因**：类型校验发生在任务执行内，异步失败的信息量天然更少。  
**修法**：`DocumentService.upload` 在返回 `202` **之前**调 `get_parser()`，不支持即同步返回 `415 UNSUPPORTED_FILE_TYPE`。**防线**：`test_documents.py` 两条 415 用例（不支持的扩展名、扩展名与魔数不符）。原则：能在同步阶段给的错误不要拖进异步。  
### 5.3 文本上传没有扩展名 → 永远 `UNSUPPORTED_FILE_TYPE`

**症状**：`doc_name="测试文档"` 上传纯文本返回 415。  
**根因**：解析器按扩展名分发，而 `doc_name` 没写扩展名。  
**修法**：`_resolve_doc_name()` 在 sanitize 后若无扩展名，补 `normalize_extension(filename)` 或 `.txt`。**防线**：契约断言 `doc_name="政策"` 最终落库为 `政策.txt`。  
### 5.4 测试假设与 SRS 不符时，先改测试

**症状**：本次 4 处「测试失败」全部是测试写错，不是实现错。  
**根因**：期望值凭印象写，没回 SRS 核对。  

| 测试假设 | SRS 实际规定 |
| --- | --- |
| 超过知识库数量上限返回 `429` | `docs/02` 表：`KB_LIMIT_EXCEEDED` → **409** |
| `/search` 响应含 `kb_id` | `docs/06` §5.1：`SearchItem` 无 `kb_id` |
| `kb_ids` 为空 = 不检索 | `docs/03` 行 51：`use_rag=true` 且 `kb_ids` 空 = 检索**全部**知识库 |
| `merge_token_budget` 返回条数 | 实际返回 `bool trimmed` |

**修法**：改测试，不改实现。**防线**：冲突时的默认动作固定为「重读 SRS」；只有 SRS 自身矛盾才改文档并在本文档记录。

## 6. 测试工程类

规模与门禁：Python 侧 41 条 HTTP 路由、19 个 `ai_*` 指标；`pytest` **1698 collected / 1688 passed / 10 skipped**、覆盖率 **89%**；Go 侧 58 处路由注册、30 个 `*_test.go` / 234 个 `Test*`。**没有 CI、没有 Kubernetes 清单**（只有 Docker Compose 本地基础设施），以上全部本机手工执行，明细见 README §8。

### 6.1 `tests/` 无 `__init__.py` → 文件名必须全局唯一

**症状**：`tests/unit/test_utils.py` 与 `tests/contract/test_utils.py` 同时存在时报 `import file mismatch`。  
**根因**：pytest rootdir 导入模式按 basename 建模块名，同名即冲突。  
**修法**：测试文件 basename 全局唯一（如 `test_rag_retrieval.py` 而不是 `test_retrieval.py`）。**防线**：命名约定；重名在 collection 阶段即失败，不会漏到运行期。  
### 6.2 替身必须与协议同形（同步 vs 异步）

**症状**：`FakeEmbedding.embed` 写成 `async def` 后，调用方 `asyncio.to_thread(embed, ...)` 拿到 coroutine 对象，`.tolist()` 之类调用全部失败。  
**根因**：替身与 `EmbeddingProvider` 协议的同步/异步形态不一致。  
**修法**：`embed` 必须是**同步**函数；写替身时先把协议抄一遍，逐方法核对同步/异步。**防线**：替身只在协议同形时才能替换真实现，形态错误在首次调用即炸。  
### 6.3 并行编辑同一个文件会损坏内容

**症状**：`replace_string_in_file` 并行作用于同一文件时，两处改动可能交错、内容损坏。  
**根因**：读-改-写不是原子的，并行编辑互相覆盖。  
**修法**：同一文件的多次编辑**串行**；不同文件才允许并行。**防线**：编辑纪律（工具层无锁），一次只改一个文件。

## 7. M4（Agent 与工具调用）新增问题

M4 的问题几乎都属于「**护栏看似存在，其实没生效**」。前四类都能靠「结果不对」被发现；护栏失效的表现却是**测试全绿**——「护栏有没有起作用」本身就靠测试证明。一旦假 LLM 比真实上游宽松，护栏测试就退化成永真断言。

### 7.1 步数耗尽与超时中断被合并成一种

**症状**：`finish_reason` 永远返回 `stop`，`max_steps` 从未出现；`degraded_reasons` 里时而多出一条 `max_steps`。  
**根因**：中断原因从中断后的计数器**反推**——`while steps < max_steps` 里超时 `break` 后 `steps` 也可能刚好等于上限，于是被判成步数耗尽。  
**修法**：`while/else` + 显式标志位：`else` 只在条件自然为假时执行，`else` 里置 `state.max_steps_hit = True` 并追加 `REASON_AGENT_MAX_STEPS`，天然区分「步数用完」与「提前 break」。**防线**：`test_loop_stops_at_max_steps` 断言 `finish_reason == "max_steps"`；`test_loop_has_total_time_budget`（慢工具 0.4s + 总预算 0.2s）断言 `REASON_AGENT_TIMEOUT in reasons` 且 `finish_reason == "stop"`。规则：不要从中断后的状态反推原因。  
### 7.2 收尾调用被计入步数

**症状**：配置 `agent_max_steps=8`、请求 `max_steps=8`，返回的 `steps` 是 **9**。  
**根因**：达上限后为拿「最终回答」额外发了一次不带工具的 `complete()`，这次调用也走了 `state.steps += 1`。  
**修法**：`steps` 语义定义为「**工具调用轮数**」（`docs/04` 口径），收尾调用不计入；`while` 内递增，收尾走循环外的 `_wrap_up()`。**防线**：`AC-AGENT-02` 断言 `steps == 8 and len(tool_calls) == 8`；若收尾算进去，两个数同时变 9，会被误认为「上限配错了」。  
### 7.3 假 LLM 在没下发 tools 时也回放工具调用

**症状**：想断言「收尾调用必须不带工具、只能直接回答」，但测试怎么写都通过，连护栏失效的实现也能过。  
**根因**：`FakeLLM` 按固定脚本回放，**不看你有没有给工具**；收尾调用也能拿到 `tool_call`，收尾逻辑被绕开，断言的是假象。  
**修法**：`_script(tools)` 在 `not tools` 时返回 `[]`——「没给工具就调不出工具」属于上游行为，替身必须复刻。**防线**：`test_loop_wrap_up_call_has_no_tools` 断言 `llm.tools_seen[-1] is None`。替身宽松多少，护栏测试就虚假多少。  
### 7.4 流式只给成功的工具调用发帧

**症状**：`docs/02` §6 要求「每个 `tool_call` 都有配对的 `tool_result`」，实现只在 `record.status == "ok"` 时发 `tool_result`。  
**根因**：把「帧」当成「结果通知」而不是「**过程可观测性**」；工具失败恰是前端最需要显示的状态。  
**修法**：一轮结束后按模型给出的顺序**逐条**成对下发，含失败、含重复调用。**防线**：`test_agent_stream_pairs_tool_frames_before_done` 断言 `tool_call` 与 `tool_result` 数量相等、`call_id` 相同、都在 `done` 之前。  
### 7.5 重复调用被算作「工具失败」

**症状**：模型第二轮重发完全相同的调用（无害），整轮却被打上 `tools_failed` 降级标记。  
**根因**：重复调用被构造成一条 `status="error"` 的伪记录，落进 `failed = [r for r in records if not r.ok]`。  
**修法**：区分「尝试过但失败」与「根本没执行」：先排除 `record.error == ERROR_DUPLICATE_CALL`，再判断 `attempted and not any(r.ok for r in attempted)`。**防线**：`test_loop_skips_duplicate_calls` 断言 `REASON_TOOLS_FAILED not in reasons`。  
### 7.6 同一错误原因，两种 payload 形状

**症状**：模型看到的重复调用提示取决于「重复」是**执行器**还是 **Agent Loop** 发现的——两条路径各写一份构造代码，`hint` 文案还不一样。  
**根因**：同一语义在两个地方各实现一次（与 §2.1「两个时间戳原语」同源）。  
**修法**：抽公共构造函数 `duplicate_record(call, arguments)`，执行器与 Loop 共用，`payload` 形状只有一份定义。**防线**：单测断言 `payload["hint"]` 的具体文案，改文案必须改两处，不会漏。  
### 7.7 参数不合法被映射成 502

**症状**：`POST /tools/calculator/invoke` 传非法表达式返回 `502 TOOL_EXECUTION_FAILED`，正确应是 `400 INVALID_ARGUMENT`。  
**根因**：错误码映射只看 `status`（`_STATUS_TO_CODE`），而「参数错」「依赖挂」「工具自己抛异常」的 `status` 全是 `error`，信息在 `record.error` 里。  
**修法**：增加 `_ERROR_TO_CODE`（7 个原因穷举），优先按 `record.error` 映射，`status` 只作兜底。**防线**：`test_error_to_code_covers_every_reason` 断言 `{全部 7 个 ERROR_*} <= set(_ERROR_TO_CODE)`，新增原因漏配直接失败。  
### 7.8 校验失败的原因只进了 `detail`，模型看不见

**症状**：模型收到 `{"error": "invalid_arguments", "message": "参数不符合工具 Schema"}`，不知道错在哪个字段，只能盲目重试或放弃。  
**根因**：pydantic 的 `errors()` 详情（`loc` / `msg`）被整块塞进 `detail`，而上游客户端常截断/丢弃结构化 `detail`，只展示 `message`。  
**修法**：`_describe(errors)` 把前 3 条拼成人话放进 `message`（如 `expression: Value error, 表达式中不允许调用函数`），`detail` 仍保留结构化数组。**防线**：`test_current_time_rejects_unknown_timezone` 断言 `message` 含「未知时区」，而不是只断异常类型。  
### 7.9 工具「静默失效」：给上游发了一条假的 tools 消息

**症状**：带 `tools` 的请求，模型从不调用工具，不报错，只是工具被忽略。  
**根因**：为把工具 schema 传给上游，实现里先构造一条内容形如 `{"tools": [...]}` 的**普通 message** 塞进 messages，而不是 `bind_tools()`；上游当普通聊天内容处理，工具能力根本没开。  
**修法**：`client = self._client_for(...).bind_tools(tool_payload)`，并把「是否带 tools」放进缓存键 `(model, temperature, max_tokens, tools: bool)`。**防线**：`FakeLLM.tools_seen` 记录每轮 tools，断言首轮含 `calculator`、收尾轮为 `None`；真实上游还要发一次最小真实调用确认。  
### 7.10 表达式求值的白名单

**症状**：`__import__('os').system('ls')` 这类输入必须被拒，且不能只靠字符串黑名单。  
**根因**：`eval()` 前的「字符串黑名单」（`"__"`/`"import"`）是**假防护**，`getattr(__import__("o"+"s"), ...)` 可绕过；必须 `ast.parse(expr, mode="eval")` 后逐节点白名单：`Expression` / `Constant`（仅 int/float）/ `BinOp` / `UnaryOp` / `operator` / `unaryop` / `expr_context` / `Load`。  
**修法**：白名单外的 `Call`/`Name`/`Attribute` 判失败，作为**可回复的工具结果**回注；指数封顶 `EXPONENT_MAX = 1000`，超出抛 `ToolExecutionError`——参数本身合法，只是代价不可接受。**防线**：反向用例要逐个确认真的该被拒——`1e999999` 是**合法** float（解析为 `inf`），拿它测黑名单等于什么都没测；`2 ** 999999` 语法合法、白名单通过但吃满 CPU，必须有上限用例。  
### 7.11 `http_fetch` 的 SSRF 防护：只校验字面量不够

**症状**：只校验 hostname 字符串（`10.`/`192.168.` 前缀黑名单）可被 `http://2130706433/`（十进制 IP）、`[::ffff:127.0.0.1]` 绕过。  
**根因**：字面量校验不覆盖解析结果与重定向；DNS rebinding 会让第一次解析给公网、第二次给内网。  
**修法**：`_assert_public_host` 先判字面量，再 `getaddrinfo` 解析并**逐个** IP 判断（`is_private`/`is_loopback`/`is_link_local`/`is_reserved`/`is_multicast`/`is_unspecified` 任一命中即拒）；**校验全部解析结果**是 DNS rebinding 的必要条件。`http_fetch` 默认 `enabled=false`——外发能力默认打开等于给模型一个 SSRF/数据外泄出口。**防线**：参数化拒绝用例 10 条（`10.0.0.1` / `192.168.1.1` / `[::1]` / `0.0.0.0` / `ftp://` / `file://` / 无主机名 …）+ 1 条 monkeypatch `getaddrinfo` 的 DNS-rebinding 用例。  
### 7.12 测试里三处「假严密」

**症状**：三种写法让测试看起来覆盖了，实际什么都没测。  

| 写法 | 问题 | 改法 |
| --- | --- | --- |
| `pytest.raises(Exception)` | 任何异常都通过，含 `AttributeError` | 断具体类型 `ValidationError` / `ToolExecutionError` / `ToolArgumentError` |
| `ToolSpec(**spec.__dict__)` | `slots=True` 没有 `__dict__`，直接 `AttributeError` | 直接断言字段值，不做反射重建 |
| 4 条脚本却断言 `steps == 8` | 脚本用完那轮直接回答，`steps` 恒为 5 | 给够轮数，或断言 `<= 上限` |

**根因**：期望值照着实现里的常量抄，而不是先把被测循环跑一遍。  
**修法**：给测试写期望值前先在脑子里跑一遍循环。**防线**：`ruff` 的 `B017`（`Do not assert blind exception`）自动抓第一类；后两类只能靠「先算一遍期望值」。  
### 7.13 `ruff format` 也会格式化 Markdown 里的 python 代码块

**症状**：给仓库新增两份文档（12 / 13）后，`ruff format --check .` 从「0 个文件需要格式化」变成「10 个」，其中两份是 `.md`。  
**根因**：文档里的 Python 代码围栏是**真代码**，`ruff format` 会格式化它。  
**修法**：文档代码块必须能通过 `ruff format`；不用空格对齐做视觉分组，改用注释或拆成两段。**防线**：`ruff format --check .` 纳入质量门禁。

## 8. M5（Memory）新增问题

M5 的问题集中在「**动作没有发生，但没人报错**」：记忆抽取、摘要、注入都是「跑一下更好、不跑也不报错」的旁路逻辑，漏接一条线、命中一次防抖、幂等键撞车，全都表现为静默失效。8.16 / 8.17 是另一类：内部命名与结构外溢到对外契约，收尾按 SRS 逐字对账才发现。

### 8.1 收尾动作只接在流式路径上

**症状**：`POST /chat/stream` 后 `GET /memories` 会新增一条；换成默认的 `POST /chat` 则永远为空，任务列表里也没有 `memory_extract`。  
**根因**：`ChatService.complete()` 里只写了 `_persist`，`_after_turn`（投递记忆抽取与摘要）只挂在 `stream_prepared()` 上；两条路径各自都能跑通，非流式不写记忆没有任何异常、日志、状态码能体现。  
**修法**：`complete()` 在 `_persist` 之后同样调用 `_after_turn`，并加注释「收尾动作必须在两条路径上都执行」。**防线**：`test_turn_triggers_memory_extraction` 走的是**非流式** `/chat`（默认路径），漏接即红。旁路动作有 N 个入口时，要么收敛成一个入口，要么每个入口一条断言。  
### 8.2 幂等键的粒度错了：把「每轮」变成「每会话」

**症状**：一个会话连聊 15 轮，`GET /tasks?type=summary_build` 只有 1 条，`memory_extract` 同理；第 2 轮之后记忆不再更新，摘要永远只覆盖最初几条消息。  
**根因**：`TaskService.create` 的默认幂等键是 `make_idem_key(type_, user_id, resource_id)`，而摘要/抽取的 `resource_id` 是**会话 id**；同会话每轮生成同一个键，第二轮返回第一轮那条**已终态**任务，`InlineTaskRunner.submit` 当重复投递跳过。`create` 返回 `created=False` 时接口仍 200，只有一行 INFO `task.submit_skipped`，与「记忆怎么没更新」是两条排障路径。  
**修法**：`ChatService._submit` 传 `idem_key=make_idem_key(type_, user_id, resource_id, turn_marker)`，`turn_marker` 取本轮最后一条消息的 `message_id`——同一轮重复投递幂等，不同轮各自成任务。**防线**：`AC-MEM-03` 造 30 条历史并断言**出现** `summary_build`；`AC-MEM-08` 断言同一句话抽两次 `hit_count=2`。用资源 id 当幂等键前先问：这个资源上会有多次不同意图吗？  
### 8.3 防抖命中被记成任务失败

**症状**：任务列表出现 `summary_build` 的 `FAILED`，错误是「摘要生成器未装配」，但摘要器明明装好了；每多聊一轮就多一条假故障。  
**根因**：`SummaryBuilder.build()` 用 `None` 表示「条件不满足或命中防抖，跳过」，而 `MemoryTaskHandlers._build_summary` 把 `None` 当成「服务没装配」并抛 `INTERNAL_ERROR`；5 分钟防抖窗口内的第二次任务必然命中。  
**修法**：先判 `service.summary_builder is None`（真正的装配错误），再把 `None` 记为 `memory.summary_skipped` 并正常结束。**防线**：`test_long_conversation_triggers_summary_task` 连投 15 轮，必然有命中防抖的。`None` 是多义的：既可能「跳过」又可能「没能力做」时，必须返回两种可区分结果，或由调用方先判能力。  
### 8.4 `messages[:-0]` 不是「全部」，而是空

**症状**：把 `SUMMARY_KEEP_RECENT_TURNS` 设成 0（意图「全部交给摘要、不留原文」）后摘要永不生成，日志只说「条件不满足」，与「消息太少」无法区分。  
**根因**：`pending = messages[:-keep] if keep and len(messages) > keep else []`——`keep == 0` 时条件为假走 `else`，`pending` 是空列表，直接 `return None`。  
**修法**：`pending = list(messages)`，仅当 `keep and len(messages) > keep` 时取 `messages[:-keep]`；给配置补「≥ 0」的启动期校验，负数不再被 `max(0, ...)` 静默吞掉——「静默吞配置」比「拒绝启动」难查。**防线**：`test_build_summarises_everything_when_keep_is_zero` + `test_negative_summary_keep_recent_turns_is_rejected`。切片边界上 `0` 与 `-0` 同值，「0 表示全部」不能交给 `x[:-n]`。  
### 8.5 处理器只能注册一次 ⇒ 重建记忆层必须「改绑」

**症状**：测试里第二次 `build_memory_services(...)` 抛 `AppError: 任务类型 summary_build 的处理器已注册`；把注册去掉，任务又继续走**旧**服务（用真模型而不是替身 LLM）。  
**根因**：`create_app` 已注册 `SUMMARY_BUILD` / `MEMORY_EXTRACT` 处理器，而「用替身 LLM 重建记忆层」的常规做法是再建一套服务，撞上「重复注册是装配错误」这条守卫。  
**修法**：`build_memory_services(..., register_handlers=False)` 只建服务不注册，调用方用 `app.state.memory_handlers.bind(新服务)` 改绑**已注册的那个**处理器——注入点是 `app.state`，不是构造期焊死的引用。**防线**：`tests/conftest.py::make_memory_client` 走这条路径，M5 的 20 条契约用例全经过它。守卫与测试注入冲突时，不拆守卫，给被守卫对象一个受控改绑入口。  
### 8.6 空的模型输出被「结构补齐」掩盖

**症状**：模型偶尔返回空串时摘要没失败，而是变成一份**格式完美**的四段 `- 无`，并覆盖掉上一版好用的摘要。  
**根因**：`ensure_structure()` 的职责是「缺段补 `- 无`」，空输入也产出合法四段；于是「模型什么都没说」与「模型说这段没有内容」在校验后**完全同形**。  
**修法**：`_generate` 在 `ensure_structure` **之前**判 `response.content.strip()`，为空即抛；顺序不能反。**防线**：`test_build_rejects_empty_model_output`；`ensure_structure` 单测另有 `count == 0` 用例，说明补结构本身的行为就该如此。任何容错补全都会把无效输入变成看似有效的输出。  
### 8.7 同一语义两处实现：正文归一化

**症状**：`content_sha256` 与 `memory_fingerprint` 各实现一遍「归一化后取哈希」，一处保留连续空格、另一处压掉，同一句话走不同路径结论不同。  
**根因**：两个函数都「看起来对」，谁也没被单独测出问题；错的是它们不相等，而没有用例同时在两条路径上跑同一句话。  
**修法**：抽唯一实现 `app.memory.long_term.normalise_content`（`" ".join(split())`），`content_sha256` 只做包装，`memory_fingerprint` 删除。**防线**：`test_hash_hit_returns_created_false_and_bumps_hit_count` 用「首尾空格不同」的同一句话断言 `created=False`；`test_merge_recomputes_content_hash` 断言哈希索引指向新正文。测试坑：归一化**不会**压掉中间连续空格（`"a  b"` → `"a b"`），「同一句话」必须用首尾空白构造。  
### 8.8 疑问句的判定条件写得太严

**症状**：抽取器把「用户是不是想了解 X」写进长期记忆，而 `docs/07` §5.1 要求疑问句 MUST NOT 抽取。  
**根因**：`_QUESTION_PATTERNS` 里多字疑问词（`是不是` / `能不能` / `有没有` …）要求后面必须跟 `？`，而模型改写会把疑问句改成第三人称陈述并去掉标点，候选全部绕过过滤。  
**修法**：多字疑问词不要求标点即可命中，保留 `(吗|呢)\s*[?？]?\s*$` 兜住「……吗」的改写。**防线**：`tests/unit/test_memory_extractor.py` 32 条用例，疑问句按「带标点 / 不带标点 / 句尾语气词」三类覆盖。过滤规则按**下游可能产生的形态**写，不按用户原文写。  
### 8.9 过滤顺序：敏感凭证必须最先判

**症状**：候选 `{"content": "我的密码是 xxx", "confidence": 0.2}` 被判 `low_confidence` 而不是 `sensitive`——结论对、原因错，排障时会去调阈值而不是查泄露。  
**根因**：`rejection_reason` 没有固定顺序，一个候选同时命中多条规则时「先判哪条」随手写。  
**修法**：顺序固定为**敏感凭证 → 太短/太长 → 疑问句 → 推测 → 一次性 → 置信度**；安全类是唯一**硬约束**（其余是质量偏好），必须最先。**防线**：`tests/unit/test_memory_extractor.py::test_sensitive_candidate_rejected_first` 等多条用例显式断言原因字符串。  
### 8.10 零向量查询与维度不符的静默成功

**症状**：零向量查询返回一串 `score=0.0` 命中，调用方以为「检索成功只是分数低」，上下文多了几条无关记忆；另：内存索引照收 8 维向量而配置是 1024 维，本地全绿，上 Milvus 才写不进去。  
**根因**：用「返回一批低分结果」代替「没有结果」；内存实现不校验维度，与 Milvus 行为不一致。  
**修法**：`search` 遇零向量（`|q| == 0`）直接返回 `[]`；`upsert` 校验维度并抛 `ValueError`。**防线**：`test_search_empty_query_returns_nothing` + `test_memory_vector_index.py` 维度用例；契约脚本向量 `DIM = 1024` 显式对齐 `embedding_dim`，写错当场炸。「返回空」可观测，「低分结果」会伪装成成功。  
### 8.11 锁的释放必须是 compare-and-delete

**症状**：并发写同一会话时偶尔交错，两个请求都写进上下文（`RPUSH` 顺序错乱）。  
**根因**：锁按「`GET` 看是不是自己的 token，是就 `DEL`」释放；锁可能在这两步之间超时并被别人重新持有，此时 `DEL` 删的是别人的锁——两个写者同时进入临界区。  
**修法**：释放走 Lua 脚本，在 Redis 侧原子完成「值等于自己的 token 才删」。**防线**：`test_lock_release_uses_compare_and_delete`（断言发的是 Lua 且带 token）+ `test_lock_release_does_not_delete_foreign_token`。「检查 + 动作」跨两步必然被并发打断，要么找一次原子完成的原语（Lua / `SET NX` / `WATCH`）。  
### 8.12 `real` 后端不许静默退化成内存

**症状**：若 `INFRA_BACKEND=real` 但 Redis 驱动缺失时退回内存实现，单进程一切正常，多副本后「同一个会话换一个实例就丢上下文」。  
**根因**：降级退化了**架构**（单实例内存状态），而不只是功能。  
**修法**：`build_conversation_store` 在 `real` 下构造失败返回 `UnavailableConversationStore`，调用点抛 `503 DEPENDENCY_UNAVAILABLE`；`ChatService` 把读取失败降级为 `memory_unavailable`（只丢上下文，对话照常）。**防线**：`tests/unit/test_memory_redis_store.py` 覆盖 `RedisUnavailable` 的 `code` 与 `hint`（`uv add redis`）。`docs/10` 把「依赖连不上」定义为运行期故障，构造期抛异常会让对话/鉴权/健康检查一起不可用。  
### 8.13 命名撞上内建泛型：方法叫 `list` 的代价

**症状**：`mypy app` 报 `valid-type: "list" is not valid as a type`，指向类里另一处 `-> list[MemoryRecord]` 注解。  
**根因**：`MemoryRepo` 与 `InMemoryMemoryRepo` 定义了 `list(...)` 方法，在**类体作用域**内遮蔽内建 `list`，同类所有 `list[X]` 注解都解析到那个方法。  
**修法**：方法改名 `list_page`。**防线**：`mypy app`（0 error 门禁）。不要用内建名当方法名/属性名（`list` / `dict` / `id` / `type` / `input`），代价是注解系统悄悄换含义。  
### 8.14 合并时把旧哈希一起带上

**症状**：语义去重命中、把新正文合并进旧记录后，再用**原来的正文**写一次会被判重复而静默丢弃——唯一索引指向合并**之前**的哈希。  
**根因**：`dataclasses.replace(record, content=..., ...)` 会把未显式覆盖的字段（含 `content_sha256`）一起拷过去，而 `__post_init__` 只在字段为空时推导哈希。  
**修法**：合并时显式重算 `content_sha256=content_sha256(new_content)`。**防线**：`test_merge_recomputes_content_hash` 断言「新正文能按哈希查到、旧正文查不到」。派生字段（哈希、长度、归一化结果、冗余索引键）必须在源字段变化的所有路径上重算。  
### 8.15 测试侧：五条记忆全指向同一个方向

**症状**：`AC-MEM-08` 想验「`top_n` 最多注入 3 条」，写 5 条记忆后断言只拿到 1 条，看起来像实现漏了。  
**根因**：脚本化向量化替身对**未登记的文本**统一返回同一向量，5 条两两相似度 1.0，被语义去重（阈值 0.92）正确合并成 1 条——实现对，断言错。  
**修法**：替身改为「未登记的文本按首次出现顺序分配到互相正交的轴」，需要相似度时显式 `blend(axis, 0.95)`。**防线**：替身的**默认行为**会被当成「数据的样子」，默认值不该制造现实中不存在的巧合（这里是「所有文本都同义」）。  
### 8.16 工具参数名与 SRS 不一致：`top_n` vs `top_k`

**症状**：`docs/04` §3 写的是 `memory_search(top_k:int=3)`，实现字段叫 `top_n`；把工具定义序列化给上游后，模型看到的参数名与 SRS 不符。  
**根因**：`app/application/memory.py` 的 `search(..., top_n=...)` 用的是**配置项**名（`MEMORY_TOP_N`），照服务层写工具参数就顺手带上；而工具层同一张表里 `kb_retrieve` 是 `top_k` / `rerank_top_n`。  
**修法**：工具参数改为 `top_k`（内部照旧传 `top_n=`），字段上注释「与工具层惯用名一致」。**防线**：**服务层的内部命名不是对外契约**；工具参数/接口字段一律回 SRS 抄，不从相邻方法签名顺着写。  
### 8.17 工具返回少了 SRS 要求的字段

**症状**：`docs/04` §3 要求 `memory_search` 返回 `{memories:[{mem_id,content,kind,score}]}`，实现只回 `content` 与 `score`，模型拿不到 `mem_id`，无法在后续 `PATCH /memories/{id}` 或工具调用里指代某一条。  
**根因**：`MemoryItem`（上下文装配用的检索结果）当初只定义 `content` / `score`，工具需要的另外两项「没地方放」就顺手省略了。  
**修法**：`MemoryItem` 补 `mem_id` / `kind`（装配侧忽略），断言钉住键集合 `set(hit) == {"mem_id","content","kind","score"}`。**防线**：用集合相等而不是逐个取值，少一个字段就会红。内部结构体只装「当时用得上」的字段，是一种会外溢的省略。

## 9. 小结：M1–M5 的八条可复用原则

1. **谁定义语义，谁负责填字段**（3.6 的 `vector_score`）：让下游「记得填」就是留坑。
2. **共享一个实现，而不是共享一个约定**（2.1 的游标原语、8.7 的归一化）：两处各自实现同一语义，迟早分叉。
3. **静默返回是 bug 的温床**（3.8 的 `if status is not PENDING: return`、8.2 的幂等键撞车、8.4 的 `messages[:-0]`）：条件不满足时必须留下可观测痕迹。
4. **测试环境的配置要贴近生产**（4.1 的日志级别）：测试里关掉的开关，等于那部分代码从未被执行。
5. **能在同步阶段给出的错误不要拖进异步**（5.2）；工具参数校验同理，作为可回复的工具结果返回给模型，而不是 500（[04](./04-Agent与工具调用.md) §5）。
6. **护栏必须有一条专门证明「它拦住了」的测试**（7.1–7.3）：把护栏拿掉，这条测试会不会变红？**对数据库约束同样成立**——`uk_kb_user_name` 曾建在含 `deleted_at` 的列上，唯一索引不比较 `NULL`，该约束一次也不会触发（见 10.1）。
7. **旁路动作要按「入口 × 路径」清点**（8.1 只接流式、8.3 防抖记成失败）：不影响响应结果的逻辑，必须在每一个入口上有一条断言，否则就是「部分流量上生效」。
8. **对外契约一律回 SRS 抄**（8.16 的 `top_n` vs `top_k`、8.17 的缺字段）：内部命名服从实现便利，对外命名服从文档；混用会在「文档能用」与「代码能用」之间裂开一道缝。

## 10. MySQL 建表脚本落地（M6 前置）

M5 当时，长期记忆仓储仍是进程内实现（`real` 下返回 503 占位），要补 MySQL 仓储就得先把表建出来（M8 已补 MySQL 仓储，现仅在初始化失败时降级为 503 占位）。`docs/09-§2` 的 DDL 已固化为 `deploy/mysql/001_init_schema.sql`，落地时发现四类问题——都不会在「照着文档写代码」时暴露。

### 10.1 唯一索引不比较 `NULL`：约束从未生效过

**症状**：自检脚本里「插入第二条同名知识库应当失败」返回 `ROW_COUNT() = 1`，即**插入成功了**。  
**根因**：`uk_kb_user_name (user_id, name, deleted_at)`——MySQL 唯一索引把 `NULL` 视为互不相等，未删除行的 `deleted_at` 全是 `NULL`，`(u_x, 手册库, NULL)` 可以存在任意多份；这条约束**一次也不会触发**。镜像坑：`document.uk_doc_dedupe (kb_id, content_sha256)` 不含 `deleted_at`，于是软删后同一文件永远传不回来（列表里看不见已删记录，只收到「文件已存在」）。  
**修法**：加生成列把 NULL 映射成哨兵时刻：`deleted_key DATETIME(3) GENERATED ALWAYS AS (IFNULL(deleted_at, '1970-01-01 00:00:00.000')) STORED`，唯一键改为 `(user_id, name, deleted_key)`。**防线**：`deploy/mysql/verify_schema.sql` 用 `INSERT IGNORE` + `ROW_COUNT()` 断言「未删冲突 / 软删后重建」，期望值 `1/0/1`（知识库）与 `1/0/1`（文档）。用 `INSERT IGNORE` 而不是「期望报错」，让**预期的冲突**与**真正的失败**不同形：脚本任何一行出现 `ERROR` 就说明真出事了。  
### 10.2 SRS 的表格漏了实现必需的列

**症状**：`docs/09-§2.8` 的 `user_settings` 只列 `user_id` / `memory_enabled` / `memory_top_n` / `updated_at`，而 `REQ-MEM-007` 的「清空后 24h 不再抽取」需要持久化 `MemoryPreference.cleared_at`；缺列时 `real` 后端下冷静期只能存在进程内存里，重启即失效（用户删了记忆，重启后旧偏好又被抽回来）。  
**根因**：SRS 表格只写「关键列」，漏的正是「只在某个分支里用到」的列。  
**修法**：建表脚本加 `cleared_at`，并同步回 `docs/09`——文档是契约，表格漏列要改文档，而不是让实现偷偷多一列。**防线**：建表阶段必做「SRS 表格 ↻ 代码实体逐字段对账」。  
### 10.3 把 SQL 交给 mysql 时的两个环境坑

**症状**：`Get-Content x.sql | mysql` 会经过 PowerShell 的编码转换，且**路径里的中文**会被 mysql 客户端按 ANSI 解释——实测 `作品集` 被解成 `浣滃搧闆哱`，报 `Failed to open file ... error: 2`。  
**根因**：文件内容与路径都经过了 shell 的字符串/管道层。  
**修法**：把脚本复制到 ASCII 路径（如 `$env:TEMP`），用客户端自带的 `-e "source <路径>"`——文件由 mysql 自己读，完全不经过 shell；复制后用 `Get-FileHash` 两边对一下，防止「临时目录改了、忘了同步回仓库」的假绿。**防线**：凡把文件交给**外部可执行程序**（mysql / psql / 解释器）读取，一律绕开 shell 的字符串与管道层。  
### 10.4 两个服务同库：同名的表只能有一份定义

**症状**：`idempotency_record` / `audit_log` 两边都在用，原本是**同名不同列**的两张表（网关多 `method` / `request_hash` / `ip` / `user_agent`），早期结论是「必须分库」；改成共库后，第二份 `CREATE TABLE IF NOT EXISTS` 会**静默跳过**——两个脚本都报成功，实际用的是先建好的那张。  
**根因**：把「表名相同」当成「表相同」；只要列集合不同，它们就是两张需要收敛的表，与在不在同一 schema 无关。幂等 DDL 只保证「不报错」，不保证「结构正确」。  
**修法**：共享表只定义一处（AI 侧 `001_init_schema.sql`，也是库的 owner），取**并集**；网关独有的四列给 `DEFAULT ''` / `NULL`，让本服务不填也能插入；网关侧脚本只留一段注释声明依赖，不再 `CREATE`。已建过旧库的补 `002_align_shared_tables.sql`——`IF NOT EXISTS` 对**已存在**的表是空操作，不会补列。同理 ID 前缀：`u_` / `rt_` 与 `app/core/ids.py::ID_PREFIXES`（`docs/02` §1）同处定义，包括本服务不生成的前缀。**防线**：两份自检脚本断言 `shared_extra_columns_must_be_4`（四列在位）、`uk_idem_columns_must_be_4`（唯一键含 `method`）、`gateway_tables_total_must_be_6` / `total_tables_must_be_15`。「应该已存在」的对象都要单独断言结构，否则新旧库会长成两个样子而两边都不报错。

## 11. M6（MCP 与可观测性）新增问题

M6 的两块（接外部 MCP Server / 埋指标与链路）共同点：**错误的表现不是异常，而是「数字不对」或「链路断了一截」**。规模：19 个 `ai_*` 指标，指标独立端口 `9100`，主应用不暴露 `/metrics`。

### 11.1 `try: return ... / else:` 里的 `else` 永远不执行 → 熔断器只记得住失败

**症状**：单测「半开探测成功后熔断器复位」失败，`failure_count` 停在 2 而非 0；生产上某条链路一旦熔断打开就**永远回不到 `closed`**，该 Server 永久不可用。  
**根因**：`try: return await ... / else: record_success()`——`else` 的触发条件是 `try` 块**自然落到末尾**，而 `return` 立即开始栈展开，两者互斥；只要 `try` 里有 `return`，同一个 `try` 的 `else` 就是死代码。  
**修法**：`record_success()` 移出 `else`，平铺在 `return result` 之前。**防线**：`tests/unit/test_mcp_manager.py::test_half_open_success_recovers_the_server`（假时钟推进 31s → 半开 → 成功 → 断言回到 `closed` 且 `failure_count == 0`）。光有「失败会打开」的测试抓不到它，必须有反向断言；AST 扫过 `app/` 与 `tests/`（`ast.Try` 有 `orelse` 且 body 含 `return`），只有这一处。  
### 11.2 `endpoint` 标签退化成 `/live`：FastAPI 0.141 起 `include_router` 不再扁平化路由

**症状**：契约测试断言 `ai_requests_total{endpoint="GET /api/v1/health/live"}` 取不到值，渲染出来真实标签是 **`GET /live`**。  
**根因**：原实现取 `scope["route"].path`；FastAPI 0.141.1 的路由表放 `_IncludedRouter` 节点，匹配后写回 scope 的是**最内层**路由，`/api/v1` 与 `/health` 两层前缀全丢。危害不只是少两个字符：不同模块下同名 `/live` 撞进同一标签，看板 QPS/延迟变成两条接口的混合值。  
**修法**：逐级降级：`scope["fastapi"]["effective_route_context"].path`（占位符未被实例值替换，正是模板）→ `scope["route"].path` → `unmatched`（404）；两个 scope 键都不是公开 API，取值全走 `getattr` / 类型检查，坏数据只降级不 500。**防线**：`tests/unit/test_route_template.py`（六分支，含 `fastapi` 键被写成字符串、上下文无 `path`）；契约 `test_path_parameters_are_not_used_as_labels` 断言 `endpoint="GET /api/v1/knowledge-bases/{kb_id}"` 且渲染文本**不出现**真实 `kb_id`。  
### 11.3 同一个调用被记两次 → `ai_tool_calls_total` 翻倍

**症状**：`ai_tool_calls_total{source="mcp"}` 按 2 递增，看板工具调用量整体偏大一倍——没有异常、没有日志，只有数字不对。  
**根因**：适配器 `app/mcp/tools.py` 与统一执行器 `app/tools/executor.py` 各记一遍——适配器知道 `mcp_server`，执行器知道 `status`，两处都「看起来该由自己记」。  
**修法**：定死只有一个来源：执行器记 `ai_tool_calls_total`，适配器只返回结果（`status` / `payload.error`），原处留注释说明原因。**防线**：`test_mcp_tool.py::test_synced_tools_work_through_the_tool_executor` 在真实执行器链路上断言该序列**恰好为 1.0** 且不存在 `2.0`——「记了指标」与「只记一次」是两条不同的断言。分叉处只允许补统一入口拿不到的字段（这里用 `source="mcp"` 表达）。  
### 11.4 OTel 的 `TracerProvider` 是进程单例：第二次 `set_tracer_provider` 被静默忽略

**症状**：测试里造第二个应用（或第二次调 `setup_tracing`）后 span 全丢，控制台只有 `Overriding of current TracerProvider is not allowed`。  
**根因**：OTel 的 `set_tracer_provider` **只能生效一次**，之后只打日志并**丢弃**后来者的 span；而一个进程里有多个 `FastAPI` 实例是测试常态。  
**修法**：`app/infrastructure/observability/tracing.py` 的 `_resolve_provider()` 复用已存在的 SDK provider；`_EXPORTER_MARKER` 防止同一 provider 挂第二个 OTLP exporter（否则 span 导出两遍）；`_provider_owned` 只在自己建的 provider 上 `shutdown`。**防线**：对接**全局单例**的第三方 SDK（OTel provider、root logger、`prometheus_client` 默认注册表）先问「一个进程会不会有第二个实例」；`Metrics` 每实例自带 `CollectorRegistry()`，否则同名指标二次注册抛 `Duplicated timeseries`。  
### 11.5 `METRICS_PORT=0` 被当成「关闭指标端口」

**症状**：契约测试里 `app.state.metrics_server_ready` 根本不存在（`AttributeError`），端口服务压根没启动。  
**根因**：`if settings.metrics_enabled and settings.metrics_port > 0:`——`MetricsServer.start()` 支持「端口 0 = 由 OS 分配」（它的单测就在用），调用方用 `> 0` 把 0 过滤掉了，而 `.env.example` 写的正是「`METRICS_PORT=0` 表示随机分配」。  
**修法**：开关只有 `METRICS_ENABLED` 一个，端口 0 照常启动；启动成功打 `app.metrics_ready` 并带**实际**端口（配 0 时只能从这里知道去哪抓）。**防线**：`test_observability.py::test_standalone_port_serves_prometheus_text` 真的去 `http://127.0.0.1:{server.port}/metrics` 抓一次并断言 200——「对象存在」与「端口在监听」是两件事。配置语义里「0」几乎总是「自动/随机」，不是「关闭」；开关与数值项别混用。  
### 11.6 `mcp` 2.2.0 的两个 API 变化：返回值个数与「没有 headers 参数」

**症状**：① `streamable_http_client(url, headers=..., timeout=...)` 直接 `TypeError: unexpected keyword argument`；② `read, write = streamable_http_client(url)` 报 `too many values to unpack`。  
**根因**：2.2.0 的签名是 `streamable_http_client(url, *, http_client=None, terminate_on_close=True)`——**没有** `headers` / `timeout`，且 `asynccontextmanager` **yield 两个值**；鉴权头与超时只能通过自建 `httpx2.AsyncClient(headers=..., timeout=...)` 传入。stdio 侧 `StdioServerParameters(command, args, env)` + `ClientSession(read, write_stream)` 未变。  
**修法**：`app/mcp/session.py` 的 `_http_session()` 自建 client；`open_session()` 统一两种 transport，对上层只暴露 `list_tools()` / `call_tool()` 两个方法，业务代码不认识 SDK 类型。**防线**：接入前先 `inspect.signature(...)` 打印真实签名（比翻文档快且不会过期），不确定的部分收在一个适配层里，换版本只改一个文件。  
### 11.7 slots dataclass 没有 `__dict__`：`asdict()` 与只读属性

**症状**：① `McpServerStatus`（`@dataclass(slots=True)`）直接丢进响应体，序列化报缺 `__dict__`；② `monkeypatch.setattr(tool, "invoke", ...)` 报 `'McpTool' object attribute 'invoke' is read-only`。  
**根因**：`slots=True` 的实例只有槽位、没有 `__dict__`，pydantic/FastAPI 默认序列化与 `vars()` 都用不了；槽位描述符**不允许**覆盖实例属性，`monkeypatch` 也改不动。  
**修法**：① 显式 `dataclasses.asdict(...)`；② 测试改它**唯一的外部依赖** `monkeypatch.setattr(client, "call_tool", ...)`，把「适配器只通过 `client.call_tool` 与外界交互」固化成测试。**防线**：测试改不动的东西往往是设计边界；被 `setattr` 挡住时先问「为什么它不可变」——通常意味着应该改它的依赖。  
### 11.8 替身不能模拟「连接正常但调用失败」→ 断言错了对象

**症状**：想验「调用失败触发重连」，测试拿到的是 `MCP_SERVER_UNAVAILABLE`（连接不可用），与预期错误不一致。  
**根因**：替身只有 `fail_connect=True` 一个开关，调用前的重连检查先失败，流程停在「连接不可用」，**根本没走到** `call_tool` 失败那条分支。  
**修法**：补 `fail_calls` 开关，在 `_FakeSession.call_tool` 抛 `RuntimeError("stream closed")`，连接阶段保持正常。**防线**：故障替身按「故障发生的**阶段**」而不是「好坏」划分开关（建连 / 握手 / 列表 / 调用 / 收尾）。只有一个 `fail=True` 的替身，测试会退化成「反正会失败」。  
### 11.9 空元组 ≠ 无退避：`RECONNECT_DELAYS = ()` 让重连永不成功

**症状**：加了「测试里不 sleep」的 fixture（`monkeypatch.setattr(client_module, "RECONNECT_DELAYS", ())`）后，一批本应重连成功的用例开始失败。  
**根因**：`_reconnect()` 的语义是「按延迟表逐个尝试，**任一次成功即成功**」；空元组 = 一次都不试 = 永远返回 `False`。测试为了「快」清空列表，顺手把被测能力删掉了。  
**修法**：改成 `(0.0,)`，**保留一次零延迟尝试**——「不等待」与「不重试」是两件事。**防线**：缩短时间类测试（假时钟、零延迟）必须**保持调用次数不变**；凡「为了测试改常量」，先查该常量是否同时参与控制流。  
### 11.10 测试里两个应用抢同一个指标端口

**症状**：偶尔出现 `metrics.server_failed`（bind 失败）警告，且成组出现。  
**根因**：测试基线 `metrics_port` 用默认值 9100，同一进程先后建的应用都想绑它（上一个还没 `stop()`）；该失败不阻断启动（正确设计），只以一条警告出现，容易被忽略成噪声。  
**修法**：测试基线改 `metrics_port: 0`（配合 11.5，现在真的走随机端口），既避开冲突，又仍然走真实的 bind + listen 代码路径。**防线**：「不影响功能的后台能力」在测试里最容易变成噪声源；定点修法是让它**可控**（随机端口 / 可注入时钟），而不是把断言放宽。  
### 11.11 OTel 测试的 fixture 顺序：`ProxyTracerProvider` 没有 `add_span_processor`

**症状**：`InMemorySpanExporter` 装不上，报 `'ProxyTracerProvider' object has no attribute 'add_span_processor'`，四个用例集体 error。  
**根因**：没有任何 `TracerProvider` 被设置过时，`trace.get_tracer_provider()` 返回空代理 `ProxyTracerProvider`；fixture 直接 `add_span_processor` 打到了代理上，必须先有一次 `setup_tracing()` 装真正的 SDK provider。  
**修法**：拆链式 fixture：`session_tracing`（调 `setup_tracing`）→ `exporter`（依赖前者再挂 `SimpleSpanProcessor`）→ `enabled_tracing`；依赖图即顺序，不靠「pytest 恰好先跑哪个」。**防线**：用 fixture 依赖表达前置条件，别用注释表达——「必须先初始化 A 才能做 B」时让 B 声明依赖 A，缺失时 pytest 直接报错而不是给出奇怪的运行时异常。  
### 11.12 「严格模型」其实不严格：`StrictModel` 用的是 `extra="ignore"`

**症状**：契约断言「`POST /mcp/servers/fs/reload` 多传一个字段应返回 422」，实测返回 200。  
**根因**：项目里的 `StrictModel`（`app/schemas/common.py`）刻意配置 `extra="ignore"`——客户端多传字段（如旧版本遗留的 camelCase）不该让调用整体失败；**真正需要「写错就报错」的是 MCP 配置**，那一层用 `extra="forbid"`（`REQ-MCP-001`）。两者不是一套规则，测试把「严格」想当然了。  
**修法**：改测试而非实现（`docs/02` 只要求未知字段被忽略，`docs/05-§2.2` 才要求 MCP 配置拒绝未知字段），并把「为什么忽略」写进测试 docstring。**防线**：测试假设与 SRS 冲突时先改测试，但必须先回文档确认**哪一边是对的**，不能因为「改测试更快」就改。  
### 11.13 目标 `up`、样本 678 条，却没有一个 `ai_*` 指标

**症状**：本地按 README 起完整套件后，Prometheus 的 `ai-platform` job 显示 `up`、`scrape_samples_scraped` 有 678 条，但 `{__name__=~"ai_.*"}` 一条都没有，Grafana 看板全空。  
**根因**：本机 `9100` 端口上常驻着**另一个 Go exporter**：应用 `MetricsServer.start()` 绑定失败只记 `metrics.server_failed` 警告（正确设计，指标不该阻断启动）；Prometheus 照旧抓 `host.docker.internal:9100`，端口**有东西在应答** ⇒ HTTP 200、target `up`、678 条全是别人的 `go_*` / `node_*`。`up` 只说明「抓取成功」，不说明「抓到了我们的指标」。  
**修法**：`METRICS_PORT` 与 `prometheus.yml` 的 `targets` 必须是同一个端口；判断「抓到的到底是不是我们」只看**哨兵指标 `ai_build_info`**（常量 1，专为确认指标端点活着且是我们而存在）。**防线**：启动日志里 `app.metrics_ready port=<实际端口>` 与 `metrics.server_failed port=...` 成对出现，一眼能看出「没起来」；契约测试直接对独立端口抓一次并要求 200 + `ai_build`。探针成功 ≠ 探到的是对的东西，跨进程/跨网络确认「对面是谁」必须断言**只有本服务能提供的标识**。  
### 11.14 小结

M6 这 13 条里真正的「业务 bug」只有 11.1（熔断器回不到 closed）与 11.3（指标翻倍），其余都是**断言写得太弱**或**框架知识过期**：反向断言比正向值钱（11.1）；框架内部知识（路由模板、全局单例、SDK 签名）必须显式测（11.2 / 11.4 / 11.6）；配置项的类型语义要写进文档（11.5）；为测试改的常量不能顺带改控制流（11.9）；fixture 依赖图即前置条件（11.11），替身按阶段划分故障开关（11.8）；测试假设与实现冲突时回 SRS 判方向（11.12）；「连接/探针成功」≠「对面是对的东西」，要拿只有本服务能提供的唯一标识去断言（11.13）。

## 12. M7（Kafka 与 Worker）新增问题

M7 的代码（`app/worker/`、`app/tasks/{transport,redis_store,events,retry,compensation,stream}.py`、`GET /tasks/{id}/events`）配了约 190 条新单测，**其中 9 条一跑就红**，另有 1 条是 review 出来的。共同特征：**在内存替身上全都「看起来对」**——内存实现是照「理解的语义」写的 Python 代码，真实现（Redis / Kafka / SSE）照「协议的真实语义」执行。规则：**跨进程/跨连接/跨时间的语义，必须用真实现或可注入时钟的测试钉住；内存替身跑绿只能证明替身自洽。**

### 12.1 用 `-1` 当「未见过」的哨兵，同时它又是合法值 → 静默丢消息

**症状**：`OffsetTracker` 按分区提交连续水位线，乱序完成时「先完成 1 号、再完成 0 号」让水位线**跳过 0**，0 号消息永远不被提交；进程重启后它会被重新消费一遍（至少一次语义下不算数据错，代价是重跑入库），若再叠一层「跳过即视为已处理」就变成真正的丢消息。  
**根因**：`watermark: int = -1` 既表示「还没见过任何消息」，又表示「0 号消息之前」；`if state.watermark == position.offset - 1` 在 `offset=0` 时恰好等于 `-1`，误判为连续。  
**修法**：`watermark: int | None = None`，`None` 表示「未见」，与合法水位线彻底分开。**防线**：**不要把「无效值」放在业务取值域里**；每次用魔法值当哨兵，先问「这个值业务上会出现吗」。  
### 12.2 异步生成器的「创建」不等于「订阅已就位」

**症状**：`stream_task_events` 的第 1 条设计约定是「先订阅、后读快照」，否则两次操作之间发布的事件会永久丢失（`docs/08` §4.5 的进度流会卡在某个阶段不动）。  
**根因**：异步生成器函数的函数体要到**第一次 `__anext__`** 才执行，`bus.subscribe(task_id)` 此刻**什么都没订阅**（Redis 的 `SUBSCRIBE` 命令也还没发出去）；Redis 的 `SUBSCRIBE` 本身还要一次往返，这个几十微秒到几毫秒的窗口，恰好是「任务很快就成功了」的时刻。  
**修法**：预热一次让订阅与快照读取重叠：`primed = asyncio.ensure_future(anext(subscription))` → `await asyncio.sleep(0)`（让生成器体真正跑起来，`SUBSCRIBE` 已发出）→ 再 `tasks.get(task_id, user_id)` → 后续 `_next_event(..., pending=primed)`。**防线**：`test_subscription_is_live_before_snapshot_is_read` 用「读快照时发布一帧」的门闩证明订阅在快照之前生效。异步生成器/协程是惰性对象，「我调用了订阅函数」与「订阅已生效」是两件事。  
### 12.3 对「正在运行」的异步生成器 `aclose()` → `RuntimeError`

**症状**：12.2 的预热引入新问题：客户端断连、任务已终态提前返回时，`primed` 的 `__anext__` 可能还挂着，直接关它抛 `RuntimeError: aclose(): asynchronous generator is already running`。  
**根因**：生成器处于「运行中」不能关闭；`cancel()` 只是投递取消，不是同步等待。  
**修法**：`finally` 里先 `primed.cancel()`，`with contextlib.suppress(asyncio.CancelledError, StopAsyncIteration): await primed`，**等它真的结束**，再 `await subscription.aclose()`。**防线**：与 M2 阶段 `asyncio.wait_for(agen.__anext__())` 的坑是同一面——取消后必须 `await`，否则取消还没进到生成器体内。  
### 12.4 `asyncio.wait` 被取消时没有转发给业务协程 → 孤儿任务

**症状**：Worker 超时写成 `done, _ = await asyncio.wait({job}, timeout=self._timeout)`；一旦 Worker 自己被取消（收到 SIGTERM），`wait` 抛 `CancelledError` 而 `job` 还在跑——关停后 Embedding 请求还在发，任务状态永远停在 `RUNNING`，`_handle_failure` 没机会执行。  
**根因**：`asyncio.wait` / `asyncio.shield` **只是等待，不是所有权转移**。  
**修法**：`except asyncio.CancelledError: job.cancel(); await asyncio.gather(job, return_exceptions=True); raise`——取消并等它真的收尾。**防线**：取消自己时必须显式 `cancel()` + `await` 被包裹的任务，否则取消语义会被静默吞掉。  
### 12.5 `except CancelledError` 里无条件写终态 → 把「超时失败」改写成「用户取消」

**症状**：Worker 超时 → 判 `TASK_TIMEOUT` FAILED → 取消执行协程，这条路径上刚写好的失败被覆盖成 `CANCELED`；用户看到一个**自己从没取消过的**「已取消」任务，错误详情里却写着「任务执行超时」。  
**根因**：`except asyncio.CancelledError:` 里无条件 `_safe_transition(TaskStatus.CANCELED)`，而状态机里 `FAILED → CANCELED` 是**合法迁移**（用户可以在失败后取消）。  
**修法**：`_cancel_or_keep` 按证据判断：存储里有取消标记 → 确实是取消；没标记但仍是 `RUNNING` → 没人负责收尾，兜底落 `CANCELED`；其余情况保留现有状态。**防线**：「先写终态、再决定是否覆盖」的顺序天然危险；判据要来自**外部证据**（取消标记），而不是「为什么会走到这个分支」。  
### 12.6 内存实现的 `close()` 清空数据，Redis 实现不清 → 关停即丢排期

**症状**：用内存后端时，一次优雅重启就把所有等待退避的任务丢掉（状态还停在 `QUEUED`，要靠补偿扫描在 30s 后才捡回来，期间用户看到「排队中」）。  
**根因**：`InMemoryRetryQueue.close()` 把待重试条目一起清了，`RedisRetryQueue.close()` 只关连接（ZSET 里的排期还在）——语义不一致。  
**修法**：`close()` 语义定为「释放资源，**不动业务数据**」，内存实现改成 no-op，并写进 docstring。**防线**：`test_close_keeps_pending_entries`。替身与真实现的**资源释放语义**也要对齐，不只是方法签名；`close()` / `reset()` / `clear()` 同名不同义最容易在重启时丢数据。  
### 12.7 一条脏数据让整个补偿扫描停摆

**症状**：`list_stale_pending()` 用 `cursor_position(task.created_at, task.id) < cutoff` 排序与过滤，只要**有一条**任务 `created_at` 是坏的（老版本写入、外部脚本改库），整次扫描就抛 `ValueError`；补偿器 `run_forever` 虽有 try/except，但**这一轮所有滞留任务都没被重投**，且每 30 秒重复失败一次，日志稳定是「扫描出错」，看起来像「没有滞留任务」。  
**根因**：`cursor_position` 对坏值抛异常，整批处理被单条数据打断。  
**修法**：坏值不再抛，而是当作「**最老**」参与排序并**算作滞留**（`_sort_key` / `_before_or_unparsable`），让补偿器把这条脏数据也捞出来处理；仍有 `max_attempts` 上限兜底。**防线**：扫描/批处理必须对单条脏数据免疫；判据是「一条坏数据会不会让整批无产出」，是就必须让坏数据走「尽力而为」路径，而不是让异常中断整轮。  
### 12.8 `TASK_RETRY_POLL_SECONDS` 是死配置

**症状**：退避后的重投只在「下一条消息到来时」顺便捞一次；低峰期表现为**重试要等很久**，而监控上「重试队列长度」一直不降。  
**根因**：配置项写了、`.env.example` 里也有、启动期还校验了取值范围，但主循环里**没人读它**。  
**修法**：接进 `_poll_retries()` 并加节流（`_next_retry_poll`）；顺带修两个伴生问题：主循环取不到消息时空转（补 `await asyncio.sleep(0)`）、被取消的 job 没计数（补 `stats.canceled += 1`）。**防线**：**新配置项必须有一条「它会改变行为」的测试**，否则「配置存在」本身就是假信号——一条 `settings.x = 0.01` 的用例就能防住。  
### 12.9 SSE `error.retryable` 的判据只用了「重试预算」

**症状**：`error` 帧/事件的 `retryable` 原本取 `task.can_retry`（= `FAILED` 且 `retry_count < max_retries`），于是 `UNPROCESSABLE_DOCUMENT` / `UNSUPPORTED_FILE_TYPE` / `VECTOR_DIM_MISMATCH` 这类**确定性**错误也返回 `true`；客户端照着重试，就是「白等 21 秒拿到同一个错误」——扫描版 PDF 重试三次还是同一份扫描版 PDF。  
**根因**：判据只用了「重试预算」，没用 `docs/02` §5.3 的 `NON_RETRYABLE_CODES`（`docs/08` §5.2）。  
**修法**：新增 `app/tasks/retry.py::error_retryable(task)` = **错误码值得重试** ∧ **预算没用完**；SSE 快照与失败事件共用这一个判据，两条路径口径必须一致。**防线**：同一契约字段在多处计算 = 早晚不一致，尤其当一处是「错帧」、另一处是「快照」时，客户端重连一次反而多跑三轮注定失败的任务；同一语义只留一个计算入口。  
### 12.10 过载边界写成 `>`：`MAX` 变成 `MAX + 1`

**症状**：`INGEST_QUEUE_MAX=1000` 时真实并发上限是 1001。  
**根因**：`_ensure_capacity()` 统计的是「本次入队**之前**的未结束任务数」，判断却写成 `if open_count > self._queue_max`；`docs/08` §174 的字面「队列长度 > max 时拒绝」更贴近 `>`，但配置项叫 `MAX`，差一的话没人能一眼看出真实上限。  
**修法**：改成 `>=`，把「统计的是入队前数量」写进 docstring；SRS 表述改成「**已达到**上限即拒绝」（`docs/08` §5.4），避免下一轮又按字面改回去。**防线**：边界类配置项的语义必须能被一句话说清（「最多 N 个在飞任务」）；文档字面与配置名冲突时选**名字**并改文档——名字是运维每天要读的东西。  
### 12.11 小结与 M7 的端到端验证

M7 这 10 条里 **9 条一跑就红**（新测试抓到），**1 条是 review 出来的契约不一致**（12.9）；9 条里 5 条属于「并发/取消/跨实现语义」，正是内存替身最难暴露的一类。可复用六条：哨兵值不进业务取值域（12.1）；惰性对象要显式确认「已生效」（12.2 / 12.3）；取消必须转发并等待（12.4 / 12.5）；替身与真实现的资源语义要对齐、脏数据不能让整轮停摆（12.6 / 12.7）；契约字段只留一个计算入口（12.9）；每个新配置项都要有一条证明它改变行为的测试（12.8）。

### 12.12 两条环境事实

**症状**：`TestClient` 测不了「永不结束的 SSE」——对「在跑的任务 / `FAILED` 等自动重试」的 `GET /tasks/{id}/events` 调 `client.stream()` 或 `client.get()` 都会**死锁**（连响应头都拿不到）。  
**根因**：它的传输层会先把 ASGI 应用跑到**生成器结束**、再把响应交给测试。  
**修法**：契约层只测**会自己结束**的流（终态任务）；「连接保持 + 增量 + 心跳」交给可注入时钟的单测 + 真机 `curl`。  
**防线**：`tests/contract/test_tasks.py` 段首注释写明这条边界。另一条历史事实：`INFRA_BACKEND=real` 的 MySQL 仓储在 M7 时仍未提供（`storage.repositories_unavailable`），`POST /knowledge-bases` 直接 503，Kafka 端到端因此走不经 HTTP 的投递脚本（`tools/kafka_e2e_check.py`）；**M8 已补齐**，real 下返回 201（§13）。

## 13. M8（真实基础设施）新增问题

M8 补上三个「留了接口没接实现」的后端点：MySQL 仓储、长期记忆的 Milvus 索引、MinIO 对象存储，以及给 `document_chunk` 补一列。共同特征：**代码逻辑本身没错，错在「它以为自己生效了」**。

### 13.1 `HF_ENDPOINT` 写进 `.env` 是静默失效的

**症状**：`.env` 里明明有 `HF_ENDPOINT=https://hf-mirror.com`，`Settings.hf_endpoint` 也读到了（日志打过），但加载本地模型仍去连 `huggingface.co`，每个缺失文件跑 **5 次重试、约 9 分钟**才降级；`rag.retrieved` 的 `elapsed_ms=558732`（约 9 分 19 秒）看起来像「重排太慢」，实际是**网络重试**。  
**根因**：两层叠加：① `huggingface_hub` 在**导入期**把 `ENDPOINT = os.getenv("HF_ENDPOINT", ...)` 固化成模块常量，`file_download.hf_hub_url()` 用的是 `HUGGINGFACE_CO_URL_TEMPLATE`，**只在显式传 `endpoint=` 参数时**才改写域名——import 之后再设环境变量完全无效；② `app` 自己会在 **`import app.main` 期间**经 `app.api.deps → app.rag.service → app.rag.chunking → langchain_text_splitters → transformers.tokenization_utils_base → huggingface_hub` 把它拉进来，`create_app()` 执行时早已错过窗口期。  
**修法**：`app/core/config.py::apply_hf_endpoint` 在 `create_app()` 里同时做两件事：设 `os.environ["HF_ENDPOINT"]`（对本进程后续导入与子进程有效），并同步改写 `hf_constants.ENDPOINT` 与 `HUGGINGFACE_CO_URL_TEMPLATE`（已被导入时唯一确定性生效的办法）。**防线**：判定脚本 `import app.main; print(hf_hub_url("BAAI/bge-m3","config.json"))` 应输出镜像域名——**问库自己的运行时状态**，而不是看自己的配置对象读到了什么；用 `sys.meta_path` 插 `MetaPathFinder` 打 `traceback.format_stack()` 可拿到精确导入链；`.env.example` 注明「不写这一行是静默失效」。  
### 13.2 只「连上了」不等于「表建对了」

**症状**：`INFRA_BACKEND=real` 下 `SHOW TABLES` 能过、`SELECT 1` 能过，但第一次 `POST /knowledge-bases/{id}/documents` 才炸在 `document_chunk.metadata` 上：`(1054, "Unknown column 'metadata' in 'field list'")`。  
**根因**：`docs/09` 的 DDL 早就有这列，但**已存在的库**不会因为 `CREATE TABLE IF NOT EXISTS` 补列——与 §10.1 / §10.4 同一形状：约束/结构的作用是「拦住」，没拦住时什么都没发生。  
**修法**：`deploy/mysql/003_add_chunk_metadata.sql`（先查 `information_schema` 计数，不存在才 `ADD COLUMN`，否则 `DO 0`，末尾打验证 `SELECT`）；`app/main.py::_check_mysql_ready()` 启动期不只 `SHOW TABLES`，而是逐个比对 `EXPECTED_TABLES`（`knowledge_base` / `document` / `document_chunk` / `user_memory` / `task`），缺了就按名称记 `app.mysql_schema_incomplete` **并带上「去执行哪个脚本」**；`app/infrastructure/mysql/db.py` 把 `ERRNO 1049/1146/1054` 映射为 `503 DEPENDENCY_UNAVAILABLE`，错误信息里含 `deploy/mysql/001_init_schema.sql`。**防线**：不用 `SELECT 1` 做自检——「连上了但库是空的」会显示成功，缺表要等第一次业务请求才暴露，那时已经是线上故障；「连接性」与「结构正确性」必须分开断言。  
### 13.3 连接池的「构造成功」不等于「连得上」，也不该被反复构造

**症状**：`create_engine()` 是**同步且惰性**的（不连网），「构造成功」不能作为「依赖可用」的判据；多个装配点各自 `create_engine()` 会产生多个连接池，关停时只关掉其中一个，剩下的让进程无法干净退出。  
**根因**：把「构造」当成了「连接」，且引擎没有共享与引用计数。  
**修法**：`app/infrastructure/mysql/db.py` **按 DSN 共享引擎 + 引用计数**：`_ENGINES: dict[str, tuple[Any, int]]`，`create_engine_from_settings()` 命中缓存则 `refcount += 1`，`release_engine()` 归零才 `dispose`，`aclose_all_engines()` 关停兜底；启动期自检用完立刻 `release_engine()`，未启用 MySQL 的部署不留常驻池。**防线**：缓存是**进程级**的，测试开头必须先 `await aclose_all_engines()` 清干净，否则「两次调用拿到同一个引擎」的断言会被其他测试遗留的引用影响（`tests/unit/test_db_helpers.py` 踩过一次）。  
### 13.4 用唯一索引做幂等，必须让「幂等命中」也走原子路径

**症状**：长期记忆去重靠 `content_sha256` 唯一索引；「先查再插」在并发下两个请求都查不到、都去插，一个成功一个 `IntegrityError`——直接抛给用户就是「同一句话并发写两次，一次报错」，吞掉则 `hit_count` 丢了。  
**根因**：幂等只做了「查」这一半，「命中」路径不是原子的。  
**修法**：`app/memory/mysql_repo.py::add`：先 `find_by_hash`，命中就 `_bump_hit()`（`created=False`）；未命中则 INSERT，捕获 `IntegrityError` 后**最多重试 3 次 `find_by_hash`**（`await asyncio.sleep(0.05)` 让赢家的事务先可见），仍找不到才 `reraise`；`_bump_hit()` 是**单条 UPDATE**，`confidence = func.greatest(table.c.confidence, confidence)` 在**数据库里**算，避免「读-改-写」丢更新。**防线**：`tests/integration/test_mysql_memory_repo.py::test_concurrent_duplicate_writes_do_not_lose_updates`——`asyncio.gather` 并发写 5 次，断言「恰好创建 1 条」且 `hit_count == 5`。  
### 13.5 Milvus 的标量索引：没有它，召回会静默变少

**症状**：`user_id` 过滤写在 `filter=` 里，看起来对；但集合上没有 `user_id` 索引时，Milvus 先全量取 top-k 再按 filter 过滤，**过滤后凑不满 `top_k` 却返回 200**；多租户下表现为「我的文档明明有，就是搜不到」。  
**根因**：过滤发生在 top-k **之后**，召回静默变少。  
**修法**：`app/memory/milvus_index.py::ensure_ready` 建集合时**同时**建标量索引：`user_id` / `kind` 用 `index_type="INVERTED"`。**防线**：`tests/integration/test_milvus_memory_index.py` 断言 `{"vector", "user_id", "kind"} <= indexes`，并显式构造**跨用户**用例（同一查询向量、另一个用户，断言后者**不出现**）——「隔离」只能靠「不该出现的没出现」来证明。  
### 13.6 过滤器表达式里的值必须转义

**症状**：`user_id` 是客户端可控的字符串，直接拼进 `filter=f'user_id == "{user_id}"'` 会被 `"` 截断（`x" or user_id == "y` 直接变成跨租户读）。  
**根因**：用字符串拼接构造过滤器表达式，等价于 SQL 注入。  
**修法**：用 `json.dumps(value, ensure_ascii=False)` 生成字面量（等价于 SQL 的参数化）。**防线**：所有客户端可控值进 `filter=` 前一律过转义函数，不做裸 f-string。  
### 13.7 删除的「级联」要能在存储侧验证

**症状**：`DELETE /documents/{id}` 返回 202、任务 `SUCCEEDED`、关系库里的行没了，但 Milvus 里的向量还在不在，接口层面看不出来。  
**根因**：`collection.row_count` 是删除标记的统计，空间由 compaction 延后回收，不能作为「已删除」的证据。  
**修法**：用带过滤的查询数条数：`client.query(collection_name="ai_platform_chunks", filter=f'kb_id == "{kb_id}"', output_fields=["chunk_id"], limit=100)`。**防线**：实测上传 2 个 chunk → `kb_id` 过滤得 **2**；`DELETE /documents/{id}` → `SUCCEEDED (stage=DELETING)` → 再查得 **0**；`DELETE /knowledge-bases/{id}?force=true` 返回 `{"documents":1,"vectors":2,"objects":1}`，`vectors: 2` **随数据变化**，所以它是真删除的证据而不是常量。  
### 13.8 `KB_NOT_EMPTY` → `force=true` 的两段式删除

**症状**：清理验证数据时 `DELETE /knowledge-bases/{id}` 返回 409 `KB_NOT_EMPTY`，加上 `?force=true` 才删掉，看起来像「参数没生效」。  
**根因**：这是**设计如此**（`docs/06-§7`）：非空知识库必须显式 `force=true`，避免误删。  
**修法**：不改实现；排查时先确认「有没有真的发出带 query 的请求」（curl 加 `-g` 关闭 URL globbing）。**防线**：两次独立复现状态码都是 `409 → 200`，`force=true` 时 `documents/vectors/objects` 计数与数据一致——设计行为不要当成 bug。  
### 13.9 小结

| # | 坑的形状 | 一句话教训 |
| --- | --- | --- |
| 13.1 | 配置写对了但没生效 | 给 import 期缓存配置的库改配置，必须在导入前完成；自检要问库自己 |
| 13.2 | 只验证「连上了」 | 连接性与结构正确性是两件事，缺表要在启动期点名 |
| 13.3 | 同步构造 ≈ 无副作用 | 惰性 connect 的构造成功不是可用性证据；共享资源要引用计数 |
| 13.4 | 幂等只做了一半 | 「命中」路径也必须原子，否则并发下丢计数 |
| 13.5 | 过滤「看起来对」 | 没有标量索引，过滤在 top-k 之后，召回静默变少 |
| 13.6 | 字符串拼查询 | 客户端可控值进过滤器必须转义（= 跨租户读） |
| 13.7 | 删除看不出级联 | 「删掉了」用带过滤的条数证明，不要看 `row_count` |
| 13.8 | 设计行为被当 bug | 两段式删除（409 → `force=true`）是有意的保护 |

**这八条里只有 13.4 是逻辑 bug**，其余都是「以为生效了」——与本文开头「代码能跑、测试能过、接口有响应，但结果是错的」一致。

## 14. M9（大文件上传与索引可见性）新增问题

入口是一次实测：**8MB 文本上传，接口秒回 `202`，任务最终 `SUCCEEDED`，文档 `INDEXED`，但只入库了 10,000 片，后面 6,969 片（41% 正文）被丢掉，全程只有一条 warning 日志。** 从「拿到成功」到「发现少了一半」之间，没有任何接口字段能让人看出来。本节五条属于同一类：**状态是对的，但没有被表达出来**。

### 14.1 截断是静默的：护栏有，护栏不发声

**症状**：8MB 中文正文（实测 3,053,429 token / 84,846 blocks）→ `parse_document` + `ChunkingService(512/64)` 切出 **16,969** 片 → `MAX_DOC_CHUNKS=10000` 截断 → 入库 **10,000** 片；`GET /documents/{id}` 显示 `chunk_count=10000`、`status=INDEXED`，**看不出被截断**。  
**根因**：截断点是一行裸切片 `drafts = drafts[:self._settings.max_doc_chunks]`，只留日志不留事实；更关键的是「切片数」这个语义被两个量共用——切分**产出**数（16,969）与实际**入库**数（10,000），对外只暴露后者。护栏本身没错（防一个超大文件打爆向量库），错的是它**不发声**。  
**修法**：把两个量拆成字段并与状态变更**同一事务**落库：`document.chunks_total`（截断前产出数，`NULL` = 还没切分）、`document.truncated`（是否因上限丢尾部）、`task.chunks_total`（同一事实在任务上的副本，便于只拿 `task_id` 的调用方判断）；`document.chunk_count` 保留为实际入库数（不新增 `chunks_kept`）。`truncated=1 且 chunk_count < chunks_total` 即「未被完整索引」。**防线**：`tests/unit/test_ingest_facts.py` 三条路径——截断（产出 ≠ 保留且 `truncated=1`）、未截断（两数相等且 `truncated=0`）、失败（不许出现假的 `truncated=1`）。上限 + 静默 = 假成功，比报错更难排查，因为调用方**已经拿到了成功**。  
### 14.2 新增「单调不减」不变量之后，`retry` 路径必须一起改

**症状**：给任务加 `chunks_done` 并强制它单调不减后，`POST /tasks/{id}/retry` 之后的第一次进度上报被自己的不变量拒掉（`AppError(INVALID_ARGUMENT)`），任务**卡在 QUEUED**。  
**根因**：`retry()` 把 `progress` 重置为 0，但没有重置分片计数；worker 从 0 开始报 `chunks_done=0`，而任务里还留着上一轮 `chunks_done=6500`，`0 < 6500` 违反单调。`requeue()` 有一模一样的问题。  
**修法**：凡「把任务拉回起点」的变更块，**所有**派生状态一起清零：`stage=None`、`progress=0`、`chunks_total=0`、`chunks_done=0`。**防线**：`test_ingest_facts.py::test_retry_resets_chunk_counters`。不变量是**全体写入者**的合同：加一条不变量必须找齐所有写该字段的路径（重试 / 重新入队 / 取消 / 失败回写），只改正向路径的后果是「正常流程全绿，走重试就卡死」。  
### 14.3 进度条会卡死：`progress` 会饱和，而去重键里没有分片计数

**症状**：大文档向量化期间 SSE **一帧都不再推**，客户端进度条停住，但任务确实在推进（`chunks_done` 一直在涨）。  
**根因**：`_snapshot_events` 的去重键是 `(stage, progress)`，而 `progress` 在 `EMBEDDING` 段**饱和**——从 55 爬到 95 后封顶，`stage` 与 `progress` 都不再变化，后续每一帧都被判重复丢掉；8MB 文档在 EMBEDDING 段停留很久，卡死时间完全等于大文件向量化时间，恰恰是最需要进度的那段。  
**修法**：去重键扩成 `(stage, progress, chunks_done)`；`chunks_total=0` 时**这两个键整个不出现**，让非 ingest 任务的事件帧与以前**逐字节相同**，不为加功能改动无关任务的契约。**防线**：`test_task_stream.py::test_progress_frames_after_saturation_are_not_deduped`（`progress=95` 固定、`chunks_done` 递增，断言每一帧都发）。去重 = 把状态压成一个键，压缩一定丢信息；加字段时回头搜所有基于旧键比较/去重/缓存的地方。  
### 14.4 文档里的 `stage` 枚举与实现不一致：一处小写别名，永无命中

**症状**：按 `docs/08` §3 的表格写 `if task["stage"] == "embedding"`，永远不成立。  
**根因**：两侧各写一套「看起来合理」的取值且从没放在一起对过：文档写 `parsing` / `chunking` / `embedding` / `indexing`，实现（`app/rag/service.py`）是 `PARSING` / `CHUNKING` / `EMBEDDING` / `INDEXED`（**直接复用 `document.status` 枚举**）。  
**修法**：以**实现**为准回写文档（`docs/08` §3/§4.2/§4.5、`docs/10` §5.1），写明「`stage` 就是 `document.status` 那套枚举，没有第二套别名」。**防线**：`tests/contract/` 承担「快照实际取值」的角色，本次同时把 `chunks_total` / `chunks_done` 加进 `test_tasks.py` 的字段集合断言——字段集合一变测试就红。同一枚举只能有一处定义：文档引用代码常量，或用契约测试快照。  
### 14.5 加了字段，但 DDL 与文档没跟上：只在真实 MySQL 上炸

**症状**：单元测试全绿，集成测试报 MySQL `1054 Unknown column 'document.chunks_total'`。  
**根因**：新字段有**三处落点**，缺一处就静默失效：实体/数据类（`Document`、`Task`，缺了启动就报，最好发现）、`001_init_schema.sql`（**新库**缺列）、旧库迁移脚本（开发机/线上**已有库**永远长不出这列）。本地开发库是几天前用 `001` 建的，`001` 后来加的列不会自动补进去（同 §10.4：幂等 DDL 只保证「不报错」）。  
**修法**：① 新库把列并进 `001_init_schema.sql`；② 旧库用 `deploy/mysql/004_add_ingest_facts.sql`——`information_schema` 守卫的**幂等 `ALTER`**，末尾自带 4 行自检 `SELECT`（列名 + `IS_NULLABLE` + `COLUMN_DEFAULT`）；③ 回写 `docs/09` §2.2/§2.4 的 DDL 与 §2.9 的脚本清单、执行命令。**防线**：迁移脚本末尾自检 + `deploy/mysql/verify_schema.sql`。幂等 DDL 只管新库，任何「新库有、旧库没有」的差异都必须在迁移里再写一遍，且迁移自带自检输出，否则「跑没跑过迁移」只能靠人 `DESCRIBE` 表。  
### 14.6 小结

| # | 坑的形状 | 一句话教训 |
| --- | --- | --- |
| 14.1 | 上限触发时没人知道 | 上限 + 静默 = 假成功；产出数与入库数必须是两个字段 |
| 14.2 | 加了不变量只改正向路径 | 不变量是全体写入者的合同；重试/重新入队/取消都是写入者 |
| 14.3 | `progress` 饱和 ⇒ SSE 全被判重 | 去重键压缩状态就会丢信息；饱和的量不能单独当去重键 |
| 14.4 | 文档一套枚举、代码一套枚举 | 同一定义只能有一处；另一处用引用或契约测试兜住 |
| 14.5 | 新字段只落了实体和 `001` | 幂等 DDL 只管新库；旧库要迁移，且迁移要自带自检 |

**这五条没有一条是「算错了」**：14.1 的护栏按设计工作、14.2 的不变量确实该有、14.3 的去重确实在去重、14.5 的 DDL 确实幂等。共同特征是开头那句话的另一面——**代码能跑、测试能过、接口有响应，只是「事实没有被表达出来」。**
