# 12 · 实现问题记录

> 关联：[11-验收标准与测试策略](./11-验收标准与测试策略.md) §6（7 项检查）、[02-接口规范与错误码](./02-接口规范与错误码.md)。
> 本文记录**实现过程中实际踩到的坑**，每条都注明「症状 → 根因 → 修法 → 留下的防线」。
> 与 11 篇 SRS 的区别：SRS 写「应该是什么」，本文写「我们曾写错成什么、为什么错」。

## 1. 为什么需要这份文档

这批问题有一个共同特征：**代码能跑、测试能过、接口有响应**，但结果是错的。

| 类型 | 表现 | 为什么难发现 |
| --- | --- | --- |
| 静默丢数据 | 分页第二页为空 | 不报错、不告警，只有用户发现「少了一条」 |
| 静默不生效 | 中文页眉永远删不掉 | 结果「看起来挺正常」，只是检索命中率低 |
| 环境相关 | 测试全绿、生产建任务即 500 | 只在日志级别允许输出时才触发 |
| 语义错位 | `vector_score` 恒为 0 | 字段存在、类型正确、值恒为 0 |
| 装配错位 | 入库成功但检索永远 0 条 | 两个向量库实例，各自都对 |
| **护栏失效**（M4） | 步数上限没生效、SSRF 防护被绕过 | **测试全绿**——「护栏在不在」正是靠测试证明的 |
| **旁路失效**（M5） | 记忆不更新、摘要不生成 | 不影响响应结果，没有异常、没有告警，只是**少做了一件事** |
| **约束失效**（M6 前置） | 唯一键从不触发、同名记录能无限插入 | 约束的作用就是「拦住」，而它没拦住时**什么都没发生** |

因此本文的每条记录都要求**留下机器可执行的防线**（测试/结构守卫），而不是「下次注意」。
「下次注意」在 6 个人月之后等于没写。

## 2. 静默丢数据类

### 2.1 时间戳与字符串比较 → 游标分页漏项

**症状**：`GET /tasks` 第一页返回 2 条，用返回的 `next_cursor` 取第二页得到**空数组**。不报错。

**根因**：两个时间戳形状不同却表示同一时刻：

| 来源 | 字符串 |
| --- | --- |
| 实体字段（`now_iso()`） | `2026-09-28T09:15:45.604Z` |
| `datetime.isoformat()` | `2026-09-28T09:15:45.604000+00:00` |

`app/tasks/store.py` 把游标解出的 `datetime` 又 `isoformat()` 回字符串，再与实体字段做**字符串**
比较。第 20 个字符处 `'.'`(0x2E) > `'+'`(0x2B)，于是**同一毫秒创建的任务全部被判为「已翻过」**。
而 Windows 上同一批创建的任务几乎必然落在同一毫秒，所以第二页 100% 为空。

**修法**：把「时间戳归一化 + 游标比较」收敛成一个共享原语，排序键与游标比较**必须是同一个函数**：

```python
# app/core/pagination.py
cursor_position(created_at, id) -> tuple[datetime, str]   # 排序与比较共用的键
is_after_cursor(created_at, id, position) -> bool
parse_stamp(value) -> datetime                            # str/datetime 归一
```

**防线**：`tests/unit/test_pagination.py::test_is_after_cursor_keeps_same_millisecond_items`
—— 显式构造「同一毫秒、id 更小」的记录，断言它留在下一页。另有一条断言
`MILLIS != SAME_MOMENT` 且 `parse_stamp(MILLIS) == parse_stamp(SAME_MOMENT)`，
把「字符串不等、时刻相等」这件事本身固定成用例。

### 2.2 排序键与游标键不一致 → 顺序错乱

**症状**：列表顺序偶发不对；同毫秒的记录顺序不稳定。

**根因**：排序用 `(task.created_at, task.id)`（字符串），比较用 `(datetime, str)`。
两把尺子量同一件事。

**修法**：`InMemoryKnowledgeBaseRepo` / `InMemoryDocumentRepo` / `InMemoryTaskStore`
统一改成 `key=lambda x: cursor_position(x.created_at, x.id)`。

**防线**：`test_cursor_position_is_datetime_keyed_not_string_keyed` 断言位置键第一段是
`datetime` 而不是 `str`。

### 2.3 同一位置产生两条不同游标

**症状**：日志里同一个位置出现两条不同 `cursor` 串，排查时误判为「位置变了」。

**根因**：`encode_cursor` 对 `datetime` 入参做 `astimezone(UTC).isoformat()` 归一，
对 `str` 入参**原样透传**。两种入参 → 两条编码。

**修法**：两种入参都先过 `parse_stamp`。

**防线**：`test_encode_cursor_accepts_datetime_and_str` 断言两者产出同一串。

### 2.4 参数被同名局部变量覆盖

**症状**：按 `resource_id` 过滤任务时结果不对（但传了值，看起来"生效了"）。

**根因**：`list()` 里 `moment, resource_id = decode_cursor(cursor)` —— 把入参 `resource_id`
覆盖掉了。Python 不报错，只是过滤条件永远用游标里的那个 id。

**防线**：改用 `moment, cursor_id = ...`，并在设计上消除了手写解包
（游标解码集中在 `is_after_cursor` 内部）。

## 3. 静默不生效类

### 3.1 清洗顺序错误 → 中文页眉页脚永远删不掉

**症状**：PDF 清洗后页眉「产品手册」仍在正文里；`detect_repeated_lines` 返回空集。

**根因**：`clean_pages` 先做 `normalize_text`，而它内部有一步 CJK 孤行合并
（`([CJK])[ \t]*\n[ \t]*([CJK])` → `\1\2`）。`产品手册` 与下一行 `退款时效…` 都是 CJK，
被粘成一行 `产品手册退款时效…`。此后**每一页的那一行都不相同**（正文不同），
`detect_repeated_lines` 的计数永远到不了阈值。

即：一个「让 PDF 更易读」的优化，静默地废掉了「去页眉」这个功能。

**修法**：把归一化拆成两步，并**固定顺序**：

```
_normalize_preserving_lines （不动行结构：零宽、换行符、NFC、断词、行尾空白）
  → strip_page_numbers     （整行识别页码）
  → detect_repeated_lines  （按行统计跨页重复）
  → normalize_text         （含 CJK 孤行合并，放最后）
```

**防线**：`test_clean_pages_removes_cjk_only_header`（纯中文页眉必须消失）
+ `test_clean_pages_keeps_cjk_body_lines_merged`（合并功能不能被一起删掉）
+ `test_clean_pages_is_idempotent`（清洗两次 == 一次，否则重新入库会产出不同切片）。

### 3.2 `.strip()` 吃掉首行缩进 → 代码块语义丢失

**症状**：`"    if x:"` 变成 `"if x:"`。

**根因**：`normalize_text` 末尾用 `.strip()`，而同函数的注释明确写着「只在行尾去空白：
行首缩进对代码/列表有意义」。注释与实现自相矛盾。

**修法**：改成 `.strip("\n")` —— 只裁剪首尾空行。

**防线**：`test_normalize_strips_trailing_space_but_keeps_indent`。

### 3.3 编码探测顺序导致 encoding 字段总是错的

**症状**：所有 UTF-8 文件元信息里的 `encoding` 都是 `utf-8-sig`。

**根因**：`for encoding in ("utf-8-sig", "utf-8")` —— `utf-8-sig` 对**没有 BOM** 的文件
同样能解码成功，所以第一个分支永远命中。

**修法**：先判 `codecs.BOM_UTF8` 前缀，再试 `utf-8`，最后 `gb18030`。

**防线**：`test_decode_bytes_plain_utf8_reports_utf8` / `test_decode_bytes_bom_is_stripped_and_reported`。

> 教训：**「能解码」和「该报什么编码名」是两件事**。探测类函数的返回值要单独测，
> 不能只测「没抛异常」。

### 3.4 HTML 解析：块级标签里的文字全丢

**症状**：真实网页解析出来是**空字符串**；表格内容重复出现两次。

**根因**：`for element in soup.descendants` 里

```python
if not isinstance(element, Tag):
    continue  # ← NavigableString（真正的文字）在这里被全部跳过
...
if name in _BLOCK_TAGS:
    flush()
    continue  # ← <p> 只断开段落，从不进入子树
```

文字在 `<p>` 的文本子节点上，而它既是 `NavigableString` 又被 `<p>` 分支拦掉。
真实网页几乎把正文都放在 `<p>` / `<div>` / `<li>` 里 → **整页解析不出来**。
同时表格既作为原子块被收一次、又作为 descendants 被收一次 → 重复。

**修法**：改成递归遍历，块级标签「先 flush 再递归进子树」，`table`/`pre` 显式不递归：

```python
def walk(node):
    for child in node.children:
        if isinstance(child, NavigableString):
            paragraph.append(...)
            continue
        if name in _HEADING_TAGS:
            flush()
            push(heading)
            continue
        if name in ("table", "pre"):
            flush()
            add(render(child), atomic=True)
            continue
        if name in _BLOCK_TAGS:
            flush()
        walk(child)
```

**防线**：`test_html_drops_script_style_nav_footer`、`test_html_builds_heading_path_and_title`、
`test_html_table_is_atomic`（断言 `len(blocks) == 1`，即「不重复收取」）。

### 3.5 解析顺序错误 → `html_title` 永远为空

**症状**：HTML 的 `metadata["html_title"]` 恒为 `""`。

**根因**：`_DROP_TAGS` 包含 `head`，而 `page_title = soup.title...` 写在
`for tag in soup.find_all(_DROP_TAGS): tag.decompose()` **之后** —— `<title>` 已经被删了。

**修法**：先读 `soup.title`，再 `decompose`。

**防线**：`test_html_builds_heading_path_and_title` 断言 `html_title == "售后政策"`。

### 3.6 `vector_score` 恒为 0

**症状**：`/search` 返回的 `vector_score` 永远是 0，而 `score` 正常。

**根因**：`vector_score` 由**存储层**负责填。两个存储实现都忘了填，
字段有、类型对、值恒为 0。

**修法**：把命名责任上移到检索层 —— `_recall` 拿到召回结果后统一
`replace(chunk, vector_score=chunk.score)`。存储只需保证 `score` 正确。

> 原则：**「谁定义语义，谁负责填字段」**。让每个存储实现各自记得填一个字段，
> 就是给未来留一个必然会被漏掉的坑。

**防线**：`tests/unit/test_rag_retrieval.py`（重排保留 `vector_score`、未重排时
`score == vector_score`）+ 契约测试 `with_rerank=false` 分支。

### 3.7 两个向量库实例 → 入库成功、检索永远 0 条

**症状**：上传文档返回 `202`、任务 `SUCCEEDED`、`/documents/{id}/chunks` 有切片，
但 `/search` 与 `/chat` 的 `references` 恒为空。**没有任何异常或日志**。

**根因**：`create_app` 里

```python
rag = build_rag_services(resolved)  # 内部 build_vector_store() → 实例 A
service = build_chat_service(resolved)  # 内部又 build_vector_store() → 实例 B
```

写入侧写 A 的内存字典，读取侧查 B 的空字典。内存实现下 100% 复现，
真实 Milvus 下因为连的是同一个服务反而是「对的」——这类 bug 会专门挑本地/测试环境骗人。

**修法**：`build_retriever(settings, *, embedding=..., vector_store=..., reranker=...)`
允许注入，`build_rag_services` **必须**注入同一批实例，并把 `app.state.retriever` 暴露出去。

**防线**：`build_retriever` 的 docstring 明确写了「写入侧与查询侧必须是同一个向量库」；
`tests/contract/test_chat_rag.py` 里 `rag_chat_client` 夹具显式复用
`application.state.retriever`，并在注释里说明原因。

### 3.8 重试静默不执行

**症状**：`POST /tasks/{id}/retry` 返回 200、状态变 `QUEUED`，然后**永远停在 QUEUED**。

**根因**：`docs/08` §4.4 要求「置 `QUEUED` **并**投递」，但 `InlineTaskRunner.submit`
只接受 `PENDING`：

```python
if task.status is not TaskStatus.PENDING:
    return  # 静默返回，连日志都没有
```

**修法**：接受 `PENDING | QUEUED`，并加 `_inflight` 集合去重；`retry()` 同时清掉
`started_at`（否则耗时 = `finished - started` 会跨轮次算出怪数字）。

**防线**：`tests/unit/test_task_state_machine.py::test_retry_resets_progress_and_started_at`；
契约 `test_tasks.py` 断言重试后任务真的重新跑完（`retry_count+1` 且最终再次 `FAILED`）。

> 静默 `return` 是这类问题的共同形状。判断条件不满足时至少要打一条日志 ——
> 否则「什么都没发生」和「发生了但没生效」无法区分。

## 4. 环境相关类

### 4.1 `extra={"created": ...}` 撞 `LogRecord.created`

**症状**：`KeyError: "Attempt to overwrite 'created' in LogRecord"`，**只出现在生产**，
建任务接口直接 500。测试全绿。

**根因**：CPython `Logger.makeRecord` 会检查 `extra` 的键是否与 `LogRecord` 已有属性重名：

```python
for key in extra:
    if (key in ["message", "asctime"]) or (key in rv.__dict__):
        raise KeyError("Attempt to overwrite %r in LogRecord" % key)
```

`LogRecord.__dict__` 自带 `created`（记录时间戳）。三重巧合让它躲过测试：

1. 只有 `isEnabledFor(level)` 为真才会走到 `makeRecord`；
2. `tests/conftest.py` 的基线配置是 `log_level="WARNING"`，而这条日志是 `INFO`；
3. 生产默认 `INFO`。

**修法**：
* 键名改 `is_new`；
* `tests/conftest.py` 的 `log_level` 对齐**生产默认值 `INFO`**（输出仍被 pytest 捕获，
  只在失败时打印），让日志分支在测试里真被执行；
* 加结构守卫 `tests/unit/test_logging_extras.py`：用 `ast` 扫全仓
  `extra={...}` 的键名，与 `logging.makeLogRecord({}).__dict__` 求交集，非空即失败。

> 这条守卫是本次最有价值的产出：单点用例防不住（要写得对、还得刚好开着 INFO），
> 结构化检查能防住一整类。

**防线**：`test_extra_keys_do_not_shadow_logrecord` +
`test_make_record_actually_rejects_reserved_keys`（反向验证：这些键确实会被标准库拒绝，
证明我们不是在凭空设限）。

### 4.2 `INFRA_BACKEND=real` 时整个应用起不来

**症状**：`app_env=prod` 下 `create_app` 直接抛 `NotImplementedError`，
连健康检查、鉴权、对话都不可用。

**根因**：`build_repositories` 在 `real` 分支直接 raise，而 `docs/10` 的依赖矩阵规定
「MySQL 不可用」只应让**依赖 MySQL 的接口**返回 503。

**修法**：新增 `app/storage/unavailable.py` —— 三个仓储的「每一个方法都抛
`503 DEPENDENCY_UNAVAILABLE`」实现，`build_repositories` 在 `real` 下返回它们并记一条 warning。

**防线**：`tests/contract/test_auth.py` 里 `real` 后端的用例。

> 原则：**启动期只做「能不能工作」的判断，不做「依赖是否齐全」的判断**。
> 后者会把一个局部故障放大成全局不可用。

### 4.3 启动期探测失败导致容器重启循环

**症状**：Milvus 没起来时容器反复重启。

**修法**：lifespan 里的 `ensure_ready()` / `verify_model()` 一律 try/except + warning，
不阻断启动；依赖健康由 `/health/ready` 的 503 表达。

**防线**：`app/main.py` 里的注释 + `docs/10` 依赖矩阵。

## 5. 契约与分层类

### 5.1 Schema 层抛不出领域错误码 → 校验放错层

**症状**：`chunk_overlap >= chunk_size` 返回 `400 INVALID_ARGUMENT`，
而 `docs/02` 要求 `400 CHUNK_STRATEGY_INVALID`。

**根因**：pydantic 的 `field_validator` / `model_validator` **只能抛 `ValueError`**，
框架统一转成 `INVALID_ARGUMENT`。而 `AppError` 是自定义异常，validator 里抛不出去
（会被 pydantic 包成 `ValidationError`）。

**修法**：把切片参数校验整体下移到 `resolve_chunk_params()`（服务层唯一实现），
schema 只留「结构性」校验。

**防线**：契约测试断言错误码是 `CHUNK_STRATEGY_INVALID`（而不是 `INVALID_ARGUMENT`）。

> 规则：**领域错误码必须在服务层抛**。schema 层的能力边界是「语法」。

### 5.2 不支持的文件类型被伪装成「任务失败」

**症状**：上传 `.xyz` 返回 `202`，任务 3 秒后 `FAILED`，错误消息是解析器的底层异常。

**根因**：类型校验发生在任务执行内。用户得到的反馈是「系统出错」，
而不是「这个格式不支持，请换 .pdf」。

**修法**：`DocumentService.upload` 在返回 `202` **之前**调用 `get_parser()`，
不支持即同步返回 `415 UNSUPPORTED_FILE_TYPE`。

**防纈**：契约测试 `test_documents.py` 的两条 415 用例（不支持的扩展名、
扩展名与魔数不符）。

> 原则：**能在同步阶段给出的错误，不要拖进异步任务**。异步失败的信息量天然更少。

### 5.3 文本上传没有扩展名 → 永远 `UNSUPPORTED_FILE_TYPE`

**症状**：`doc_name="测试文档"` 上传纯文本 → `415`。

**根因**：解析器按扩展名分发，而 `doc_name` 没写扩展名。

**修法**：`_resolve_doc_name()`：sanitize 后若**无扩展名**，补上 `normalize_extension(filename)`
或 `.txt`。

**防线**：契约测试断言 `doc_name="政策"` 最终落库为 `政策.txt`。

### 5.4 测试假设与 SRS 不符时，先改测试

本次有 4 处「测试失败」，全部是测试写错，不是实现错：

| 测试假设 | SRS 实际规定 |
| --- | --- |
| 超过知识库数量上限返回 `429` | `docs/02` 表：`KB_LIMIT_EXCEEDED` → **409** |
| `/search` 响应含 `kb_id` | `docs/06` §5.1：`SearchItem` 无 `kb_id` |
| `kb_ids` 为空 = 不检索 | `docs/03` 行 51：`use_rag=true` 且 `kb_ids` 为空 = 检索**全部**知识库 |
| `merge_token_budget` 返回条数 | 实际返回 `bool trimmed` |

**规则**：测试与 SRS 冲突时的默认动作是**重读 SRS**，而不是改实现。
只有在 SRS 自身矛盾时才改文档，并在本文档记录。

## 6. 测试工程类

### 6.1 `tests/` 无 `__init__.py` → 文件名必须全局唯一

pytest 的 rootdir 导入模式下，两个 `tests/unit/test_utils.py` 与
`tests/contract/test_utils.py` 会报 `import file mismatch`。

**规则**：测试文件 basename 全局唯一（如 `test_rag_retrieval.py` 而不是 `test_retrieval.py`）。

### 6.2 替身必须与协议同形（同步 vs 异步）

`FakeEmbedding.embed` 必须是**同步**函数（与 `EmbeddingProvider` 协议一致），
因为调用方会 `asyncio.to_thread(embed, ...)`。写成 `async def` 会让 `to_thread`
拿到一个 coroutine 对象，`.tolist()` 之类调用全部失败。

**规则**：写替身时先把协议抄一遍，逐个方法核对同步/异步。

### 6.3 并行编辑同一个文件会损坏内容

`replace_string_in_file` 并行作用于同一文件时，两处改动可能交错。

**规则**：同一文件的多次编辑**串行**；不同文件才允许并行。

## 7. M4（Agent 与工具调用）新增问题

M4 的问题几乎都属于一个新类型：**「护栏看似存在，其实没生效」**。

前四类（静默丢数据 / 静默不生效 / 环境相关 / 契约错位）都能靠「结果不对」被发现；
护栏失效的表现却是**测试全绿**——因为「护栏有没有起作用」本身就是靠测试来证明的。
一旦替身（fake LLM）的行为比真实上游更宽松，护栏测试就会变成一条永远为真的断言。

### 7.1 步数耗尽与超时中断被合并成一种

**症状**：`finish_reason` 永远返回 `stop`，`max_steps` 从未出现；`degraded_reasons`
里时而多出一条 `max_steps`。

**根因**：中断原因从中断后的计数器**反推**。

```python
while state.steps < state.max_steps:
    if state.expired():
        break
    ...

# 错：超时 break 之后 steps 也可能刚好等于上限
if state.steps >= state.max_steps:
    state.degraded.append(REASON_AGENT_MAX_STEPS)
```

**修法**：`while/else` + 显式标志位。`else` 分支只在「条件自然为假」时执行，
天然区分「步数用完」与「提前 break」。

```python
while state.steps < state.max_steps:
    if state.expired():
        break
    ...
else:
    state.max_steps_hit = True
    state.degraded.append(REASON_AGENT_MAX_STEPS)
```

**防线**：`test_loop_stops_at_max_steps` 断言 `finish_reason == "max_steps"`；
`test_loop_has_total_time_budget`（慢工具 0.4s + 总预算 0.2s）断言
`REASON_AGENT_TIMEOUT in reasons` 且 `finish_reason == "stop"`。

**通用规则**：**不要从中断后的状态反推中断原因**，要在中断发生的那个位置记录原因。

### 7.2 收尾调用被计入步数

**症状**：配置 `agent_max_steps=8`，请求 `max_steps=8`，返回的 `steps` 是 **9**。

**根因**：达上限后为了拿到「最终回答」额外发了一次不带工具的 `complete()`，
这次调用也走了 `state.steps += 1`。

**修法**：`steps` 的语义定义为「**工具调用轮数**」（这也是 `docs/04` 的口径），
收尾调用不计入。`while` 里递增，收尾走循环外的 `_wrap_up()`。

**防线**：`AC-AGENT-02` 契约断言 `steps == 8 and len(tool_calls) == 8`。
若把收尾算进去，这两个数会同时变成 9，很容易被误认为「上限配错了」。

### 7.3 假 LLM 在没下发 tools 时也回放工具调用

**症状**：想断言「收尾调用必须不带工具、只能直接回答」，但测试怎么写都通过——
连「工具护栏失效」的实现也能通过。

**根因**：`FakeLLM` 按固定脚本回放，**不看你有没有给它工具**。于是收尾调用也能
拿到一条 `tool_call`，收尾逻辑被绕开，测试断言的是假象。

**修法**：`_script(tools)` 在 `not tools` 时返回 `[]`——**「没给工具就调不出工具」
这条约束属于上游行为，替身必须复刻**。

**防线**：`test_loop_wrap_up_call_has_no_tools` 断言 `llm.tools_seen[-1] is None`。

**通用规则**：替身宽松多少，护栏测试就虚假多少。写替身时逐条问
「真实上游会怎么做」。

### 7.4 流式只给成功的工具调用发帧

**症状**：`docs/02` §6 要求「每个 `tool_call` 都有配对的 `tool_result`」，
但实现只在 `record.status == "ok"` 时发 `tool_result`。

**根因**：把「帧」当成了「结果通知」而不是「**过程可观测性**」。
工具失败恰恰是前端最需要显示的状态（「正在重试」「该工具不可用」）。

**修法**：一轮结束后按模型给出的顺序，**逐条**成对下发（含失败、含重复调用）。

**防线**：`test_agent_stream_pairs_tool_frames_before_done` 断言
`tool_call` 与 `tool_result` 数量相等、`call_id` 相同、都在 `done` 之前。

### 7.5 重复调用被算作「工具失败」

**症状**：模型第二轮重发了一个完全相同的调用（无害），整轮却被打上
`tools_failed` 降级标记。

**根因**：`failed = [record for record in records if not record.ok]`，
而重复调用会被构造成一条 `status="error"` 的伪记录 → 落进 `failed`。

**修法**：区分「**尝试过但失败**」与「**根本没执行**」：

```python
attempted = [record for record in records if record.error != ERROR_DUPLICATE_CALL]
if attempted and not any(record.ok for record in attempted):
    state.degraded.append(REASON_TOOLS_FAILED)
```

**防线**：`test_loop_skips_duplicate_calls` 断言 `REASON_TOOLS_FAILED not in reasons`。

### 7.6 同一错误原因，两种 payload 形状

**症状**：模型看到的重复调用提示，取决于「重复」是**执行器**发现的还是
**Agent Loop** 发现的——两条路径各写了一份构造代码，`hint` 文案还不一样。

**根因**：同一个语义在两个地方各实现一次（与 §2.1「两个时间戳原语」同源）。

**修法**：抽出公共构造函数 `duplicate_record(call, arguments)`，
执行器与 Loop 共用；`payload` 的形状只有一份定义。

**防线**：单测断言 `payload["hint"]` 的具体文案（改文案就必须改两处，不会漏）。

### 7.7 参数不合法被映射成 502

**症状**：`POST /tools/calculator/invoke` 传一个非法表达式，返回
`502 TOOL_EXECUTION_FAILED`；正确应是 `400 INVALID_ARGUMENT`。

**根因**：错误码映射只看 `status`：

```python
_STATUS_TO_CODE = {"error": TOOL_EXECUTION_FAILED, "timeout": TOOL_TIMEOUT, ...}
```

而「参数错」「依赖挂」「工具自己抛异常」的 `status` **全都是 `error`**，
信息在 `record.error` 里，映射函数没看它。

**修法**：增加 `_ERROR_TO_CODE`（7 个原因穷举），优先按 `record.error` 映射，
`status` 只作兜底。

**防线**：`test_error_to_code_covers_every_reason` 断言
`{全部 7 个 ERROR_*} <= set(_ERROR_TO_CODE)`——以后新增原因时漏配会直接失败。

### 7.8 校验失败的原因只进了 `detail`，模型看不见

**症状**：模型收到 `{"error": "invalid_arguments", "message": "参数不符合工具 Schema"}`，
不知道错在哪个字段，只能盲目重试或放弃。

**根因**：pydantic 的 `errors()` 详情（`loc` / `msg`）被整块塞进 `detail`。
而**上游客户端常常会截断/丢弃结构化 `detail`**，只展示 `message`。

**修法**：`_describe(errors)` 把前 3 条拼成人话放进 `message`：

```text
参数不符合工具 Schema —— expression: Value error, 表达式中不允许调用函数
```

`detail` 仍保留结构化数组（程序可读），`message` 负责**模型/用户可读**。

**防线**：`test_current_time_rejects_unknown_timezone` 断言 `message` 里含
`未知时区`（而不是只断 `ToolArgumentError` 类型）。

### 7.9 工具「静默失效」：给上游发了一条假的 tools 消息

**症状**：带 `tools` 的请求，模型从不调用工具（**不报错**，只是工具被忽略）。

**根因**：为了把工具 schema 传给上游，实现里先构造了一条内容形如
`{"tools": [...]}` 的**普通 message** 塞进 messages，而不是调用 `bind_tools()`。
上游把它当普通聊天内容，工具能力根本没开。

**修法**：`client = self._client_for(...).bind_tools(tool_payload)`，
把绑定后的 client 与「是否需要 tools」一起放进缓存键
（`(model, temperature, max_tokens, tools: bool)`）。

**防线**：`FakeLLM.tools_seen` 记录每轮收到的 tools，测试断言第一轮含
`calculator`、收尾轮为 `None`。**真实上游也要发一次最小真实调用确认**
（见 `llm-apis.md` 的「验证手法」）。

### 7.10 表达式求值的白名单

`calculator` 用 `ast.parse(expr, mode="eval")` 后逐节点白名单校验：

```python
_ALLOWED_NODES = (
    ast.Expression,
    ast.Constant,  # 仅 int / float
    ast.BinOp,
    ast.UnaryOp,
    ast.operator,
    ast.unaryop,
    ast.expr_context,
    ast.Load,
)
```

`__import__('os').system('ls')` 会解析出 `Call`/`Name`/`Attribute` → 白名单外 → 校验失败，
作为**可回复的工具结果**回注。

**两个踩到的坑**：

1. 走 `eval()` 前只做「字符串黑名单」（`"__"`/`"import"`）是**假防护**——
   `getattr(__import__("o"+"s"), ...)` 之类可以绕过。**必须用 AST 白名单**。
2. 反向的坑：`1e999999` 是**合法** float 字面量（解析为 `inf`），
   拿它当「非法表达式」测黑名单等于什么都没测。**测拒绝列表时要逐个确认真的该被拒**。

**另一个坑**：`2 ** 999999` 语法合法、白名单通过，但会吃满 CPU。指数必须封顶
（`EXPONENT_MAX = 1000`），超出抛 `ToolExecutionError`——它属于「执行失败」而非
「参数非法」，因为参数本身合法，只是代价不可接受。

### 7.11 `http_fetch` 的 SSRF 防护：只校验字面量不够

| 写法 | 结果 |
| --- | --- |
| 只校验 hostname 字符串（`10.`/`192.168.` 前缀黑名单） | **可绕过**：`http://2130706433/`（十进制 IP）、`[::ffff:127.0.0.1]` |
| 用 `ipaddress` 判断**解析后的全部 IP** | 覆盖字面量、十进制、IPv6 映射、重定向 |

**修法**：`_assert_public_host` 先判断字面量，再 `getaddrinfo` 解析并**逐个** IP
判断（`is_private`/`is_loopback`/`is_link_local`/`is_reserved`/`is_multicast`/`is_unspecified`
任一命中即拒）。**校验全部解析结果**是 DNS rebinding 的必要条件——
只查第一个 IP 会被「第一次解析给公网、第二次给内网」绕过。

**额外的取舍**：`http_fetch` 默认 `enabled=false`。它是一个**外发请求**能力，
默认打开等于给模型一个 SSRF/数据外泄的出口；要开必须显式配置。

**防线**：参数化拒绝用例 10 条（`10.0.0.1` / `192.168.1.1` / `[::1]` / `0.0.0.0` /
`ftp://` / `file://` / 无主机名 …）+ 1 条 monkeypatch `getaddrinfo` 的
DNS-rebinding 用例。

### 7.12 测试里三处「假严密」

| 写法 | 问题 | 改法 |
| --- | --- | --- |
| `pytest.raises(Exception)` | 任何异常都通过，包括 `AttributeError`（写错了也绿） | 断具体类型：`ValidationError` / `ToolExecutionError` / `ToolArgumentError` |
| `ToolSpec(**spec.__dict__)` | `slots=True` 的 dataclass **没有 `__dict__`**，直接 `AttributeError` | 直接断言字段值，不做反射重建 |
| 断言「被拒」但只给了 4 条脚本却断言 `steps == 8` | 脚本用完的那轮模型直接回答 → 循环提前结束，`steps` 恒为 5 | 要么脚本给够轮数，要么断言 `<= 上限` |

`ruff` 的 `B017`（`Do not assert blind exception`）能自动抓出第一类，
后两类只能靠「**先算一遍期望值**」。规矩：**给测试写期望值时，先在脑子里把
被测循环跑一遍**，而不是照着实现里的常量抄。

### 7.13 `ruff format` 也会格式化 Markdown 里的 python 代码块

本次给仓库新增两份文档（12 / 13）后，`ruff format --check .` 从「0 个文件需要格式化」
变成「10 个文件需要格式化」，其中两份是 `.md`。

**规则**：文档里的 ```python 代码块是**真代码**，必须能通过 `ruff format`。
写文档时留的「为了对齐而多打空格」会被格式化掉——**不要用空格对齐做视觉分组**，
改用注释或拆成两段。

## 8. M5（Memory）新增问题

M5 的问题集中在**「动作没有发生，但没人报错」**这类形态上：记忆抽取、摘要、注入
都是「跑一下更好、不跑也不报错」的旁路逻辑，所以漏接一条线、命中一次防抖、
幂等键撞车，全都表现为静默失效。

最后两条（8.16 / 8.17）是另一类：由「内部命名/结构外溢到对外契约」引起，
收尾自查（把工具定义按 SRS 逐字对一遍）才发现的。

### 8.1 收尾动作只接在流式路径上

**症状**：用 `POST /chat/stream` 对话后，`GET /memories` 会新增一条；换成
`POST /chat`（默认路径）则永远为空，任务列表里也没有 `memory_extract`。

**根因**：`ChatService.complete()` 里只写了 `_persist`，`_after_turn`（投递记忆抽取
与摘要）只挂在 `stream_prepared()` 里。

**为什么难发现**：两条路径各自都是「能跑通」的。非流式不写记忆这件事没有任何
异常、日志、状态码能体现出来——它只是**少做了一件事**。

**修法**：`complete()` 在 `_persist` 之后同样调用 `_after_turn`，并加注释说明
「收尾动作必须在两条路径上都执行」。

**防线**：契约用例 `test_turn_triggers_memory_extraction` 走的是**非流式** `/chat`
（默认路径），它一旦漏接就会红。

**推广**：一个「旁路动作」有 N 个入口时，要么收敛成一个入口，要么每个入口都写
一条断言。只在一个入口上接了线，等价于这个能力只在部分流量上存在。

### 8.2 幂等键的粒度错了：把「每轮」变成「每会话」

**症状**：一个会话里连续聊 15 轮，`GET /tasks?type=summary_build` 只有 1 条任务；
`memory_extract` 同理。第 2 轮之后记忆再也不会更新，摘要也永远只覆盖最初那几条消息。

**根因**：`TaskService.create` 的默认幂等键是
`make_idem_key(type_, user_id, resource_id)`。摘要/抽取的 `resource_id` 是
**会话 id**，于是同一会话的每一轮都在生成同一个幂等键：第二轮返回的是第一轮
那条**已经终态**的任务，`InlineTaskRunner.submit` 把它当成重复投递跳过。

**为什么难发现**：`create` 返回 `created=False` 时接口依旧 200，日志里只有一行
`task.submit_skipped`（INFO 级），而「记忆怎么没更新」是完全另一条排障路径。

**修法**：`ChatService._submit` 传入 `idem_key=make_idem_key(type_, user_id,
resource_id, turn_marker)`，`turn_marker` 取本轮最后一条消息的 `message_id`。
语义变成「同一轮的重复投递幂等，不同轮各自成任务」——这正是幂等键该表达的东西。

**防线**：`AC-MEM-03` 的用例构造 30 条历史并断言**出现** `summary_build` 任务；
`AC-MEM-08` 的用例断言「同一句话抽两次 → `hit_count=2`」，等价于要求第 2 轮真的
又跑了一次抽取。

**推广**：用「资源 id」当幂等键时，先问一句：**这个资源上会有多次不同的意图吗？**
有（每轮对话、每次重算、每个新数据版本），就必须把「意图版本」也放进键里。

### 8.3 防抖命中被记成任务失败

**症状**：任务列表里出现 `summary_build` 的 `FAILED`，错误是「摘要生成器未装配」，
但摘要器明明装好了；同一会话里每多聊一轮就多一条假故障。

**根因**：`SummaryBuilder.build()` 用 `None` 表示「条件不满足或命中防抖，跳过」，
而 `MemoryTaskHandlers._build_summary` 把 `None` 当成「服务没装配」并抛
`INTERNAL_ERROR`。5 分钟防抖窗口内的第二次任务必然命中这条路径。

**修法**：处理器先用 `service.summary_builder is None` 判装配（真正的装配错误），
再把 `None` 记为 `memory.summary_skipped` 并正常结束。

**防线**：`test_long_conversation_triggers_summary_task` 会连续按 15 轮投递摘要任务，
其中必然有命中防抖的；假故障会让 `AC-MEM-03` 的断言与任务列表一起变红。

**推广**：`None` / 空返回值是**多义**的。一个函数如果既可能「跳过」又可能
「没能力做」，它必须返回两种可区分的结果，或者由调用方先判断能力（这里是
`summary_builder is None`）。

### 8.4 `messages[:-0]` 不是「全部」，而是空

**症状**：把 `SUMMARY_KEEP_RECENT_TURNS` 设成 0（意图是「全部交给摘要、不留原文」）
后，摘要**永远不生成**，而日志只显示「条件不满足」——与「消息太少」无法区分。

**根因**：`pending = messages[:-keep] if keep and len(messages) > keep else []`。
`keep == 0` 时条件为假走 `else`，`pending` 是空列表，直接 `return None`。

**修法**：

```python
keep = max(0, settings.summary_keep_recent_turns) * 2
pending = list(messages)
if keep and len(messages) > keep:
    pending = list(messages[:-keep])
```

同时给 `SUMMARY_KEEP_RECENT_TURNS` 补上「≥ 0」的启动期校验：负数会被 `max(0, ...)`
静默吞掉，而「静默吞掉配置」比「拒绝启动」难查得多。

**防线**：`test_build_summarises_everything_when_keep_is_zero`（覆盖 `keep == 0`）
与 `test_negative_summary_keep_recent_turns_is_rejected`（覆盖负数配置）。

**推广**：切片边界上的 `0` 与 `-0` 是同一个值。凡是「0 表示全部」的语义，
都不能交给 `x[:-n]` 去表达。

### 8.5 处理器只能注册一次 ⇒ 重建记忆层必须「改绑」

**症状**：测试里第二次调用 `build_memory_services(...)` 直接抛
`AppError: 任务类型 summary_build 的处理器已注册`；把注册去掉，任务又会继续
走**旧**服务（用真模型而不是替身 LLM）。

**根因**：`create_app` 已经注册了 `SUMMARY_BUILD` / `MEMORY_EXTRACT` 的处理器；
而「用替身 LLM 重建记忆层」的常规做法是再建一套服务，于是撞上「重复注册是装配
错误」这条守卫。

**修法**：`build_memory_services(..., register_handlers=False)` 只建服务不注册，
调用方再用 `app.state.memory_handlers.bind(新服务)` 把**已注册的那个**处理器
改绑过去。`bind` 的存在理由与路由层「每次请求从 `app.state` 取服务」一致：
注入点是 `app.state`，而不是构造期就焊死的引用。

**防线**：`tests/conftest.py::make_memory_client` 走的就是这条路径，M5 的 20 条
契约用例全都经过它。

**推广**：当「守卫」与「测试要用的注入方式」冲突时，不要拆守卫（重复注册确实是
装配错误），而要给被守卫的对象一个**受控的改绑入口**。

### 8.6 空的模型输出被「结构补齐」掩盖

**症状**：模型偶尔返回空串时，摘要并没有失败，而是变成一份**格式完美**的四段
`- 无`，并且覆盖掉了上一版好用的摘要。

**根因**：`ensure_structure()` 的职责是「缺段补 `- 无`」，它对空输入的输出也是
合法的四段结构；因此「模型什么都没说」与「模型说这段没有内容」在校验后**完全同形**。

**修法**：`_generate` 在 `ensure_structure` **之前**判 `response.content.strip()`，
为空即抛。顺序不能反。

**防线**：`test_build_rejects_empty_model_output`；`ensure_structure` 的单测里也
专门有一条 `count == 0` 的用例，说明「补结构」本身的正确行为就是这样的。

**推广**：任何「容错补全」函数都会把无效输入变成看起来有效的输出。
判定必须在补全之前做，而且必须有一条测试以空输入覆盖它。

### 8.7 同一语义两处实现：正文归一化

**症状**：`content_sha256` 与 `memory_fingerprint` 各自实现了一遍「归一化后取哈希」，
其中一处保留了连续空格、另一处压掉了，于是同一句话走不同路径会得到不同结论。

**根因**：两个函数都「看起来对」，谁也没有被单独测出问题；错的是它们不相等这件事，
而没有任何用例同时在两条路径上跑同一句话。

**修法**：抽出唯一实现 `app.memory.long_term.normalise_content`（`" ".join(split())`），
`content_sha256` 只是它的包装，`memory_fingerprint` 删除。

**防线**：`test_hash_hit_returns_created_false_and_bumps_hit_count` 用「首尾空格不同」
的同一句话断言 `created=False`；`test_merge_recomputes_content_hash` 断言合并后
哈希索引指向新正文。

**测试侧的坑**：归一化**不会**压掉中间的连续空格（`" ".join("a  b".split()) == "a b"`），
所以「同一句话」的用例必须用**首尾**空白构造，不能用中间双空格——后者是两条不同记忆。

**推广**：与 2.1 同一条原则：**共享一个实现，而不是共享一个约定**。

### 8.8 疑问句的判定条件写得太严

**症状**：抽取器把「用户是不是想了解 X」这样的痕迹写进了长期记忆，而
`docs/07` §5.1 明确要求「疑问句 MUST NOT 抽取」。

**根因**：`_QUESTION_PATTERNS` 里的多字疑问词（`是不是` / `能不能` / `有没有` …）
要求后面必须跟 `？`。而模型在改写时会把疑问句改成**第三人称陈述句**并去掉标点，
于是这些候选全都绕过了过滤。

**修法**：多字疑问词不要求标点即可命中，另外保留 `(吗|呢)\s*[?？]?\s*$` 这条
「句尾语气词」规则兜住「……吗」的改写。

**防线**：`tests/unit/test_memory_extractor.py` 里有 32 条用例，其中疑问句是
按「带标点 / 不带标点 / 句尾语气词」三类分别覆盖的。

**推广**：过滤规则要按**下游可能产生什么形态**来写，而不是按「用户原文长什么样」。

### 8.9 过滤顺序：敏感凭证必须最先判

**症状**：被测模型给出的候选 `{"content": "我的密码是 xxx", "confidence": 0.2}` 被
判成 `low_confidence` 而不是 `sensitive`——结论是对的，但原因写错了，
排障时会去调阈值而不是去查泄露。

**修法**：`rejection_reason` 的判定顺序固定为
**敏感凭证 → 太短/太长 → 疑问句 → 推测 → 一次性 → 置信度**。

**为什么要定死顺序**：一个候选可能同时命中多条规则，此时「先判哪条」决定了
日志、错误说明与后续调优方向。安全类规则必须最先，因为它是唯一的**硬约束**
（其余都是质量偏好）。

**防线**：`tests/unit/test_memory_extractor.py::test_sensitive_candidate_rejected_first`
等多条用例显式断言「原因字符串」。

### 8.10 零向量查询与维度不符的静默成功

**症状（零向量）**：`search()` 返回了一串 `score=0.0` 的命中，调用方以为「检索成功、
只是分数低」，于是上下文里多了几条毫不相关的记忆。

**症状（维度不符）**：内存索引照收 8 维向量，而配置里是 1024 维——本地全绿，
上 Milvus 才写不进去。

**修法**：`search` 遇到零向量（`|q| == 0`）直接返回 `[]`；`upsert` 校验维度并抛
`ValueError`，与 Milvus 的行为对齐。

**防线**：`test_search_empty_query_returns_nothing`（空/空白 query 不检索）+
`test_memory_vector_index.py` 的维度用例。契约测试里脚本向量的维度由
`DIM = 1024` 显式对齐 `embedding_dim`，写错就会在 upsert 当场炸。

**推广**：「返回空」与「返回一批低分结果」在监控上是两回事。前者可观测，
后者会伪装成成功。

### 8.11 锁的释放必须是 compare-and-delete

**症状**：并发写同一会话时偶尔交错，两个请求都写进了上下文（`RPUSH` 顺序错乱）。

**根因**：直觉写法是「`GET` 看是不是自己的 token，是就 `DEL`」。但锁可能**刚好在
这两步之间超时并被别人重新持有**，此时 `DEL` 删掉的是别人的锁 —— 两个写者同时
进入临界区，正是锁要防的事。

**修法**：释放走 Lua 脚本，在 Redis 侧原子完成「值等于自己的 token 才删」。

**防线**：`test_lock_release_uses_compare_and_delete`（断言发的是 Lua 且带 token）与
`test_lock_release_does_not_delete_foreign_token`（token 已被别人改掉时不许删）。

**推广**：「检查 + 动作」跨两步就一定会被并发打断。凡是这类组合，找到能一次原子
完成的原语（Lua / `SET NX` / `WATCH`）——找不到就说明方案本身有问题。

### 8.12 `real` 后端不许静默退化成内存

**症状（如果按直觉实现）**：`INFRA_BACKEND=real` 但 Redis 驱动缺失时退回内存实现。
单进程里一切正常，多副本部署后表现为「同一个会话换一个实例就丢上下文」。

**修法**：`build_conversation_store` 在 `real` 下构造失败时返回
`UnavailableConversationStore`，调用点抛 `503 DEPENDENCY_UNAVAILABLE`；
`ChatService` 把读取失败降级为 `memory_unavailable`（只丢上下文，对话照常）。

**为什么要显式选择「报 503」**：`docs/10` 把「依赖连不上」定义为**运行期故障**，
由 `/health/ready` 表达；构造期抛异常会让「对话/鉴权/健康检查」一起不可用。

**防线**：`tests/unit/test_memory_redis_store.py` 覆盖 `RedisUnavailable` 的
`code` 与 `hint`（`uv add redis`），并有一条「驱动缺失时的提示」用例。

**推广**：降级可以退化**功能**（没有上下文），但不能退化**架构**（单个实例的
内存状态）。前者用户能感知并接受，后者只会在扩容那天暴露。

### 8.13 命名撞上内建泛型：方法叫 `list` 的代价

**症状**：`mypy app` 报 `valid-type`：`"list" is not valid as a type`，
指向类里另一处 `-> list[MemoryRecord]` 注解。

**根因**：`MemoryRepo` 与 `InMemoryMemoryRepo` 里定义了 `list(...)` 方法，
它在**类体作用域**内遮蔽了内建 `list`，于是同一类里所有 `list[X]` 注解都解析到
了那个方法。

**修法**：方法改名 `list_page`。

**防线**：`mypy app`（0 error 门禁）。

**推广**：不要用内建名当方法名/类属性名（`list` / `dict` / `id` / `type` / `input`）。
这个坑的代价不是「运行时报错」，而是「注解系统悄悄换了含义」。

### 8.14 合并时把旧哈希一起带上

**症状**：语义去重命中后「把新正文合并进旧记录」，之后再用**原来的正文**写一次，
会被判定为重复而静默丢弃——唯一索引指向的是合并**之前**的哈希。

**根因**：`dataclasses.replace(record, content=..., ...)` 会把未显式覆盖的字段
（包括 `content_sha256`）一起拷过去；而 `__post_init__` 只在字段为空时才推导哈希。

**修法**：合并时显式重算 `content_sha256=content_sha256(new_content)`。

**防线**：`test_merge_recomputes_content_hash` 断言「新正文能按哈希查到、旧正文查不到」。

**推广**：任何「派生字段」（哈希、长度、归一化结果、冗余索引键）都必须在该字段
**源字段变化的所有路径**上重算。`replace` 这类「拷贝 + 覆写」的工具最容易漏掉它们。

### 8.15 测试侧：五条记忆全指向同一个方向

**症状（写作过程中真实发生）**：`AC-MEM-08` 的用例想验证「`top_n` 最多注入 3 条」，
写 5 条记忆后断言却只拿到 1 条，看起来像实现漏了。

**根因**：脚本化的向量化替身对**未登记的文本**统一返回同一个向量，5 条记忆两两
相似度为 1.0，被语义去重（阈值 0.92）正确合并成 1 条。**实现是对的，断言是错的。**

**修法**：替身改为「未登记的文本按首次出现顺序分配到互相正交的轴」，于是
「多条相似但不等价」可以被精确构造；需要相似度时显式指定
（`blend(axis, 0.95)`）。

**推广**：替身的**默认行为**会被当成「数据的样子」。默认值不该制造现实中不存在的
巧合（这里是「所有文本都同义」）。

### 8.16 工具参数名与 SRS 不一致：`top_n` vs `top_k`

**症状（收尾自查时发现）**：`docs/04` §3 写的是 `memory_search(top_k:int=3)`，
实现里字段叫 `top_n`。两者都「能跑」，但把工具定义序列化给上游后，
模型看到的参数名与 SRS 不符 —— 以后照文档写的调用方会踩空。

**根因**：`app/services/memory.py` 的 `search(..., top_n=...)` 用的是**配置项**的名字
（`MEMORY_TOP_N`），照着服务层写工具参数就顺手带上了 `top_n`。但工具层已有自己的
惯用名：同一张表里 `kb_retrieve` 就是 `top_k` / `rerank_top_n`。

**修法**：工具参数改为 `top_k`（内部照旧传 `top_n=`），并在字段上留注释说明
「与工具层惯用名一致」。

**推广**：**服务层的内部命名不是对外契约**。工具参数/接口字段一律回 SRS 抄一遍，
不要从相邻的服务方法签名「顺着写」。

### 8.17 工具返回少了 SRS 要求的字段

**症状**：`docs/04` §3 要求 `memory_search` 返回
`{memories:[{mem_id,content,kind,score}]}`，实现只回了 `content` 与 `score`。
模型因此拿不到 `mem_id`，无法在后续 `PATCH /memories/{id}` 或工具调用里指代某一条。

**根因**：`MemoryItem`（上下文装配用的检索结果）当初只定义了 `content` / `score` ——
装配只需要这两项，工具需要的另外两项「没地方放」，就顺手省略了。

**修法**：给 `MemoryItem` 补上 `mem_id` / `kind`（装配侧忽略），并加断言钉住键集合
（`set(hit) == {"mem_id","content","kind","score"}`）—— 用集合相等而不是逐个取值，
少一个字段就会红。

**推广**：**内部结构体只装「当时用得上」的字段，是一种会外溢的省略**。
一旦它被当成对外结构复用，缺字段就会变成契约破洞；补字段时把断言写成「集合相等」，
而不是「取某个键」。

## 9. 小结：M1–M5 的八条可复用原则

1. **谁定义语义，谁负责填字段**（3.6 的 `vector_score`）。让下游"记得填"就是留坑。
2. **共享一个实现，而不是共享一个约定**（2.1 的游标原语、8.7 的归一化）。
   两个地方各自实现同一语义，迟早分叉。
3. **静默返回是 bug 的温床**（3.8 的 `if status is not PENDING: return`、
   8.2 的幂等键撞车、8.4 的 `messages[:-0]`）。条件不满足时必须留下可观测痕迹。
4. **测试环境的配置要贴近生产**（4.1 的日志级别）。测试里关掉的开关，
   等于那部分代码从未被执行。
5. **能在同步阶段给出的错误不要拖进异步**（5.2）。也适用于「工具参数校验：
   作为可回复的工具结果返回给模型，而不是 500」（见 [04](./04-Agent与工具调用.md) §5）。
6. **护栏必须有一条专门证明「它拦住了」的测试**（7.1–7.3）。
   没有这条测试的护栏，等于没有护栏——尤其当替身比真实上游更宽松时。
   具体做法：「把护栏拿掉，这条测试会不会变红？」
   **这条对数据库约束同样成立**：`uk_kb_user_name` 曾建在含 `deleted_at` 的列上，
   而唯一索引不比较 `NULL` —— 该约束一次也不会触发，且没有任何测试会发现（见 10.1）。
7. **旁路动作要按「入口 × 路径」清点**（8.1 的收尾动作只接在流式路径、
   8.3 的防抖被记成失败）。凡是不影响响应结果的逻辑，都必须在**每一个入口**
   上有一条断言，否则它就是「部分流量上生效」。
8. **对外契约（工具参数 / 接口字段）一律回 SRS 抄，不从相邻服务方法签名顺着写**
   （8.16 的 `top_n` vs `top_k`、8.17 的缺字段）。内部命名服从实现便利，
   对外命名服从文档；两者混用就会在「文档能用」与「代码能用」之间裂开一道缝，
   而这道缝只在别人照文档调用时才暴露。

## 10. MySQL 建表脚本落地（M6 前置）

M5 的长期记忆仓储仍是进程内实现（`real` 下返回 `503` 占位），要补 MySQL 仓储就得先把表建出来。
`docs/09-§2` 的 DDL 已固化为 `deploy/mysql/001_init_schema.sql`；落地时发现三类问题，
它们都**不会**在「照着文档写代码」时暴露。

### 10.1 唯一索引不比较 `NULL`：约束从未生效过

**症状**：自检脚本里「插入第二条同名知识库应当失败」这一步返回 `ROW_COUNT() = 1`，
即**插入成功了**。

**根因**：`uk_kb_user_name (user_id, name, deleted_at)`。MySQL 的唯一索引把 `NULL`
视为互不相等，而未删除的行 `deleted_at` 全是 `NULL`，于是 `(u_x, 手册库, NULL)` 可以存在
任意多份。文档注解写的是「软删记录保留 30 天后物理删除」，显然期望「只有一条未删除的同名」——
但这条约束**一次也不会触发**。

`document.uk_doc_dedupe (kb_id, content_sha256)` 是同一个坑的镜像：它不含 `deleted_at`，
于是软删后同一文件永远传不回来（列表里看不见那条已删记录，只收到「文件已存在」）。

**修法**：加一个把 NULL 映射成哨兵时刻的生成列，让两条语义同时成立：

```sql
deleted_key DATETIME(3) GENERATED ALWAYS AS (IFNULL(deleted_at, '1970-01-01 00:00:00.000')) STORED,
UNIQUE KEY uk_kb_user_name (user_id, name, deleted_key)
```

**防线**：`deploy/mysql/verify_schema.sql` 用 `INSERT IGNORE` + `ROW_COUNT()` 断言
「未删冲突 / 软删后重建」，期望值 `1/0/1`（知识库）与 `1/0/1`（文档）。
用 `INSERT IGNORE` 而不是「期望报错」，是为了让**预期的冲突**与**真正的失败**不同形：
脚本任何一行出现 `ERROR` 就说明真出事了。

**推广**：见 §9 第 6 条 —— 护栏要有「证明它拦住了」的验证，这条对**数据库约束**同样成立。

### 10.2 SRS 的表格漏了实现必需的列

`docs/09-§2.8` 的 `user_settings` 只列了 `user_id` / `memory_enabled` / `memory_top_n` /
`updated_at`，而 `REQ-MEM-007` 的「清空后 24h 不再抽取」需要持久化
`MemoryPreference.cleared_at` —— 没有这列，`real` 后端下冷静期只能存在进程内存里，
重启即失效（表现：用户删了记忆，重启后旧偏好又被抽回来）。

**修法**：建表脚本加 `cleared_at`，并同步回 `docs/09`（§9 第 8 条：文档是契约，
表格漏列要改文档，而不是让实现偷偷多一列）。

**推广**：建表阶段必做「SRS 表格 ↻ 代码实体逐字段对账」。表格里写「关键列」的地方
最容易漏的就是那种「只在某个分支里用到」的列（本例：只在清空后的 24h 内用到）。

### 10.3 把 SQL 交给 mysql 时的两个环境坑

* **不要用管道与中文路径**。`Get-Content x.sql | mysql` 会经过 PowerShell 的编码转换；
  同时**路径里的中文**会被 mysql 客户端按 ANSI 解释 —— 实测 `作品集` 被解成
  `浣滃搧闆哱`，报 `Failed to open file ... error: 2`。
  正解：把脚本复制到 ASCII 路径（如 `$env:TEMP`），再用客户端自带的
  `-e "source <路径>"` —— 文件由 mysql 自己读，完全不经过 shell 的字符串/管道层。
* **顺手验一次「执行的就是仓库里的那份」**：复制后用 `Get-FileHash` 两边对一下。
  不验的话，「在临时目录改了一版、忘了同步回仓库」会表现为假绿。

**推广**：凡是要把文件交给**外部可执行程序**读取的场合（mysql / psql / 解释器），
一律绕开 shell 的字符串与管道层，改成「程序自己读文件」。

### 10.4 两个服务同库：同名的表只能有一份定义

* **背景**：`idempotency_record` / `audit_log` 两边都在用，原本是**同名不同列**的两张表
  （网关多 `method` / `request_hash` / `ip` / `user_agent`），因此早期结论是「必须分库」。
  改成两个服务共用一个库之后，这个前提变了：**同库同名只能有一张表**。
* **最隐蔽的一点**：两份 DDL 都带 `IF NOT EXISTS`，所以第二个 `CREATE TABLE` 会
  **静默跳过** —— 两个脚本都报成功，实际用的是先建好的那一张。
  「表看起来建好了」与「表的列对得上」是两件事，而幂等 DDL 只保证前者的后半句：
  *不报错*。
* **根因**：把「表名相同」当成「表相同」。只要两边的列集合不同，
  它们就是两张需要被收敛的表，与在不在一个 schema 里无关。
* **修法**：共享表只定义一处（AI 侧的 `001_init_schema.sql`，也是库的 owner），
  取**并集**；网关独有的四列给 `DEFAULT ''` / `NULL`，让本服务不填也能插入
  （否则「共用的表」会变成「共用的表 + 本服务写入报错」）。
  网关侧脚本只留一段注释声明依赖，不再 `CREATE`。
* **已经建过旧库的要额外一步**：`002_align_shared_tables.sql` —— `IF NOT EXISTS` 对
  **已存在**的表是空操作，它不会补列。这一步容易被漏掉，因为新库测试完全正常。
* **防线**：两份自检脚本各自断言
  `shared_extra_columns_must_be_4`（四列在位）与 `uk_idem_columns_must_be_4`
  （唯一键已含 `method`）；网关侧还断言单库表集合（`gateway_tables_total_must_be_6` /
  `total_tables_must_be_15`）。
* **同一个道理也适用于 ID 前缀**：网关签发 `u_` / `rt_`，而前缀集合在
  `app/core/ids.py::ID_PREFIXES`（与 `docs/02` §1）里。「每组自己维护前缀表」的结果是
  网关新增前缀时本侧认不出来 —— 所以这**两个本服务不生成的前缀也定义在同一处**。

**推广**：**幂等的 DDL 只保证「不报错」，不保证「结构正确」**。
凡是「应该已存在」的对象（表、列、索引、前缀集合），都要单独断言其结构，
否则旧库与新库会长成两个样子，而两边跑起来都不报错。

## 11. M6（MCP 与可观测性）新增问题

M6 的两块内容（接外部 MCP Server / 埋指标与链路）有一个共同点：**错误的表现都不是异常，
而是「数字不对」或「链路断了一截」**。下面 11.1 与 11.2 两条都是「代码看起来完全正常、
测试只差一个断言」的类型。

### 11.1 `try: return ... / else:` 里的 `else` **永远不执行** → 熔断器只记得住失败

**症状**：单测里「半开探测成功后熔断器应当复位」失败，`failure_count` 停在 2 而不是 0；
表现到生产上就是 —— 某条链路一旦熔断打开，**永远回不到 `closed`**，该 Server 永久不可用。

**根因**（最容易看走眼的一处 Python 语义）：

```python
try:
    result = await self._call_with_reconnect(tool, arguments)
except AppError:
    self._breaker.record_failure()
    raise
else:
    self._breaker.record_success()  # ← 永远不会执行
return result
```

我最初写的是 `try: return await ...` + `else: record_success()`。直觉上「没有异常走到 `else`」——
但 `else` 子句的触发条件是 **`try` 块「自然落到末尾」**，而 `return` 是**立即开始栈展开**，
两者互斥。也就是说：只要 `try` 块里有 `return`，同一个 `try` 的 `else` 就是死代码。

**修法**：把 `record_success()` 移出 `else`，在 `return` 之前**平铺**写：

```python
    if self._breaker is not None:
        self._breaker.record_success()
    return result
```

**防线**：`tests/unit/test_mcp_manager.py::test_half_open_success_recovers_the_server`
（假时钟推进 31s → 半开 → 成功 → 断言回到 `closed` 且 `failure_count == 0`）。
**光有「失败会打开」的测试抓不到它** —— 必须有一条「成功后要回到 closed」的反向断言。

**推广**：写完之后**扫一遍**所有 `try/else` 组合。当时用 AST 脚本扫了 `app/` 与 `tests/`
（`ast.Try` 有 `orelse` 且 body 里含 `return`）确认只有这一处。这条已经记进
[10-§3.2](./10-非功能需求与可观测性.md)。

### 11.2 `endpoint` 标签退化成 `/live`：FastAPI 0.141 起 `include_router` 不再扁平化路由

**症状**：契约测试里断言 `ai_requests_total{endpoint="GET /api/v1/health/live"}` 取不到值，
把渲染结果打出来才发现真实标签是 **`GET /live`**。

**根因**：原来的实现是 `scope["route"].path`。这条在旧版 FastAPI（把子路由**复制**进父路由表）
下是对的，但 0.141.1 的路由表里放的是 `_IncludedRouter` 节点，匹配后写回 scope 的
`scope["route"]` 是**最内层**那条路由（`/live`），`/api/v1` 与 `/health` 两层前缀全丢了。

危害不是「少两个字符」：**不同模块下同名的 `/live` 会撞进同一个标签**，看板上的
QPS/延迟是两条接口的混合值，而且排障时根本看不出是哪个接口。

**修法**：完整模板只有 FastAPI 的「有效路由上下文」里有，于是逐级降级：

1. `scope["fastapi"]["effective_route_context"].path` —— 实测拿到的是
   `/api/v1/knowledge-bases/{kb_id}`（占位符**没有**被实例值替换，正好是我们要的模板）；
2. 退回 `scope["route"].path`（未嵌套注册时它就是完整模板）；
3. 都没有 → `unmatched`（404）。

两个 scope 键名都不是公开 API，所以取值全部走 `getattr` / 类型检查，**坏数据只会降级、不会让请求 500**。

**防线**：`tests/unit/test_route_template.py`（六个分支，含 `fastapi` 键被写成字符串/
上下文没有 `path` 等坏数据）；契约侧
`tests/contract/test_observability.py::test_path_parameters_are_not_used_as_labels`
断言 `endpoint="GET /api/v1/knowledge-bases/{kb_id}"` 且渲染文本里**不出现**真实 `kb_id`。

**推广**：**「取路由模板」是框架内部知识的活**，写的时候一定要有一条「标签里不能出现真实参数值」
的断言；只断言「标签是字符串」等于没断言。

### 11.3 同一个调用被记两次 → `ai_tool_calls_total` 翻倍

**症状**：写 MCP 适配器时顺手把工具调用计数也写在适配器里，结果是同一个调用被记两遍 ——
`ai_tool_calls_total{source="mcp"}` 按 2 递增，看板上的工具调用量**全部偏大一倍**
（没有异常、没有日志，只有数字不对）。

**根因**：适配器（`app/mcp/tools.py`）与统一执行器（`app/tools/executor.py`）
各记了一遍。两处都「看起来该由自己记」——适配器知道 `mcp_server`，执行器知道 `status`。

**修法**：定死**只有一个来源**：执行器记 `ai_tool_calls_total`，适配器只负责返回结果
（`status` / `payload.error`）。适配器里不再记任何指标，并在原处留注释说明原因。

**防线**：`tests/unit/test_mcp_tool.py::test_synced_tools_work_through_the_tool_executor`
在真实执行器链路上断言 `ai_tool_calls_total{source="mcp",...,tool_name=...}` **恰好为 1.0**，
且不存在同一序列的 `2.0` —— 「记了指标」与「只记一次」是两条不同的断言。

**推广**：「埋点」与「业务逻辑」一样要遵守单一职责。凡是**能在统一入口记的指标，
不要在分叉出去的实现里再记一遍**；分叉处只允许补充统一入口拿不到的字段（这里用 `source="mcp"` 表达）。

### 11.4 OTel 的 `TracerProvider` 是**进程单例**：第二次 `set_tracer_provider` 被静默忽略

**症状**：测试里造第二个应用（或第二次调 `setup_tracing`）后，span 全丢，
控制台只有一句 `Overriding of current TracerProvider is not allowed`。

**根因**：OTel 的 `set_tracer_provider` **只能生效一次**，之后再调用只是打日志、并**丢弃**后来者的 span。
而我们一个进程里会有多个 `FastAPI` 实例（测试常态）。

**修法**（`app/observability/tracing.py`）：

- `_resolve_provider()` 复用已存在的 SDK provider，而不是无脑 `set_tracer_provider`；
- `_EXPORTER_MARKER` 防止给同一个 provider 挂第二个 OTLP exporter（否则 span 会被导出两遍）；
- `_provider_owned` 标记「这个 provider 是我们建的」，只有自己建的才在 `shutdown_tracing()` 里关。

**推广**：凡是对接**全局单例**的第三方 SDK（OTel provider、日志 root logger、
`prometheus_client` 默认注册表），都要先问「一个进程里会不会有第二个实例」——
会的话就得写「复用 or 自建」的判断。顺带：`Metrics` 也是这么处理的，
每个实例自带 `CollectorRegistry()`，否则同名指标第二次注册直接抛
`Duplicated timeseries in CollectorRegistry`。

### 11.5 `METRICS_PORT=0` 被当成「关闭指标端口」

**症状**：契约测试里 `app.state.metrics_server_ready` 根本不存在（`AttributeError`）——
端口服务压根没启动。

**根因**：`if settings.metrics_enabled and settings.metrics_port > 0:`。
`MetricsServer.start()` 明明支持「端口 0 = 由 OS 分配」（它的单元测试就在用），
但调用方用 `> 0` 把它过滤掉了。而 `.env.example` 里写的正是
「`METRICS_PORT=0` 表示由操作系统随机分配端口」。

**修法**：开关只有 `METRICS_ENABLED` 一个，端口 0 照常启动；
并在启动成功后打一条 `app.metrics_ready` 日志带**实际**端口（配成 0 时只能从这里知道去哪抓）。

**防线**：`tests/contract/test_observability.py::test_standalone_port_serves_prometheus_text`
真的去 `http://127.0.0.1:{server.port}/metrics` 抓一次并断言 200 —— 「对象存在」
与「端口真的在监听」是两件事。

**推广**：**「0」在配置语义里几乎总是「自动/随机」，不是「关闭」**；
一个布尔开关负责开关，数值项负责取值，两者别混用（同类的还有 `limit=0`、`timeout=0`）。

### 11.6 `mcp` 2.2.0 的两个 API 变化：返回值个数与「没有 headers 参数」

**症状**：① `streamable_http_client(url, headers=..., timeout=...)` 直接
`TypeError: unexpected keyword argument`；② 解包 `read, write = streamable_http_client(url)`
报 `too many values to unpack`。

**根因**：2.2.0 里 `streamable_http_client(url, *, http_client=None, terminate_on_close=True)`
—— **没有** `headers` / `timeout` 参数，且 `asynccontextmanager` **yield 两个值**。
鉴权头与超时只能通过自建 `httpx2.AsyncClient(headers=..., timeout=...)` 传进去；
stdio 侧的 `StdioServerParameters(command, args, env)` + `ClientSession(read, write_stream)`
则未变。

**修法**：`app/mcp/session.py` 里 `_http_session()` 自建 client；
`open_session()` 统一两种 transport 的上下文，对上层只暴露
`list_tools()` / `call_tool()` 两个方法（业务代码不认识 SDK 类型）。

**推广**：第三方 SDK 的**小版本**也可能改签名。接入前先
`inspect.signature(...)` 打印一次真实签名（比翻文档快且不会过期），
然后把不确定的部分收在一个适配层里 —— 换版本时只改一个文件。

### 11.7 slots dataclass 没有 `__dict__`：`asdict()` 与只读属性

**症状**：① 把 `McpServerStatus`（`@dataclass(slots=True)`）直接丢进响应体，
序列化报缺 `__dict__`；② `monkeypatch.setattr(tool, "invoke", ...)` 报
`AttributeError: 'McpTool' object attribute 'invoke' is read-only`。

**根因**：`slots=True` 的实例只有槽位、没有 `__dict__`，
pydantic/FastAPI 的默认序列化路径和 `vars()` 都用不了；
而且槽位描述符**不允许**覆盖实例属性（连 `monkeypatch` 也改不动）。

**修法**：① 显式 `dataclasses.asdict(...)`；② 测试不再改方法，
改成改**它唯一的外部依赖**（`monkeypatch.setattr(client, "call_tool", ...)`）——
这反而把「适配器只通过 `client.call_tool` 与外界交互」这个设计约束固化成了测试。

**推广**：**测试改不动的东西，往往是设计边界所在**。被 `setattr` 挡住时不要绕道去改内部字段，
先问「为什么它不可变」——通常意味着应该改它的依赖。

### 11.8 替身不能模拟「连接正常但调用失败」→ 断言错了对象

**症状**：想验「调用失败会触发重连」时，测试拿到的是 `MCP_SERVER_UNAVAILABLE`
（连接不可用），与预期错误不一致。

**根因**：替身只有 `fail_connect=True` 一个开关。调用前的重连检查先失败，
于是流程停在「连接不可用」，**根本没走到** `call_tool` 失败那条分支。

**修法**：补一个 `fail_calls` 开关，在 `_FakeSession.call_tool` 里抛
`RuntimeError("stream closed")`；连接阶段保持正常。

**推广**：编写故障替身时，**按「故障发生的阶段」而不是「好坏」来划分开关**
（建连 / 握手 / 列表 / 调用 / 收尾）。只有一个 `fail=True` 的替身，
测试会退化成「反正会失败」，分支覆盖是假的。

### 11.9 空元组 ≠ 无退避：`RECONNECT_DELAYS = ()` 让重连永不成功

**症状**：加了「测试里不 sleep」的 fixture（`monkeypatch.setattr(client_module, "RECONNECT_DELAYS", ())`）后，
一批本应重连成功的用例开始失败。

**根因**：`_reconnect()` 的语义是「按延迟表逐个尝试，**任一次成功即成功**」。
空元组 = 一次都不试 = 永远返回 `False`。测试为了「快」把这个列表清空了，
却顺手把被测能力也删掉了。

**修法**：改成 `(0.0,)` —— **保留一次零延迟尝试**。「不等待」与「不重试」是两件事。

**推广**：缩短时间类测试的手段（假时钟、零延迟）都必须**保持调用次数不变**。
凡是「为了测试而改常量」，都要检查这个常量是否同时参与了控制流。

### 11.10 测试里两个应用抢同一个指标端口

**症状**：偶尔出现 `metrics.server_failed`（binds 失败）警告，且成组出现。

**根因**：测试基线配置里 `metrics_port` 用的是默认值 9100，
同一进程里先后建的应用都想绑它（上一个还没 `stop()`）。
这类失败**不阻断启动**（正确设计），所以它只会以一条警告的形式出现 —— 很容易被忽略成噪声。

**修法**：测试基线里改 `metrics_port: 0`（配合 11.5 的修复，现在真的会走随机端口），
既避开冲突、又仍然走真实的「bind + listen」代码路径。

**推广**：「不影响功能的后台能力」在测试里最容易变成噪声源。
定点修法是让它**可控**（随机端口 / 可注入时钟），而不是把断言放宽。

### 11.11 OTel 测试的 fixture 顺序：`ProxyTracerProvider` 没有 `add_span_processor`

**症状**：`InMemorySpanExporter` 装不上，报 `AttributeError: 'ProxyTracerProvider' object has no attribute 'add_span_processor'`，
四个用例集体 error。

**根因**：`trace.get_tracer_provider()` 在**没有任何 `TracerProvider` 被设置过**时返回的是
`ProxyTracerProvider`（一个空代理）。fixture 直接去 `get_tracer_provider().add_span_processor(...)`，
于是打到代理上。必须先有一次 `setup_tracing()` 把真正的 SDK provider 装上。

**修法**：拆成链式 fixture：`session_tracing`（调 `setup_tracing`）
→ `exporter`（依赖前者再挂 `SimpleSpanProcessor`）→ `enabled_tracing`。
依赖图即顺序，不靠「pytest 恰好先跑哪个」。

**推广**：**用 fixture 依赖表达前置条件，别用注释表达**。凡是「必须先初始化 A 才能做 B」的地方，
让 B 的 fixture 声明 `(A)`，缺失时 pytest 会直接报错而不是给出奇怪的运行时异常。

### 11.12 「严格模型」其实不严格：`StrictModel` 用的是 `extra="ignore"`

**症状**：契约测试断言「`POST /mcp/servers/fs/reload` 多传一个字段应返回 422」，
实测返回 200。

**根因**：项目里的 `StrictModel`（`app/schemas/common.py`）刻意配置了
`extra="ignore"` —— 客户端多传字段（例如旧版本遗留的 camelCase）不该让调用整体失败。
**而真正需要「写错就报错」的是 MCP 配置**，那一层用的是 `extra="forbid"`（`REQ-MCP-001`）。
两者不是一套规则，测试把「严格」这个词想当然了。

**修法**：改测试而非改实现（回 SRS：`docs/02` 只要求未知字段被忽略；
`docs/05-§2.2` 才要求 MCP 配置拒绝未知字段），并把「为什么忽略」写进测试 docstring。

**推广**：见 §9 第 4 条与 5.4 —— **测试假设与 SRS 不符时，先改测试**。
但必须先回文档确认**哪一边是对的**，不能因为「改测试更快」就改测试。

### 11.13 目标 `up`、样本 678 条，却没有一个 `ai_*` 指标

**症状**：本地按 README 起完整套件后，Prometheus 的 `ai-platform` job 显示 `up`、
`scrape_samples_scraped` 有 678 条，但查 `{__name__=~"ai_.*"}` **一条都没有**，
Grafana 看板全空。

**根因**：本机 **9100 端口上常驻着另一个 Go exporter**，于是

1. 应用侧 `MetricsServer.start()` 绑定失败 → 只记 `metrics.server_failed` 警告
   （这是**正确**的设计：指标不该阻断启动）；
2. Prometheus 照旧去抓 `host.docker.internal:9100`，那个端口**有东西在应答**，
   于是 HTTP 200、target `up`、样本数 678 —— 全是别人的 `go_*` / `node_*` 指标。

**最误导的一点**：整条链路上**没有任何一处报错**。`up` 是「抓取成功」的意思，
**不是**「抓到了我们的指标」的意思。

**修法 / 排查手段**：`METRICS_PORT` 与 `prometheus.yml` 的 `targets` 必须是同一个端口；
判断「抓到的到底是不是我们」只看**哨兵指标 `ai_build_info`**
（常量 1，专为「确认指标端点活着且是我们」而存在）：

```powershell
curl.exe -s "http://localhost:9090/api/v1/label/__name__/values" | Select-String "ai_build_info"
```

**防线**：应用启动日志里 `app.metrics_ready port=<实际端口>` 与
`metrics.server_failed port=...` 成对出现，一眼能看出「没起来」；
契约测试则直接对独立端口抓一次并要求 200 + `ai_build`。

**推广**：**「探针成功」≠「探到的是对的东西」**。凡是要跨进程/跨网络确认「对面是谁」的地方，
都要有一个**只有我们能提供的标识**（哨兵指标、响应头、`/health` 里的 `service` 字段），
并且断言这个标识，而不是断言「连接成功」。同类的坑：健康检查 200 但连到了别的服务、
DNS 指到旧集群。

### 11.14 小结

M6 这 13 条里，真正的「业务 bug」只有 11.1（熔断器回不到 closed）与 11.3（指标翻倍）；
其余都是**「断言写得太弱」或「框架知识过期」**：

1. **反向断言**比正向断言值钱（11.1：失败会打开 ≠ 成功会恢复）；
2. **框架内部知识的活（路由模板、全局单例、SDK 签名）必须显式测**（11.2 / 11.4 / 11.6）；
3. **配置项的类型语义要写进文档**（11.5：「0 = 随机」不是「关闭」）；
4. **为了测试而改的常量不能顺带改控制流**（11.9）；
5. **fixture 依赖图即前置条件**（11.11），**替身按阶段划分故障开关**（11.8）；
6. **测试假设与实现冲突时回 SRS 判方向**（11.12）；
7. **「连接/探针成功」≠「对面是对的东西」**，要拿**只有我们能提供的唯一标识**去断言（11.13）。
   M6 里最后一处真正的发现正是它：本地套件跑通后看板全空，而链路上**没有任何一处报错**。

## 12. M7（Kafka 与 Worker）新增问题

M7 的代码（`app/worker/`、`app/tasks/{transport,redis_store,events,retry,compensation,stream}.py`、
`GET /tasks/{id}/events`）写完后配了约 190 条新单测。**其中 8 条一跑就红**，另有 1 条是自己
review 出来的。它们有一个共同特征：**在内存替身上全都「看起来对」** ——
因为内存实现是照着「我理解的语义」写的 Python 代码，而真实现（Redis / Kafka / SSE）
是照着「协议的真实语义」执行。所以这一节的教训统一是：

> **凡是「跨进程 / 跨连接 / 跨时间」的语义，都必须用真实现或可注入时钟的测试去钉住；
> 内存替身上跑绿，只能证明替身自洽。**

### 12.1 用 `-1` 当「未见过」的哨兵，同时它又是合法值 → 静默丢消息

`OffsetTracker`（按分区提交连续水位线）里，`watermark` 的初值是 `int = -1`，
既表示「还没见过任何消息」，又表示「0 号消息之前」。乱序完成时这条判断失效：

```python
# 错：-1 既是「未初始化」又是「合法水位线」
class _PartitionState:
    watermark: int = -1

if state.watermark == position.offset - 1:  # offset=0 时恰好等于 -1，误判为连续
```

后果是「先完成 1 号、再完成 0 号」时水位线**跳过 0**，于是 0 号消息永远不被提交 ——
进程重启后它会被**重新消费一遍**（至少一次语义下不算数据错，但代价是重跑一遍入库）。
若再叠上一层「跳过即视为已处理」，就变成真正的丢消息。

**修法**：用 `None` 表示「未见」，与 `-1` 彻底分开：

```python
watermark: int | None = None
if state.watermark is None:
    state.watermark = position.offset - 1
```

**推广**：**不要把「无效值」放在业务取值域里**。哨兵要么是 `None`/`Optional`，
要么是明确越界的类型（负数当「未知」而 offset 本身可以合法地是 `-1` 时，
就该换 `None`）。每次用「魔法值」当哨兵，都要先问一句：**这个值业务上会出现吗？**

### 12.2 异步生成器的「创建」不等于「订阅已就位」

`stream_task_events` 的第 1 条设计约定是「**先订阅、后读快照**」，否则两次操作之间发布
的事件会永久丢失（`docs/08` §4.5 的进度流会「卡在某个阶段不动」）。代码一开始长这样：

```python
subscription = bus.subscribe(task_id)  # 只是造了个异步生成器对象！
task = await tasks.get(task_id, user_id)  # 这次往返期间的事件全掉在地上
async for event in subscription:
    ...
```

**根因**：异步生成器函数的函数体要到**第一次 `__anext__`** 才执行，所以 `bus.subscribe()`
此刻**什么都没订阅**（Redis 实现的 `SUBSCRIBE` 命令也还没发出去）。Redis 的 `SUBSCRIBE`
本身还要一次往返，这个窗口在真机上几十微秒到几毫秒 —— 恰好是「任务很快就成功了」的时刻。

**修法**：预热一次，让订阅与随后的快照读取重叠：

```python
primed = asyncio.ensure_future(anext(subscription))
await asyncio.sleep(0)  # 让生成器体真正跑起来，SUBSCRIBE 已发出
task = await tasks.get(task_id, user_id)
...
event = await _next_event(subscription, deadline, clock, pending=primed)
```

测试上也留了一条**回归用例**：`test_subscription_is_live_before_snapshot_is_read`
用「读快照时发布一帧」的门闩（gate）证明订阅在快照之前就生效。

**推广**：**异步生成器/协程函数是「惰性对象」**。「我调用了订阅函数」与
「订阅已经生效」是两件事，任何「先登记再读状态」的模式（订阅 → 快照、
注册回调 → 触发、加监听 → 发请求）都要显式确认登记**已经到达对方**。

### 12.3 对「正在运行」的异步生成器 `aclose()` → `RuntimeError`

12.2 的预热引入了新问题：收尾时那个 `primed` 的 `__anext__` 可能还挂着（客户端断连、
任务已终态提前返回）。此时生成器处于「运行中」，直接关它会抛
`RuntimeError: aclose(): asynchronous generator is already running`：

```python
finally:
    # 必须先取消并**等它结束**
    if primed is not None:
        primed.cancel()
        with contextlib.suppress(asyncio.CancelledError, StopAsyncIteration):
            await primed
    await subscription.aclose()
```

**注意 `cancel()` 只是投递取消，不是同步等待**：必须 `await` 那个 future，
否则取消还没进到生成器体内，`aclose()` 依旧撞上「running」（这正是 M2 阶段
`asyncio.wait_for(agen.__anext__())` 那个坑的另一面）。

### 12.4 `asyncio.wait` 被取消时没有转发给业务协程 → 孤儿任务

Worker 的超时控制写成 `done, _ = await asyncio.wait({job}, timeout=self._timeout)`：
**一旦 Worker 自己被取消（收到 SIGTERM），`wait` 抛 `CancelledError`，而被它包着的
`job` 协程还在跑** —— 表现为「关停后 Embedding 请求还在发」，任务状态永远停在 `RUNNING`
（`_handle_failure` 根本没机会执行）。

```python
try:
    done, _ = await asyncio.wait({job}, timeout=self._timeout)
except asyncio.CancelledError:
    job.cancel()
    await asyncio.gather(job, return_exceptions=True)  # 等它真的收尾
    raise
```

**推广**：`asyncio.wait`/`asyncio.shield` **只是等待，不是所有权转移**。
取消自己时一定要显式 `cancel()` + `await` 被包裹的那个任务，否则取消语义会被静默吞掉。

### 12.5 `except CancelledError` 里无条件写终态 → 把「超时失败」改写成「用户取消」

`TaskService.track()` 的取消收尾原本是：

```python
except asyncio.CancelledError:
    await self._safe_transition(task_id, TaskStatus.CANCELED)  # 无条件
    raise
```

而状态机里 `FAILED → CANCELED` 是**合法迁移**（用户可以在失败后取消）。
于是「Worker 超时 → 判 `TASK_TIMEOUT` FAILED → 取消执行协程」这条路径上，
刚写好的失败被覆盖成 `CANCELED`：用户看到一个**自己从没取消过的**「已取消」任务，
错误详情里却写着「任务执行超时」。

**修法**（`_cancel_or_keep`）按证据判断：存储里有取消标记 → 确实是取消；
没标记但仍是 `RUNNING` → 没人负责收尾，兜底落 `CANCELED`；其余情况**保留现有状态**。

**推广**：**「先写终态、再决定是否覆盖」的顺序天然危险**。凡是收尾逻辑，
都要问「此刻的权威状态是什么？我凭什么覆盖它？」——判据要来自**外部证据**
（取消标记）而不是「我为什么会走到这个分支」。

### 12.6 内存实现的 `close()` 清空数据，Redis 实现不清 → 关停即丢排期

`InMemoryRetryQueue.close()` 把待重试条目一起清了，而 `RedisRetryQueue.close()`
只关连接（ZSET 里的排期还在）。二者语义不一致的后果：**用内存后端时，
一次优雅重启就把所有等待退避的任务丢掉了**（状态还停在 `QUEUED`，
要靠补偿扫描在 30s 后才捡回来，期间用户看到的是「排队中」）。

**修法**：`close()` 的语义定为「释放资源，**不动业务数据**」，内存实现改成 no-op，
并把这条写进 docstring。测试 `test_close_keeps_pending_entries` 钉住。

**推广**：**替身与真实现的「资源释放语义」也要对齐**，不只是方法签名。
`close()`/`reset()`/`clear()` 这类名字在两边含义不同的地方，最容易在重启时丢数据。

### 12.7 一条脏数据让整个补偿扫描停摆

`list_stale_pending()` 用 `cursor_position(task.created_at, task.id) < cutoff` 排序与过滤，
而 `cursor_position` 会 `datetime.fromisoformat`。只要**有一条**任务的 `created_at`
是坏的（老版本写入、外部脚本改库），整次扫描就抛 `ValueError` ——
补偿器的 `run_forever` 虽然有 try/except，但**这一轮所有滞留任务都没被重投**，
而且每 30 秒重复失败一次，日志是稳定的「扫描出错」，看起来像「没有滞留任务」。

**修法**：坏值不再抛，而是当作「**最老**」参与排序、并**算作滞留**（`_sort_key` /
`_before_or_unparsable`），让补偿器把这条脏数据也捞出来处理掉；同时它仍有
`max_attempts` 上限兜底。

**推广**：**扫描/批处理必须对单条脏数据免疫**。判据是「一条坏数据会不会让整批无产出」——
如果是，就必须让坏数据走「尽力而为」的路径（多尝试、进死信/人工队列），
而不是让异常中断整轮。

### 12.8 `TASK_RETRY_POLL_SECONDS` 是死配置

配置项写了、`.env.example` 里也有、启动期还校验了它的取值范围，但主循环里**没人读它**：
退避后的重投只在「下一条消息到来时」才顺便捞一次。低峰期（消息很少）表现为
**重试要等很久才发生**，而监控上「重试队列长度」一直不降。

**修法**：接进 `_poll_retries()` 并加节流（`_next_retry_poll`），
顺带发现两个伴生问题：主循环「取不到消息」时的空转（补 `await asyncio.sleep(0)`）
和被取消的 job 没计数（补 `stats.canceled += 1`）。

**推广**：**新配置项必须有一条「它会改变行为」的测试**。否则「配置存在」本身就是假信号 ——
它让人以为调大/调小有用，而实际上是常量。一条 `settings.x = 0.01` 的用例就能防住。

### 12.9 SSE `error.retryable` 的判据只用了「重试预算」

`error` 帧/事件的 `retryable` 原本是 `task.can_retry`（= `FAILED` 且 `retry_count < max_retries`）。
但 `docs/02` §5.3 明确规定 `UNPROCESSABLE_DOCUMENT` / `UNSUPPORTED_FILE_TYPE` /
`VECTOR_DIM_MISMATCH` 这类**确定性**错误 `retryable=false` —— 扫描版 PDF 重试三次
还是同一份扫描版 PDF。客户端照着 `true` 去重试，就是「白等 21 秒拿到同一个错误」，
而 `NON_RETRYABLE_CODES` 这批常量（`docs/08` §5.2）本就是为了避免它。

**修法**：新增 `app/tasks/retry.py::error_retryable(task)` = **错误码值得重试** ∧ **预算没用完**，
SSE 快照与失败事件共用一个判据（两条路径口径必须一致，否则「重连后重读快照」的说法会和
「当时收到的那一帧」不一样）。

**推广**：**同一份契约字段在多处计算 = 早晚不一致**。凡是「同一语义有两处实现」，
就要合并成一个函数；尤其当其中一处是「错帧」、另一处是「快照」时，
不一致的后果是**客户端重连一次反而多跑三轮注定失败的任务**。

### 12.10 过载边界写成 `>`：`MAX` 变成 `MAX + 1`

`_ensure_capacity()` 统计的是「本次入队**之前**的未结束任务数」，判断写成了
`if open_count > self._queue_max`：于是 `INGEST_QUEUE_MAX=1000` 时真实并发上限是 1001。
`docs/08` §174 的原文是「队列长度 > `ingest_queue_max` 时拒绝」——按字面更贴近 `>`，
但配置项叫 `MAX`，差一的话没人能一眼看出真实上限。

**修法**：改成 `>=`，并把「统计的是入队前的数量」写进 docstring；同时把 SRS 的表述
改成「**已达到**上限即拒绝」（`docs/08` §5.4），避免下一轮又按字面改回去。

**推广**：**边界类配置项的语义必须能被一句话说清**（「最多 N 个在飞任务」，
而不是「超过 N 之后的下一个才拒绝」）。当文档的字面与配置项的名字冲突时，
选**名字**并改文档 —— 名字是运维每天要读的东西。

### 12.11 小结与 M7 的端到端验证

M7 这 10 条的分布很有意思：**9 条是「一跑就红」**（新测试抓到的），
**1 条是 review 出来的契约不一致**（12.9）。抓到的 9 条里有 5 条属于
「**并发/取消/跨实现语义**」——正是内存替身最难暴露的一类。可复用的六条：

1. **哨兵值不要放进业务取值域**（12.1）；
2. **惰性对象（异步生成器/协程）要显式确认「已生效」**（12.2 / 12.3）；
3. **取消必须转发并等待**，否则留下孤儿协程与被覆盖的终态（12.4 / 12.5）；
4. **替身与真实现的资源语义要对齐**，脏数据不能让整轮批处理停摆（12.6 / 12.7）；

6. **每个新配置项都要有一条测试证明它真的能改变行为**，否则它就是死配置（12.8）。
5. **契约字段在两个地方各算一次，就一定会分叉**，而且分叉最难看的时候是

### 13.1 `HF_ENDPOINT` 写进 `.env` 是静默失效的

`Settings.hf_endpoint` 也读到了值（日志打过），但每次加载本地模型仍然去连

```
Retrying in 8s [Retry 5/5].
app.rag.reranker: rerank.failed  error=We couldn't connect to 'https://huggingface.co' …
app.rag.retriever: rag.retrieved  recalled=3 returned=2 rerank_applied=False elapsed_ms=558732
```

（那次请求的 `elapsed_ms` 是 **558732**，约 9 分 19 秒 —— 看起来像「重排太慢」，
实际是**网络重试**。）

**根因**是两层叠加：

1. `huggingface_hub` 在**导入期**就把环境变量固化进模块常量：

   ```python
   # huggingface_hub/constants.py
   ENDPOINT = os.getenv("HF_ENDPOINT", _HF_DEFAULT_ENDPOINT).rstrip("/")
   HUGGINGFACE_CO_URL_TEMPLATE = ENDPOINT + "/{repo_id}/resolve/{revision}/{filename}"
   ```

   而 `file_download.hf_hub_url()` 用的是 `HUGGINGFACE_CO_URL_TEMPLATE`，
   **只在显式传 `endpoint=` 参数时**才改写域名：

   ```python
   url = constants.HUGGINGFACE_CO_URL_TEMPLATE.format(...)
   if endpoint is not None and url.startswith(constants.ENDPOINT):
       url = endpoint + url[len(constants.ENDPOINT) :]
   ```

   所以「import 之后再设环境变量 = 完全无效」。

2. 而 `app` 自己会在 **`import app.main` 期间**就把它拉进来，链路是：

   ```
   app.main → app.api.routes → app.api.deps → app.rag.service
            → app.rag.chunking → langchain_text_splitters
            → transformers.tokenization_utils_base → huggingface_hub
   ```

   （`langchain_text_splitters` 只用来做切分，却顺带把 `transformers` 拖了进来。）
   等 `create_app()` 执行时早已错过窗口期。

**判定手法**（不用猜，直接问库）：

```python
import app.main  # 触发 create_app()
import huggingface_hub.constants as c

print(c.ENDPOINT)  # 修复前：https://huggingface.co（即使 os.environ 里是镜像）
from huggingface_hub import hf_hub_url

print(hf_hub_url("BAAI/bge-m3", "config.json"))  # 修复后：https://hf-mirror.com/…
```

用 `sys.meta_path` 插一个 `MetaPathFinder` 打印 `traceback.format_stack()`
就能拿到上面那条精确的导入链 —— 比翻代码快得多。

**修法**（`app/config.py::apply_hf_endpoint`）：在 `create_app()` 里**同时**做两件事，
而不是只设环境变量：

```python
os.environ["HF_ENDPOINT"] = endpoint  # 对本进程后续导入的模块、子进程有效
from huggingface_hub import constants as hf_constants

if hf_constants.ENDPOINT != endpoint:  # 已被导入时同步改写常量
    hf_constants.ENDPOINT = endpoint
    hf_constants.HUGGINGFACE_CO_URL_TEMPLATE = endpoint + "/{repo_id}/resolve/{revision}/{filename}"
```

**留下的防线**：修复后的判定脚本（上文的 `hf_hub_url` 断言）已作为验证手法记在此处；
`.env.example` 里补了注释说明「不写这一行是静默失效」。

**可复用原则**：**给「在 import 期缓存配置的第三方库」改配置，必须在它被导入之前完成；
导入顺序不可控时，同步改写它的常量是唯一确定性生效的办法。**
配套的自检手段是「问库自己的运行时状态」，而不是「看自己的配置对象读到了什么」。

### 13.2 只「连上了」不等于「表建对了」

**症状**：`INFRA_BACKEND=real` 下，`SHOW TABLES` 能过、`SELECT 1` 能过，但第一次
`POST /knowledge-bases/{id}/documents` 才炸在 `document_chunk.metadata` 上：

```
(1054, "Unknown column 'metadata' in 'field list'")
```

**根因**：`docs/09` 的 DDL 早就有这列，但**已存在的库**不会因为 `CREATE TABLE
IF NOT EXISTS` 而补列 —— 这是 M6 前置那批坑（§10.1）的同一个形状：**约束/结构的作用
是「拦住」，而它没拦住时什么都没发生**。

**修法**：
1. `deploy/mysql/003_add_chunk_metadata.sql`：幂等 `ALTER`（先查 `information_schema`
   计数，不存在才 `ADD COLUMN`，否则 `DO 0`），并在末尾打一条验证 `SELECT`。
2. `app/main.py::_check_mysql_ready()`：启动期不只 `SHOW TABLES`，而是把
   `EXPECTED_TABLES`（`knowledge_base` / `document` / `document_chunk` / `user_memory` / `task`）
   逐个比对，缺了就按名称记 `app.mysql_schema_incomplete` **并带上「去执行哪个脚本」**。
3. `app/core/db.py`：`ERRNO 1049/1146/1054` → `503 DEPENDENCY_UNAVAILABLE`，
   错误信息里含 `deploy/mysql/001_init_schema.sql`。

**为什么不用 `SELECT 1` 做自检**：那样「连上了但库是空的」会显示为成功，
而真正的问题（少建表）要等第一次业务请求才暴露 —— 那时它已经是一次线上故障了。
「连接性」和「结构正确性」必须分开断言。

### 13.3 连接池的「构造成功」不等于「连得上」，也不该被反复构造

**症状**：`create_engine()` 是**同步且惰性**的（不连网），所以「构造成功」不能作为
「依赖可用」的判据；同时多个装配点各自 `create_engine()` 会产生多个连接池，
关停时又只关掉其中一个，剩下的池让进程无法干净退出。

**修法**（`app/core/db.py`）：**按 DSN 共享引擎 + 引用计数**。

```python
_ENGINES: dict[str, tuple[Any, int]] = {}  # DSN -> (engine, refcount)


def create_engine_from_settings(settings): ...  # 命中缓存则 refcount += 1
async def release_engine(engine): ...  # refcount -= 1，归零才 dispose
async def aclose_all_engines(): ...  # 关停时兜底
```

启动期自检用完立刻 `release_engine()`，所以「没启用 MySQL 的部署」不会留一个常驻池。
**测试侧注意**：这个缓存是**进程级**的，单测断言「两次调用拿到同一个引擎」会受
**其他测试遗留的引用**影响，所以测试开头必须先 `await aclose_all_engines()` 把状态清干净
（这条踩过一次，见 `tests/unit/test_db_helpers.py`）。

### 13.4 用唯一索引做幂等，必须让「幂等命中」也走原子路径

**症状**：长期记忆的去重靠 `content_sha256` 唯一索引。若「先查再插」，
并发下两个请求都查不到 → 都去插 → 一个成功一个 `IntegrityError` →
若此时直接把异常抛给用户，就变成「同一句话并发写两次，一次报错」；
若不处理而只是吞掉，`hit_count` 就**丢了**。

**修法**（`app/memory/mysql_repo.py::add`）：

1. 先 `find_by_hash`，命中就 `_bump_hit()`（`created=False`）；
2. 未命中则 INSERT，捕获 `IntegrityError` 后**最多重试 3 次 `find_by_hash`**
   （`await asyncio.sleep(0.05)` 让赢家的事务先可见），仍找不到才 `reraise`；
3. `_bump_hit()` 是**单条 UPDATE**：

   ```python
   values["hit_count"] = table.c.hit_count + 1
   values["confidence"] = func.greatest(table.c.confidence, confidence)
   values["updated_at"] = db_now()
   ```

   `GREATEST` 在**数据库里**算，避免「读-改-写」丢更新。

**留下的防线**：`tests/integration/test_mysql_memory_repo.py::test_concurrent_duplicate_writes_do_not_lose_updates`
—— `asyncio.gather` 并发写 5 次，断言「恰好创建 1 条」且 `hit_count == 5`。

### 13.5 Milvus 的标量索引：没有它，召回会**静默**变少

**症状**：`user_id` 过滤写在 `filter=` 里，看起来对；但集合上没有 `user_id` 索引时，
Milvus 的执行计划会变成「先全量取 top-k，再按 filter 过滤」。结果是
**过滤后凑不满 `top_k`，接口却返回 200**。多租户下表现为「我的文档明明有，就是搜不到」。

**修法**（`app/memory/milvus_index.py::ensure_ready`）：建集合时**同时**建标量索引：

```python
for field in ("user_id", "kind"):
    index_params.add_index(field_name=field, index_type="INVERTED")
```

**留下的防线**：`tests/integration/test_milvus_memory_index.py` 断言
`{"vector", "user_id", "kind"} <= indexes`，并且显式构造**跨用户**用例
（同一个查询向量、另一个用户，断言后者**不出现**）——「隔离」这件事只能靠
「不该出现的没出现」来证明。

### 13.6 过滤器表达式里的值必须转义

`user_id` 是客户端可控的字符串，直接拼进 `filter=f'user_id == "{user_id}"'`
会被 `"` 截断（`user_id = 'x" or user_id == "y'` 直接变成跨租户读）。
修法是用 `json.dumps(value, ensure_ascii=False)` 生成字面量（等价于 SQL 的参数化）。

### 13.7 删除的「级联」要能在存储侧验证

**症状**：`DELETE /documents/{id}` 返回 202、任务 `SUCCEEDED`、关系库里的行没了 ——
但 Milvus 里的向量还在不在？**接口层面看不出来。**

**判定手法**：不要看 `collection.row_count`（删除是标记，空间由 compaction 延后回收），
要用带过滤的查询数条数：

```python
client.query(
    collection_name="ai_platform_chunks",
    filter=f'kb_id == "{kb_id}"',
    output_fields=["chunk_id"],
    limit=100,
)
```

实测：上传 2 个 chunk → `kb_id` 过滤得 **2**；`DELETE /documents/{id}` →
`SUCCEEDED (stage=DELETING)` → 再查得 **0**。同时
`DELETE /knowledge-bases/{id}?force=true` 返回 `{"documents":1,"vectors":2,"objects":1}`
—— `vectors: 2` 这个数**随数据变化**，所以它是真删除的证据，而不是常量。

### 13.8 `KB_NOT_EMPTY` → `force=true` 的两段式删除

**症状**：清理验证数据时，`DELETE /knowledge-bases/{id}` 返回 409 `KB_NOT_EMPTY`，
加上 `?force=true` 才删掉。看起来像「参数没生效」。

**结论**：这是**设计如此**（`docs/06-§7`）：非空知识库必须显式 `force=true`，
避免误删。两次独立复现的状态码都是 `409 → 200`，`force=true` 时的
`documents/vectors/objects` 计数与数据一致。排查时先确认「有没有真的发出带 query 的请求」
（curl 建议加 `-g` 关闭 URL globbing），不要把设计行为当成 bug。

### 13.9 小结

| # | 坑的形状 | 一句话教训 |
| --- | --- | --- |
| 13.1 | 配置写对了但**没生效** | 给「import 期缓存配置的库」改配置，必须在它被导入前完成；自检要问库自己 |
| 13.2 | 只验证「连上了」 | 连接性与**结构正确性**是两件事，缺表要在启动期就点名 |
| 13.3 | 同步构造 ≈ 无副作用 | 惰性 connect 的「构造成功」不是可用性证据；共享资源要引用计数 |
| 13.4 | 幂等只做了一半 | 「命中」路径也必须是原子的，否则并发下丢计数 |
| 13.5 | 过滤「看起来对」 | 没有标量索引，过滤发生在 top-k **之后**，召回静默变少 |
| 13.6 | 字符串拼查询 | 客户端可控的值进过滤器表达式必须转义（= 跨租户读） |
| 13.7 | 删除看不出级联 | 「删掉了」要用带过滤的条数证明，不要看 `row_count` |
| 13.8 | 设计行为被当 bug | 两段式删除（409 → `force=true`）是有意的保护 |

**这九条里只有 13.4 是逻辑 bug，其余八条都是「以为生效了」。**
这与本文开头的判断一致：这类问题的共同特征是
**代码能跑、测试能过、接口有响应，但结果是错的**。
