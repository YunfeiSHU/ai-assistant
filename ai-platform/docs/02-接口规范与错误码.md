# 02 · 接口规范与错误码

> 本篇是所有模块接口的**公共契约**。任何模块的接口文档若与本篇冲突，以本篇为准。

## 1. 通用约定

| 项 | 约定 | 需求 ID |
| --- | --- | --- |
| Base URL | `http://{host}:{port}`，默认 `0.0.0.0:8000` | `REQ-API-001` |
| 路径前缀 | `settings.api_prefix`，默认 `/api/v1`；本文档路径均省略该前缀 | `REQ-API-001` |
| 版本策略 | 前缀带大版本；**破坏性变更**必须升 `v2`，不允许原地改字段语义 | `REQ-API-001` |
| 请求 Content-Type | `application/json`；文件上传用 `multipart/form-data` | `REQ-API-001` |
| 响应 Content-Type | `application/json`；流式为 `text/event-stream` | `REQ-API-001` |
| 字段命名 | `snake_case`，不接受 camelCase（不做自动兼容） | `REQ-API-002` |
| 未知字段 | 请求体中的未知字段 MUST 被**忽略而非报错**（Pydantic `extra="ignore"`） | `REQ-API-002` |
| 时间格式 | RFC 3339 UTC，毫秒精度，固定 `Z` 结尾：`2026-09-28T10:00:00.123Z` | `REQ-API-002` |
| ID 格式 | `{前缀}_{26 位 ULID}`，如 `doc_01J8ZQ3K7N9P2V6R4T8W1Y5B3C`；前缀集合：`kb` `doc` `chk` `task` `mem` `msg` `srv` `cv`（会话）`req`（请求号）`u`（用户）`rt`（刷新令牌） | `REQ-API-003` |
| 布尔/数值 | 严格类型校验，不做 `"1"` → `true` 的隐式转换 | `REQ-API-002` |
| 空值与缺省 | `null` 与「字段缺失」语义等价；数组默认 `[]` 不返回 `null` | `REQ-API-002` |
| OpenAPI | `/openapi.json` 与 `/docs` MUST 始终可访问 | `REQ-API-004` |

> **不支持驼峰**是刻意选择：现有 `app/schemas/*.py` 全是 `snake_case`，同时兼容两套命名会让契约不可预测。

## 2. 请求头

| 头 | 必填 | 说明 |
| --- | --- | --- |
| `Authorization` | 是 | `Bearer <JWT>`。JWT 由 Go 侧签发，`sub` = `user_id` |
| `X-Request-Id` | 否 | 客户端请求号；缺失时服务端生成 `req_<ULID>` 并在响应头回写 |
| `Idempotency-Key` | 否 | 仅用于**创建类**接口（上传文档、创建 KB、写记忆）；见第 7 节 |
| `traceparent` | 否 | W3C Trace Context，缺失时服务端新建 trace |
| `Accept-Language` | 否 | `zh-CN` / `en-US`，影响错误 `message` 语言（默认 `zh-CN`） |
| `X-Conversation-Id` | 否 | 流式接口可用其替代 body 字段，便于客户端统一注入 |

### 2.1 鉴权规则（`REQ-API-005`）

1. 除 `/health`、`/health/live`、`/health/ready`、`/openapi.json`、`/docs`、`/redoc` 外，**所有**接口 MUST 要求有效 JWT。
2. 校验项：签名、`exp`、`iss`（期望 `ai-assistant`）、`aud`（期望 `ai-platform`）。
3. `auth.enabled=false` 时允许关闭（仅 `local` 环境），此时 `user_id` 取 `X-Debug-User-Id` 头，默认 `u_dev`。生产环境（`app_env=prod`）下 MUST 忽略该开关并强制校验。
4. 校验失败返回 `401 UNAUTHENTICATED`，不区分「无 token / 过期 / 签名错」（防探测）。
5. 拿到 `user_id` 后 MUST 作为所有存储访问的过滤条件，禁止仅凭请求体里的 `user_id` 做授权。

## 3. 统一响应结构

### 3.1 成功（单对象）

直接返回业务对象，**不额外包一层 `data`**（减少无意义的嵌套）：

```json
{
  "id": "kb_01J8ZQ3K7N9P2V6R4T8W1Y5B3C",
  "name": "产品文档",
  "created_at": "2026-09-28T10:00:00.123Z"
}
```

### 3.2 成功（列表分页）

```json
{
  "items": [],
  "next_cursor": null,
  "has_more": false
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `items` | `array` | 当前页数据；无数据时 `[]` |
| `next_cursor` | `string \| null` | 下一页游标；`null` 表示没有下一页 |
| `has_more` | `boolean` | 是否还有更多；与 `next_cursor != null` 等价（冗余便于前端） |

> 列表接口统一**不返回 `total`**：游标分页下 `total` 需额外全表计数，成本高且会不一致。若确需总数，用独立 `HEAD` 或统计接口。

### 3.3 失败（统一错误信封）

```json
{
  "error": {
    "code": "KB_NOT_FOUND",
    "message": "知识库不存在或无权访问",
    "details": { "kb_id": "kb_01J8..." },
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "retryable": false
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `error.code` | `string` | 是 | 业务错误码，机器可读，见第 5 节 |
| `error.message` | `string` | 是 | 人类可读，可被前端直接展示；不泄漏内部堆栈/SQL |
| `error.details` | `object` | 否 | 结构化补充：字段名、冲突资源 ID、上游错误摘要等 |
| `error.trace_id` | `string` | 是 | 与日志、链路追踪一致，便于排障 |
| `error.retryable` | `boolean` | 是 | 客户端**是否可安全重试**（含 `retry_after` 时一并给出） |
| `error.retry_after` | `integer` | 否 | 建议重试秒数，仅 `retryable=true` 时出现 |

> 错误响应 MUST NOT 出现在 SSE 已开始推送之后（此时用 `event: error` 帧，见第 6 节）。

## 4. HTTP 状态码使用规则

| 状态码 | 使用场景 | 典型业务码 |
| --- | --- | --- |
| `200` | 查询、更新、非流式对话成功 | — |
| `201` | 资源创建成功（创建 KB、上传文档、写记忆） | — |
| `202` | 已受理异步任务（上传文档触发的入库） | — |
| `204` | 删除成功，无响应体 | — |
| `400` | 参数校验失败、语义非法（如 `top_k > 100`） | `INVALID_ARGUMENT` |
| `401` | 未认证 | `UNAUTHENTICATED` |
| `403` | 已认证但无权访问该资源 | `PERMISSION_DENIED` |
| `404` | 资源不存在（含「存在但不属于你」，防枚举） | `*_NOT_FOUND` |
| `409` | 冲突（重名 KB、重复文档、状态不允许的操作） | `CONFLICT` / `TASK_NOT_CANCELABLE` |
| `413` | 上传文件过大 | `FILE_TOO_LARGE` |
| `415` | 不支持的文件类型 | `UNSUPPORTED_FILE_TYPE` |
| `422` | 参数结构合法但无法处理（如文档无有效文本） | `UNPROCESSABLE_DOCUMENT` |
| `429` | 限流 | `RATE_LIMITED` |
| `500` | 未预期内部错误 | `INTERNAL_ERROR` |
| `502` | 上游 LLM / MCP 返回异常 | `UPSTREAM_LLM_ERROR` / `UPSTREAM_MCP_ERROR` |
| `503` | 依赖不可用（Milvus/Redis 宕、队列满） | `DEPENDENCY_UNAVAILABLE` / `OVERLOADED` |
| `504` | 上游超时 | `UPSTREAM_TIMEOUT` |

## 5. 错误码总表（`REQ-API-006`）

### 5.1 通用

| code | HTTP | retryable | message（zh-CN） | 触发条件 | 客户端建议 |
| --- | --- | --- | --- | --- | --- |
| `INVALID_ARGUMENT` | 400 | 否 | 请求参数不合法 | 校验失败；`details.fields` 列出字段与原因 | 修正参数 |
| `UNAUTHENTICATED` | 401 | 否 | 身份未认证 | JWT 缺失/过期/签名错 | 重新获取 token |
| `PERMISSION_DENIED` | 403 | 否 | 无权访问该资源 | `user_id` 与资源属主不符 | 停止重试 |
| `RATE_LIMITED` | 429 | 是 | 请求过于频繁 | 超过限流阈值 | 按 `retry_after` 退避 |
| `INTERNAL_ERROR` | 500 | 是 | 服务内部错误 | 未捕获异常 | 带退避重试，必要时上报 `trace_id` |
| `DEPENDENCY_UNAVAILABLE` | 503 | 是 | 依赖服务不可用 | Milvus/Redis/MySQL/Kafka 连接失败 | 退避重试 |
| `OVERLOADED` | 503 | 是 | 服务繁忙 | 并发或队列超上限（入库任务：「未结束任务数」达到 `ingest_queue_max`） | 退避重试 |
| `UPSTREAM_TIMEOUT` | 504 | 是 | 上游服务超时 | LLM / MCP 超时 | 退避重试 |

### 5.2 对话与 Agent

| code | HTTP | retryable | message | 触发条件 |
| --- | --- | --- | --- | --- |
| `CONVERSATION_NOT_FOUND` | 404 | 否 | 会话不存在 | `conversation_id` 未知或不属于当前用户 |
| `CONTEXT_TOO_LONG` | 400 | 否 | 上下文超出模型上限 | 裁剪后仍超 `context_token_budget` |
| `QUERY_EMPTY` | 400 | 否 | 提问内容为空 | `query` 去空白后为空 |

## 6. 流式协议（SSE）通用规范（`REQ-API-007`）

适用于 `/chat/stream`、`/agent/run/stream`、`/tasks/{task_id}/events`。

### 6.1 帧格式

标准 SSE：`event:` + `data:` + 空行。`data` 为**单行 JSON**（不允许内部换行）。

```text
event: meta
data: {"conversation_id":"cv_01J8...","message_id":"msg_01J8...","model":"deepseek-flash","created_at":"2026-09-28T10:00:00.123Z"}

event: token
data: {"delta":"你好"}

event: token
data: {"delta":"，有什么可以帮你？"}

event: usage
data: {"prompt_tokens":812,"completion_tokens":37,"total_tokens":849}

event: done
data: {"finish_reason":"stop","elapsed_ms":2043}

```

### 6.2 事件类型总表

| event | 出现次数 | data 字段 | 说明 |
| --- | --- | --- | --- |
| `meta` | 恰好 1 次，**首帧** | `conversation_id`, `message_id`, `model`, `created_at`, `degraded`(可选) | 客户端据此建消息卡片 |
| `reference` | 0..n | `references[]`（结构见 06） | RAG 召回结果，**在 `token` 之前**推送 |
| `token` | 0..n | `delta` | 增量文本；客户端直接追加拼接 |
| `tool_call` | 0..n | `call_id`, `name`, `arguments`(object) | Agent 决定调用工具 |
| `tool_result` | 0..n | `call_id`, `name`, `status`, `summary`, `elapsed_ms` | 工具返回；`summary` 为截断后的可展示摘要 |
| `usage` | 0..1 | `prompt_tokens`, `completion_tokens`, `total_tokens` | 用量统计，用于计费 |
| `error` | 0..1 | `code`, `message`, `retryable` | 流中途失败；**之后 MUST NOT 再发 `done`** |
| `done` | 0..1，**末帧** | `finish_reason`, `elapsed_ms` | 正常结束标记 |
| `ping` | 0..n | `{}` | 心跳，见 6.4 |

`finish_reason` 取值：`stop`（自然结束）、`length`（截断）、`max_steps`（Agent 步数用尽）、`canceled`（客户端断连或超时）。

### 6.2.1 任务进度流（`GET /tasks/{task_id}/events`）

任务进度流的**帧集合不同**：它没有 `meta`（任务信息由 `GET /tasks/{task_id}` 提供），
也不推 `token`；只有下面四种帧（详细字段与推送时机见 [08-异步任务](./08-异步任务.md) §4.5）。

| event | 出现次数 | data 字段 | 何时推送 | 推完关流？ |
| --- | --- | --- | --- | --- |
| `progress` | 0..n | `stage`, `progress`(0..100), `message`(可选) | 任务上报阶段/进度时 | 否 |
| `error` | 0..1 | `code`, `message`, `retryable` | 任务进入 `FAILED` | **否**（见下） |
| `done` | 0..1，末帧 | `status`, `finished_at` | 任务进入 `SUCCEEDED` / `FAILED` / `CANCELED` 之一 | **是**（发完即关） |
| `ping` | 0..n | `{"ts":"<RFC3339>"}` | 15s 无事件 | 否 |

三条硬约定（与对话流不同，客户端必须按此实现）：

1. **`error` 与对话流不同**：它是「任务失败」而非「流失败」，因此
   **`FAILED` 之后 MUST NOT 关流** —— `FAILED → QUEUED` 是合法迁移，自动重试随后可能发生，
   关流会让客户端错过后续进度。客户端看到 `error` 后应继续读，直到收到 `done` 或状态变为终态。
2. **`error` / `done` 互斥**：进入 `FAILED` 时推 `error`，真正的终态（含用户取消）推 `done`；
   退出码语义只有一个 —— `done` 一定是最后一帧。
3. **`retryable` 的判据是两个条件同时成立**：错误码本身值得重试（见 §5 各表中的 `retryable` 列）
   **且** 重试预算未用尽（`retry_count < task_max_retries`）。因此确定性失败
   （如 `UNPROCESSABLE_DOCUMENT`）即使预算有剩也 MUST 为 `false`，客户端不得重试。

> `progress` 的取值 MUST 单调不减，且落在 `[0, 100]`；任务进入 `QUEUED`（含重试重新入队）时
> 上报的进度会**重置为 0**，客户端应按「新一次尝试」处理，而不是当作进度回退。

### 6.3 顺序约束

```
meta → (reference*) → (tool_call → tool_result)* → token* → usage? → done
                                  ↘ error（任意位置出现后立即终止）
```

- `meta` MUST 是第一帧（错误发生在准备阶段时改为直接返回 HTTP 错误，不进入 SSE）。
- `token` 与 `tool_call`/`tool_result` 可以交替：Agent 可能先说话再调工具。
- `done` 与 `error` **互斥**，且必居其一（除客户端主动断开）。

任务进度流（§6.2.1）的顺序约束较弱，只有两条：

```
progress* → error* → done      # done 一定是最后一帧，发完即关
（整条流中可随时插入 ping）
```

- 首帧 MUST 是**当前状态的快照**（终态任务则直接是 `done`），保证「进去就能看到现状」；
- 连接建立后新产生的事件按发生顺序推送：**先订阅、后读快照**，两者若有重叠由客户端按
  `(status, progress)` 幂等处理即可（MUST NOT 因重复帧报错）。

### 6.4 心跳与超时

| 项 | 值 | 说明 |
| --- | --- | --- |
| 心跳间隔 | 15s | 15s 无任何事件时发 `event: ping`，防中间层（Nginx/NAT）掐连接 |
| 首字节超时 | 30s | 30s 内未发出 `meta` 视为启动失败 |
| 空闲超时 | 120s | 连续 120s 无 `token`/`tool_*` 事件则发 `error(code=UPSTREAM_TIMEOUT)` |
| 总时长上限 | 300s | 到点强制 `done(finish_reason=length)` 并记警告 |
| 缓冲 | `X-Accel-Buffering: no` 响应头 + 关闭应用层缓冲 | 否则 Nginx 会整段缓存导致「不流式」 |
| 压缩 | 流式响应 MUST NOT 启用 gzip | 压缩会破坏增量输出 |

### 6.5 客户端断连

1. MUST 监听 `request.is_disconnected()`（或 `asyncio.CancelledError`）。
2. 断连后 MUST 取消正在进行的 LLM 流（避免白烧 token）与正在执行的工具任务。
3. 已产生的部分回答 SHOULD 落库到会话消息（标记 `partial=true`），由 Go 侧决定是否展示。

## 7. 分页、过滤与幂等

### 7.1 分页参数（`REQ-API-008`）

| 参数 | 类型 | 默认 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `limit` | `integer` | 20 | 1..100 | 每页条数；超限返回 `INVALID_ARGUMENT`（不静默截断） |
| `cursor` | `string` | — | 上一页的 `next_cursor` 原样回传 | 不透明游标，客户端 MUST NOT 解析 |

排序：默认 `created_at` 降序；游标编码 `(created_at, id)` 二元组，保证同一时间戳下不漏不重。

### 7.2 幂等（`REQ-API-009`）

| 接口类型 | 幂等要求 |
| --- | --- |
| `POST /knowledge-bases/{kb_id}/documents` | `Idempotency-Key` 24h 内重复提交返回**首次的 202 响应体**，不重复建任务 |
| `POST /memories` | 同上；语义去重另由 `content_sha256` 保证 |
| `POST /knowledge-bases` | 自然幂等：同名同属主直接返回 `409 KB_NAME_CONFLICT` |
| `DELETE *` | 天然幂等：删除不存在的资源返回 `404`（不返回 `204`，避免掩盖越权） |
| `POST /chat*`、`/agent/run*` | **不幂等**，不参与幂等键；重复调用会产生多次 LLM 计费 |
| `POST /tasks/{id}/retry` | 幂等：重复调用在 `QUEUED/RUNNING` 状态下返回当前任务而非再排队 |

`Idempotency-Key` 建议为 UUID；服务端以 `(user_id, path, key)` 为唯一键，命中缓存则直接回放响应（含状态码）。

### 7.3 限流（`REQ-API-010`）

| 维度 | 默认阈值 | 超限行为 |
| --- | --- | --- |
| 单用户并发对话 | 5 | 排队 3s；仍无空位返回 `429 OVERLOADED` |
| 单用户文档上传 | 10 次/分钟 | `429 RATE_LIMITED` |
| 单用户检索 | 30 次/分钟 | `429 RATE_LIMITED` |
| 全局 LLM 并发 | `llm_max_concurrency`（默认 8） | 信号量阻塞，超时返回 `429 OVERLOADED` |
| 全局入库任务队列 | `ingest_queue_max`（默认 1000） | `503 OVERLOADED` |

实现建议：Redis 令牌桶（`rate:{user_id}:{scope}`）+ 进程内 `asyncio.Semaphore`。响应 MUST 带 `Retry-After` 头（秒）。

## 8. 向后兼容规则

| 允许（非破坏性） | 禁止（破坏性，需升 v2） |
| --- | --- |
| 新增可选请求字段、新增响应字段 | 删除或重命名字段 |
| 新增错误码 | 修改既有错误码语义/HTTP 状态码 |
| 新增枚举值（客户端需容忍未知值） | 收紧既有字段的校验（如新增 `max_length`） |
| 放宽校验 | 修改默认值导致行为变化 |
| 新增接口、新增 SSE 事件类型 | 改变 SSE 事件顺序约束 |

> 新增 SSE 事件类型前必须确认客户端会忽略未知 `event:`，否则需先发布客户端兼容版本。
