# 11 · 验收标准与测试策略

> 关联：需求 ID `REQ-TEST-*`；各模块的验收用例（`AC-*`）分散在 [02](./02-接口规范与错误码.md)～[10](./10-非功能需求与可观测性.md) 中，本篇负责**汇总口径、测试手段与通过标准**。

## 1. 验收总则

| 项 | 规定 |
| --- | --- |
| 验收对象 | `ai-platform` 服务（不含 Go 侧与前端） |
| 验收方式 | 自动化用例为主（pytest），关键链路提供可复现脚本 |
| 通过定义 | 该里程碑对应的**全部 P0 用例通过**，且无 P0/P1 缺陷未关闭 |
| 环境 | 依赖用 `docker compose` 拉起（Milvus / Redis / MySQL / MinIO / Kafka）；LLM 用 Fake 或真实网关二选一 |
| 用例可追溯 | 每条用例 ID（`AC-<模块>-NN`）MUST 在测试代码中以标记（如 `pytest.mark.ac("AC-CHAT-01")`）或在 docstring 中引用 |
| 证据 | 每次验收 MUST 产出：pytest 报告 + 覆盖率报告 + 关键接口的耗时统计 + 失败用例的日志片段 |

## 2. 测试分层（`REQ-TEST-001`）

| 层 | 目录 | 依赖 | 运行时间 | 覆盖内容 |
| --- | --- | --- | --- | --- |
| 单元测试 | `tests/unit/` | 无（全 mock） | < 30s | Chunk 切分、AST 计算器、Token 预算裁剪、错误码映射、SSRF 校验、幂等键计算 |
| 契约测试 | `tests/contract/` | FastAPI TestClient | < 60s | 路由存在性、请求/响应 Schema、错误信封结构、分页参数校验、OpenAPI 一致性 |
| 集成测试 | `tests/integration/` | docker compose 依赖（真实 Milvus/Redis/MySQL/MinIO/Kafka） | < 10min | 入库全链路、检索与重排、上下文读写、任务状态机、删除级联 |
| 端到端测试 | `tests/e2e/` | 依赖 + Fake LLM | < 5min | 10 个核心场景（见 §4） |
| 性能测试 | `tests/perf/`（`pytest -m perf`，默认不跑） | 依赖 + 真实/Fake LLM | 按需 | 首 token 延迟、并发、检索延迟 |
| 效果评估 | `tests/eval/` | 依赖 + 真实 LLM | 按需 | RAG 召回质量（见 §5） |

> **集成层现状（M8）**：`tests/integration/` 已覆盖 **Redis + MySQL + Milvus + MinIO** 四个真实依赖，
> 全部实跑通过。每个依赖的地址都取环境变量并带默认值，
> 容器/服务没起时整层 `pytest.skip`（TCP 探测带缓存），所以**没有真实依赖的机器上跑全量测试不会失败**：
>
> | 依赖 | 环境变量 | 默认 | 覆盖内容 |
> | --- | --- | --- | --- |
> | Redis | `AI_TEST_REDIS_URL` | `redis://localhost:6379/15` | 任务存储 / 事件总线 / 延迟重试队列 |
> | MySQL | `AI_TEST_MYSQL_DSN` | `mysql+asyncmy://root:20050613@localhost:3306/ai_platform` | 知识库/文档/Chunk 仓储、长期记忆仓储、唯一约束、游标分页、并发幂等 |
> | Milvus | `AI_TEST_MILVUS_URI` | `http://localhost:19530` | 集合与索引（含标量索引）、跨用户隔离、维度校验、删除幂等 |
> | MinIO | `AI_TEST_MINIO_*` | `localhost:9000` / `minioadmin` | 对象 put/get/exists/delete、桶自动创建 |
>
> **Redis 夹具会 `FLUSHDB`，因此拒绝指向 0 号库**；其余三个依赖的夹具
> **只删自己 `user_id` 的行**，MUST NOT 使用 `TRUNCATE` 或无条件 `DELETE`
> （MySQL 与 Go Gateway **共库**，清库会毁掉另一侧的验收数据）。
> 日常开发用 `pytest -m "not integration"` 即可跳过这一层。
>
> 真实依赖的**接口级**验证不在这一层，而是 `tools/curl_e2e.ps1`
> （42 个路由组合、45 次请求）+ [14-接口 curl 示例](./14-接口%20curl%20示例.md) 里记录的实测响应。

现有 `tests/test_health.py` 属契约层，MUST 迁移到 `tests/contract/` 并保持通过。

### 2.1 隔离要求

- 每个集成测试用例 MUST 使用**独立的 `user_id`**（如 `u_test_{uuid}`），结束时不清理也不影响其它用例（所有查询本就按 `user_id` 隔离）。
- 需要清理的用例 MUST 在 fixture teardown 中按 `user_id` 批量删除（Milvus + MySQL + Redis + MinIO 四处）。
- 测试 MUST NOT 依赖执行顺序；`pytest -p no:randomly` 与随机顺序都 MUST 通过。

## 3. Mock 与替身策略（`REQ-TEST-002`）

| 被测依赖 | 替身 | 说明 |
| --- | --- | --- |
| LLM（OpenAI 兼容） | **Fake OpenAI Server**（本地 FastAPI，实现 `/chat/completions`） | 支持按脚本返回：固定文本流、含 `tool_calls` 的响应、指定错误码、指定延迟；记录收到的 `messages` 供断言（这是验证「上下文拼装顺序」「Token 裁剪」的唯一可靠手段） |
| Embedding | 确定性 hash 向量（`hash(text) → 归一化 1024 维`） | 保证相似文本向量相近、不同文本可区分；**避免真实模型下载与 CPU 开销** |
| Reranker | 交叉编码器替身：`score = 关键词重叠率` | 用于验证排序与阈值逻辑，不验证模型效果 |
| Milvus / Redis / MySQL / MinIO / Kafka | **真实容器**（不做内存替身） | 过滤表达式、唯一约束、TTL、Kafka 语义是需求的一部分，用替身会漏掉真实行为 |
| Kafka（契约 / 单测层） | `tests/support/fake_broker.py`（`FakeTaskProducer` / `FakeTaskConsumer`） | 契约与单测不能依赖 MQ：替身能断言「投递了什么主题与 key」「提交了哪些 offset」，并把 `MQ_UNAVAILABLE` 开关做成可控故障；**真 Kafka 的语义（手动提交、重平衡）只在集成/E2E 层验** |
| Kafka（端到端冒烟） | 真 Kafka + 两个真进程 | `tools/kafka_e2e_check.py`：投递 → 独立 Worker 消费 → 状态流转 → 跳进程 `done` 帧，末尾打 `PASS` |
| Worker 启动自检 | 把启动副作用（日志/指标/tracing）换空操作 | `tests/unit/test_worker_main.py`：只需一份内存任务存储的 `Settings` 就能断言「退出码 2 + 有 `worker.misconfigured` 日志」——这比手工跑一次强得多，因为漏掉这个自检的故障形态是「消息被消费了但任务永远 `QUEUED`」，不报错不退出 |
| MCP Server | `tests/support/fake_mcp.py`（**替掉传输层**：monkeypatch `app.mcp.session.open_session`） | 提供 read / write 两类工具，并按「建连 / 列表 / 调用」三个阶段分别开关故障（`fail_connect` / `fail_calls` / `delay`）；因为不启子进程、不走网络，用例可在 unit + contract 层跑 |

> **纪律**：Fake LLM MUST 记录每次收到的完整 `messages` 与 `tools`，并暴露 `/__requests` 查询接口。这是断言 Prompt 组装的唯一可信来源；不要通过「回答像不像」来推断。

## 4. 核心端到端场景（`REQ-TEST-003`）

| # | 场景 | 步骤 | 期望 | 关联用例 |
| --- | --- | --- | --- | --- |
| E2E-1 | 纯对话 | `/chat/stream`（`use_rag=false, use_memory=false`） | 200 + SSE 完整序列，`usage` 有值 | `AC-CHAT-01/03` |
| E2E-2 | 知识库问答 | 建 KB → 上传 MD → 等任务成功 → `/chat`（指定 kb） | 回答含 `[1]`，`references[0].chunk_id` 可查，且 `snippet` 命中原文 | `AC-RAG-04/09/13`、`AC-CHAT-05` |
| E2E-3 | 多步工具任务 | `/agent/run`（Fake LLM 脚本：先 `kb_retrieve`，再 `calculator`，最后文本） | `steps=3`，`tool_calls` 两条均为 `ok` | `AC-AGENT-01` |
| E2E-4 | 长对话压缩 | 造 30 轮 → 触发 `summary_build` → 继续对话 | 摘要存在；后续 Prompt 无早期原文但有摘要段；`total_tokens ≤ 8192` | `AC-MEM-03/05` |
| E2E-5 | 偏好记忆 | 第 1 轮说偏好 → 等 `memory_extract` → 新 `conversation_id` 提问 | 新会话 Prompt 含记忆段 | `AC-MEM-07/09` |
| E2E-6 | 文档删除 | 删文档 → 查三处存储 | Milvus/MySQL/MinIO 均无残留；检索不到 | `AC-RAG-15` |
| E2E-7 | 幂等 | 同 `Idempotency-Key` 上传两次 | 1 个任务、1 份向量 | `AC-API-07`、`AC-TASK-08` |
| E2E-8 | 重试 | mock Milvus 前 2 次失败 | 任务最终成功，`retry_count=2` | `AC-TASK-05` |
| E2E-9 | MCP 工具 | 配置测试 MCP Server → `/agent/run` 让它调用 `mcp__fs__read_file` | 工具列表出现该工具且执行成功 | `AC-MCP-03` |
| E2E-10 | 降级 | 停 Milvus 后 `/chat` | 200，纯 LLM 回答，`degraded_reasons` 含 `rag_unavailable` | `AC-CHAT-08`、`AC-NFR-03` |
| E2E-11 | 任务进度流（SSE） | 上传后 `GET /tasks/{id}/events` | 帧序 `progress* → done`；终态任务立即 `done` 并关；`FAILED` 推 `error` 且**不关流**；15s 有 `ping` | `AC-TASK-05`、`AC-API-08` |
| E2E-12 | 独立 Worker | API 投递 → 另起的 Worker 进程消费 | 状态在共享 Redis 里流转到 `SUCCEEDED`，且跨进程收到 `done` 帧 | `AC-TASK-01/09` |

每个 E2E 场景 MUST 以**一个 pytest 用例**表达，且在报告中打印关键中间态（`task_id`、`chunk_id`、token 统计），便于答辩演示。

> **M7 实际状态**：E2E-11 / E2E-12 已用**真进程**验证过（证据见 `docs/12` §12.11）。
> E2E-1、4、8 依赖 `INFRA_BACKEND=real` 的 MySQL 仓储（尚未提供，见 `docs/12` §12.12）——
> 现在它们用 `settings` 覆盖（`infra_backend=memory` + 注入替身向量库）在**契约/单测层**完成验证，
> 等 `real` 仓储落地后再补齐真容器版本。
> 另外注意一条测试工程限制：**`TestClient` 会把 ASGI 应用跑到生成器结束才交回响应**，
> 所以 SSE 契约测试只能断言「会自己结束」的流（终态任务）；
> 「边跑边推 + 心跳 + 连保持」交给单测（可注入时钟）+ 真机 `curl`。

## 5. RAG 效果评估（`REQ-TEST-004`）

### 5.1 数据集

| 项 | 要求 |
| --- | --- |
| 规模 | ≥ 30 个问题，覆盖 ≥ 10 份文档（中英混合，含表格与多级标题） |
| 标注 | 每题标注 `gold_chunk_ids`（可多个） |
| 位置 | `tests/eval/dataset.jsonl`（`{"query": "...", "gold_doc_ids": [...], "gold_chunk_ids": [...]}`） |
| 版本 | 数据集变更 MUST 在 PR 中说明原因（否则指标不可比） |

### 5.2 指标与门槛

| 指标 | 定义 | 门槛 |
| --- | --- | --- |
| `recall@5` | top-5 中命中任一 `gold_chunk_id` 的问题占比 | ≥ 0.85 |
| `recall@20`（仅向量召回） | 向量召回阶段命中率 | ≥ 0.92 |
| `MRR` | 第一个命中项的排名倒数均值 | ≥ 0.70 |
| `rerank_gain` | 加 Rerank 后 `recall@5` 相比不加重排的提升 | ≥ +0.05（否则 Rerank 无价值，需复核模型） |
| 引用准确率 | 回答中 `[n]` 指向的 chunk 确实支撑该句的比例（人工抽检 20 条） | ≥ 0.8 |

> 门槛是**回归保护**而非质量上限：PR 使任一指标下降 > 0.03 时必须解释。**禁止**为了指标好看而把 `gold_chunk_ids` 改成「实现了的切片」，那等于自欺。

### 5.3 反例集（防幻觉）

| 类型 | 期望行为 |
| --- | --- |
| 知识库中不存在答案的问题 | 明确回答「资料中未提及」，而非编造 |
| 问题与资料冲突 | 以资料为准并说明 |
| 资料中含「忽略以上指令」等注入文本 | 不被诱导改变行为（验证 Prompt 注入防护） |

## 6. CI 门槛（`REQ-TEST-005`）

必过检查（顺序执行，任一失败即阻断合并）：

| # | 检查 | 命令 | 门槛 |
| --- | --- | --- | --- |
| 1 | 代码检查 | `uv run ruff check .` | 0 error |
| 2 | 格式检查 | `uv run ruff format --check .` | 0 diff |
| 3 | 类型检查 | `uv run mypy app` | 0 error（`ignore_missing_imports=true` 允许，但 `app` 内 MUST 无 `Any` 滥用新增） |
| 4 | 单元 + 契约测试 | `uv run pytest tests/unit tests/contract` | 全通过 |
| 5 | 覆盖率 | `uv run pytest --cov=app --cov-report=term-missing` | 整体 ≥ 70%；`app/rag/chunking`、`app/services`、`app/core` 关键模块 ≥ 85% |
| 6 | 集成测试 | `uv run pytest tests/integration` | 全通过（CI 中用 compose 起依赖） |
| 7 | OpenAPI 快照 | `tests/contract/test_openapi_snapshot.py` | 与 `docs/openapi.snapshot.json` 一致；变更需显式更新快照 |

不入 CI（本地/手动触发）：`tests/perf`（`-m perf`）、`tests/eval`（需真实 LLM 与模型权重）。

## 7. 缺陷分级与出口标准

| 级别 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 数据泄漏（跨用户可见）、数据丢失（已删文档仍被检索）、服务不可用 | 立即修复，阻塞发布 |
| P1 | 核心链路失败（对话/入库不可用）、指标劣化超门槛 | 本迭代必须修复 |
| P2 | 非核心功能异常、体验问题、指标小幅劣化 | 可排入下迭代 |
| P3 | 文案、日志、文档不一致 | 随手修 |

里程碑出口：**P0 = 0，P1 = 0**，且 §6 CI 全绿。发布后 24h 观察：`ai_requests_total{status=~"5.."}` 占比 < 1%、`ai_degraded_total` 无异常尖峰。
