# 09 · 数据存储模型

> 关联：需求 ID `REQ-DATA-*`；使用方见 [06 RAG](./06-RAG知识库.md)、[07 Memory](./07-Memory.md)、[08 异步任务](./08-异步任务.md)。

## 1. 存储职责划分

| 存储 | 存什么 | 不存什么 |
| --- | --- | --- |
| **MySQL** | KB / 文档 / 切片元数据 / 任务 / 长期记忆 / 摘要 / 幂等记录 / 审计 | 向量、原文文件、上下文原文 |
| **Milvus** | chunk 与 memory 的向量 + 检索所需标量字段 | 完整原文（只存能直接展示的 `content`） |
| **Redis** | 短期上下文、摘要缓存、**任务状态与索引（M7）**、任务事件总线（pub/sub）、退避重试队列、锁、限流计数、Embedding 缓存 | 权威数据（除 §4 注明的任务状态例外，均可重建） |
| **MinIO** | 上传的原始文件 | 解析后的中间产物 |
| **Kafka** | 任务消息 | 业务状态（以任务存储为准） |

**权威性**：对 KB / 文档 / 切片 / 长期记忆，MySQL 是**唯一权威**；Milvus/Redis/MinIO 均为可重建的派生物，但删除时必须同步清理。

> **M7 的一个例外（必须显式记住）**：当 `TASK_RUNNER=kafka` 时，任务状态的权威是
> **Redis**（`task:{task_id}`），因为在独立 Worker 进程里必须有一份**跨进程共享**的状态；
> 而 MySQL 的 `task` 表仓储（§2.4）尚未实现。也就是说：
> * `INFRA_BACKEND=memory` → 任务状态在**进程内存**（仅限单进程，故 `inline` 可用、`kafka` 不行）；
> * `INFRA_BACKEND=real` → 任务状态在 **Redis**（跨进程；TTL 30d）；
> * `task` 表是**最终形态**（持久、可 SQL 审计），但当前无实现，这一点在 `docs/12` §12.12 有记录。
> 这不是「Redis 偷偷变权威」的意外，而是「MySQL 仓储未实现」时的显式降级 —— Worker 启动时会**自检并拒绍启动**，
> 不允许在内存存储上跑（那种情况下消息能被消费但任务永远停在 `QUEUED`）。

## 2. MySQL 表结构（`REQ-DATA-001`）

约定：`utf8mb4` / `utf8mb4_0900_ai_ci`；时间列 `DATETIME(3)` 存 UTC；主键为 `VARCHAR(32)` 的带前缀 ULID；所有业务表 MUST 有 `user_id`（除 `idempotency_record` 外均建索引）。

**库名 `ai_platform`，两个服务（AI 与网关 `go-services`）的表全部在这一个库里**，合计 **15 张**：

| 归属 | 表 | 建表脚本 |
| --- | --- | --- |
| AI 独占（7） | `knowledge_base` / `document` / `document_chunk` / `task` / `user_memory` / `conversation_summary` / `user_settings` | `deploy/mysql/001_init_schema.sql` |
| **共享**（2） | `idempotency_record` / `audit_log` | 同上（**只在此定义**，见 §2.7 / §2.8） |
| 网关独占（6） | `user` / `refresh_token` / `conversation` / `message` / `quota_usage` / `usage_record` | `ai-platform-go/deploy/mysql/001_gateway_tables.sql` |

> ⚠️ **共享表 MUST 只有一份定义**：同库同名只能有一张表，所以本节 §2.7 / §2.8 给出的是
> 两个服务的**并集**（网关要的 `method` / `request_hash` / `ip` / `user_agent` 也在里面），
> 网关侧 MUST NOT 再 `CREATE` 一遍。两边各写一份的直接后果是：第二个 `CREATE TABLE`
> 因「表已存在」而**看起来成功**，实际用的是先建好的那张，缺列要到写入时才暴露。
>
> 另外：**会话台账、用户、配额在网关侧**（见 §2.6 注），所以本服务的建表脚本不会创建
> `conversation` / `message` / `user`；而 `user_id` 的权威行也在网关的 `user` 表里 ——
> 本服务只存 `user_id` 这个标量，不建跨表引用（§6 "不建物理外键"）。

### 2.1 `knowledge_base`

```sql
CREATE TABLE knowledge_base (
  id                VARCHAR(32)  NOT NULL COMMENT 'kb_*',
  user_id           VARCHAR(64)  NOT NULL,
  name              VARCHAR(64)  NOT NULL,
  description       VARCHAR(500) NOT NULL DEFAULT '',
  chunk_size        INT          NOT NULL DEFAULT 512,
  chunk_overlap     INT          NOT NULL DEFAULT 64,
  embedding_model   VARCHAR(128) NULL,
  embedding_dim     INT          NOT NULL DEFAULT 1024,
  retrieval_top_k   INT          NOT NULL DEFAULT 20,
  rerank_top_n      INT          NOT NULL DEFAULT 5,
  score_threshold   FLOAT        NOT NULL DEFAULT 0,
  status            VARCHAR(16)  NOT NULL DEFAULT 'active' COMMENT 'active|indexing|failed',
  document_count    INT          NOT NULL DEFAULT 0,
  chunk_count       BIGINT       NOT NULL DEFAULT 0,
  metadata          JSON         NULL,
  created_at        DATETIME(3)  NOT NULL,
  updated_at        DATETIME(3)  NOT NULL,
  deleted_at        DATETIME(3)  NULL,
  deleted_key       DATETIME(3)  GENERATED ALWAYS AS (IFNULL(deleted_at, '1970-01-01 00:00:00.000')) STORED,
  PRIMARY KEY (id),
  UNIQUE KEY uk_kb_user_name (user_id, name, deleted_key),
  KEY idx_kb_user_created (user_id, created_at DESC)
) ENGINE=InnoDB;
```

> `deleted_key` 是**必须**的：唯一索引不比较 `NULL`，若直接对 `(user_id, name, deleted_at)` 建键，
> 未删除行（`deleted_at IS NULL`）彼此不冲突，同名知识库可以无限插入 —— 约束形同虚设
> （实测第二条同名插入 `ROW_COUNT() = 1`）。生成列把 NULL 换成哨兵时刻，同时保住
> 「同名只能有一条未删除」与「软删后可以重建同名」。

> 计数列（`document_count`/`chunk_count`）是**冗余缓存**，MUST 在任务完成时用 `UPDATE ... SET x = (SELECT COUNT(*) ...)` 重算，不做 `+1` 累加（避免重试导致漂移）。

### 2.2 `document`

```sql
CREATE TABLE document (
  id              VARCHAR(32)  NOT NULL COMMENT 'doc_*',
  kb_id           VARCHAR(32)  NOT NULL,
  user_id         VARCHAR(64)  NOT NULL,
  doc_name        VARCHAR(512) NOT NULL,
  file_ext        VARCHAR(16)  NOT NULL,
  mime_type       VARCHAR(128) NOT NULL,
  size_bytes      BIGINT       NOT NULL,
  page_count      INT          NULL,
  object_key      VARCHAR(1024) NOT NULL COMMENT 'MinIO key',
  content_sha256  CHAR(64)     NOT NULL,
  status          VARCHAR(16)  NOT NULL COMMENT 'PENDING|PARSING|CHUNKING|EMBEDDING|INDEXED|FAILED',
  chunk_count     INT          NOT NULL DEFAULT 0,
  chunks_total    INT          NULL COMMENT '切分产出切片数（截断前）；NULL=还没走到切分',
  truncated       TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '是否因 MAX_DOC_CHUNKS 丢弃尾部切片',
  char_count      INT          NOT NULL DEFAULT 0,
  chunk_size      INT          NOT NULL,
  chunk_overlap   INT          NOT NULL,
  task_id         VARCHAR(32)  NULL,
  error_code      VARCHAR(64)  NULL,
  error_message   VARCHAR(1000) NULL,
  metadata        JSON         NULL,
  indexed_at      DATETIME(3)  NULL,
  created_at      DATETIME(3)  NOT NULL,
  updated_at      DATETIME(3)  NOT NULL,
  deleted_at      DATETIME(3)  NULL,
  deleted_key     DATETIME(3)   GENERATED ALWAYS AS (IFNULL(deleted_at, '1970-01-01 00:00:00.000')) STORED,
  PRIMARY KEY (id),
  UNIQUE KEY uk_doc_dedupe (kb_id, content_sha256, deleted_key),
  KEY idx_doc_kb_status (kb_id, status),
  KEY idx_doc_user_created (user_id, created_at DESC)
) ENGINE=InnoDB;
```

> 去重键里带上 `deleted_key`（而不是只靠 `(kb_id, content_sha256)`）：未删除时同一文件在一个库里
> 只能有一份；已软删后允许重新上传 —— 否则用户删了文档就再也传不回同一份，而列表里又看不见
> 那条已删记录，只能收到一句「文件已存在」。

> **M9 补列（截断事实外显，`docs/10` UP-01）**：`chunks_total` / `truncated`。
> 三者的关系要一次说清：
>
> - `chunk_count` = **实际入库**的切片数（截断**后**）；
> - `chunks_total` = **切分产出**的切片数（截断**前**），`NULL` = 还没走到切分这一步；
> - `truncated` = 是否因 `MAX_DOC_CHUNKS` 丢了尾部。
>
> ⇒ `truncated = 1 且 chunk_count < chunks_total` **就是**「这份文档没有被完整索引」的判据；
> `truncated = 0` 时 `chunk_count == chunks_total`（除 FAILED/CANCELED 的中途态外）。
> 已并入 `001_init_schema.sql`（新库一次到位），老库执行 `deploy/mysql/004_add_ingest_facts.sql` 补列。

### 2.7 `idempotency_record`（**共享表**）

```sql
CREATE TABLE idempotency_record (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  user_id       VARCHAR(64)  NOT NULL,
  method        VARCHAR(8)   NOT NULL DEFAULT '' COMMENT '网关必填；AI 侧不填',
  path          VARCHAR(255) NOT NULL,
  idem_key      VARCHAR(128) NOT NULL,
  request_hash  CHAR(64)     NOT NULL DEFAULT '' COMMENT '网关必填；AI 侧不填',
  status_code   SMALLINT     NOT NULL,
  response_body JSON         NOT NULL,
  created_at    DATETIME(3)  NOT NULL,
  expires_at    DATETIME(3)  NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_idem (user_id, method, path, idem_key),
  KEY idx_idem_expire (expires_at)
) ENGINE=InnoDB;
```

> `method` / `request_hash` 是**网关**要的（它靠 `request_hash` 识别「同一个
> `Idempotency-Key` 换了请求体」）；本服务不填，所以给了 `DEFAULT ''` —— 只填
> `(user_id, path, idem_key)` 也能插入，旧写法不会因缺列而报错。
>
> 本服务写接口靠路径本身区分动作，所以不依赖 `method`。

## 3. Milvus 集合（`REQ-DATA-002/003`）

约定：时间戳在 Milvus 中以 `INT64` 毫秒存储（Milvus 无 datetime 类型）；`NULL` 用哨兵值（`page = -1`）。向量维度必须与 `embedding_dim` 一致，启动期 MUST 校验（不一致 → `VECTOR_DIM_MISMATCH`，应用拒绝启动）。

### 3.1 `ai_platform_chunks`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `VARCHAR(64)`（主键） | `chk_*` |
| `user_id` | `VARCHAR(64)` | 租户过滤，**必备** |
| `kb_id` | `VARCHAR(64)` | 知识库过滤 |
| `doc_id` | `VARCHAR(64)` | 文档过滤/删除 |
| `chunk_index` | `INT64` | 顺序 |
| `content` | `VARCHAR(65535)` | 切片原文 |
| `content_sha256` | `VARCHAR(64)` | 去重 |
| `page` | `INT64` | 页码，`-1` 表示无 |
| `heading_path` | `VARCHAR(512)` | 标题路径，`""` 表示无 |
| `char_start` / `char_end` | `INT64` | 原文偏移 |
| `created_at` | `INT64` | epoch ms |
| `embedding` | `FLOAT_VECTOR(1024)` | 默认档为 Qwen3-Embedding 向量（已归一化）；⚠️ 本地 bge-m3 档**也是 1024 维但向量空间不同**，不能因为"维度一样"就复用同一集合 ⇒ **换模型必须换集合名或 drop 重建**（启动期已加"已存在集合的实际维度"校验） |

索引：

| 类型 | 字段 | 参数 |
| --- | --- | --- |
| 向量 | `embedding` | `HNSW`，`M=16`，`efConstruction=200`，`metric_type=COSINE` |
| 标量 | `user_id` / `kb_id` / `doc_id` | `INVERTED` |

## 4. Redis Key 规范（`REQ-DATA-004`）

**所有 Key MUST 带 TTL**（`PERSIST` 禁止），防止漏删导致内存持续增长。

记忆与限流域（M2–M5）：

| Key 模式 | 类型 | TTL | 内容 | 需求 |
| --- | --- | --- | --- | --- |
| `ctx:{conversation_id}` | List | 7d | 上下文消息 JSON，`LTRIM` 保留 200 条 | `REQ-MEM-001` |
| `summary:{conversation_id}` | String | 1d | 摘要 JSON 缓存 | `REQ-MEM-003` |
| `lock:ctx:{conversation_id}` | String(NX) | 5s | 上下文写锁 | `REQ-MEM-001` |
| `lock:summary:{conversation_id}` | String(NX) | 300s | 摘要防抖 | `REQ-MEM-003` |
| `lock:ingest:{doc_id}` | String(NX) | 1800s | 入库互斥 | `REQ-TASK-005` |
| `embed:cache:{sha256}` | String | 24h | 向量缓存（base64 float32） | `REQ-RAG-005` |
| `rate:{user_id}:{scope}` | String | 60s | 限流计数 | `REQ-API-010` |
| `dedupe:{kb_id}:{sha256}` | String | 7d | sha256 → `doc_id` 快速去重 | `REQ-RAG-007` |

异步任务域（M7 落地，实现见 `app/tasks/redis_store.py` / `retry.py` / `events.py`）：

| Key 模式 | 类型 | TTL | 内容 | 说明 |
| --- | --- | --- | --- | --- |
| `task:{task_id}` | Hash | 30d | 字段 `json` = 任务快照 JSON | 创建与更新都是**单次往返**（`HSET` + `EXPIRE` / Lua CAS） |
| `task:idem:{idem_key}` | String | 30d | `idem_key` → `task_id` | `SET NX` 完成幂等占位；抢占失败则 `GET` 取回既有 `task_id` |
| `task:user:{user_id}` | ZSet | 30d | score = `created_at` 毫秒，member = `task_id` | 列表查询的**索引**（`ZREVRANGE` 即天然倒序），避免 `SCAN` 全库 |
| `task:open` | ZSet | 30d | score = `created_at` 毫秒，member = **未结束**任务的 `task_id` | 供「队列容量闸」`ZCARD` 与补偿扫描使用；终态时 `ZREM` |
| `cancel:{task_id}` | String(NX) | 1d | 取消标记 | 只用 `SET NX` + `EXISTS`：取消是**单向**的，重复请求不刷新状态 |
| `retry:zset` | ZSet | **无 TTL** | score = 到期时间毫秒，member = `{task_id}:{attempt}` | 空即无害（`ZSET` 自清）；member 带 `attempt` 使同一次重试**可去重** |
| `task:events:{task_id}` | pub/sub 频道 | — | `TaskEvent` JSON 帧 | 无持久化语义：**不重放、不保证送达**，所以首帧一定取自 `task:{task_id}` 快照 |

> 「Hash 还是 String」这条选择是实测出来的：`task:{id}` 用 Hash 装一个 `json` 字段，
> 是为了让「写入 + 设 TTL」和「CAS 更新」能各自塞进一段 Lua 原子完成（单次往返）。
> 若用普通 String，`SET` 会**清掉 TTL**，而 `SET ... KEEPTTL` 又无法与 `WATCH`/`CAS` 同时表达。
>
> `retry:zset` 是唯一的无 TTL Key：它本身有自清性质（成员被认领后即 `ZREM`），
> 加 TTL 反而会静默丢掉尚未到期的重试。上面的「所有 Key MUST 带 TTL」以**业务数据域**为界，
> 队列类结构（`retry:zset`）用「成员生命周期」而非 TTL 控制。

> `{conversation_id}`/`{user_id}` 直接拼接会有 Key 注入风险，MUST 校验其满足 `^[A-Za-z0-9_-]{1,64}$`，否则拒绝。
> 同理，`retry:zset` 的 member 编码 `{task_id}:{attempt}` 依赖**`task_id` 不含 `:`**
> （ULID + 前缀天然满足；解码时对格式不符的 member 只告警跳过，不使整批认领失败）。

## 5. MinIO 与 Kafka（`REQ-DATA-005`）

### 5.1 MinIO

| 项 | 约定 |
| --- | --- |
| Bucket | `MINIO_BUCKET`（默认 `ai-platform`），**私有**，禁止公开读 |
| 对象路径 | `{user_id}/{kb_id}/{doc_id}/{sanitized_filename}` |
| 文件名清洗 | 去掉路径分隔符与控制字符，保留扩展名，长度 ≤ 128；同名冲突由 `doc_id` 目录天然隔离 |
| 写入 | MUST 用 `put_object` 流式上传（禁止整体读入内存）；写入后校验大小与 `content_sha256` |
| 读取 | 解析时用流式读取（`get_object`），大文件禁止 `read()` 全量 |
| 下载 | 通过 `presigned_get_object` 提供临时 URL，有效期 15 分钟 |
| 生命周期 | 文档删除时 MUST 删除对象；Bucket 规则：无孤立对象（`document` 表无引用即应删除） |
| 加密 | 生产环境 SHOULD 启用 SSE-S3 |

### 5.2 Kafka

| Topic | 分区键 | 消费组 | 说明 |
| --- | --- | --- | --- |
| `ai.task.document_ingest` | `resource_id` | `ai-platform-worker` | 文档解析与索引 |
| `ai.task.document_delete` | `resource_id` | `ai-platform-worker` | 三存储清理 |
| `ai.task.summary_build` | `resource_id`（= `conversation_id`） | `ai-platform-worker` | 摘要生成 |
| `ai.task.memory_extract` | **`user_id`** | `ai-platform-worker` | 记忆抽取（按用户保序） |
| `ai.task.dlq` | 沿用原消息的 key | —（仅人工/告警消费） | 死信 |

消息体 MUST 只含 `{"task_id": "...", "attempt": 1}`，**业务参数一律从 MySQL 读**（避免消息与库不一致）。

实现约定（M7 落地，`app/tasks/transport.py`）：

1. **主题名由任务类型推导**，不查表：`topic_for(type) = "ai.task." + type`。
   查表漏一行的表现是「任务建好了但投到了不存在的主题」，而推导漏不了。
   `TaskType` 的取值集合与上表四行**完全一致**（`document_ingest` / `document_delete` /
   `summary_build` / `memory_extract`），因此 `docs/08` §5.1 的「一类型一主题」是同一回事。
2. **分区键冲突时以本表为准**（按主题逐个写明，比 `docs/08` 的通用规则更具体）：
   只有 `memory_extract` 用 `user_id`，其余一律 `resource_id`。理由不是「按用户保序」这句口号，
   而是 `memory_extract` 会 **merge 同一行记忆**，同用户并发两个抽取任务会互相覆盖 `hit_count` 与正文。
3. **`type` / `topic` / `partition_key` 不进消息体**：它们分别由主题名与消息 key 解出。
   消息体越小，能漂移的地方越少。
4. **offset 提交条件**：任务状态**已落库**且该分区**连续水位线**已推进（`app/worker/offsets.py`）。
   按「谁先完成谁先提交」会跳消息（见 `docs/12` §12.1）。
5. **`FETCH_MAX_RECORDS = 1`**：单次只拉一条。调大后并发完成顺序与 `batch` 返回顺序不一致，
   水位线会提前推进 —— 这是「用性能换正确性」的显式取舍，不是漏优化。
6. 启动不依赖主题预先存在：`apache/kafka` 的 `AUTO_CREATE_TOPICS_ENABLE=true`
   （见 `deploy/infra/compose.yml`），生产环境 SHOULD 改为预先建主题并显式指定分区数。

## 6. 一致性与删除（`REQ-DATA-006/007`）

| 要求 | 说明 |
| --- | --- |
| 租户隔离 | `knowledge_base`/`document`/`document_chunk`/`task`/`user_memory`/`conversation_summary` MUST 有 `user_id`；Milvus 两个集合 MUST 有 `user_id` 标量字段与索引 |
| 软删除 | `knowledge_base` / `document` 用 `deleted_at`；所有查询 MUST 带 `deleted_at IS NULL`；软删记录保留 30 天后由清理任务物理删除 |
| 硬删除（派生数据） | Milvus 向量、Redis Key、MinIO 对象 MUST **立即**物理删除，不留软删标记 |
| 跨存储一致性 | 采用「先建后删」：入库先向量后状态；删除先向量/对象后 MySQL（若中途失败，任务重试可幂等补齐） |
| 孤儿清理 | 每日任务扫描：Milvus 中 `doc_id` 不存在于 `document` 的向量 → 删除并告警；MinIO 中无引用的对象 → 删除并告警 |
| 事务边界 | 「建任务 + 改文档状态」在同一 MySQL 事务；**投递 Kafka 在事务提交后** |
