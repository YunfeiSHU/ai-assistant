# 09 · 数据存储模型

> 关联：需求 ID `REQ-DATA-*`；使用方见 [06 RAG](./06-RAG知识库.md)、[07 Memory](./07-Memory.md)、[08 异步任务](./08-异步任务.md)。

## 1. 存储职责划分

| 存储 | 存什么 | 不存什么 |
| --- | --- | --- |
| **MySQL** | KB / 文档 / 切片元数据 / 任务 / 长期记忆 / 摘要 / 幂等记录 / 审计 | 向量、原文文件、上下文原文 |
| **Milvus** | chunk 与 memory 的向量 + 检索所需标量字段 | 完整原文（只存能直接展示的 `content`） |
| **Redis** | 短期上下文、摘要缓存、**任务状态与索引（M7）**、任务事件总线（pub/sub）、退避重试队列、锁、限流计数、Embedding 缓存 | 权威数据（除 §4 注明的任务状态例外，均可重建） |
| **MinIO** | 上传的原始文件 | 解析后的中间产物 |
| **Kafka** | 任务消息 | 业务状态（以任务存储为准） |

**权威性**：KB / 文档 / 切片 / 长期记忆以 MySQL 为**唯一权威**；Milvus/Redis/MinIO 都是可重建的派生物，但删除时必须同步清理。

> **M7 的任务状态例外**：`TASK_RUNNER=kafka` 时任务状态的权威是 Redis `task:{task_id}`（Worker 在独立进程，必须有一份跨进程共享的状态），因为 MySQL `task` 表仓储尚未实现（`app/tasks/store.py` 只有内存与 Redis 两个实现）。`INFRA_BACKEND=memory` → 状态在**进程内存**（仅单进程，故 `inline` 可用、`kafka` 不行）；`real` → Redis（TTL 30d）。Worker 启动时自检并**拒绝启动**于内存存储，否则消息能被消费而任务永远停在 `QUEUED`。

## 2. MySQL 表结构（`REQ-DATA-001`）

约定：`utf8mb4` / `utf8mb4_0900_ai_ci`；时间列 `DATETIME(3)` 存 UTC；主键为 `VARCHAR(32)` 的带前缀 ULID；**未标 `NULL` 的列一律 NOT NULL**；所有业务表 MUST 有 `user_id`（除 `idempotency_record` 外均建索引）。

**库名 `ai_platform`，两个服务的表全部在这一个库里，合计 15 张**：

| 归属 | 表 | 建表脚本 |
| --- | --- | --- |
| AI 独占（7） | `knowledge_base` / `document` / `document_chunk` / `task` / `user_memory` / `conversation_summary` / `user_settings` | `deploy/mysql/001_init_schema.sql` |
| **共享**（2） | `idempotency_record` / `audit_log` | 同上（**只在此定义**，见 §2.7 / §2.8） |
| 网关独占（6） | `user` / `refresh_token` / `conversation` / `message` / `quota_usage` / `usage_record` | `ai-platform-go/deploy/mysql/001_gateway_tables.sql` |

> **共享表 MUST 只有一份定义**：同库同名只能有一张表，所以 §2.7 / §2.8 给的是两服务的**并集**（网关要的 `method` / `request_hash` / `ip` / `user_agent` 也在里面），网关侧 MUST NOT 再 `CREATE` 一遍 —— 各写一份时第二个 `CREATE` 会因「表已存在」看起来成功，缺列要到写入时才暴露。
> 会话台账、用户、配额都在网关侧，所以本服务不建 `conversation` / `message` / `user`；`user_id` 的权威行在网关 `user` 表，本服务只存这个标量、不建跨表引用（§6）。
> 网关 6 张表的键（只列约束，不重复列定义）：`uk_user_email (email)`、`uk_rt_hash (token_hash)`、`uk_msg_conv_seq (conversation_id, seq)`；`quota_usage` 以业务键 `(user_id, metric, period)` 为 PK（无代理 `id`），其余 PK 为 `id`。

### 2.1 `knowledge_base`

| 列 | 类型 / 约束 |
| --- | --- |
| `id` | `VARCHAR(32)` PK，`kb_*` |
| `user_id` | `VARCHAR(64)` NOT NULL |
| `name` | `VARCHAR(64)` NOT NULL |
| `description` | `VARCHAR(500)` NOT NULL DEFAULT `''` |
| `chunk_size` / `chunk_overlap` | `INT` NOT NULL，默认 512 / 64 |
| `embedding_model` | `VARCHAR(128)` NULL |
| `embedding_dim` / `retrieval_top_k` / `rerank_top_n` | `INT` NOT NULL，默认 1024 / 20 / 5 |
| `score_threshold` | `FLOAT` NOT NULL DEFAULT 0 |
| `status` | `VARCHAR(16)` DEFAULT `active`（`active\|indexing\|failed`） |
| `document_count` / `chunk_count` | `INT` / `BIGINT` NOT NULL DEFAULT 0 |
| `metadata` | `JSON` NULL |
| `created_at` / `updated_at` / `deleted_at` | `DATETIME(3)` NOT NULL / NOT NULL / NULL |
| `deleted_key` | `DATETIME(3)` GENERATED ALWAYS AS `IFNULL(deleted_at,'1970-01-01 00:00:00.000')` STORED |
| 索引 | PK `(id)`；`uk_kb_user_name (user_id,name,deleted_key)`；`idx_kb_user_created (user_id,created_at DESC)` |

> `deleted_key` 是**必须**的：唯一索引不比较 `NULL`，直接对 `(user_id, name, deleted_at)` 建键时未删除行彼此不冲突，同名知识库可以无限插入（实测第二条 `ROW_COUNT() = 1`，约束形同虚设）；生成列把 `NULL` 换成哨兵时刻，同时保住「同名只能有一条未删除」与「软删后可重建同名」。
> 计数列 `document_count` / `chunk_count` 是**冗余缓存**，任务完成时用 `UPDATE ... SET x = (SELECT COUNT(*) ...)` 重算，不做 `+1` 累加（避免重试导致漂移）。

| `char_count` | `INT` DEFAULT 0 |

| `created_at` / `updated_at` / `deleted_at` | `DATETIME(3)` NOT NULL / NOT NULL / NULL |
| `deleted_key` | `DATETIME(3)` 生成列，同 §2.1 |
| 索引 | PK `(id)`；`uk_doc_dedupe (kb_id,content_sha256,deleted_key)`；`idx_doc_kb_status (kb_id,status)`；`idx_doc_user_created (user_id,created_at DESC)` |

> 去重键带 `deleted_key`：未删除时同一文件在一个库里只能有一份；软删后允许重新上传 —— 否则用户删了文档就再也传不回同一份，而列表里又看不见那条记录，只能收到「文件已存在」。
> **M9 截断事实外显（`docs/10` UP-01）**：`truncated = 1 且 chunk_count < chunks_total` 就是「这份文档没有被完整索引」的判据；`truncated = 0` 时两者相等（除 FAILED/CANCELED 中途态）。

## 4. Redis Key 规范（`REQ-DATA-004`）

**所有 Key MUST 带 TTL**（`PERSIST` 禁止），防止漏删导致内存持续增长。

| Key 模式 | 类型 | TTL | 内容 | 需求 |
| --- | --- | --- | --- | --- |
| `ctx:{conversation_id}` | List | 7d | 上下文消息 JSON，`LTRIM` 保留 200 条 | `REQ-MEM-001` |
| `summary:{conversation_id}` | String | 1d | 摘要 JSON 缓存 | `REQ-MEM-003` |
| `lock:ctx:{conversation_id}` | String(NX) | 5s | 上下文写锁 | `REQ-MEM-001` |
| `lock:summary:{conversation_id}` | String(NX) | 300s | 摘要防抖 | `REQ-MEM-003` |
| `lock:ingest:{doc_id}` | String(NX) | 1800s | 入库互斥 | `REQ-TASK-005` |
| `embed:cache:{sha256}` | String | 24h | 向量缓存（base64 float32） | `REQ-RAG-005` |
| `rate:{user_id}:{scope}` | String | 60s | 限流计数 | `REQ-API-010` |
| `dedupe:{kb_id}:{sha256}` | String | 7d | sha256 → `doc_id` 快速去重 | `REQ-RAG-007` |

异步任务域（M7 落地，`app/tasks/{redis_store,retry,events}.py`）：

| Key 模式 | 类型 | TTL | 内容 | 说明 |
| --- | --- | --- | --- | --- |
| `task:{task_id}` | Hash | 30d | 字段 `json` = 任务快照 JSON | 创建与更新都是**单次往返**（`HSET` + `EXPIRE` / Lua CAS） |
| `task:idem:{idem_key}` | String | 30d | `idem_key` → `task_id` | `SET NX` 完成幂等占位；抢占失败则 `GET` 取回既有 `task_id` |
| `task:user:{user_id}` | ZSet | 30d | score = `created_at` 毫秒，member = `task_id` | 列表查询的**索引**（`ZREVRANGE` 即天然倒序），避免 `SCAN` 全库 |
| `task:open` | ZSet | 30d | score = `created_at` 毫秒，member = **未结束**任务的 `task_id` | 供「队列容量闸」`ZCARD` 与补偿扫描使用；终态时 `ZREM` |
| `cancel:{task_id}` | String(NX) | 1d | 取消标记 | 只用 `SET NX` + `EXISTS`：取消是**单向**的，重复请求不刷新状态 |
| `retry:zset` | ZSet | **无 TTL** | score = 到期时间毫秒，member = `{task_id}:{attempt}` | 空即无害（`ZSET` 自清）；member 带 `attempt` 使同一次重试**可去重** |
| `task:events:{task_id}` | pub/sub 频道 | — | `TaskEvent` JSON 帧 | 无持久化语义：**不重放、不保证送达**，所以首帧一定取自 `task:{task_id}` 快照 |

> 「Hash 还是 String」是实测出来的：`task:{id}` 用 Hash 装一个 `json` 字段，是为了让「写入 + 设 TTL」和「CAS 更新」各自塞进一段 Lua 原子完成（单次往返）；普通 String 的 `SET` 会**清掉 TTL**，而 `SET ... KEEPTTL` 又无法与 `WATCH`/`CAS` 同时表达。
> `retry:zset` 是唯一的无 TTL Key：成员被认领后即 `ZREM`（自清），加 TTL 反而会静默丢掉尚未到期的重试 —— 「所有 Key MUST 带 TTL」以**业务数据域**为界，队列类结构用成员生命周期控制。
> `{conversation_id}` / `{user_id}` 直接拼接有 Key 注入风险，MUST 校验其满足 `^[A-Za-z0-9_-]{1,64}$`；`retry:zset` 的 member 编码依赖 **`task_id` 不含 `:`**（ULID + 前缀天然满足；格式不符的 member 只告警跳过，不使整批认领失败）。

## 5. MinIO 与 Kafka（`REQ-DATA-005`）

### 5.1 MinIO

| 项 | 约定 |
| --- | --- |
| Bucket | `MINIO_BUCKET`（默认 `ai-platform`），**私有**，禁止公开读 |
| 对象路径 | `{user_id}/{kb_id}/{doc_id}/{sanitized_filename}` |
| 文件名清洗 | 去掉路径分隔符与控制字符，保留扩展名，长度 ≤ 128；同名冲突由 `doc_id` 目录天然隔离 |
| 写入 | MUST 用 `put_object` 流式上传（禁止整体读入内存）；写入后校验大小与 `content_sha256` |
| 读取 | 解析时用流式读取（`get_object`），大文件禁止 `read()` 全量 |
| 下载 | 通过 `presigned_get_object` 提供临时 URL，有效期 15 分钟 |
| 生命周期 | 文档删除时 MUST 删除对象；Bucket 规则：无孤立对象（`document` 表无引用即应删除） |
| 加密 | 生产环境 SHOULD 启用 SSE-S3 |

### 5.2 Kafka

主题清单、分区键、消费组与重试/背压见 [08 异步任务](./08-异步任务.md) §5.1–§5.5（本文不重复表格），存储侧只保留四条约定：

1. **主题名由 `type` 推导**（`topic_for(type) = "ai.task." + type`），不查表 —— 查表漏一行的表现是「任务建好了但投到不存在的主题」，推导漏不了；`TaskType` 共 6 个取值（`document_ingest` / `document_delete` / `kb_reindex` / `summary_build` / `memory_extract` / `memory_delete`）。
2. **分区键只有 `memory_extract` 用 `user_id`**，其余一律 `resource_id`：前者会 merge 同一行记忆，同用户并发两个抽取任务会互相覆盖 `hit_count` 与正文。
3. **消息体只有 `{"task_id": "...", "attempt": 1}`**，业务参数一律从 MySQL 读；`type` / `topic` / `partition_key` 不进消息体（分别由主题名与消息 key 解出，消息越小能漂移的地方越少）。
4. **`FETCH_MAX_RECORDS = 1`**，offset 只在任务状态已落库且该分区**连续水位线**推进后提交 —— 调大后并发完成顺序与 `batch` 返回顺序不一致会跳消息，这是「用性能换正确性」的显式取舍。
5. **主题不预建**：`apache/kafka` 设 `AUTO_CREATE_TOPICS_ENABLE=true`（`deploy/infra/compose.yml`），生产环境 SHOULD 改为预先建主题并显式指定分区数。

## 6. 一致性与删除（`REQ-DATA-006/007`）

| 要求 | 说明 |
| --- | --- |
| 租户隔离 | `knowledge_base`/`document`/`document_chunk`/`task`/`user_memory`/`conversation_summary` MUST 有 `user_id`；Milvus 两个集合 MUST 有 `user_id` 标量字段与索引 |
| 无物理外键 | 跨服务（会话台账在网关）与跨存储（Milvus/Redis/MinIO）的一致性由应用层与孤儿清理保证；物理外键只会在删除派生数据时挡路 |
| 软删除 | `knowledge_base` / `document` 用 `deleted_at`；所有查询 MUST 带 `deleted_at IS NULL`；软删记录保留 30 天后由清理任务物理删除 |
| 硬删除（派生数据） | Milvus 向量、Redis Key、MinIO 对象 MUST **立即**物理删除，不留软删标记 |
| 跨存储一致性 | 采用「先建后删」：入库先向量后状态；删除先向量/对象后 MySQL（若中途失败，任务重试可幂等补齐） |
| 孤儿清理 | 每日任务扫描：Milvus 中 `doc_id` 不存在于 `document` 的向量 → 删除并告警；MinIO 中无引用的对象 → 删除并告警 |
| 事务边界 | 「建任务 + 改文档状态」在同一 MySQL 事务；**投递 Kafka 在事务提交后** |
