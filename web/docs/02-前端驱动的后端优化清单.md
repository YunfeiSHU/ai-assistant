## 1. P0 · 体验硬伤

### B-01 · 任务进度 SSE

**前端遇到的问题**：上传 20MB 文档后只有一个“处理中”；任务进度每 2 秒跳一次，完成到界面更新最多延迟 2 秒。任务列表页为了显示多条进度，还要额外开 5 秒列表轮询。

**后端解决方案（已实施）**：

- 新增独立 `TaskEventHandler` 透传 `GET /api/v1/tasks/{id}/events`；
- 转发 Bearer / trace，逐块读取并 Flush，不缓冲整个响应；
- 非 2xx 原样返回 JSON 错误信封；
- Python 已有 `progress / error / done / ping` 事件，网关不重新定义协议。

**为什么选这个**：

- 不复用现有 `Forward`：它会把 `resp.Body` 读完再写回，结构上不可能透传 SSE；
- 不继续只靠轮询：2s 粒度是体验硬伤，且任务多时 QPS 高；
- 不上 WebSocket：任务是“一轮一个 SSE”，WebSocket 会多一套连接/鉴权/重连状态；
- 前端保留轮询兜底：SSE 失败/结束后退回 2s 轮询，旧行为不退化。

**状态/边界**：✅ 已完成；SSE 未做自动重连与 `Last-Event-ID` 续传。

### B-02 · 文档下载 / 预览

**前端遇到的问题**：回答里的 `[1]` 点开后只能看切片，不能打开原文 PDF/文档；用户无法核对引用。

**后端解决方案（已实施）**：

- `GET /documents/{id}/download`：真实对象存储 302 到短 TTL 预签名 URL；内存存储直接返回字节流；
- `GET /documents/{id}/download-url`：返回 `{url, expires_in, doc_name, mime_type}`；
- 网关透传 `Location`（原透传只回 `Content-Type` / `Retry-After`，会丢 302）；
- 前端引用卡加“查看原文”：有 URL 新窗口打开；无 URL 用 Bearer 拉字节后 `blob:` 打开。

**为什么选这个**：

- 预签名 URL 优于“网关代理整个文件”：大文件不经过网关内存；
- 不选“前端拿切片自己拼原文”：切片本来就不是完整原文，也不适合 PDF；
- 内存存储保留字节流分支：本地没有 MinIO 也能开发和验收。

**状态/边界**：✅ 已完成；真实 MinIO 预签名分支代码已实现，但本地主要验证 memory 字节流。

## 2. P1 · 正确性、安全与复杂度

### B-03 · 重新生成回答

**前端遇到的问题**：回答不满意只能重发问题，结果是多一条 user 消息、多扣一次配额、历史出现两组几乎一样的问答。

**后端解决方案（已实施）**：

- 新增 `POST /messages/{message_id}/regenerate`；
- 复用该 assistant 之前最近的一条 user，**不新增 user 消息**；
- 只写一条新 assistant；成功后删旧 assistant 并扣减会话计数；
- 生成前从 AI 上下文删旧 assistant；`use_memory=true` 时生成后删掉 Python 落下的重复 user。

**为什么选这个**：

- 不选“前端再发一次”：会重复 user 和配额，正是要解决的问题；
- 不选“原地覆盖旧 assistant”：需要更新消息表/审计字段，改动更大；当前删除旧回答后写新回答，语义更简单；
- 不选“流式重新生成”：实现成本高；先做非流式，把语义和配额做对。

**状态/边界**：✅ 已完成（非流式）；没有 `regenerated_from`/`superseded` 审计字段；生成失败时旧上下文已删，属于已知边界。

---

### B-04 · 删除消息同步 AI 上下文

**前端遇到的问题**：用户删掉含敏感信息的消息，界面消失了，但下一轮回答模型仍然“记得”；前端只能加免责声明。

**后端解决方案（已实施）**：

- Python 上下文存储新增 `delete_message`（按 ID 或 role+content 匹配）与 `delete_summary`；
- 内部接口 `POST /conversations/{id}/context/messages/delete`，不存在时幂等；
- 网关删除消息：**先同步 AI 上下文，成功后再删台账**；
- 摘要失效；`message_count` 用 `GREATEST(count-1,0)` 扣减；
- 前端消息项加删除入口 + 二次确认。

**为什么选这个**：

- 不选“删消息就清空整个上下文”：会丢失该会话所有其他上下文；
- 不选“异步删上下文、台账先删”：会出现“台账没了、模型还记得”的窗口，隐私不一致；
- 不选“只删台账”：就是原问题；
- 按 role+content 兜底：网关消息 ID 与 Python 上下文 ID 不保证一致。

**状态/边界**：✅ 已完成；只清短期上下文和摘要，**长期记忆里由该消息抽取的条目不会自动清**；Redis 删除是读改写，非 Lua 原子操作。

### B-05 · 流式 meta 补用户消息 ID/seq

**前端遇到的问题**：流式期间临时渲染 user/assistant 两个气泡；结束后要再拉一页消息对账。重复内容提问时靠内容匹配可能匹配错，且多一次 GET。

**后端解决方案（已实施）**：

- `StreamMetaEvent` 增加 `UserMessageID` / `UserSeq`；
- 网关在写 user 消息后，把这两个值注入 `meta`；
- SSE DTO 增加 `user_message_id` / `user_seq`；
- 前端 `ChatEvent.meta` / `TurnState` 保存，LiveTurn user 节点带 `data-message-id`。

**为什么选这个**：

- 用户消息在调用 AI 前已经落库并拿到 ID/seq，数据现成；
- 不选“前端自己生成 ID”：台账权威在网关，客户端 ID 不能直接作为服务端 ID；
- 纯增量字段，旧客户端忽略未知字段即可，不需要新接口。

**状态/边界**：✅ 已完成；仍保留结束后一次 refetch 拿 finalized assistant，B-05 解决的是“身份确定”，不是彻底取消对账。

---

### B-08 · refresh 令牌 HttpOnly Cookie

**前端遇到的问题**：refresh 30 天只能放 localStorage，任何 XSS 都能带走；sanitize/CSP 只能缓解。

**后端解决方案（已实施）**：

- 登录/刷新通过 `Set-Cookie: ai_refresh=...; HttpOnly; SameSite=Lax; Path=/api/v1/auth` 下发；
- JSON 不再返回 refresh；刷新轮换 Cookie；
- 登出、改密、刷新失败清 Cookie；
- 本地 HTTP 不设 `Secure`；HTTPS/`X-Forwarded-Proto=https` 自动设置；
- 跨站防线：SameSite + `Sec-Fetch-Site`；
- CLI/脚本保留 body 刷新，body 模式响应返回新 refresh。

**为什么选这个**：

- 不选 localStorage：XSS 可读，原问题；
- 不选“只存内存”：刷新页面就丢登录；
- 不选“refresh 放 URL/query”：会进日志和 Referer；
- Cookie 是浏览器唯一不暴露给 JS 的持久凭证通道；CLI 用 body 模式兼容。

**状态/边界**：✅ 已完成；生产必须 HTTPS；多标签轮换靠 `navigator.locks` 单飞。

### B-14 · 并发建会话 ID 冲突

**前端遇到的问题**：并发创建会话偶发 `503 DEPENDENCY_UNAVAILABLE`；用户看到“创建失败”，重试可能重复建会话。

**后端解决方案（已实施）**：

- `pkg/ids/ids.go` 的 `defaultNewID` 外层加 `sync.Mutex`；
- 补 2000 并发唯一性测试 + 20 路实测。

**为什么选这个**：

- 根因是全局 `ulid.Monotonic` 无并发保护，加锁最小、行为不变；
- 不选“数据库唯一冲突后重试”：会把错误变成多次写，且所有 ID 前缀都要处理；
- 不选“换成 UUID”：会改变现有 `cv_/msg_/doc_` 格式和排序语义。

**状态/边界**：✅ 已完成；锁是进程级，多实例各自生成仍靠 ULID 自身唯一性。

---

### B-15 · 上下文与 `use_memory` 解耦

**前端遇到的问题**：关闭记忆后，`/context` 为空、摘要无法生成；前端看起来像“漏渲染”，实际是后端把“短期上下文”和“长期记忆”共用一个开关。

**后端解决方案（已实施）**：

- `PreparedChat` 增加 `use_memory`，只表示长期记忆；
- `persist = conversation_id is not None`；有会话 ID 就先 `ensure` 再读写短期上下文；
- `_load_memory(..., include_memories=request.use_memory)`：历史/摘要始终读，长期记忆按开关；
- `_after_turn(..., use_memory=...)`：关闭记忆跳过 `memory_extract`，摘要仍按阈值生成。

**为什么选这个**：

- 不选“前端强制打开记忆”：用户关记忆是真实需求，不能绕过；
- 不选“拆成两个接口/两个开关”：会改变客户端契约，且用户心智还是一个“记忆”开关；
- 用 `conversation_id` 判断是否持久化：会话上下文本来就该跟会话走，和“是否召回长期记忆”无关。

**状态/边界**：✅ 已完成；语义变化：有 `conversation_id` 时以存储历史为准，请求体 `history` 不再混入。

## 3. P2 · 体验增强

### B-06 · 侧栏最后消息预览

**前端遇到的问题**：自动标题经常是“新对话 10-26”，几个会话长得一样；没有预览无法区分。前端自己逐条查消息就是 N+1。

**后端解决方案（已实施）**：

- 会话列表批量查每个会话最后一条非空 user/assistant；
- 返回 `last_message_preview`（120 字）；
- 用一条聚合 SQL 查全部会话，不在 Go 里循环查。

**为什么选这个**：

- 不选“前端 N+1”：列表一页 20 条会变 21 次查询；
- 不选“新增冗余列 + 迁移”：当前聚合查询足够，避免改表；
- 不选“只显示 message_count”：标题重复时仍然分不清。

**状态/边界**：✅ 已完成；预览未做脱敏/角色专项过滤，后续可加。

---

### B-07 · 限流剩余量响应头

**前端遇到的问题**：发送按钮只有 429 之后才知道“20 次/分钟用完了”；剩余 0 时不能提前禁用。

**后端解决方案（已实施）**：

- 限流器增加 `AllowInfo`，一次判定返回 used/remaining；
- 网关返回 `X-RateLimit-Scope/Limit/Remaining/Reset`；
- 429 保留 `Retry-After`；
- CORS `Expose-Headers` 暴露这些头；
- 前端只处理 `scope=message`，显示剩余次数，0 时禁用发送。

**为什么选这个**：

- 不选“中间件再读一次 Redis”：一次请求两次计数读，且固定窗口下两次读可能不一致；
- 不选“前端自己估算”：窗口边界/并发下不可靠；
- 限流头是标准做法，不改变限流算法。

**状态/边界**：✅ 已完成；固定窗口剩余量是近似值，前端只做提示。

---

### B-11 · `after_seq` 增量拉取

**前端遇到的问题**：断线重连、多标签同步或流式结束对账，只需要“seq > N”的消息；现在只能取一页再自己过滤。

**后端解决方案（已实施）**：

- `GET /conversations/{id}/messages?after_seq=N`，只返回 `seq > N`；
- 前端 `MessageFilters.after_seq` 支持；
- 会话头“增量刷新”：只拉新增、按 ID 去重后合并第一页，不整页重拉。

**为什么选这个**：

- 不选“整页 refetch”：消息多时浪费带宽，且会打乱当前分页状态；
- 不选“WebSocket 推送”：当前没有服务端主动通道，引入成本大于收益；
- 复用现有 `seq` 索引，不新增游标语义。

**状态/边界**：✅ 已完成；当前是手动增量刷新，没有自动断线重连。

---

### B-13 · 任务「取消中」可见

**前端遇到的问题**：`RUNNING` 任务点取消后接口仍返回 `RUNNING`（单批 Embedding 不可中断），前端无法区分“已请求取消”和“没点过”，用户反复点。

**后端解决方案（已实施）**：

- `Task` 增加派生字段 `cancel_requested`；
- 服务层对 RUNNING 任务查取消标记，`get/list` 补出该字段；
- 取消接口回显 `cancel_requested=true`；
- 前端显示“取消中…”并禁用重复取消。

**为什么选这个**：

- 不选“取消立即置 CANCELED”：这一批还在写向量库，前端会显示错误的“已取消”；
- 不选“前端自己计时猜”：没有服务端事实；
- 不新增取消表/字段，复用已有取消标记。

**状态/边界**：✅ 已完成；`cancel_requested` 是派生值，不持久化到任务记录。

## 4. 产品级能力

### B-09 · 聊天附件

**前端遇到的问题**：用户最自然的动作是把文件拖进对话框；旧实现 `attachments` 非空直接 400，只能引导“先上传知识库”，多三步。

**后端解决方案（已实施，方案 A）**：

- 请求新增 `attachment_doc_ids`（最多 5 个，已入库文档 ID）；
- 网关透传到 Python；
- Python RAG 检索用 `doc_ids` 过滤，用户隔离仍由 `user_id` 保证；
- 前端从当前会话资料库选择文档，发送时强制 `use_rag`，本轮结束清理选择。

**为什么选这个**：

- 不选“二进制文件直传对话”：需要上传、存储、解析、过期清理、配额口径，成本远高于当前需求；
- 不选“把附件所在 KB 全部加入检索”：范围太大，会召回无关文档；
- 复用已有文档入库/RAG 链路，不新建文件生命周期。

**状态/边界**：✅ 已完成（文档 ID 附件）；不支持 PDF/图片二进制直传；gRPC proto 未加字段，`AI_GRPC_ENABLED=true` 时附件会被忽略。

### B-10 · 会话内容检索

**前端遇到的问题**：侧栏只能按标题 `title LIKE` 搜索；用户记得“上次聊过 Milvus 分片”，标题没有这个词就找不到。

**后端解决方案（已实施）**：

- 新增 `GET /search/messages?q=&limit=`；
- join message + conversation，按用户隔离，LIKE 转义 `%`/`_`；
- 返回 `conversation_id/title/message_id/role/snippet/created_at`；
- 侧栏标题命中之外展示“消息命中”，点击打开会话。

**为什么选这个**：

- 先不选 FULLTEXT/embedding/ES：需要索引/迁移/调参，当前数据量与使用频率下 LIKE 足够验证需求；
- 不选“前端拉全量消息自己搜”：权限、分页、性能都不可控；
- 接口形状不绑定实现，后续换 FULLTEXT/embedding 不动前端。

**状态/边界**：✅ 已完成（LIKE）；无中文分词/排序质量优化，搜索量大时再升级。

## 5. 工程效率

### B-12 · 网关 OpenAPI

**前端遇到的问题**：网关路由没有 OpenAPI，认证/会话/消息/配额只能手写 Zod/TS 类型；字段改名只能靠契约测试兜底。

**后端解决方案（已实施）**：

- `docs/openapi.yaml` 覆盖全部 `/api/v1` 路由（42 path）；
- 新增 `openapi_parity_test.go`：构造真实 Gin 引擎，用 `engine.Routes()` 与 YAML 做 **path + method 双向 diff**；
- 新增/删除路由未同步即测试失败。

**为什么选这个**：

- 不选“只写核心 path 的 YAML”：核心 path 守卫不能防新增/删除路由漂移；
- 不选“立刻上注解生成 + codegen”：工具链改造成本高；先把路由级契约锁住；
- 不做全字段 schema 自动生成：当前核心实体已手写，字段级后续再补。

**状态/边界**：✅ 已完成（42 path、method 双向 diff）；请求/响应字段级 schema 只覆盖核心实体，不是全量生成。

## 6. 全部完成了吗？

**是，但要说清“完成”的范围：**

- B-01–B-15 都已有代码、验收或单测，没有“待触发/未做”的 B 项；
- 其中五项是 MVP 范围：
  - B-03 非流式重新生成；
  - B-04 只清短期上下文/摘要，长期记忆不自动清；
  - B-09 只支持文档 ID 附件，不做二进制直传；
  - B-10 是 LIKE 检索，不是 FULLTEXT/embedding；
  - B-12 是路由级 42 path 契约，不是全字段生成。

> 对外建议表述：**B-01–B-15 已完成可运行闭环；B-03/B-04/B-09/B-10/B-12 为明确范围的 MVP。**

## 7. 明确不做

| 不做 | 理由 |
| --- | --- |
| WebSocket / 服务端主动推送 | 当前一轮一个 SSE，没有主动事件通道 |
| 服务端“停止生成”接口 | 断开连接即取消，已有 partial 落库 |
| `Last-Event-ID` 断线续传 | 台账是唯一真源，重放会拼两遍正文 |
| 聚合 bootstrap | 并行请求 + Query 缓存已够，过早聚合会让失效矩阵复杂 |
| 消息编辑历史/对话分支 | 先做重新生成，验证需求 |
| 未读数/已读回执 | 没有多端消息场景 |
| 50MB 以上分片直传 | B-09 当前只做文档 ID 附件 |
| 全文检索直接上 ES | 先用 LIKE 验证需求 |
