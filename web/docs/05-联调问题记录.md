### 3.1 前端问题

#### F2 · 会话与历史

##### I-01 · 认证完成前挂会话查询

**现象**：F2 首次 E2E 在 `/chat` 等待会话列表超时；网关日志先出现无 user 的
`GET /conversations 401 UNAUTHENTICATED`，随后 refresh 成功，又出现一次
`INVALID_REFRESH_TOKEN`。

**根因**：`AppLayout` 在 `status === "booting"` 时就执行了 `useConversationList()` 等 hooks，
查询在 access token 就绪前发出；401 又触发刷新，与启动恢复竞争。

**处理**：把 `AppLayout` 拆成两层：

- `AppLayout` 只做认证门（booting 骨架 / anonymous 跳登录 / authed 渲染壳）；
- `AppShell` 才挂载会话查询、创建、登出等需要 token 的逻辑。

**验证**：`pnpm e2e:f2` 通过；登录后列表正常，无未认证请求。

---

##### I-05 · 助手 Markdown 原样显示

**现象**：F2 会话历史里模型输出的 `**粗体**`、`- 列表`、代码块按纯文本显示。

**处理**：新增 `shared/ui/Markdown.tsx`，使用
`react-markdown + remark-gfm + rehype-sanitize`；模型输出一律过 sanitize。

**代价**：主包 gzip 从 117.2 KB 增至 166.6 KB，仍低于 F6 的 180 KB；
F6 会把会话页/Markdown 做路由级拆包。

**状态**：✅ 已修复。

---

##### I-06 · 侧栏分页口径

**现象**：侧栏原为 30/页，55 条会话只有 2 页，与计划的“55 条 3 页”不一致。

**处理**：改为 20/页；55 条为 20 / 20 / 15 三页。

**状态**：✅ 已修复。

---

##### I-09 · 注册响应形状假设错误

**现象**：F2 E2E 首次失败：`注册响应缺少 access/refresh token`。

**根因**：`POST /auth/register` 只返回用户对象，token 需要再调 `/auth/login`；
F1 的 store 已有 fallback，E2E 直接假设了 token。

**处理**：E2E 注册后显式登录，不依赖注册响应是否带 token。

**状态**：✅ 已修复（测试代码）。

#### F3 · 流式对话

##### I-10 · 停止测试落在模型完成之后

**现象**：F3 第一次 E2E 点击停止后，刷新看到的助手消息是 `completed`，没有 `partial`；
E2E 报“停止后历史里没有 partial 消息”。

**排查**：直接查 MySQL，助手消息 `status=completed`、`finish_reason=stop`，
说明停止请求到达时模型已经生成完，不是“abort 没生效”。

**处理**：把提示词改成约一千字的长文，并在首个 token 出现 350ms 后立即停止；
之后 E2E 稳定看到 `partial`，刷新后仍是 `partial`。

**结论**：产品代码不需要改；这是验收脚本的时序问题。F3 的 abort 链路本身正常。

**状态**：✅ 已修复（测试代码）。

##### I-11 · F3 文案与流式计数

- 顶栏阶段文案改为 F3；

**验证**：`f3-streaming.png` / `f3-partial.png`。

**状态**：✅ 已修复。

##### I-12 · 历史工具轨迹与引用角标

##### I-22 · F3 停止后 live 不收起

**现象**：B-08/B-15 后 F3 回归，停止后 live turn 一直显示“已停止 partial”，历史里只有 user
消息；服务端其实已经落了 partial。

**根因**：`stop` 后 `onSettled` 立即 refetch，但服务端 partial 落库晚于这次 GET；第一次 refetch
200 但只拿到 user 消息。live turn 等 `assistantPersisted`，于是永远不收起。

**处理**：`ConversationPage` 在 `phase=aborted/done` 且 `assistantId` 尚未出现在台账时，
每 250ms refetch 一次，最多 12 次（约 3s）；assistant 出现后 `assistantPersisted` 变 true，
live 收起。不是无限轮询，也不会重复消息。

**验证**：F3 `pnpm e2e:f3` 通过；停止后出现一次额外 `/messages` GET，随后 live 收起、
partial chip 出现在历史；刷新后仍是 partial。

**状态**：✅ 已修复。

#### F4 · 知识库与任务

##### I-13 · 知识库页入库任务为空

**现象**：文档已入库，但知识库页右侧“入库任务”一直显示“还没有任务”。

**根因**：任务查询按 `resource_id = 当前 KB ID` 过滤；但 `document_ingest` 任务的
`resource_id` 是 **文档 ID**，不是 KB ID。后端行为正确，是前端过滤维度错了。

**处理**：知识库页拉最近任务，再按当前 KB 的文档 ID 集合过滤；
`kb_reindex` 这类 `resource_type=knowledge_base` 的任务仍按 KB ID 匹配。

**验证**：`f4-knowledge.png` 中“文档入库 / 已完成 / INDEXED / 2/2”可见。

**状态**：✅ 已修复（前端）。

---

##### I-14 · 上传横幅状态滞后

**现象**：文档已 `INDEXED`，上传横幅仍显示“上传完成，等待入库”。

**处理**：用当前文档集合匹配上传文件名，按文档终态显示：

- `INDEXED` → “已入库”；
- `FAILED` → “入库失败，去任务中心查看原因”；
- 其它 → “上传完成，等待入库”；
- 增加关闭按钮，保留上传百分比。

**状态**：✅ 已修复。

---

##### I-15 · “最近刷新”不是数据时间

**现象**：任务页“最近刷新”每次 render 都取 `new Date()`，看起来一直在刷新，实际不代表
最后一次请求成功。

**处理**：改用 `useTasks` 的 `dataUpdatedAt`，没有数据时显示 “—”。

**状态**：✅ 已修复。

---

#### F5 · 记忆/配额/设置

##### I-16 · 记忆设置“关 → 开”被 refetch 覆盖

**现象**：F5 E2E 把记忆开关从开切到关、保存，再切回开、保存；页面仍显示“记忆已关闭”。

**根因**：保存设置后 React Query 失效并 refetch；`useEffect` 无条件用旧响应覆盖本地
`enabled`，第二次保存实际发出的是旧值 `false`。

**处理**：增加 `settingsDirty`：用户一改开关/召回数就置 dirty，refetch 不覆盖；
保存成功后清 dirty，再让新响应同步。

**状态**：✅ 已修复。

---

##### I-17 · switch 的视觉层挡住 checkbox

**现象**：Playwright `uncheck` 超时，日志显示 `<span>` intercepts pointer events。

**根因**：透明 `input` 绝对定位铺满，但后面的视觉 `span` 接收了点击；用户点开关也可能
只点到装饰层。

**处理**：`.switch span { pointer-events: none; }`，让点击落到 input。

**状态**：✅ 已修复。

---

##### I-20 · 429 错误态残留与侧栏计数过期

**现象**：用 `MSG_RATE_PER_MINUTE=1` 定向测试 429 时，错误卡上方仍出现一个空的
“生成失败”助手占位；侧栏该会话仍显示“0 条消息”，而头部已经 2 条。

**根因**：

- `liveVisible` 在 `error` 阶段只要 refetch 完成就隐藏，但空内容占位在 refetch 前仍然渲染；
- 流结束后只 refetch 了 detail + messages，没有失效会话列表缓存。

**处理**：

- `error` 且 `content.length===0` 时不再渲染 live turn，只留错误卡；
- `handleSettled` 额外失效 `['conversations','list']`，侧栏 `message_count` 立即更新。

**验证**：429 截图无 live 占位；侧栏显示“2 条消息 · 刚刚”。

**状态**：✅ 已修复。

**证据**：F2 E2E 第一次失败；数据库无重复行（插入被拒），说明冲突发生在主键 `id`。

**根因**：`ai-platform-go/pkg/ids/ids.go` 里全局共享：

```go
var entropy = ulid.Monotonic(rand.Reader, 0)
```

`ulid.Monotonic` 返回的 `MonotonicEntropy` **没有并发保护**；同一毫秒内的并发调用
会读到同一个 entropy 快照，生成相同 ULID。网关的 `cv_` / `msg_` / `u_` / `rt_`
都走同一个生成器，所以不只影响会话列表。

**影响**：

- 正常 UI 单次点“新建对话”不受影响；
- 并发创建、批量导入、脚本压测会出现 503；
- 错误码是 `DEPENDENCY_UNAVAILABLE`，会误导为 MySQL 故障。

**处理（已实施）**：

- 在 `defaultNewID` 外包一层 `sync.Mutex`，只串行化 `ulid.MustNew` 这一小段；
- 保留 Monotonic 的时间有序性（不改成纯随机）；
- 新增 `pkg/ids/ids_test.go::TestNewConcurrentUnique`，2000 个 goroutine 断言唯一。

```go
var entropyMu sync.Mutex

func defaultNewID(prefix string) string {
    entropyMu.Lock()
    defer entropyMu.Unlock()
    return prefix + "_" + ulid.MustNew(ulid.Timestamp(time.Now().UTC()), entropy).String()
}
```

**验证**：

```text
go test ./pkg/ids -count=1          ok
go test ./pkg/ids -race -count=1    ok
```

真实网关：注册/登录后 **20 路并发** 建会话 → `{201: 20}`，20 个 ID 全唯一。

**回归位置**：`ai-platform-go/pkg/ids/ids_test.go`。F6 压测时再跑一次 100 并发。

**状态**：✅ 已修复（ROADMAP B-14）。

##### I-19 · 关闭记忆后上下文为空

**现象**：发送消息时带 `use_memory=false`，随后 `/conversations/{id}/context` 返回
`message_count=0`，摘要也无法生成。

**根因**：Python `ChatService.prepare` 里把 `persist` 设为 `request.use_memory`，
即“不召回长期记忆”同时关闭了 **上下文落库**。记忆与上下文本是两个能力，不应共用一个开关。

**处理（已实施 B-15）**：

- `PreparedChat` 增加 `use_memory`，只表示长期记忆；
- `persist = conversation_id is not None`；有会话 ID 时先 `ensure` 再读写短期上下文；
- `_load_memory(..., include_memories=request.use_memory)`：历史/摘要始终读，长期记忆按开关；
- `_after_turn(..., use_memory=...)`：关闭记忆时跳过 `memory_extract`，摘要仍按阈值生成。

**验证**：Python 契约测试 `test_context_persists_when_memory_disabled` 通过；
真实网关两轮（`use_memory=true` 后 `false`）`/context` 返回 4 条、预算 203 tokens；
旧 AC-CHAT-12 语义已更新为“短期上下文仍读写，长期记忆不注入”。

**状态**：✅ 已修复（B-15）。

##### I-21 · refresh 令牌放 localStorage（B-08）

**现象**：`ai.refresh.v1` 在 `localStorage`，任何 XSS 都能读取并长期换新。

- 登录/刷新通过 `Set-Cookie: ai_refresh=...; HttpOnly; SameSite=Lax; Path=/api/v1/auth` 下发；

**验证**：
